# Kill Switch 검증 루프 (Generator-Evaluator)

Kill Switch를 "통과/미통과" 선언만으로 처리하면 검증이 무력화된다. 이 문서는 모든 Phase의 Kill Switch 판정에 적용되는 검증 루프 표준을 정의한다. 산출물을 생성한 흐름이 스스로 통과를 선언하는 것을 차단하고, 체크리스트와 산출물의 1:1 대조 결과를 텍스트로 먼저 출력한 뒤에만 판정을 허용한다.

> 근거 패턴: Reflexion(Actor/Evaluator 분리), prd-flow Evaluator 검증 루프 표준. bizplan-builder는 대화형 단일 흐름이므로 독립 서브에이전트 대신 **"판정 전 대조 목록 강제 출력"**으로 생성-평가 분리를 구현한 경량판이다.

---

## 1. 핵심 원칙

1. **선언적 통과 금지**: "Kill Switch 전 항목 통과" 요약만 쓰고 넘어가지 않는다. 항목별 대조 결과를 개별 출력해야만 통과를 선언할 수 있다.
2. **결정론 검증 우선**: 수치 재계산(정량 가드레일 공식), 필수 항목 존재 여부, 산정 방식 위반(예: LTV 매출 기준) 등 기계적으로 판별 가능한 항목을 먼저 확인한다. 서술 품질·논리 정합 같은 주관 판단은 그다음이다.
3. **불확실하면 갭**: 충족 여부가 애매하면 ✅가 아니라 🟡로 분류한다.
4. **보상 해킹 금지**: 통과를 위해 체크리스트 항목 자체를 느슨하게 재해석하거나 항목을 삭제하지 않는다. 기준 변경이 필요하면 사용자에게 명시적으로 제안하고 승인받는다.
5. **선행 조건 — 미확인 SD 0개**: 미확인 Silent Default(`references/silent-defaults.md`)가 남아 있으면 Kill Switch 판정에 진입하지 않는다. SD 일괄 확인을 먼저 완료한다.

---

## 2. 검증 루프 절차

### Step 1 — 대조 목록 출력 (필수)

해당 Phase의 Kill Switch 체크리스트 **전 항목**을 산출물과 1:1 대조하고, 결과를 아래 형식으로 출력한다. 이 출력 없이 통과를 선언하지 않는다.

```
[항목] {Kill Switch 체크 항목명}
[판정] ✅ 충족 / 🟡 부분 충족 / 🔴 미충족
[근거] 산출물의 해당 부분 인용 또는 수치 + 판정 이유 1줄
```

- 전 항목이 ✅라도 항목별 근거를 생략하지 않는다. "전 항목 충족"으로 뭉뚱그리는 것이 이 루프가 차단하려는 실패 모드다.
- 정량 항목(LTV:CAC, Payback, Gross Margin 등)은 근거에 **재계산 값**을 기입한다. 산출물의 수치를 그대로 옮겨 적지 않고 공식으로 재계산해 대조한다.

### Step 2 — 🔴 처리 (Kill Switch 발동)

- 어느 항목이 어떤 수치·근거로 미달인지 명시한다.
- 재기획 가이드(보강 대상 산출물, 개선 방향)를 제시한다.
- 사용자가 산출물을 수정하면 Step 1을 처음부터 재실행한다. 수정 항목만 대조하지 않는다 — 수정이 다른 항목을 깨뜨릴 수 있다.
- Notion 업로드를 사용 중이면 Phase 상태를 "Kill Switch 발동"으로 변경한다.

### Step 3 — 🟡 처리 (보완)

- 보완 방향을 제시하고 산출물에 반영한다.
- 반영 후 **수정 구간만** 재대조한다(🔴와 달리 국소 재검증 허용).
- 🟡을 해소하지 않고 통과하려면 사용자의 명시적 승인이 필요하며, 잔여 🟡 목록을 decision-log에 기록한다.

### Step 4 — 종료 판정 (4출구)

| 출구 | 조건 | 처리 |
|---|---|---|
| **통과** | 전 항목 ✅ (또는 잔여 🟡 사용자 승인) | Phase 통과 선언, 다음 Phase 진입 |
| **재기획** | 🔴 존재 | Step 2 수행, 수정 후 재루프 |
| **상한 중단** | 동일 항목이 3회 연속 🔴 | 아래 "상한 중단 처리" 수행 |
| **진전 없음** | 라운드 간 갭 수·내용이 실질 동일 | 상한 중단과 동일 처리 |

### 상한 중단 처리

동일 항목 3회 연속 미충족은 산출물 표현의 문제가 아니라 **사업 가설의 구조적 결함** 신호다. 수정 루프를 반복하지 않고:

1. 현 상태 + 잔여 갭 목록을 사용자에게 보고
2. 세 갈래 선택지 제시: **피벗**(가설 자체 변경, 해당 Phase 또는 이전 Phase 재진입) / **범위 축소**(사업 단계·목적을 낮춰 기준 재설정, 예: IR용 → 내부 검토용) / **보류**(현 상태로 중단, 미통과 상태 기록)
3. 선택 결과와 사유를 decision-log에 기록

---

## 3. 페르소나 리뷰 연계 (🔴 승격)

페르소나 리뷰에서 나온 **🔴 차단 이슈**는 해당 Phase Kill Switch의 임시 항목으로 승격해 Step 1 대조 목록에 포함한다.

- 승격된 항목은 `[항목] (페르소나 승격) {이슈 요약}` 형식으로 표기
- 사용자가 해당 피드백을 명시적으로 기각한 경우에만 대조 목록에서 제외하고, 기각 사유를 decision-log에 기록
- 🟡 보완 제안은 승격하지 않는다 — 채택 여부를 사용자가 선택하는 기존 흐름 유지

---

## 4. Phase별 적용 지점

| Phase | 대조 대상 체크리스트 | 결정론 검증 항목 예시 |
|---|---|---|
| 1 | phase1 Kill Switch 6항목 | 상향식 TAM 산정 공식 존재, MECE 교차 검사 |
| 2 | phase2 Kill Switch 7항목 | 사업 유형별 필수 항목(BOM·환각 통제 등) 존재 여부 |
| 3 | phase3 Kill Switch 8항목 | LTV:CAC·Payback·Gross Margin·런웨이 재계산 |
| 4 | phase4 통과 조건 (최종) | 5기둥 전 항목 작성 여부, 레드팀 시나리오 수행 여부 |

Phase 3는 `references/unit-economics-benchmarks.md`의 자동 계산 출력이 Step 1의 결정론 검증 입력이 된다. 가드레일 계산 → 대조 목록 → 판정 순서를 지킨다.
