# 작성 가드레일 (Writing Guardrails)

모든 Phase 의 산출물에 적용되는 문체·서술 규칙. C-level 임원·VC 심사역 검토용 문서 표준을 따른다.

## 1. Answer First (Minto Pyramid 원칙)

### 원칙

핵심 결론을 가장 먼저 배치하고, 그 아래 근거·데이터로 뒷받침한다. 장황한 배경 설명을 앞세우지 않는다.

### 적용 예시

❌ **나쁜 예시**:
```
최근 산업 안전에 대한 사회적 관심이 증가하고 있고, AI 기술도 발달하면서
정부 규제도 강화되고 있습니다. 이러한 환경 변화 속에서 우리는 새로운 기회를
모색하게 되었고, 화학 산업의 안전 관리 시장이 유망하다고 판단했습니다.
따라서 우리는 Protect GO AI 라는 솔루션을 개발했습니다.
```

✅ **좋은 예시**:
```
Protect GO AI 는 한국 화학·정유 50개 사업장의 안전 사고 보고서 작성을
2시간 → 10분으로 단축하여 사업장당 연 5,000만원 인건비를 절감하는
AI 기반 산업 안전 솔루션이다.

근거 1: PoC (한화솔루션) 에서 보고서 작성 시간 평균 89% 단축 검증
근거 2: TAM 720억원, 5년 SOM 36억원 (5% 점유 시)
근거 3: 한화솔루션 5년치 데이터 독점 라이선싱으로 진입 장벽 확보
```

## 2. 화살표(→) 금지

### 원칙

화살표는 의미 전달을 모호하게 만들며, 읽는 사람마다 해석이 달라질 수 있다. 명확한 인과관계 또는 변환 관계를 한국어로 풀어 쓴다.

### 예외

다음의 경우에만 화살표 허용:
- 시각적 조건 표현 (조건문)
- 상태 전이 다이어그램 (Mermaid)
- 프로세스 흐름의 단계 표시

### 적용 예시

❌ **나쁜 예시**:
```
게이트웨이 다운 → 센서 중단 → 데이터 손실 → 알람 누락 → 사고
```

✅ **좋은 예시**:
```
게이트웨이가 다운되면 하위 센서 다수가 중단되어 실시간 데이터가 손실되고,
이로 인해 사고 직전 알람이 누락될 수 있다.
```

✅ **허용되는 화살표 사용**:
```
조건: 장소 동일 + 탐지 유형 동일 + 60초 내 3개 이상 발생 → 통합 알람 생성
```

## 3. 변수명·코드 표기 금지

### 원칙

사업계획서는 비즈니스 문서이지 기술 문서가 아니다. 변수명·DB 컬럼명·API 경로 등 코드 표기는 금지.

### 적용 예시

❌ **나쁜 예시**:
```
사용자 식별을 위해 user_id 와 tenant_id 를 사용하며, JWT 토큰의 sub claim 으로
인증한다. POST /api/v1/incidents 엔드포인트로 이상 감지 이벤트를 전송한다.
```

✅ **좋은 예시**:
```
사용자 식별 정보와 테넌트 식별 정보를 기반으로 인증하며, 이상 감지 이벤트는
실시간으로 중앙 대시보드로 전송된다.
```

기술 상세는 별도 기술 명세서 (PRD, API 문서) 로 분리한다.

## 4. 디자인 심미성 배제

### 원칙

색상·폰트·여백·아이콘 등 디자이너 영역의 세부 사항은 사업계획서에 작성하지 않는다. UX 흐름·정보 우선순위·사용자 여정은 작성 가능.

### 적용 예시

❌ **나쁜 예시**:
```
대시보드 상단에 #1E40AF (브랜드 블루) 색상의 헤더를 두고, 16px 폰트로
"안전 현황" 을 표시. 좌측에 사이드바 240px 폭으로 배치.
```

✅ **좋은 예시**:
```
대시보드 진입 시 사용자가 가장 먼저 인지해야 할 정보는 현재 진행 중인
이상 알람 건수이며, 이를 화면 최상단 좌측에 배치한다. 알람을 클릭하면
해당 현장의 실시간 영상으로 이동한다.
```

## 5. 개발 구현 디테일 배제

### 원칙

라이브러리·DB 스키마·서버 아키텍처 등 개발자 영역의 세부 사항은 사업계획서에 작성하지 않는다. 비즈니스 로직·시스템 기능·데이터 흐름 (높은 수준) 은 작성 가능.

### 적용 예시

❌ **나쁜 예시**:
```
React 18 + TypeScript 로 프론트엔드를 구현하고, 백엔드는 NestJS + PostgreSQL 14
로 구성. Redis 캐시와 RabbitMQ 메시지 큐를 사용하여 이벤트 처리.
```

✅ **좋은 예시**:
```
실시간 영상 분석은 엣지에서 처리하여 지연시간을 최소화하고, 장기 통계·리포트
생성은 클라우드에서 처리한다. 이상 감지 시 1초 이내 관리자 알람이 전송된다.
```

기술 스택 상세는 Phase 2 의 시스템 아키텍처 다이어그램에 시각화로 표현하되, 본문은 비즈니스 영향 중심으로 서술.

## 6. 개조식 우선

### 원칙

C-level 임원·VC 심사역은 줄글을 끝까지 읽지 않는다. 번호 계층 + 짧은 서술형으로 작성하여 핵심을 빠르게 전달.

### 적용 예시

❌ **나쁜 예시 (줄글)**:
```
우리의 타겟 고객은 한국 화학 산업의 대기업이며, 특히 매출 1,000억원 이상의
회사를 대상으로 합니다. 이들은 안전 관리에 대한 규제 압력이 크고, ISO 45001
인증을 보유하고 있으며, OT 시스템을 이미 운영하고 있습니다. 우리는 이들에게
연 6,000만원 수준의 라이선스를 판매할 계획입니다.
```

✅ **좋은 예시 (개조식)**:
```
타겟 고객 (ICP):
- 산업: 한국 화학·정유·조선
- 규모: 매출 1,000억~1조원, 직원 200~2,000명
- 인증: ISO 45001 보유
- 인프라: OT 시스템 (SCADA/DCS) 운용 중
- 예상 ARR: 6,000만원/년
```

## 7. 수치 기반 서술 (정성적 수사 금지)

### 원칙

"빠른", "혁신적인", "효율적인", "최고의" 같은 정성적 수사는 금지. 모든 주장은 수치·기간·대상으로 치환.

### 금지 표현 예시

- "빠른 도입": ❌ → "PoC 4주, 정식 도입 12주" ✅
- "혁신적인 솔루션": ❌ → "기존 수기 보고 대비 80% 시간 단축" ✅
- "고성능 AI": ❌ → "이상 감지 정확도 94.3%, F1-Score 0.91" ✅
- "최고의 보안": ❌ → "ISO 27001 인증 보유, 침해 사고 0건 (2년)" ✅

## 8. 반증 가능성 (Falsifiability)

### 원칙

모든 가설·주장은 측정 가능한 형태로 작성한다. 어떤 데이터를 보면 그 가설이 틀렸다고 판단할지 명시.

### 적용 예시

❌ **나쁜 예시**:
```
우리의 솔루션은 시장에서 큰 성공을 거둘 것이다.
```

✅ **좋은 예시**:
```
가설: 출시 후 12개월 내 한국 화학·정유 사업장 50개 중 5개 이상 (10%)
       유료 계약 체결.
반증 조건: 12개월 시점에 유료 계약이 3개 미만이면 ICP 가설 또는
           가격 정책 재검토 필요.
```

## 9. 한국어 우선, 고유명사 보존

### 원칙

본문은 한국어로 작성하되, 다음은 원문 보존:
- 모델명: YOLO, ByteTrack, GPT-4o
- 프레임워크명: LTV, CAC, MECE, Minto Pyramid, Rule of 40
- 기술 표준: ISO 27001, GDPR, EU AI Act, K-ISMS
- 회사명·제품명: AWS, Anthropic, Snowflake, Palantir

### 적용 예시

✅ **좋은 예시**:
```
LTV:CAC 비율은 5.4 로, 최소 통과 기준 (3.0) 을 충족한다. CAC Payback Period 는
14개월로 Enterprise 세그먼트의 통과 기준 (18개월) 이내. EU AI Act 의 '고위험 AI'
분류 가능성에 대비하여 FRIA 수행 계획.
```

## 10. C-Level 임원 문서 스타일

### 원칙

다음 4가지를 동시에 충족하는 문서:
1. **객관적**: 자랑이나 추측이 아닌 사실과 수치
2. **구조적**: 헤딩 + 번호 + 표 + 시각화의 균형
3. **간결**: 한 문단 5줄 이내, 한 항목 2줄 이내
4. **설득력**: 반박 가능한 약점도 정직하게 명시 (신뢰도 확보)

### 약점 명시 패턴 (신뢰도 확보용)

```
강점:
- ...

약점 (인지하고 있는 한계):
- 한국 시장에 한정된 데이터 해자 → 글로벌 확장 시 재구축 필요
- AI 추론 비용이 ARPA 대비 18% → Foundation Model 가격 인상 시 압박

대응 계획:
- 18개월 내 자체 경량 모델 마이그레이션
- 동남아 진출 시 현지 데이터 파트너십 우선 확보
```

## 11. 문서 길이 가이드

| 산출물 | 권장 길이 |
|---|---|
| One-Page Summary | A4 1페이지 (Notion 기준 토글 1개) |
| Phase 별 산출물 | A4 3-5페이지 |
| 전체 사업계획서 | A4 15-25페이지 |
| 투자자용 Pitch Deck | 슬라이드 12-15장 (Sequoia 표준) |

길이 초과 시 정보가 충분히 압축되지 않은 신호. 재작성 권장.

## 12. 자가 점검 체크리스트

산출물 작성 후 사용자에게 제출하기 전, 다음을 자동 점검:

- [ ] Answer First 적용 (결론이 첫 문단에 있는가?)
- [ ] 화살표 사용 시 예외 조건 부합하는가?
- [ ] 변수명·코드 표기 없는가?
- [ ] 디자인 세부사항 (색상·폰트) 없는가?
- [ ] 개발 구현 디테일 (라이브러리·스키마) 없는가?
- [ ] 개조식 + 짧은 서술형으로 작성되었는가?
- [ ] 정성적 수사 ("빠른", "혁신적인") 없는가?
- [ ] 모든 주장이 수치·기간·대상으로 표현되었는가?
- [ ] 반증 조건이 명시되었는가?
- [ ] 약점·한계도 정직하게 명시되었는가?
- [ ] 권장 길이 범위 내인가?

위반 항목 발견 시 자동 수정 후 사용자에게 변경 사항 보고.
