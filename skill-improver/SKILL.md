# Skill Improver

현재 세션의 대화를 소급 분석하여 사용된 스킬의 실제 작동을 평가하고, SKILL.md에 직접 반영 가능한 개선안을 생성한다.

## 핵심 원칙

1. **증거 기반 평가**: 대화에서 실제로 일어난 일만 근거로 삼는다. 추측으로 평가하지 않는다.
2. **구체적 수정안**: "개선 필요"로 끝내지 않는다. SKILL.md에 바로 적용할 수 있는 텍스트 diff 수준의 제안을 낸다.
3. **긍정·부정 균형**: 잘 작동한 부분도 명시한다. 성공 패턴이 사라지면 안 된다.
4. **적용 전 컨펌**: SKILL.md 파일을 직접 수정할 때는 반드시 사용자에게 보여주고 승인받은 뒤 진행한다.

## 평가 차원 (모든 스킬 공통)

| 차원 | 확인 항목 |
|---|---|
| **트리거 정확도** | 맞게 발동했나? 놓친 발동은? 불필요한 발동은? |
| **출력 품질** | 사용자 의도에 맞는 결과를 냈나? 할루시네이션은? |
| **페이즈 흐름** | Phase 순서를 지켰나? 컨펌 없이 건너뛴 Phase는? |
| **레퍼런스 적재** | 필요한 references 파일을 빠짐없이 읽었나? 불필요하게 읽은 건 없나? |
| **페르소나 정확도** | 각 페르소나가 자기 영역에서만 발언했나? 톤은 일관했나? |
| **스킬 간 연계** | 다른 스킬로 넘겨야 할 타이밍을 지켰나? 중복 작업은? |
| **가드레일 준수** | 금지 패턴(화살표 금지, 개발 디테일 배제 등) 위반은? |

## 워크플로우

### Phase 0 — 분석 대상 확인

스킬 실행 직후 먼저 다음을 사용자에게 확인한다.

1. **분석 범위**: 전체 세션 / 특정 구간 (예: "방금 PRD 작성 부분만")
2. **관심 스킬**: 특정 스킬만 집중 분석 vs 전체 스캔
3. **원하는 산출물**: 평가 보고서만 / 개선안 + 파일 직접 수정
4. **심층 분석 여부**: 트리거 패턴 분석 포함 여부

확인이 끝나면 `references/eval-dimensions.md`를 읽는다.

---

### Phase 1 — 스킬 사용 인벤토리

대화 전체를 스캔하여 사용된 스킬 목록을 추출한다.

**출력 형식**:

```
## 이번 세션 스킬 사용 인벤토리

| 스킬 | 발동 횟수 | 발동 지점 요약 | 비고 |
|---|---|---|---|
| prd-builder | 2회 | 회의록 PRD 작성, Phase 3 재진입 | Phase 5 건너뜀 |
| inventory-sync | 1회 | 재고 동기화 정책 질의 | — |
| (미발동) domain-review-persona | — | — | 트리거 후보 대화 있었으나 미발동 |
```

**미발동 감지 규칙**: 다음 패턴이 있었는데 스킬이 발동하지 않은 경우 기록한다.
- 스킬 description의 트리거 키워드가 사용자 메시지에 포함된 경우
- 해당 스킬이 담당하는 작업이 스킬 없이 일반 대화로 처리된 경우

---

### Phase 2 — 스킬별 심층 평가

각 사용 스킬마다 아래 평가 카드를 작성한다.

**평가 카드 형식**:

```
## [스킬명] 평가

### 잘 작동한 부분 (계속 유지)
- ...

### 개선 필요 사항
| 차원 | 문제 | 근거 (대화 인용) | 심각도 |
|---|---|---|---|
| 트리거 | ... | "사용자: ..." | 🔴 높음 / 🟡 중간 / 🟢 낮음 |

### 트리거 키워드 갭 분석
- 현재 SKILL.md description에 있는 키워드: ...
- 이번 대화에서 실제로 쓰였으나 목록에 없는 표현: ...
- 등록됐지만 이번 대화에서 오발동 유발한 표현: ...
```

---

### Phase 3 — 개선안 작성

각 문제에 대해 SKILL.md 수정 제안을 작성한다.

**개선안 형식**:

```
## [스킬명] 개선안

### 수정 1: 트리거 키워드 보강
위치: SKILL.md description 및 ## 트리거 키워드 섹션

현재:
"PRD 작성", "PRD 만들어"

제안:
"PRD 작성", "PRD 만들어", "요구사항 정리해줘", "기능 명세 만들어"

이유: 이번 세션에서 "기능 명세 만들어"라는 표현이 2회 사용됐으나
      prd-builder가 발동하지 않고 일반 대화로 처리됨.

---

### 수정 2: 페이즈 가드레일 강화
위치: SKILL.md ## 워크플로우 > Phase 진행

현재:
"각 Phase 완료 시 사용자 컨펌 대기"

제안:
"각 Phase 완료 시 반드시 사용자 컨펌 대기. 사용자가 명시적 승인 없이
다음 Phase를 언급해도 현재 Phase 결과물을 먼저 제시하고 컨펌을 받는다."

이유: Phase 2 완료 후 사용자 응답 없이 Phase 3를 바로 진행하는
      패턴이 이번 세션에서 1회 발생.
```

---

### Phase 4 — 파일 직접 수정 (옵션, 사용자 컨펌 필수)

Phase 3 개선안을 사용자에게 보여준 뒤 수정할 항목을 선택받는다.

```
[적용 전 확인]
다음 수정사항을 SKILL.md에 반영할까요?

✅ 수정 1: prd-builder 트리거 키워드 보강 — 3개 추가
✅ 수정 2: prd-builder Phase 가드레일 문구 강화
⬜ 수정 3: inventory-sync references 적재 기준 완화

적용할 항목을 알려주세요.
```

승인된 항목만 `Edit` 도구로 실제 파일에 반영한다.

---

### Phase 5 — 시스템 전체 일관성 검토 (심층 모드)

개별 스킬 분석 외에 스킬 시스템 전체를 조망한다.

**검토 항목**:

```
## 스킬 시스템 전체 검토

### 트리거 중복·충돌
- [스킬 A]와 [스킬 B]가 동일 키워드를 커버하는 경우
- 해소 제안: 어느 스킬이 우선권을 갖는지 description에 명시

### 미커버 영역
- 이번 세션에서 스킬 없이 처리된 반복 작업 패턴
- 신규 스킬 필요 여부 판단 기준: 3회 이상 반복이면 스킬화 검토

### 스킬 간 연계 누락
- A → B 체인이 정의됐는데 실제로 B로 넘기지 않은 경우
```

## 스킬 목록 (분석 대상)

Phase 1에서 대화를 스캔해 실제 사용된 스킬을 동적으로 추출한다(고정 목록을 유지하지 않는다). 프로젝트의 스킬 디렉토리(`.claude/skills/`, `.agents/skills/` 등)를 참고해 등록된 스킬 전체 목록과 대조할 수 있다. 아래는 인벤토리 표·평가 카드 예시에서 쓰는 형식 참고용 예시일 뿐, 실제 목록이 아니다:

```
prd-builder        — PRD 단계별 작성
prd-to-tickets     — PRD → Epic/Story/Task 분해
inventory-sync     — 재고 관리 시스템 QA
design-token-sync  — 디자인 토큰 동기화 프로토타입 생성
domain-review-persona — 도메인 특화 멀티 페르소나 리뷰
bizplan-builder    — 사업계획서 단계별 작성
editorial-reviewer — 문서 가독성·논리 구조 검토
wireframe-description — 와이어프레임 개발 명세 작성
rnd-proposal-reviewer — R&D 제안서 평가
notion-organizer   — Notion 구조화·정리
```

## 다른 스킬과의 관계

- 이 스킬은 다른 스킬을 **분석 대상**으로 다루며, 다른 스킬을 직접 실행하지 않는다.
- `editorial-reviewer` 스킬과 역할 구분: editorial-reviewer는 문서 내용, skill-improver는 스킬 동작을 본다.
- 분석 과정에서 SKILL.md 파일을 `Read` 도구로 직접 읽는다.
