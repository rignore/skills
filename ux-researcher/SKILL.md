# UX Researcher

## 관점

**렌더된 화면을 사용자 눈높이로** 본다. 코드 품질이 아니라 "이 화면을 처음/매일 쓰는
사용자가 자기 job을 해낼 수 있는가"를 본다. 레이아웃·시각 위계·인터랙션 비용·유저플로우가
대상이다. 기능이 옳은지(전략)·문서가 잘 쓰였는지(editorial)는 이 스킬의 범위가 아니다.

## 설계 전제 (왜 이렇게 도는가)

리서치 근거(`references/research-basis.md`): LLM UX 평가기는 플래그의 약 40%가 false
positive(GPT-4 precision 0.603), 전문가 이슈의 21%만 재현하고 환각을 다수 생성한다.
**결론: 단독 판정자로 쓰면 안 되고, pre-screener + 적대 게이트 + 사람 확인으로만 유효하다.**
그래서 이 스킬은 생성(finder)과 판정(evaluator)을 분리한다 — 생성자와 판정자를 분리하는
검증 루프(judge≠solver)와 동형이다. 오탐을 억제하는 세 방어선은 (1) 증거 강제,
(2) 맥락 그라운딩, (3) 적대 검증이다.

## 프로세스 (Phase 0 ~ 4.5)

오탐을 막는 것은 게이트만이 아니다. **관찰 조건이 틀리면 게이트도 못 막는다** — Phase 1의
2패스가 게이트만큼 중요하다.

### Phase 0 — 컨텍스트 팩 조립 (없으면 진행 불가)

`references/context-pack-spec.md` 형식으로 4요소를 SoT에서 적재한다.

1. persona (숙련도·빈도·환경·동시작업)
2. 핵심 job (needs-view, Universal Job Map 8단계)
3. 불변 설계 원칙 (의도된 제약 — over-application 오탐 방어)
4. 주행할 유저플로우 (매일반복/저빈도 구분)

- SoT는 프로젝트마다 다르다. persona는 페르소나 문서·PRD의 사용자 정의·사용 로그 실측에서,
  불변 원칙은 설계 원칙 문서·ADR·PRD의 Non-goal 절에서 가져온다. **없으면 사용자에게 묻는다.
  추측으로 채우지 않는다.**
- 팩을 1장으로 요약해 이후 finder·evaluator에 공통 전달한다.

### Phase 1 — 실물 관찰 (코드 아님, 화면) — **2패스 필수**

- 대상을 **두 번 구동한다. 한 번으로 끝내지 않는다.**
  - **1패스(빈/초기 상태)**: 레이아웃·정보구조·빈 상태 안내·온보딩 경로를 본다.
  - **2패스(실데이터)**: 채워진 화면의 밀도·스캔성·실제 플로우를 본다. 아래 **실데이터
    안전 프로토콜**을 반드시 따른다.
- **finding은 2패스를 마치기 전에 확정하지 않는다.** 1패스 결과는 전부 "후보"다.
  빈 상태는 조건부 렌더 컴포넌트(데이터가 있을 때만 표시되는 요소)를 "부재"로 오판한다.
  실증 사례: 빈 상태에서 "이 화면에는 상태 표시 칩이 없다"고 낸 finding이 적대 게이트까지
  통과해 설계 문서에 반영됐으나, 실데이터로 다시 보니 **그 칩은 원래 있었다**(데이터가
  있을 때만 렌더되는 구조였다). 반영을 되돌려야 했다. 2패스가 불가능하면 보고서에
  **"1패스 한정·미확정"**으로 명시하고 어떤 문서에도 반영하지 않는다.
- 정적 화면은 **스크린샷**으로, 동적 항목(피드백·로딩·상태전이)은 **Playwright 주행**으로
  캡처한다. 주행 시 유저플로우 스텝별 클릭·화면 전환·대기를 **숫자로** 기록한다
  (`references/evidence-protocol.md` §4 — Interaction Cost baseline).
- 정적 캡처만으로는 동적 주장을 못 낸다(리서치: false positive의 상당수가 정적 이미지로
  판별 불가한 동적 인터랙션에서 발생). 동적 항목은 반드시 주행 근거를 남긴다.

#### 실데이터 안전 프로토콜 (외부 호출·데이터 손상 차단)

2패스 전 반드시 지킨다. 실사용 앱은 자격증명으로 외부 수집을 발동하고, 2차 인스턴스가
원본 상태 파일을 손상시킬 수 있다.

1. **격리 복사**: 상태 파일을 임시 디렉토리로 복사하고 원본을 절대 가리키지 않는다.
   Electron이면 `--user-data-dir=<복사본>`으로 격리한다(이 스위치가 앱의 데이터 경로를
   덮어쓴다).
2. **자격증명 제외**: 복사본에서 secrets·토큰 파일을 뺀다. 자격증명이 없으면 수집기가
   외부로 나가지 못하고, 이미 수집된 상태는 그대로 렌더된다 — 실데이터 관찰에 충분하다.
3. **원본 무결성 확인**: 구동 후 원본이 유효한지 확인한다(파싱 성공·주요 컬렉션 건수).
4. **사후 삭제**: 복사본은 검토가 끝나면 삭제한다. 사용자의 실업무 내용을 담고 있다.
5. 자격증명이 필요한 검토(실시간 수집·외부 연동 상태 전이)는 **사용자 감독 하에서만** 한다.
   비감독 세션에서 실자격증명으로 구동하지 않는다.

#### 환경 함정

- **Electron + Playwright**: 하네스 환경에 `ELECTRON_RUN_AS_NODE=1`이 설정돼 있으면 Electron이
  GUI 없이 Node로 실행돼 런치가 `Process failed to launch`로 실패한다. 런치 env에서 이 변수를
  **삭제**한다(`delete env.ELECTRON_RUN_AS_NODE`). 증상이 "app.whenReady가 undefined"로 나기도
  한다.
- **렌더러만 띄우면 안 된다**: 개발 서버(Vite 등)만 띄우면 IPC로 채워지는 데이터가 없어
  빈 껍데기가 렌더된다. 그 화면을 실제 UI로 오독하면 증거 프로토콜 위반이다. 메인
  프로세스까지 함께 구동한다.

### Phase 2 — 차원별 격리 finder 병렬 발견 (pre-screen)

finder 역할(`references/finder-role.md`)을 렌즈별로 **병렬 호출**한다(`references/heuristics.md`
배정 지도). 각 finder는 컨텍스트 팩 + 스크린샷/주행 로그 + 배정 렌즈만 받는다
(생성 맥락 미전달 — 격리).

1. 유저플로우 finder — Cognitive Walkthrough per-step 4문항
2. 레이아웃 finder — Gestalt 시각 위계
3. 인터랙션 비용 finder — Interaction Cost 9종 계량
4. 상태·피드백 finder — Nielsen 10 heuristics

- **관찰 조건에 맞게 렌즈를 배정한다.** 빈 상태 1패스에서는 인터랙션 비용 finder를 돌리지
  않는다 — 측정할 플로우·데이터가 없어 수치 없는 추측만 나온다. 실데이터 2패스에서 배정한다.
  생략한 렌즈는 보고서에 사유와 함께 남긴다(무엇을 안 봤는지 숨기지 않는다).
- 2패스에서는 1패스 finding의 **재검증도 함께 배정한다** — 어느 것이 빈 상태 아티팩트였는지
  실데이터로 색출하는 것이 2패스의 1차 목적이다.
- finder는 채택 전 자가 검사(`evidence-protocol.md` §2)로 환각·정적판별불가·일반론·
  over-application을 스스로 거른다.
- 리서치상 단일 run 재현성이 moderate(κ 0.50)이므로 **병렬 발견 후 병합**한다.

### Phase 3 — 적대 검증 게이트 (evaluator)

병합 전 finding 묶음을 **독립 evaluator 역할**(`references/evaluator-role.md`)에 넘겨 적대적으로
검증한다. finder를 돌린 컨텍스트와 분리해 실행한다.

- evaluator 입력: finding 배열 + 컨텍스트 팩 + 스크린샷/주행 로그(`evidence-protocol.md` §6
  체크리스트 충족분만).
- evaluator는 각 finding을 "화면에 실존하나(환각) / 의도된 컨벤션 아닌가(over-application) /
  정적으로 단정한 동적 주장 아닌가 / 일반론 filler 아닌가"로 기각한다. 애매하면 기각.
- 기각 통과분만 남긴다. finder가 표기한 불확실도가 높은 항목을 집중 검증한다.

### Phase 4 — 중복 병합 + 상대 severity 종합

- 살아남은 finding을 병합한다(같은 화면+같은 개선안=중복, `evidence-protocol.md` §5).
- severity는 **절대 점수 금지, 상대 순위 강제**(`references/severity-rubric.md`).
  frequency·impact·persistence 서술 → 전체 상대 순위 → 3밴드(Blocker/Friction/Polish).
- 파워유저 보정 적용(learnability 한 밴드↓, 매일 반복 플로우 efficiency 한 밴드↑).
- 개선안 우선순위 = severity 밴드 × 수정 비용(코드 변경 범위 추정).

### Phase 4.5 — 사용자 확인 게이트 (밀도·의도 판정)

아래 유형은 에이전트가 확정할 수 없다. 판정하지 말고 **사용자에게 질문으로 넘긴다.**

- **밀도 관찰**: "항상 노출된다·빽빽하다"가 의도인지 마찰인지는 사용자만 안다
  (`heuristics.md` 밀도 승격 기준). interaction-cost 실측이나 사용자 확인 전에는 확정
  finding이 아니라 후보로 둔다.
- **의도 불명 컨트롤**: 목적이 읽히지 않는 UI 요소는 "이게 무슨 의도인가"를 되묻는다.
  **사용자가 자기 제품의 컨트롤 의도를 모른다면 그 자체가 강한 근거다.** 실증 사례: 이
  질문에서 드롭다운의 **라벨과 데이터 모델이 어긋난** 결함이 드러났다 — 라벨은 A를 고르는
  것처럼 쓰여 있는데 실제 옵션 소스와 저장 필드는 B였고, 그래서 사용자가 기대한 A 항목은
  목록에 나오지도 않았다. 화면만 봐서는 안 잡히고 사용자 질문에서 나왔다.

보고서에 **"사용자가 판단할 항목"**을 별도 절로 분리해 질문 형태로 제시한다. 각 질문에는
답에 따라 무엇이 달라지는지(승격/기각/설계 변경)를 함께 적는다.

## 산출물

1. **UX 리뷰 보고서**:
   - 관찰 조건(1패스·2패스 각각 무슨 상태로 봤는가, 못 본 영역은 무엇인가)
   - 컨텍스트 팩 요약(누구의 무슨 job을 기준으로 봤는가)
   - 주행한 플로우 + Interaction Cost baseline 수치
   - finding: 화면·위치 / job 연결 / 증거(캡처·주행) / 개선안 / severity 밴드 / 수정 비용
   - 우선순위 실행 목록(즉시 / quick win / 계획 / 보류)
   - **사용자가 판단할 항목**(Phase 4.5) — 질문 형태
   - 검증 이력(발견 N → 적대 기각 M → 2패스 반증 R → 확정 K) — 오탐 억제 과정을 투명하게.
     **1패스 finding이 2패스에서 뒤집힌 것도 반드시 기록한다**(정정 이력을 숨기지 않는다).
2. **라우팅**: `context-pack-spec.md` 라우팅 원칙대로 기록한다. 프로젝트에 UX 피드백을
   관리하는 원천 필드·문서가 있으면 거기 넣고, 없으면 사용자에게 묻는다.

## 한계 (보고서에 명시)

- 이것은 전문가 휴리스틱 평가의 자동 pre-screen이지 **사용자 테스트의 대체가 아니다**.
  "사용자가 실제로 어디서 멈추는지"는 로그·실사용에서 온다.
- **근거 공백 영역**: 주의력 관리·알림 최소화·오케스트레이션 대시보드 UX 패턴은 리서치에서
  확증 근거를 확보하지 못했다(`research-basis.md` 한계 1). 이 영역은 학술 근거로 단정하지
  말고 대상의 불변 설계 원칙과 persona를 기준으로만 판단한다.
- finding은 사람 확정이 필요한 후보다. 확정·적용은 사용자가 한다.
- **1패스(빈 상태) 단독 결과는 어떤 문서·이슈에도 반영하지 않는다.** 2패스 실데이터 검토를
  마쳐야 확정이다. 이 규칙은 실제 오탐 사고에서 나왔다 — 빈 상태에서 "없다"고 판정한 요소가
  실데이터에는 있었고, 그 오탐이 적대 게이트를 통과해 설계 문서에 반영된 뒤 되돌려졌다.

## 역할 실행 방법 (에이전트 설치 불필요)

이 스킬은 특정 에이전트 파일에 의존하지 않는다. **역할 분리가 본질이고, 실행 수단은 자유다.**

- **finder(발견자)**: `references/finder-role.md`를 서브에이전트 프롬프트로 그대로 넣어
  렌즈별로 **병렬 호출**한다. 커스텀 에이전트를 쓰고 싶으면 그 파일을 에이전트 정의로
  등록해도 된다. 핵심은 **컨텍스트 격리** — finder에게 생성 맥락·개발 의도를 주지 않는다.
- **evaluator(판정자)**: `references/evaluator-role.md`를 별도 서브에이전트로 실행한다.
  **finder와 같은 컨텍스트에서 돌리지 않는다** — 자기 산출물을 관대하게 보는 편향을 구조로
  차단하는 것이 이 분리의 목적이다.
- 두 역할을 한 컨텍스트에서 겸하면 이 스킬의 오탐 억제가 무력화된다. 설계 전제(§설계 전제)를
  다시 읽어라.
