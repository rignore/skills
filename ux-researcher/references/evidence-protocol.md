# 증거 프로토콜 — finding 채택 게이트

근거: `research-basis.md` 근거 2·3·6. LLM UX 평가의 false positive 40%(GPT-4 precision
0.603)를 억제하는 유일한 방어선이다. **이 프로토콜을 통과 못 한 finding은 보고서에서
삭제한다.** 관대하게 두지 않는다 — 애매하면 탈락.

## 1. finding 필수 3요소 (하나라도 없으면 탈락)

모든 finding은 아래 세 가지를 반드시 갖춘다. 서술이 아니라 **구체 증거**여야 한다.

1. **화면 증거 (evidence)**: 해당 문제가 보이는 스크린샷 파일명 + 화면 내 위치(어느
   영역·어느 요소). "전반적으로"·"여러 곳에서"는 증거가 아니다. 캡처 1장을 지목하라.
2. **플로우·맥락 연결 (grounding)**: 어느 유저플로우의 몇 번째 스텝에서 발생하는가 +
   어느 persona의 어느 job을 막는가. context-pack의 job map 단계로 지목한다.
3. **개선안 (fix)**: 무엇을 어떻게 바꾸면 되는지 구체적으로. "개선 필요"는 개선안이 아니다.

## 2. 실패 모드 3종 + over-application 방어 (채택 전 자가 검사)

각 finding에 대해 아래 4개 질문에 모두 통과해야 채택한다. 하나라도 "예"면 탈락 또는
downgrade.

| # | 검사 질문 | 걸리면 |
|---|---|---|
| 환각 | 이 문제가 실제 스크린샷에 **보이는가**? 추측·기억으로 쓴 것 아닌가? | 삭제 |
| 정적 판별 불가 | 이 주장이 **동적 인터랙션**(hover·로딩·상태 전이·애니메이션)에 관한 것인데 정적 캡처만 근거로 삼았는가? | 주행 관찰로 재확인하거나 삭제 |
| 일반론 | "인지 부하가 높다"·"일관성을 높여라" 류 **구체성 없는 filler**인가? 특정 화면·요소·수치로 못 내리는가? | 삭제 |
| over-application | 비일관성·비표준으로 보이는 것이 실은 **의도된 컨벤션**(선택 상태 표시, 파워유저용 밀도, 앱의 다크 테마 규약)일 가능성을 배제했는가? | context-pack 대조 후 근거 없으면 삭제 |

**over-application이 최다 실패 모드**(스터디 12/12 전원 지적)임을 기억한다. 파워유저용
밀집 레이아웃·정보 밀도는 의도된 설계인 경우가 많다. "너무 빽빽하다"를 쓰기 전에 컨텍스트
팩의 persona가 그 밀도를 원하는지 먼저 확인한다(`heuristics.md` 밀도 승격 기준).

## 3. 정적 캡처만으로 쓸 수 있는 것 / 없는 것

- **정적 캡처로 판정 가능**: 레이아웃·시각 위계·정보 그룹핑·라벨 명료성·대비·정렬·
  빈 상태(empty state) 존재 여부·빈 상태 안내 문구의 품질·요소 라벨.
- **주행(비디오·클릭 로그) 없이는 금지**: 피드백 유무("클릭해도 반응 없음")·로딩 처리·
  상태 전이·전환 애니메이션·포커스 이동·에러 처리·인터랙션 지연. 이 항목은 반드시
  Playwright 주행 또는 실제 클릭 관찰 로그를 근거로 든다.
- **빈 상태 placeholder 배치는 실데이터 레이아웃 판정 근거로 쓰지 않는다**(2026-07-15
  실전 검증에서 추가). 빈 userData 캡처의 중앙 정렬 안내문·placeholder 위치를 "라벨과
  값이 좌우로 벌어졌다"처럼 데이터 로드 시의 레이아웃 결함으로 단정하면 오탐이다 —
  실데이터가 들어오면 그 자리에 콘텐츠가 채워져 배치가 달라진다. 빈 상태에서 판정 가능한
  것은 (a) 안내 문구 품질, (b) 진입점·다음 행동 안내 유무, (c) 컨테이너·구분선 등 데이터
  무관 구조뿐이다. placeholder의 정렬·간격을 근거로 삼으려면 실데이터 주행으로 재확인한다.

## 4. Interaction Cost 계량 (주행 시 필수 기록)

유저플로우를 주행할 때 아래를 **숫자로** 기록한다(근거: research-basis 근거 4). 이 수치
자체가 강한 finding 증거다.

- 태스크 완료까지 **클릭·키 입력 수**
- **화면 전환 수**(뷰 이동 횟수)
- **주의 전환**(attention switch): 사용자가 목적 정보를 찾으려고 시선을 옮겨야 하는 영역 수
- 대기·로딩 발생 지점

예: "항목 검색에서 상세 열람을 거쳐 처리 완료"까지 클릭 9회·화면 전환 4회면, 이 수치를
개선안의 기준선(baseline)으로 보고한다. 개선안은 "클릭 9회에서 5회로 감소"처럼 정량 목표를
제시한다.

## 5. 중복 병합 (dedup)

- 서로 다른 heuristic에서 같은 화면·같은 원인을 지목한 finding은 **하나로 병합**한다.
  판단 기준: 화면 위치가 같고 개선안이 실질적으로 동일하면 중복.
- 병합 후 severity를 매긴다(순서 중요 — 중복이 severity를 부풀리지 않게).
- 근거: 문헌은 임베딩 cosine 0.7 임계 자동 병합을 쓰나, 이 에이전트는 finder 수가 적어
  **의미 판단으로 병합**한다(같은 화면+같은 개선안 = 중복). 자동 임계가 필요할 만큼
  finding이 많아지면 그때 임베딩 병합을 도입한다.

## 6. 적대 게이트로 넘기기 전 체크리스트

finder가 낸 finding 묶음을 evaluator(적대 게이트)로 넘기기 전, 각 finding이 아래를
갖췄는지 확인한다. 이것이 evaluator의 입력 계약이다.

- [ ] 스크린샷 파일명 + 화면 내 위치 명시
- [ ] job map 단계 + persona 지목
- [ ] 동적 주장이면 주행 로그 근거 첨부
- [ ] 개선안이 구체적(무엇을 어떻게)
- [ ] Interaction Cost 관련이면 baseline 수치 첨부
