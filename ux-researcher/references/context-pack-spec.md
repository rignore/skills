# 컨텍스트 팩 규약 — 맥락을 SoT에서 적재한다

근거: `research-basis.md` 근거 4(context divergence — 맥락 없는 평가는 false alarm을 양산하고,
persona·job 그라운딩이 over-application 오탐을 상쇄한다). **대상을 "일반 앱"으로 보면 리뷰가
일반론으로 퇴행한다.** 리뷰 시작 전 컨텍스트 팩을 반드시 조립한다.

맥락은 스킬에 하드코딩하지 않는다 — 프로젝트별 SoT(Source of Truth)에서 매번 적재한다.
대상이 바뀌면 이 팩만 갈아끼운다. 그래서 이 스킬은 특정 제품에 결합되지 않는다.

## 컨텍스트 팩 4요소 (없으면 리뷰 중단하고 요청)

### 1. 사용자 특성 (persona)

- **SoT 후보**: 페르소나 문서, PRD의 사용자 정의, 사용 로그 실측, 사용자 인터뷰 노트.
  없으면 **사용자에게 직접 묻는다.** 추측으로 채우지 않는다.
- **필수 추출 항목**
  - 숙련도: 파워유저인가, 신규·간헐 사용자인가
  - 사용 빈도: 매일인가, 가끔인가
  - 사용 환경·시간대: 어떤 상황에서 쓰는가
  - 동시에 다루는 작업 수
  - 무엇에 능숙하고 무엇을 질문으로 확인하는가
- 이 항목들이 severity 보정을 좌우한다(`heuristics.md` 파워유저 보정 참조). 숙련도와 빈도를
  모르면 learnability 문제의 경중을 판단할 수 없다.

### 2. 핵심 니즈·job (JTBD)

- 사용자가 이 화면·플로우로 **완수하려는 job**을 needs-view로 적는다. "무엇을 하고 있는가"가
  아니라 "무엇을 해내려는가"다.
- Universal Job Map 8단계로 프레이밍한다: define, locate, prepare, confirm, execute, monitor,
  modify, conclude.
- **SoT 후보**: PRD의 문제 정의·핵심 가치 가설, 요구사항 문서의 "문제 정의" 절.
- 이미 알려진 제품 결손(설계상 미구현으로 남긴 것)은 job 서술에 포함하되 **UX 버그로
  올리지 않는다.** 그건 로드맵이지 사용성 결함이 아니다.

### 3. 불변 설계 원칙 (제약 — over-application 방어의 핵심)

- 대상이 **의도적으로** 지키는 규칙. 이걸 모르면 의도된 설계를 "위반"으로 오탐한다
  (리서치 최다 실패 모드: 참가자 12/12 전원이 지적).
- **SoT 후보**: 설계 원칙 문서, 아키텍처 결정 기록(ADR), PRD의 Non-goal 절, 제품 철학 문서.
- 전형적인 예 — 아래에 해당하면 finding이 아니다:
  - "수집·표시는 읽기 전용"이면 "왜 여기서 바로 편집이 안 되나"는 finding이 아니다.
  - "확정 주체는 항상 사용자, 앱은 제안까지만"이면 "왜 자동으로 안 해주나"는 finding이 아니다.
  - "목록을 앱이 몰래 재배열하지 않는다"면 "왜 자동 정렬이 없나"는 finding이 아니다.
  - "능동 알림 최소화"면 "왜 알림이 안 오나"는 finding이 아니다. 단 대체 표현(배지·요약·
    대기열)이 **충분한지**는 검토 대상이다.
  - "파워유저용 정보 밀도는 의도"면 "너무 빽빽하다"는 persona 확인 후에만 낸다
    (`heuristics.md` 밀도 승격 기준).

### 4. 유저플로우 정의 (주행 대상)

- 리뷰할 핵심 플로우를 스텝 목록으로 명시한다. Cognitive Walkthrough와 Interaction Cost
  주행의 대상이 된다.
- **매일 반복 플로우**와 **저빈도 플로우**를 나눠 적는다. 둘은 severity 보정이 다르다.
  매일 반복 플로우는 efficiency에 가중하고, 저빈도 플로우는 learnability를 유지한다.
- 플로우가 정의돼 있지 않으면 사용자에게 "무엇을 가장 자주 하는가"를 물어 만든다.

## 컨텍스트 팩 조립 산출물

리뷰 시작 시 아래 형식으로 1장 요약을 만든 뒤 finder에 전달한다. finder는 이 팩과 화면 증거만
받는다(생성 맥락·개발 의도는 전달하지 않는다 — 격리).

```
## 컨텍스트 팩 — {대상}
### persona: {숙련도·빈도·환경·동시작업}
### 핵심 job (needs-view): {job 1~2개, 8단계 중 어디를 지원해야 하나}
### 불변 원칙 (finding 금지 영역): {의도된 제약 목록}
### 주행 플로우: {스텝 목록, 매일반복/저빈도 구분}
### 관찰 조건: {1패스 상태 / 2패스 상태 / 못 보는 영역}
```

## findings 라우팅

리뷰 결과를 어디에 기록할지는 **프로젝트 규약을 따른다.** 규약이 없으면 사용자에게 묻는다.
일반 원칙은 둘이다.

1. **원천 필드에 기록한다.** UX·레이아웃·유저플로우 피드백을 관리하는 필드·문서가 이미
   있으면 거기 넣는다. 리뷰 결과만 따로 떠다니게 두지 않는다.
2. **기능 범위가 바뀌는 개선안은 요구사항 문서로 역전파한다.** 프로토타입만 고치고 PRD를
   그대로 두면 문서와 구현이 어긋난다.
