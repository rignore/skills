# Severity·우선순위 루브릭

근거: `research-basis.md` 근거 5. **핵심 규칙: LLM에 절대 척도(0-4 점수)를 매기게 하지
않는다.** 절대 척도는 동일 등급이 다발해 순서가 붕괴한다(FSE 2026 실험). 대신 **상대
순위(relative ranking)**로 강제한다.

## 1. Severity를 정하는 3요소 (Nielsen)

각 finding을 세 축으로 서술한다. 점수가 아니라 서술이다.

1. **frequency(빈도)**: 이 문제를 사용자가 얼마나 자주 마주치는가. 매일 반복하는 핵심
   플로우인가, 가끔 쓰는 화면인가.
2. **impact(영향)**: 마주쳤을 때 얼마나 극복하기 어려운가. 막히는가(task 실패), 짜증나는가,
   우회 가능한가.
3. **persistence(지속성)**: 한 번 배우면 넘어가는가(1회성), 알고도 매번 다시 괴로운가(반복).
   persistence가 높은 것이 가장 나쁘다 — 학습으로 해소 안 됨.

## 2. 상대 순위 산정 (절대 점수 대신)

finding 전체를 놓고 **서로 비교해 순서를 매긴다.** 비교 기준 4개:

- task 성공에 대한 영향 (막는가 vs 불편한가)
- 사용자 좌절도 (frustration)
- 발생 가능성 (likelihood of occurrence = frequency)
- 복구 노력 (effort for recovery)

산출은 점수표가 아니라 **순위 목록**이다: "1순위 …, 2순위 …" 형식. 동점을 허용하지
않는다 — 반드시 순서를 강제한다(둘이 비슷하면 frequency 높은 쪽을 위로).

## 3. 3단 밴드 (보고용 그룹핑)

상대 순위를 낸 뒤 세 밴드로 묶는다. 밴드는 절대 기준이 아니라 이 리뷰 배치 안의 상대
구분이다.

| 밴드 | 의미 | 예 |
|---|---|---|
| **Blocker** | 핵심 플로우에서 task를 막거나 데이터 손실·오처분 위험 | 제출한 작업의 결과를 다시 찾을 경로가 화면에 없어 플로우가 끊김 |
| **Friction** | task는 되나 반복 비용·혼란이 큼 (특히 매일 반복 플로우) | 한 항목의 상태를 알려면 화면 3곳을 번갈아 봐야 함 |
| **Polish** | 심미·미세 개선, 우회 쉬움 | 카드 정렬이 미세하게 어긋남 |

## 4. 파워유저 보정 (persona가 파워유저·매일 반복일 때만)

`heuristics.md` 파워유저 보정과 연동한다. 컨텍스트 팩의 persona가 신규·간헐 사용자면
적용하지 않는다.

- **learnability 단독 문제는 한 밴드 낮춘다.** 매일 쓰면 학습된다. 단 저빈도 화면
  (설정·관리 등 가끔 쓰는 기능)은 예외로 유지한다.
- **매일 반복 핵심 플로우의 efficiency 문제는 한 밴드 높인다.** 클릭 1회 절감이 반복
  횟수만큼 누적된다.
- persistence가 높은 friction은 Blocker에 준해 다룬다. 파워유저가 매일 겪는 반복 마찰은
  누적 손실이 크다.

## 5. 개선안 우선순위 = severity × 수정 비용

최종 보고서의 실행 순서는 severity만으로 정하지 않는다. **수정 비용(추정)**과 결합한다.

- 우선순위 = severity 밴드 ↔ 수정 비용의 2×N 매트릭스.
- **Blocker + 저비용 = 즉시**, Blocker + 고비용 = 계획, Friction + 저비용 = quick win,
  Polish + 고비용 = 보류.
- 수정 비용은 코드 변경 범위로 추정한다(단일 컴포넌트 스타일 vs 상태 모델·IPC 변경).
  프로토타입 코드를 열어 대략의 변경 지점 수로 low/med/high를 판단한다.

## 6. 금지

- 절대 점수(0-4)를 최종 산출로 내지 않는다 — 상대 순위 + 3밴드만.
- severity를 finding 개수로 부풀리지 않는다 — 중복 병합(evidence-protocol §5) 후 매긴다.
- "심각함"·"매우 중요"류 무근거 강조어 금지 — frequency·impact·persistence 서술로 대체.
