# 라운드 절차 — Round 0 / Round N

전제: `harness-plan.md`가 confirmed 상태다. 없으면 Phase P(`planning.md`)로 돌아가라.

## 1. Round 0 — 하네스 구축

고정축(Evaluator) 4요소 중 빈 것을 채우는 라운드. solver 개선은 하지 않는다.

1. **정답표 확정**: 판정 항목 ID·기대값·허용 오차를 표로 고정한다.
2. **판정 프로토콜 문서화**: 항목별 측정 방법과 pass/fail 조건을 실측 전에 기록한다.
3. **집계 스크립트 작성**: 판정 출력을 파싱해 수치를 확정하는 스크립트. 이론값·기대값은 설계 명세에서 독립 재계산한다 — solver 코드의 함수를 그대로 불러 검산하면 자기 채점이다(예외는 계산 경로가 다른 경우뿐이며 사유를 주석으로 남긴다).
4. **상태 파일 생성**: `state.json`(harness-plan의 metric·target·max_rounds·stat_design 반영)과 빈 `lessons.md`를 만들고 commit한다.
5. **캘리브레이션 게이트 (LLM 심판 시 필수)**: baseline 전에 심판이 정답표와 얼마나 일치하는지 측정한다. 정책 오너가 라벨한 소량 gold(30개 안팎)로 심판 판정 vs 정답 라벨의 일치도 κ를 구한다. **κ≥0.6이어야 loop 진입** — 미달이면 (a) 그 항목을 규칙 판정으로 이관하거나 (b) 루브릭·캘리브레이션 예시를 재작성하고 재측정한다. 단순 동의율은 쓰지 않는다(라벨 편중 시 90% 동의여도 κ가 음수일 수 있다). 각 등급에 실제 산출물 앵커 예시를 심판 프롬프트에 첨부한다(앵커 없으면 채점이 중앙값으로 붕괴). 결정론 스크립트 단독 판정이면 이 단계를 생략한다.
6. **기준선(baseline) 실측**: 현재 solver 그대로 측정한다. 확률적 시스템이면 이때부터 N회 반복 집계다(`statistics.md` §2). 결과를 `history[0]`에 기록한다.

## 2. Round N — 표준 6단계

0. **개선 고정** — `lessons.md`의 잔여 원인 목록(리서치 반영분 포함)에서 개선안을 골라 실측 전에 문서로 고정한다(사후 완화 차단). 라운드당 개선안은 1~3개로 유지한다 — 많이 넣으면 귀속 분석이 안 된다.
1. **solver 수정** — 고정한 개선안만 반영한다. 병렬 세션이 참조 중인 부분은 수정하지 않는다.
2. **블라인드 산출** — 정답표·판정 기준 열람이 금지된 별도 에이전트/프로세스가 산출물을 생성한다. 확률적 시스템이면 같은 조건으로 N회 반복 생성한다(N은 `stat_design.n_reps`, 사후 변경 금지).
3. **페어링/전처리** — 정답 항목과 산출물을 연결한다. 이 단계에서 판정 의견을 내지 않는다.
4. **판정 (two-stage)** — 사전 고정된 프로토콜 기준만 적용한다. **① 규칙 프리필터 선행**: 결정 신호(hex·px·토큰명·금지패턴)를 스크립트로 먼저 판정한다. BLOCKER(무결성 필수) 위반이면 그 산출물은 즉시 최저 등급으로 확정하고 LLM 심판에 넘기지 않는다(비용·False Positive 절감). **② 의미 항목만 심판**: 규칙이 확정 못한 항목(incomplete)만 LLM 심판 3인 병렬 표결(서로의 판정·과거 라운드 열람 금지, 2/3표 확정). 심판은 solver와 다른 계열, 정답표를 reference로 프롬프트에 동봉, 점수 전 근거를 먼저 출력, 결함마다 원인·수정 지침을 붙인다. 수치 계산만이면 스크립트가 유일 심판이고 ②는 생략한다.
5. **기계 집계 + 분해** — 스크립트로 수치를 확정한다. N회 반복이면 항목별 통과율·신뢰구간으로 집계하고 불안정 항목을 표시한다. 이상 산출물(할루시네이션 등)은 전수 대조한다.
6. **귀속 분석 + 기록** — 직전 라운드와 항목 단위 1:1 대조(회복/퇴행/불변, paired 원칙 — `statistics.md` §4). 개선 항목별 기여와 재실행 변동을 분리해 보수적 순효과를 산출한다. `state.json`·`lessons.md`·결과 문서를 갱신하고 commit한다.

**리서치 분기**: 6단계 후 순효과가 유의 기준 미만이면 `stalled_rounds`를 +1 한다. `research.md`의 발동 조건에 해당하면 리서치 루프를 실행하고, 그 결과를 다음 라운드의 0단계(개선 고정) 입력으로 넘긴다. 원인 가설 검증이 필요하면 변형(variation) 실행을 다음 라운드에 편성한다(`statistics.md` §5).

## 3. 역할 분리 (자기 채점 차단)

| 주체 | 하는 일 | 금지 사항 |
|---|---|---|
| 산출자(Solver 실행) | 산출물 생성 | 정답표·판정 기준·개선 목표 수치 열람 |
| 페어링 담당 | 정답 항목과 산출물 연결 | 판정 의견 제시 |
| 심판 | 프로토콜 기준 판정 (solver와 다른 모델 계열, 정답표 reference 동봉) | 다른 심판·과거 라운드 열람, 자기 계열 산출물 판정 |
| 집계 | 수치 확정 | 사람/LLM 개입 (스크립트만) |

## 4. lessons.md — 라운드마다 append하는 4항목

1. 시도한 개선과 결과 (항목별 회복/퇴행/불변, 보수적 순효과)
2. 실패·부작용 (예: 개선 X가 항목 Y 퇴행 유발)
3. 잔여 원인 구조 — 다음 개선 후보 (리서치 근거 링크 포함)
4. 하지 말 것 (철회된 접근과 그 이유)

## 5. 보고서 프로세스 (2단계)

라운드 로그(작업 노트)와 최종 보고서(제출본)를 분리한다. 독자가 다르고 품질 기준이 다르다.

### 5-1. 라운드 보고서 — 매 라운드 종료 시 (작업 노트)

- 위치: `verification/loop/reports/round-N.md`. 독자는 다음 라운드를 도는 자기 자신·병렬 세션.
- 내용: ① 이번 라운드 측정값(항목별 판정표, 확률적이면 N회 통과율·신뢰구간) ② 직전 라운드 대비 paired 대조(회복/퇴행/불변, 보수적 순효과) ③ FAIL 항목의 3분류(모델 결함 / 기준 부적정 / 구현 버그)와 근거 ④ 다음 개선 후보(lessons.md와 연동) ⑤ 리서치 발동 시 research-notes 링크.
- 형식: 개조식·표 위주. editorial 검토는 생략한다(중간 산출물).
- 6단계 "귀속 분석 + 기록"에서 state.json·lessons.md와 함께 작성하고 commit한다.

### 5-2. 최종 보고서 — 종료 시 (제출본, 협상 불가 프로세스)

수렴(converged) 또는 max_rounds 도달로 loop를 종료할 때 1회 작성한다. 독자는 이 검증을 처음 보는 이해관계자다.

1. **집계**: 전 라운드 state.json·round-N.md를 읽어 최종 판정과 개선 궤적을 확정한다. 수치는 라운드 보고서에서 인용하며 새로 만들지 않는다.
2. **초안 작성**: 아래 구조로 작성한다.
   - 검증 개요: 지표 정의, 판정 기준의 근거(정답표 출처), 통계 설계(mode·N·유의 기준)를 처음 보는 독자가 이해하도록 명시. **판정 방식을 과정으로 풀어 쓴다** — 각 판정 층위(결정론 규칙 검사·LLM 심판 등)가 **어떤 항목을 · 어떤 방식으로 · 어떻게 테스트했는지**, 비개발자 PM도 과정을 인지·판단할 수 있게 서술한다(예: "규칙 검사 = 생성된 코드를 정규식으로 훑어 임의 색상 코드·이모지·비표준 아이콘이 있는지 기계가 확정 판정. 심판 = 다른 AI가 코드를 읽고 색의 의미 적절성·문구 어조를 판단").
   - 최종 판정표: 전 항목 `ID | 최종 측정값 | 판정 기준 | 판정(PASS/FAIL/조정) | 비고`. 각 판정에 구체 사례 1건 이상을 붙인다(예: FAIL 항목이면 실제 측정값과 기준값을 나란히).
   - 개선 궤적: 라운드별 순효과와 무엇을 바꿔 무엇이 회복됐는지.
   - 미해결·한계: 종료 시점의 FAIL·조정 항목, seed 민감 항목, 범위 밖 항목.
   - 결론과 권고: 판정 요약 + 다음 행동 권고.
3. **editorial 검토 게이트 (필수)**: 초안을 editorial-reviewer 스킬로 가독성·용어 일관성·논리 흐름을 검토한 뒤 확정한다. 사용자가 검토를 요청하지 않아도 최종 보고서면 자동 적용한다.
4. **비개발자 PM 기준 풀어쓰기 (필수)**: 보고서만 보고도 무슨 내용인지 판단할 수 있어야 한다. 판정 항목 코드·티어 약어·통계 용어를 단독 표기하지 않고 **의미와 평가 기준**을 병기한다.
   - "T1 BLOCKER fail"이 아니라 → "결정론 규칙 검사(코드를 정규식으로 확정 판정)에서 치명 항목 위반 — 예: 임의 색상 코드를 직접 입력".
   - "T1 Wilson 95 lower 0.72"가 아니라 → "통과율의 95% 신뢰구간 하한 0.72 — 반복 측정해도 최소 72%는 통과한다는 보수적 추정".
   - "M-statecolor fail"이 아니라 → "색의 의미 적절성 판정 실패 — 위험 상황이 아닌데 위험색(빨강)을 써서 오독 유발".
   - 판정 항목 코드·약어는 **최초 1회 의미 병기 후** 재등장 시 단독 허용.
5. **위치**: preset이 지정한 리포트 경로. 미지정이면 `<프로젝트>/docs/<지표명>-검증결과-YYYYMMDD.md`.

## 6. 실행 형태 3단계

## 5. 실행 형태 3단계

1. **수동 사이클**: 세션 내에서 서브에이전트로 산출·판정·집계를 분리 수행. 첫 도입 시 기본 형태.
2. **로컬 /loop**: `/loop` 스킬로 반복 실행. `state.json`을 진입 가드로 쓰고 종료 조건(converged 또는 max_rounds)을 프롬프트에 명시한다.
3. **클라우드 routine**: `/schedule`로 등록. 각 run은 fresh clone이므로 state는 git이 유일 저장소다 — 프롬프트가 직접 commit·push하게 한다. `converged=true` 또는 `round >= max_rounds`면 no-op으로 종료. 실행 간격은 넓게 잡는다.

## 7. 서브에이전트 운영 노하우 (실측 이슈와 대응)

- **긴 파일을 한 번에 생성시키지 말라**(stall 실측). 분할 작성 후 append.
- **판정 출력은 기계 파싱 형식 강제**: `ID | 측정값 | 판정 기준 | 판정(pass/fail) | 원인·수정` 표 형식, verdict 소문자, 셀 내 `|` 금지, 전 항목 누락 없이. FAIL 항목은 마지막 열에 원인(why)과 수정 지침(how-to-fix)을 적어 solver가 바로 개선하게 한다. 집계 스크립트가 정규식으로 읽는다.
- **산출 에이전트에게 개선 내용·목표 수치를 알리지 말라**(측정 오염). "이번에 기준이 바뀌었다"를 알면 측정이 오염된다 — 지시문을 따르라고만 한다.
- **라운드 간 대조는 스크립트로**: 항목 ID와 verdict 매핑으로 회복/퇴행/불변을 기계 산출. 수작업 대조는 실수와 편향의 진입로다.
- **파일 기반 핸드오프**: 서브에이전트 간 전달은 대화가 아니라 파일로 한다. 컨텍스트 리셋·세션 교체 후에도 `harness-plan.md`·`state.json`·`lessons.md`·`research-notes.md`만 읽으면 재개할 수 있어야 한다.
- **중단 시 재개**: 출력 파일의 마지막 완결 블록을 확인하고, 같은 에이전트에 "현재 파일 상태 + 남은 작업"을 명시해 재개한다. 서버 과부하(HTTP 529)면 2~3분 대기 후 재시도.
