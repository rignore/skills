# 한국어 자연스러움 교정 패턴

## 0. 사용 목적

이 문서는 `AI 같다`는 모호한 느낌을 한국어 문장 수준의 진단 항목으로 바꾼다. 패턴을 찾는 목적은 탐지기를 피하는 것이 아니라, 독자가 실제 주체·행동·근거를 빠르게 이해하도록 문장을 고치는 데 있다.

규칙을 기계적으로 적용하지 않는다. 제목, 표, 기술 명세처럼 명사형과 기호가 자연스러운 문맥은 예외다.

---

# 1. 최우선 패턴: 추상 명사와 변환 동사 남용

## 1.1 `전환·연결·구체화·구조화·고도화` 반복

### 증상

- 프로필과 프로젝트마다 같은 추상 동사가 반복된다.
- 무엇을 실제로 바꿨는지 보이지 않는다.
- 문장이 있어 보이지만 장면이 떠오르지 않는다.

```text
원문
고객의 모호한 요구를 구체적인 제품 구조와 실행 가능한 대안으로 전환했습니다.

교정
고객이 원하는 기능부터 적지 않았습니다. 먼저 반복 업무와 판단 기준을 확인한 뒤, 개발 범위와 우선순위를 정했습니다.
```

### 교정 질문

- 무엇을 나눴는가?
- 무엇을 묶었는가?
- 어떤 기준을 적었는가?
- 어떤 화면·정책·데이터로 만들었는가?
- 누구의 행동이 어떻게 달라졌는가?

추상 동사를 삭제한 자리에 실제 답을 넣는다.

## 1.2 `~기반`, `~관점`, `~중심`, `~단위` 연쇄

```text
원문
데이터 기반 사용자 중심 의사결정 지원 구조를 설계했습니다.

교정
사용자가 판단에 필요한 수치를 데이터베이스에서 바로 조회하고, AI는 조회 결과만 설명하도록 역할을 나눴습니다.
```

`기반`, `중심`, `단위`가 전문적으로 필요한 경우는 유지하되 한 문장에 둘 이상 겹치지 않게 한다.

## 1.3 가능형 수식어

### 감지 표현

- 실행 가능한
- 검증 가능한
- 통제 가능한
- 확장 가능한
- 지속 가능한
- 재사용 가능한

### 문제

가능하다는 말만 있고, 무엇 때문에 가능한지 설명하지 않는다.

```text
원문
검증 가능한 AI 운영 구조를 마련했습니다.

교정
AI 결과에 원문 근거와 확신도를 붙이고, 낮은 확신도는 담당자 검토로 보냈습니다.
```

# 2. 번역투 어순과 조사

## 2.1 `~를 통해`

`~를 통해`가 수단을 명확히 나타내는 경우는 맞는 표현이다. 다만 AI 초안에서는 거의 모든 인과관계에 붙는다.

```text
원문
사용자 인터뷰를 통해 신청 과정의 문제를 발견했습니다.

교정
이탈 고객 15명을 인터뷰해 신청 과정의 병목을 찾았습니다.
```

```text
원문
프로토타입을 통해 개발팀과 의사소통했습니다.

교정
동작하는 프로토타입으로 사용자 흐름과 예외 조건을 함께 확인했습니다.
```

## 2.2 `~에 대한`, `~에 있어서`, `~측면에서`

```text
원문
품질 관리 측면에서 테스트 케이스에 대한 정비를 진행했습니다.

교정
테스트 케이스를 정비해 품질 기준을 맞췄습니다.
```

## 2.3 영어식 피동

```text
원문
담당자에 의해 승인된 결과만 시스템에 반영되도록 설계했습니다.

교정
담당자가 승인한 결과만 시스템에 반영했습니다.
```

사람 또는 시스템이 실제 행위 주체라면 능동형으로 쓴다.

## 2.4 `~함으로써`, `~함에 따라`

```text
원문
상황 단위로 통합함으로써 담당자의 판단 부담을 낮췄습니다.

교정
여러 알림을 하나의 상황으로 묶었습니다. 담당자는 같은 사고인지 다시 판단할 필요가 줄었습니다.
```

결과가 실측되지 않았다면 `줄였습니다` 대신 `줄이도록 설계했습니다`로 제한한다.

# 3. 명사화와 보조용언

## 3.1 `진행·수행·실시·제공`

```text
원문
요구사항 수집 및 우선순위 결정 업무를 수행했습니다.

교정
고객 요구사항을 모으고 개발 우선순위를 정했습니다.
```

```text
원문
사용자가 근거를 확인할 수 있는 기능을 제공합니다.

교정
사용자는 답변 옆에서 근거 문서를 바로 확인할 수 있습니다.
```

## 3.2 긴 목적어 + `관리했습니다`

```text
원문
프로젝트의 요구사항, 일정, 산출물, 품질 기준 및 이해관계자를 관리했습니다.

교정
요구사항을 개발 일정과 시험 기준에 연결했습니다. 대학·연구기관·개발팀의 산출물도 같은 연차 계획으로 맞췄습니다.
```

`관리했다`를 없애는 것보다 무엇을 어떤 기준으로 관리했는지 풀어 쓴다.

## 3.3 명사 연쇄

```text
원문
AI 상담 지식 품질 검토 승인 반영 프로세스 구축

교정
AI가 제안한 답변을 운영자가 검토하고 승인한 뒤 지식에 반영하는 절차를 만들었습니다.
```

표 제목이나 도식 레이블에서는 명사형을 허용한다.

# 4. 주체와 책임이 보이지 않는 문장

## 4.1 주체 없는 `정의·설계·마련`

```text
원문
복합 위험을 종합 판단하는 구조를 설계했습니다.

교정
저는 환경·설비·작업자 분석 결과를 합칠 기준을 제품 요구사항으로 정리했고, AI 개발팀과 입력·출력 범위를 맞췄습니다.
```

이력서 불릿에서는 `저는`을 생략해도 된다.

```text
교정
환경·설비·작업자 분석 결과를 합칠 기준을 제품 요구사항으로 정리하고, AI 개발팀과 입력·출력 범위를 맞췄습니다.
```

## 4.2 `기여했습니다`

`기여`는 책임이 약하거나 공동 결과를 정직하게 표현할 때 필요하다. 다만 구체적인 행동 없이 단독으로 쓰면 정보가 없다.

```text
원문
GS인증 1등급 획득에 기여했습니다.

교정
기능 명세, 시험 기준, 결함 목록과 사용자 문서를 맞춰 GS인증 심사를 준비했습니다. 제품은 GS인증 1등급을 받았습니다.
```

책임 범위가 제한적이면 다음처럼 쓴다.

```text
기능 명세와 사용자 문서 정비를 맡아 GS인증 1등급 획득에 기여했습니다.
```

## 4.3 과도한 `리드·총괄·전담`

### 사용 조건

- 의사결정 권한
- 책임 기간
- 직접 작성·승인한 산출물
- 조율한 조직
- 결과

중 두세 가지를 같은 문단에서 설명할 수 있어야 한다.

```text
피할 문장
프로젝트 전 과정을 총괄했습니다.

권장 문장
5개월 동안 고객 요구사항과 개발 범위를 정리하고, 주간 일정·기능 검수·최종 인도 일정을 관리했습니다.
```

# 5. 기계적 병렬과 리듬

## 5.1 완벽한 3단 병렬

AI 초안은 세 항목을 정확히 맞추는 경향이 있다. 내용상 세 개가 맞으면 유지하되, 모든 섹션이 세 항목이면 구조를 다시 본다.

```text
원문
문제를 정의하고, 솔루션을 설계하고, 결과를 검증했습니다.

교정
반복 알림 때문에 담당자가 같은 사고를 다시 조립하고 있었습니다. 이를 `상황` 단위로 묶는 흐름을 설계했고, 주요 예외는 프로토타입으로 확인했습니다.
```

## 5.2 동일한 종결 어미

```text
원문
요구사항을 수집했습니다.
PRD를 작성했습니다.
개발팀과 협업했습니다.
QA를 진행했습니다.
릴리스했습니다.

교정
고객 요구사항을 PRD와 개발 우선순위로 정리했습니다. 개발 중에는 예외 흐름과 QA 기준을 맞췄고, 최종 릴리스까지 담당했습니다.
```

문장을 억지로 다른 어미로 바꾸지 않는다. 내용 단위가 같으면 묶고, 다르면 문단을 나눈다.

## 5.3 문장 길이 획일화

핵심 판단은 짧게 쓴다. 배경이나 제약은 다음 문장에서 설명한다.

```text
상황이 제품의 중심 단위가 됐습니다.
기존에는 센서와 AI 모델이 같은 원인의 이벤트를 따로 보냈고, 담당자가 직접 관계를 판단해야 했습니다.
```

## 5.4 쉼표 과다

한 문장 안에 쉼표가 세 개 이상이면 다음을 확인한다.

- 독립된 행동이 둘 이상인가?
- 주어가 바뀌는가?
- 조건과 결과가 겹치는가?
- 목록으로 바꾸는 편이 나은가?

한국어는 영어보다 쉼표에 덜 의존한다. 조사와 어미로 관계를 보여주거나 문장을 나눈다.

# 6. 기호와 외래어

## 6.1 가운데점 `·`

### 유지 가능한 곳

- 역량 키워드
- 팀 직군 목록
- 짧은 기술 스택
- 표와 제목

### 줄여야 하는 곳

- 한 문장에 네 개 이상 등장
- 동사 관계를 가운데점이 대신함
- 원인·행동·결과가 같은 수준으로 나열됨

```text
원문
요구사항·우선순위·AI 아키텍처·개발 범위·QA·릴리스를 관리했습니다.

교정
요구사항과 개발 우선순위를 정하고, AI 구조를 개발 범위와 QA 기준에 맞췄습니다. 릴리스 일정도 함께 관리했습니다.
```

## 6.2 슬래시 `/`

`승인/반려`, `기획/디자인/개발`처럼 선택지나 병렬 표기에만 사용한다. 산문에서는 조사로 풀어 쓴다.

## 6.3 화살표 `→`

도식과 프로세스에는 유용하다. 문장 본문에서는 인과관계를 말로 설명한다.

## 6.4 영어 혼용

### 유지

- API, SaaS, PRD, RAG, LLM처럼 업계에서 관행으로 굳은 용어
- 제품명과 기술 고유명사

### 교체 검토

- Scope → 범위
- Delivery → 인도, 출시, 구축 완료
- Alignment → 합의, 정렬
- Ownership → 책임 범위
- Validation → 검증

독자가 더 빨리 이해하는 쪽을 선택한다. 한 문서 안에서는 표기를 통일한다.

# 7. 이력서 특유의 AI 문장

## 7.1 `~해 온 사람입니다`

```text
원문
복잡한 산업 현장의 문제를 AI 제품으로 전환해 온 Product Manager입니다.

교정
산업안전·공공기관 AI 제품을 기획했습니다. 고객 요구사항을 제품 범위와 개발 우선순위로 정리하고, QA와 릴리스까지 담당했습니다.
```

한 줄 소개가 필요하면 다음처럼 짧게 쓴다.

```text
산업안전·공공기관 AI 제품을 기획하고 출시한 Product Manager
```

## 7.2 역량 자기평가

```text
원문
뛰어난 커뮤니케이션 역량으로 다양한 이해관계자를 조율했습니다.

교정
대학·연구기관·사내 개발팀의 산출물과 일정을 연차 계획에 맞춰 조율했습니다.
```

## 7.3 업무 목록형 불릿

```text
원문
- 요구사항 수집
- PRD 작성
- 개발팀 커뮤니케이션
- QA 진행

교정
- 고객 요구사항을 기능 우선순위와 PRD로 정리하고, 개발 중 예외 흐름과 QA 기준을 조율했습니다.
```

단, 채용 플랫폼의 구조화 필드에는 짧은 명사형 목록도 가능하다.

## 7.4 모든 프로젝트가 같은 공식

프로젝트마다 가장 강한 증거가 다르다.

- 문제 재정의가 강한 프로젝트
- 품질·출시가 강한 프로젝트
- 사업 성과가 강한 프로젝트
- 협업·리스크 관리가 강한 프로젝트

각 프로젝트에 같은 3단 구조를 억지로 채우지 않는다.

# 8. 포트폴리오 특유의 AI 문장

## 8.1 주제형 제목

```text
피할 제목
문제 정의
솔루션
시스템 구조
성과

권장 제목
반복 알림보다 더 큰 문제는 담당자가 사고를 다시 조립해야 한다는 점이었습니다.
이벤트가 아니라 현장에서 함께 대응할 `상황`을 제품 단위로 정했습니다.
AI는 가설을 제안하고, 최종 판단은 담당자가 내리게 했습니다.
```

제목이 너무 길면 결론과 부제를 나눈다.

## 8.2 페이지마다 같은 설명 틀

모든 페이지에 `배경–문제–해결–성과`를 반복하지 않는다. 페이지마다 질문 하나에 답한다.

- 왜 문제였는가?
- 무엇을 포기했는가?
- 어떤 기준으로 결정했는가?
- 사용자는 무엇을 보며 판단하는가?
- 무엇을 실제로 검증했는가?

## 8.3 화면 기능 설명

```text
원문
상황 상세 화면에서는 원인 가설, 유사 사례, 권장 조치를 제공합니다.

교정
담당자는 같은 화면에서 세 가지를 확인합니다. 왜 위험하다고 판단했는지, 과거에 어떻게 대응했는지, 지금 어떤 조치를 먼저 해야 하는지입니다.
```

## 8.4 회고의 상투어

```text
원문
사용자 중심 사고의 중요성을 배웠습니다.

교정
초기에는 알림 수를 줄이는 데 집중했습니다. 현장 인터뷰 후에는 담당자가 여러 신호를 한 사고로 묶는 시간이 더 큰 병목이라는 점을 확인했고, 제품 단위를 이벤트에서 상황으로 바꿨습니다.
```

# 9. IR·회사소개서 특유의 AI 문장

## 9.1 빈 슬로건

```text
원문
혁신적인 AI 기술로 산업의 새로운 가치를 창출합니다.

교정
작업자가 30분 동안 여러 시스템을 확인하던 안전 점검을 한 화면에서 처리합니다.
```

실제 수치가 없으면 과장하지 않는다.

```text
교정
여러 시스템에 흩어진 안전 정보를 한 화면에서 확인하고, 담당자가 조치 순서를 정할 수 있게 돕습니다.
```

## 9.2 기능 나열

```text
원문
OCR, LLM, RAG, 에이전트, 대시보드를 제공합니다.

교정
서류에서 필요한 값을 읽고, 근거 문장을 함께 보여줍니다. 담당자가 승인한 값만 기존 업무 시스템에 전달합니다.
```

## 9.3 제목과 근거 분리

```text
피할 제목
시장 기회

권장 제목
공공기관의 문서 자동화 수요는 PoC보다 운영·보안 단계에서 막힙니다.
```

제목 옆에는 기준 시점과 출처가 있는 수치 또는 고객 근거를 둔다.

## 9.4 계획과 실적 혼합

- `도입 예정`과 `도입 완료`
- `협의 중`과 `계약 체결`
- `목표 매출`과 `확정 매출`
- `잠재 고객`과 `유료 고객`

을 같은 단어로 쓰지 않는다.

# 10. 브랜드 소개 특유의 AI 문장

## 10.1 누구에게나 맞는 문장

```text
원문
우리는 더 나은 내일을 위한 새로운 경험을 만듭니다.

교정 방향
브랜드가 실제로 하는 행동과 고객 장면을 찾는다.
```

예시:

```text
주문이 몰리는 점심에도 매장이 놓치는 주문이 없도록, 결제부터 주방 전달까지 한 흐름으로 묶습니다.
```

## 10.2 감성어 뒤에 행동이 없음

```text
원문
고객의 일상에 따뜻한 변화를 더합니다.

교정
매일 아침 7시 전에 구운 빵을 매장과 드라이브스루에서 바로 받을 수 있게 준비합니다.
```

## 10.3 브랜드 목소리 평준화

원문에 짧은 문장, 유머, 고유 표현이 반복되면 무조건 기업 문체로 바꾸지 않는다. 어색한 번역투와 사실 불명확성만 교정하고, 의도적인 리듬은 남긴다.

# 11. 과잉 교정 방지

## 유지해야 할 것

- 업계에서 통용되는 정확한 전문용어
- 짧은 명사형 제목과 표 레이블
- 작성자의 의도적인 단문
- 브랜드의 고유한 말끝과 유머
- 역할을 정직하게 제한하는 `기여`, `참여`
- 실제로 필요한 병렬 구조

## 바꾸지 말아야 할 문장 예시

```text
매출 21% 증가
```

표 제목이나 성과 카드에서는 자연스럽다. 억지로 `매출이 21% 늘었습니다`로 바꿀 필요가 없다.

```text
문서 분류 → 필드 추출 → 담당자 검수 → ERP 반영
```

프로세스 도식에서는 화살표가 적절하다.

```text
AI Project Manager | B2G·Enterprise AI
```

헤드라인에서는 가운데점과 영어가 역할을 명확히 한다.

# 12. 빠른 진단 체크리스트

문서 전체를 읽고 다음 질문에 `예`가 세 개 이상이면 AI·번역투 교정이 필요하다.

- [ ] 첫 문장에 추상 명사가 세 개 이상 있다.
- [ ] `전환·연결·구조화·구체화`가 두 번 이상 반복된다.
- [ ] 문장 대부분이 30~50자로 비슷하다.
- [ ] 모든 불릿이 `~했습니다`로 끝난다.
- [ ] `·`가 한 문장에 네 번 이상 나온다.
- [ ] 실제 주체 없이 `설계·정의·마련`이 반복된다.
- [ ] 기술명이 사용자 문제보다 먼저 나온다.
- [ ] `리드·총괄·기여`의 범위를 설명할 수 없다.
- [ ] 결과 수치의 기간·분모·출처가 없다.
- [ ] 어떤 회사나 제품에도 붙일 수 있는 문장이 있다.
- [ ] 페이지 제목을 읽어도 결론을 알 수 없다.
- [ ] 소리 내어 읽으면 조사와 수식어 때문에 숨이 찬다.
