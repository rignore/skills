# 문서 유형별 한국어 편집 플레이북

## 0. 공통 원칙

같은 사실도 문서의 독자와 용도에 따라 길이, 어휘, 설명 순서가 달라진다. 이 문서는 문체만 바꾸는 것이 아니라 **무엇을 남기고 무엇을 줄일지** 결정하는 기준이다.

모든 유형에 공통으로 적용한다.

1. 독자가 가장 먼저 판단할 질문을 앞에 둔다.
2. 한 문단 또는 한 페이지에는 핵심 메시지를 하나만 둔다.
3. 자기평가보다 실제 행동·근거·결과를 쓴다.
4. 기술명은 문제 해결의 근거로 배치한다.
5. 확인되지 않은 수치와 인과관계는 삭제하거나 제한해서 쓴다.
6. 팀 성과와 개인 책임을 분리한다.
7. 문서가 단독으로 읽혀도 뜻이 통하게 한다.

# 1. 이력서

## 1.1 독자가 확인하는 것

- 어떤 직무의 사람인가
- 최근에 어떤 책임을 맡았는가
- 다른 후보와 무엇이 다른가
- 가장 강한 결과가 무엇인가
- 면접에서 더 확인할 가치가 있는가

## 1.2 권장 정보 순서

```text
이름·직무 헤드라인
→ 간단 소개 2~3문장
→ 핵심 역량 3개
→ 회사·직책·기간
→ 관련 프로젝트와 결과
→ 기술·도구
→ 학력·자격·링크
```

채용 플랫폼이 구조화 필드를 제공하면 해당 순서를 따르되, 가장 중요한 프로젝트가 첫 화면에 나오게 한다.

## 1.3 헤드라인

### 형식

```text
[목표 직무] | [주요 도메인 또는 반복 역량]
```

### 예시

- AI Product Manager | 산업·공공 AI 제품 기획·딜리버리
- B2B Product Manager | 운영 자동화·데이터 제품
- Product Designer | 금융 서비스·복잡한 업무 흐름

### 피할 표현

- 문제 해결형 인재
- 끊임없이 성장하는 PM
- 고객과 비즈니스를 연결하는 사람
- 혁신을 만드는 프로덕트 리더

헤드라인은 슬로건보다 검색 가능한 직무명과 경력 범위를 우선한다.

## 1.4 간단 소개

### 3문장 공식

1. 최근 경력과 직무 정체성
2. 반복해서 해결한 문제와 방식
3. 공식 결과 또는 대표 성과

### 예시

```text
산업안전·공공기관 AI 제품을 기획한 Product Manager입니다. 고객 요구사항을 제품 범위와 개발 우선순위로 정리하고, AI 결과를 담당자 검수와 후속 업무로 연결했습니다. 요구사항·시험 기준·결함 문서를 정비해 GS인증 1등급 획득에 기여했습니다.
```

### 편집 기준

- `~해 온`, `전환`, `연결`이 반복되면 실제 프로젝트로 바꾼다.
- 대표 프로젝트를 세 개 이상 나열하지 않는다.
- 자기평가 형용사를 쓰지 않는다.
- 250~400자 안팎을 기본으로 하되 플랫폼 제한을 따른다.

## 1.5 핵심 역량

역량은 성격이 아니라 반복 행동으로 쓴다.

```text
역량 제목
한두 문장으로 판단 방식과 대표 증거
```

### 예시

**고객 요구를 제품 범위로 정리**  
요청받은 기능부터 만들지 않고, 사용자 업무와 데이터 제약을 확인해 우선순위와 제외 범위를 정합니다.

**AI 품질과 사람 검수 설계**  
낮은 확신도와 예외 결과를 담당자 검토로 보내고, 수정 이력을 다음 평가 데이터로 남깁니다.

## 1.6 회사 설명

### 구성

```text
회사명 | 실제 직책 | 기간
제품·사업 범위와 내 책임을 1~2문장으로 설명
```

### 예시

```text
산업안전 AI 플랫폼과 공공기관 AI 구축에서 요구사항, 제품 범위, PRD, 개발 검토, QA와 릴리스를 담당했습니다. 정부 R&D에서는 대학·연구기관·개발팀의 산출물과 일정을 조율했습니다.
```

`전담`, `총괄`, `리드`보다 실제 책임을 먼저 쓴다.

## 1.7 프로젝트 불릿

### 기본 구조

- 첫 불릿: 문제 또는 핵심 판단
- 둘째 불릿: 개인의 실행·협업
- 셋째 불릿: 결과·검증

프로젝트가 짧으면 두 개로 줄인다.

### 예시

```text
- 센서와 AI 모델이 같은 원인의 알림을 반복해 담당자가 사고 관계를 직접 판단하던 문제를 정의했습니다.
- 이벤트를 현장 대응 단위의 `상황`으로 묶고, 원인 가설과 근거를 담당자 확인·조치 흐름에 연결했습니다.
- 기능 명세·시험 기준·결함 문서를 정비해 GS인증 1등급 획득에 기여했습니다.
```

### 한 불릿의 길이

- 한 가지 판단 또는 결과
- 가능하면 두 줄 이내
- 접속사로 네 행동을 붙이지 않음

## 1.8 결과 수치

### 좋은 형식

```text
2025년 2분기 기준, 신청 완료율 42%에서 55%로 13%p 개선
```

### 확인할 것

- 퍼센트와 퍼센트포인트 구분
- 비교 기간
- 분모
- 본인 기여
- 실측·목표·추정 구분

## 1.9 이력서에서 줄일 내용

- 장문의 프로젝트 배경
- 기능 목록 전체
- 익숙한 도구에 대한 설명
- 직무와 관련성이 낮은 초기 경험의 세부 업무
- 확인되지 않은 기대 매출
- 모든 교육 과정의 커리큘럼

# 2. 경력기술서

## 2.1 이력서와의 차이

이력서는 면접 여부를 빠르게 판단하는 문서다. 경력기술서는 다음을 설명한다.

- 어떤 상황과 제약이 있었는가
- 본인이 어디까지 결정했는가
- 누구와 어떤 쟁점을 조율했는가
- 일정·품질·리스크를 어떻게 관리했는가
- 결과와 한계는 무엇인가

## 2.2 권장 구조

```text
회사·직책·기간
→ 회사에서 맡은 역할
→ 대표 프로젝트
   1. 프로젝트 개요
   2. 문제와 제약
   3. 핵심 판단
   4. 개인 책임과 협업
   5. 실행·관리
   6. 결과·검증
   7. 한계·학습
```

## 2.3 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 기간 | 시작–종료 |
| 역할 | 실제 직책과 프로젝트 책임 |
| 팀 | 직군과 인원 |
| 대상 | 고객·사용자·시장 |
| 목표 | 해결할 문제와 성공 기준 |
| 결과 | 공식 결과·측정 결과·출시 상태 |

표에 모든 서술을 넣지 않는다. 비교 가능한 기본 정보만 넣는다.

## 2.4 문제와 제약

문제는 기능 부재가 아니라 사용자의 손실과 판단 부담으로 쓴다.

```text
피할 문장
상황 관리 기능이 없었습니다.

권장 문장
센서와 영상 모델이 같은 원인의 알림을 따로 보냈습니다. 담당자는 여러 알림이 한 사고인지 직접 판단해야 했고, 반복 알림 사이에서 긴급한 위험을 놓칠 수 있었습니다.
```

제약을 숨기지 않는다.

- 데이터 부족
- 보안·온프레미스
- 일정
- 기술 성숙도
- 고객의 기존 시스템
- 여러 기관의 이해관계

## 2.5 핵심 판단

`무엇을 만들었다`보다 `무엇을 선택하고 무엇을 포기했는가`를 쓴다.

```text
초기에는 탐지 임계값을 낮추는 방안을 검토했습니다. 알림은 줄지만 치명 위험을 놓칠 수 있어 제외했습니다. 대신 여러 탐지를 한 사고로 묶는 상황 레이어를 제품 범위에 넣었습니다.
```

## 2.6 개인 책임과 협업

### 나눠 쓸 것

- 직접 결정한 것
- 직접 작성한 산출물
- 공동 결정한 것
- 개발팀이 구현한 것
- 고객 또는 외부 기관이 승인한 것

### 예시

```text
이벤트·상황·조치 이력의 개념과 상태 전이는 직접 정의했습니다. AI 모델의 병합 알고리즘과 임계값은 AI 개발자와 공동 검토했고, 구현은 개발팀이 맡았습니다.
```

## 2.7 프로젝트 관리

`일정을 관리했다`보다 실제 방법을 쓴다.

- 선행 의존성을 정리
- 주간 마일스톤
- 변경 요청 영향도
- 결함 심각도와 재검증
- 인수 기준
- 의사결정 기록

```text
데이터 정제 이후에만 모델 평가가 가능했기 때문에 데이터·AI·화면 개발 순서를 따로 관리했습니다. 고객의 추가 요구는 출시 필수와 후속 범위로 나눠 5개월 일정 안에 맞췄습니다.
```

## 2.8 결과와 한계

결과는 다음을 구분한다.

- 실제 출시·사용
- 공식 인증·평가
- 내부 테스트
- 합성 데모
- 측정하지 않은 기대 효과

```text
GS인증 1등급은 공식 결과입니다. 반면 알림 감소율과 대응 시간은 운영 지표로 정의했지만 아직 실측하지 않았습니다.
```

# 3. 포트폴리오

## 3.1 독자의 사고 흐름

포트폴리오는 화면을 설명하는 문서가 아니라 판단을 따라가게 하는 문서다.

```text
왜 중요한 문제인가
→ 무엇을 확인했는가
→ 어떤 선택지가 있었는가
→ 왜 이 결정을 했는가
→ 실제로 무엇을 만들고 조율했는가
→ 무엇으로 검증했는가
→ 무엇을 다음에 바꿀 것인가
```

## 3.2 권장 전체 구성

1. 표지와 한 줄 포지셔닝
2. 핵심 역량 또는 일하는 방식
3. 대표 프로젝트 2~3개
4. 최근 공개 작업물
5. 공통 학습·일하는 방식
6. 연락처·링크

## 3.3 프로젝트 페이지 구성

### 최소 5페이지

1. 개요와 한 줄 결론
2. 사용자 문제와 근거
3. 선택지와 핵심 판단
4. 제품 구조·사용자 흐름·협업
5. 결과·한계·학습

복잡한 프로젝트는 6~8페이지까지 확장한다.

## 3.4 페이지 제목

제목만 읽어도 전체 이야기가 이어져야 한다.

```text
피할 제목
문제 정의
솔루션
기능
결과

권장 제목
반복 알림보다 더 큰 문제는 담당자가 사고를 다시 조립해야 한다는 점이었습니다.
이벤트가 아니라 현장에서 함께 대응할 `상황`을 제품 단위로 정했습니다.
AI는 가설을 제안하고, 최종 판단은 담당자가 내리게 했습니다.
요구사항과 시험 기준을 연결해 GS인증 1등급을 받았습니다.
```

## 3.5 한 페이지의 구성

```text
결론형 제목
→ 핵심 시각물 하나
→ 근거 2~3개
→ 상태·범위 주석
```

본문은 100~180자 안팎을 출발점으로 삼되, 근거가 필요하면 늘린다.

## 3.6 화면 캡션

```text
피할 캡션
상황 상세 화면

권장 캡션
담당자는 같은 화면에서 위험 판단 근거, 과거 유사 사례, 우선 조치를 확인합니다.
```

## 3.7 결과 페이지

결과와 해석을 분리한다.

| 구분 | 예시 |
|---|---|
| 공식 결과 | GS인증 1등급 |
| 운영 결과 | 처리시간 18% 단축 |
| 내부 검증 | 고정 시나리오 120건 중 106건 정확히 그룹화 |
| 합성 데모 | 자동 테스트 25건 통과 |
| 미측정 | 실제 고객의 업무시간 절감 |

## 3.8 회고

상투적인 교훈 대신 판단이 어떻게 바뀌었는지 쓴다.

```text
초기에는 알림 수를 줄이는 데 집중했습니다. 인터뷰 후에는 담당자가 여러 알림을 한 사고로 묶는 시간이 더 큰 병목이라는 점을 확인했습니다. 이후 제품의 중심 단위를 이벤트에서 상황으로 바꿨습니다.
```

# 4. IR·피치덱

## 4.1 먼저 구분할 자료

### 발표용 덱

- 발표자가 설명함
- 한 장의 문장이 짧아도 됨
- 시각물과 말의 역할을 나눔

### 배포용 덱

- 발표 없이 읽힘
- 주장·수치·주석이 페이지 안에서 완결
- 주요 용어와 데이터 기준을 설명

같은 덱을 쓸 경우 배포용 기준을 우선하고 발표 때 말로 덜어낸다.

## 4.2 초기·성장 단계 기본 구조

1. 한 줄 회사 정의
2. 고객 문제
3. 기존 대안과 한계
4. 제품·서비스
5. 사용 흐름 또는 기술 차별점
6. 시장과 고객군
7. 실제 사용·매출·계약·검증
8. 사업 모델
9. 시장 진입·성장 전략
10. 경쟁과 방어력
11. 팀
12. 재무·로드맵·투자 요청

회사의 단계와 투자자 질문에 따라 순서를 조정한다.

## 4.3 Executive Summary

첫 1~2장에 다음을 답한다.

- 누구의 어떤 문제를 푸는가
- 무엇이 기존과 다른가
- 현재 어디까지 검증했는가
- 어떻게 돈을 버는가
- 이번 투자로 무엇을 달성하는가

## 4.4 슬라이드 제목

```text
피할 제목
시장 규모
고객 문제
비즈니스 모델

권장 제목
```

## 4.5 숫자 쓰기

숫자 옆에 네 가지를 붙인다.

- 지표명
- 기간
- 비교 기준
- 출처 또는 산정 방식

```text
월간 활성 고객 142개사
2026년 6월 말 기준, 유료 계정의 월 1회 이상 사용
```

## 4.6 시장 문장

TAM·SAM·SOM 숫자보다 산정 논리를 먼저 검증한다.

```text
피할 문장
글로벌 시장은 2030년 50조 원으로 성장합니다.

권장 문장
1차 목표 고객은 연간 10만 장 이상 문서를 처리하는 국내 금융·공공기관 320곳입니다. 대상 기관 수와 평균 계약 규모를 기준으로 초기 시장을 추정했습니다.
```

## 4.7 경쟁과 차별점

형용사보다 고객의 선택 기준으로 비교한다.

- 정확도
- 처리 가능한 문서 범위
- 온프레미스
- 검수 화면
- 연동 기간
- 페이지당 비용
- 책임·감사 로그

`압도적`, `유일`, `최초`는 근거가 있을 때만 쓴다.

## 4.8 투자 요청

```text
피할 문장
글로벌 확장과 기술 고도화를 위해 30억 원을 투자받고자 합니다.

권장 문장
30억 원 중 18억 원은 문서 모델과 온프레미스 배포 인력 12명 채용에 사용합니다. 12개월 안에 금융 문서팩 3종을 출시하고 유료 고객 40곳을 확보하는 것이 목표입니다.
```

계획은 목표로 표시하고 확정 성과처럼 쓰지 않는다.

# 5. 회사소개서

## 5.1 회사소개서의 유형

| 유형 | 독자의 질문 |
|---|---|
| 일반 회사소개 | 이 회사는 무엇을 하고 믿을 만한가 |
| 영업용 소개서 | 내 문제를 어떻게 해결하고 도입은 어떻게 하는가 |
| 제휴 제안서 | 함께하면 어떤 가치와 역할이 생기는가 |
| 채용 브랜드 | 어떤 문제를 어떤 방식으로 푸는 팀인가 |

목적이 다르면 같은 회사 설명을 그대로 쓰지 않는다.

## 5.2 일반 회사소개 기본 구조

1. 한 줄 회사 정의
2. 고객과 문제
3. 제품·서비스 영역
4. 핵심 역량·기술
5. 고객·성과·인증
6. 도입·협업 방식
7. 팀·연혁
8. 연락처

연혁을 앞에 두지 않는다. 독자가 회사를 이해한 뒤 신뢰 근거로 배치한다.

## 5.3 영업용 문장

```text
피할 문장
당사는 차별화된 기술력을 바탕으로 고객 맞춤형 솔루션을 제공합니다.

권장 문장
고객 문서 100건을 먼저 분석해 자동 처리 필드와 사람 검수 항목을 나눕니다. 검증이 끝나면 기존 ERP와 API로 연결합니다.
```

## 5.4 고객 사례

```text
고객 상황
→ 적용 범위
→ 기간
→ 결과
→ 한계·다음 확장
```

고객명 비공개 시 업종·규모·업무를 설명한다.

# 6. 제품·서비스 소개서

## 6.1 첫 페이지가 답할 것

- 누구를 위한 제품인가
- 어떤 순간에 필요한가
- 사용 후 무엇이 달라지는가

```text
예시
여러 문서에서 같은 고객 정보를 다시 입력하는 보험 심사팀을 위한 문서 자동화 도구입니다. 서류에서 필요한 값을 뽑고, 낮은 신뢰도의 결과만 담당자에게 보냅니다.
```

## 6.2 기능 설명 공식

```text
사용자 상황
→ 사용자가 하는 행동
→ 제품이 처리하는 일
→ 사용자가 얻는 결과
```

```text
피할 문장
AI 기반 자동 분류 기능을 제공합니다.

권장 문장
담당자가 문서 유형을 먼저 고르지 않아도 됩니다. 시스템이 신청서·증빙서류·계약서를 구분하고 각 문서에 맞는 검수 화면을 엽니다.
```

## 6.3 기술 설명

기술명은 다음 중 하나를 증명할 때만 쓴다.

- 더 정확함
- 더 빠름
- 비용이 낮음
- 보안 요구를 충족
- 운영·검수가 쉬움
- 새로운 범위를 처리

## 6.4 CTA

다음 행동을 구체적으로 쓴다.

- 샘플 문서 10건으로 정확도 확인하기
- 30분 제품 시연 신청하기
- 도입 범위 상담하기

`문의하기`, `자세히 보기`만 쓰지 않는다.

# 7. 브랜드 소개

## 7.1 브랜드 문장의 역할

브랜드 문장은 회사 설명을 감성적으로 포장하는 문장이 아니다. 고객에게 반복해서 지킬 약속과 그 약속을 지키는 방식을 보여준다.

## 7.2 브랜드 핵심 문장

다음 질문에 답한다.

1. 누구의 어떤 순간을 바꾸는가
2. 어떤 태도로 일하는가
3. 무엇을 반복해서 제공하는가
4. 어떤 증거가 있는가

## 7.3 추상 슬로건 교정

```text
원문
기술로 더 나은 세상을 연결합니다.

교정 방향
어떤 기술이 누구의 어떤 일을 줄이는지 확인한다.
```

예시:

```text
현장 작업자가 위험 신호를 놓치지 않도록 센서·영상·작업 기록을 한 상황으로 묶습니다.
```

## 7.4 말투

| 브랜드 성격 | 문체 |
|---|---|
| 신뢰·금융·공공 | 짧고 정확한 문장, 조건과 책임 명확화 |
| 생산성·B2B | 구체적인 업무 장면과 시간·단계 변화 |
| 라이프스타일 | 감각적 문장을 허용하되 제품 경험으로 뒷받침 |
| 기술·딥테크 | 기술보다 해결하는 제약과 검증 근거를 먼저 제시 |

## 7.5 브랜드 개성 보존

- 의도적인 반복은 남긴다.
- 짧은 구어적 표현이 브랜드답다면 유지한다.
- 모든 문장을 정중한 공문체로 만들지 않는다.
- 다만 이해를 방해하는 번역투, 근거 없는 과장, 표기 혼용은 교정한다.

# 8. 문서 간 재사용 규칙

같은 프로젝트 사실을 문서별로 다르게 압축한다.

## 이력서

```text
반복 탐지 이벤트를 현장 대응 단위의 `상황`으로 묶고, AI 분석을 담당자 확인·조치 흐름에 연결했습니다.
```

## 경력기술서

```text
센서와 AI 모델이 같은 원인의 이벤트를 따로 보내 담당자가 관계를 직접 판단해야 했습니다. 탐지 민감도를 낮추면 치명 위험을 놓칠 수 있어, 이벤트를 시간·장소·설비 맥락으로 묶는 상황 레이어를 제품 범위에 넣었습니다.
```

## 포트폴리오 제목

```text
이벤트가 아니라 현장에서 함께 대응할 `상황`을 제품 단위로 정했습니다.
```

## 제품 소개

```text
같은 사고에서 발생한 여러 알림을 하나의 상황으로 모아 보여줍니다.
```

## IR

```text
반복 알림을 줄이면서 치명 위험은 놓치지 않도록, 탐지 이후에 상황 구성·검수 레이어를 추가했습니다.
```

사실은 같지만 독자의 질문과 정보 밀도가 다르다.

# 9. 최종 선택 기준

문장을 고른 뒤 다음을 확인한다.

| 질문 | 이력서 | 경력기술서 | 포트폴리오 | IR·소개서 |
|---|---|---|---|---|
| 직무·제품이 바로 보이는가 | 필수 | 필수 | 필수 | 필수 |
| 배경 설명이 충분한가 | 최소 | 상세 | 페이지별 | 독자 질문 중심 |
| 개인 책임이 보이는가 | 필수 | 상세 | 필수 | 팀·회사 책임 중심 |
| 결과 근거가 있는가 | 필수 | 상세 | 상태 구분 | 수치·출처 필수 |
| 한계가 보이는가 | 선택 | 권장 | 필수 | 리스크·가정으로 표시 |
| 문장 자체가 독립적인가 | 필수 | 필수 | 제목+시각물 | 발표 없이도 이해 |
