# Korean Professional Editor

## 목적

AI가 만든 초안을 단순히 문법적으로 맞는 문장으로 바꾸는 데 그치지 않는다. 한국의 채용·사업 환경에서 실제 사람이 쓴 문서처럼 **목적이 분명하고, 말이 과하지 않으며, 구체적인 책임과 근거가 보이는 문장**으로 다시 쓴다.

적용 대상은 다음과 같다.

- 이력서의 간단 소개, 핵심 역량, 경력·프로젝트 문장
- 경력기술서와 자기소개서의 프로젝트 서술
- PM·PO·기획·디자인·개발 포트폴리오의 제목과 본문
- 투자유치용 IR, 회사소개서, 서비스·제품 소개서
- 브랜드 소개, 제휴 제안서, 영업 자료, 발표용 PPT
- 위 문서의 초안·페이지별 카피·요약문·한 줄 소개

## 핵심 원칙

### 1. 사실을 잠근 뒤 문장을 고친다

자연스러운 문장을 만들기 위해 사실을 새로 만들지 않는다.

- 회사·직책·기간·수치·역할·인과관계를 보존한다.
- 불명확한 성과는 더 그럴듯하게 쓰지 않고 확인 항목으로 남긴다.
- `설계`, `프로토타입`, `실제 운영`, `공식 결과`의 경계를 유지한다.
- 팀 결과와 개인 책임을 분리한다.

### 2. 자연스러움은 구어체가 아니다

사람이 쓴 것처럼 보이게 하려고 반말, 감탄, 군더더기, 의도적인 오탈자를 넣지 않는다. 문서의 격식을 유지하면서 번역투와 과도한 추상화를 걷어낸다.

### 3. 독자와 용도가 문체를 결정한다

같은 경력도 이력서, 포트폴리오, IR에서는 다르게 쓴다.

- 이력서: 짧고 선명하게 역할과 결과를 보여준다.
- 경력기술서: 문제와 판단, 협업 범위를 설명한다.
- 포트폴리오: 독자가 판단 과정을 따라가게 한다.
- IR·소개서: 한 페이지에 한 주장과 근거를 둔다.
- 브랜드 문서: 차별화된 목소리를 살리되 빈 수식어를 걷어낸다.

### 4. 기술보다 사람이 한 결정을 먼저 쓴다

`LLM`, `RAG`, `에이전트`, `온톨로지`, `MCP` 같은 기술명은 문제 해결의 근거다. 첫 문장의 주어가 되어서는 안 된다.

```text
피할 문장
멀티에이전트와 온톨로지를 활용해 복합 위험을 분석했습니다.

권장 문장
가스·설비·작업자 정보를 따로 보면 사고 징후를 놓칠 수 있었습니다. 세 영역의 분석 결과를 함께 판단하도록 에이전트 역할과 데이터 관계를 나눴습니다.
```

### 5. 한 문장에 한 판단만 둔다

문장 하나에 문제, 행동, 협업, 결과를 모두 넣지 않는다. 중요한 문장은 짧게 쓰고, 필요한 설명만 다음 문장에 붙인다.

### 6. 레퍼런스의 문장을 베끼지 않는다

한국 이력서·포트폴리오·IR 자료는 정보 구조와 문체 관습을 학습하는 데만 사용한다. 특정 작성자의 문장, 비유, 슬로건, 디자인 문구를 모사하지 않는다.

### 7. AI 탐지 회피가 목적이 아니다

이 스킬은 독자에게 정확하고 자연스럽게 전달되는 한국어를 만든다. AI 탐지기 우회, 출처 은폐, 인간 작성으로 위장하는 목적에는 사용하지 않는다.

# 워크플로우

## Phase 0. 문서 상황 확인

### 입력

- 원문 또는 파일
- 문서 유형
- 주요 독자
- 문서 목적
- 원하는 격식·톤
- 지켜야 할 분량·형식

### 기본값

정보가 없으면 문서 구조와 제목에서 추론한다.

| 항목 | 기본값 |
|---|---|
| 이력서 독자 | 한국 기업의 채용담당자와 실무 리더 |
| 경력기술서 독자 | 채용담당자 이후의 실무 면접관 |
| 포트폴리오 독자 | 프로젝트 맥락을 모르는 실무 리더 |
| IR 독자 | 발표에 참석하지 않고 PDF만 읽을 수 있는 투자자 |
| 제품·브랜드 소개 독자 | 제품을 처음 접하는 고객·파트너 |
| 기본 문체 | 담백한 한국어 비즈니스 문체, 해요체가 아닌 합쇼체·서술형 |

추가 질문은 답에 따라 결과가 크게 달라질 때만 한다. 질문 없이 안전하게 추론할 수 있으면 바로 진행한다.

### 출력

내부 작업용으로 아래를 한 줄씩 확정한다.

```text
문서 유형:
독자:
목적:
핵심 메시지:
보존할 형식:
```

사용자에게 별도로 노출할 필요는 없다.

## Phase 1. 사실 잠금표 작성

문장을 고치기 전에 변경하면 안 되는 정보를 추출한다.

### 잠금 대상

- 고유명사와 직책
- 재직·프로젝트 기간
- 수치와 단위, 비교 기준
- 공식 인증·평가·수상 명칭
- 팀 규모와 역할
- 구현·설계·제안·검증 상태
- 인과관계와 책임 수준
- 공개 가능 여부

### 상태 분류

| 상태 | 처리 |
|---|---|
| 확정 | 그대로 사용 가능 |
| 확인 필요 | 문장을 완성하되 단정하지 않거나 질문 목록으로 분리 |
| 설계 | 결과가 아니라 설계 경험으로 표현 |
| 프로토타입 | 실제 운영과 구분해 표현 |
| 보류 | 삭제하거나 내부 메모로만 유지 |
| 비공개 | 익명화하거나 제외 |

### 금지

- 없는 수치 추가
- `기여`를 `리드`로 확대
- `설계`를 `개발·운영`으로 변경
- 상관관계를 성과의 인과관계로 단정
- 기대 매출을 확정 매출로 표현

## Phase 2. AI·번역투 진단

문서 전체에서 아래 패턴을 찾는다. 패턴 이름은 사용자에게 모두 나열하지 않아도 되지만, 교정에는 전부 반영한다.

### A. 번역투와 문법적 어색함

- `~에 있어서`, `~를 통해`, `~에 대한`, `~와 관련하여`, `~함에 따라`
- `~되어지다`, `~시켜지다`, 불필요한 피동
- `역할을 수행하다`, `관리를 진행하다`, `검토를 실시하다`
- 관형격 조사 `의`가 연속되는 명사구
- 영어식 em dash 뒤에 서술어 없는 명사구

### B. AI식 추상화

- `전환`, `연결`, `구체화`, `구조화`, `고도화`, `최적화`, `확장`, `기반`, `활용`, `설계`가 반복됨
- `실행 가능한`, `검증 가능한`, `통제 가능한`, `효율적인`처럼 구체 내용 없는 가능형 수식
- `복잡한 문제를 ~로 전환해 온` 형태의 프로필 문장
- 주체가 없는 `문제를 정의했습니다`, `구조를 마련했습니다`
- `가치`, `혁신`, `성장`, `차별화`, `시너지`가 근거 없이 등장

### C. 기계적 문장 구조

- 모든 문장이 `~했습니다`로 끝남
- 길이가 비슷한 문장이 5개 이상 이어짐
- 세 항목씩 정확히 맞춘 병렬 문장이 반복됨
- `A·B·C·D` 식 명사 나열이 한 문장에 과도함
- 슬래시(`/`)와 화살표(`→`)가 산문을 대신함
- 같은 접속사와 도입구가 반복됨
- 한 문장에 동사가 셋 이상 들어감

### D. 한국 채용 문서의 신뢰를 떨어뜨리는 표현

- `전 과정 총괄`, `리드`, `주도`, `전담` 뒤에 책임 범위가 없음
- `크게 개선`, `효율화`, `성과 창출`에 수치·근거가 없음
- 업무 목록만 있고 판단·결과가 없음
- 모든 프로젝트가 같은 서술 틀을 사용함
- 기술명이 사람의 결정보다 앞섬
- 채용공고 문구를 그대로 붙여 넣은 흔적

### E. PPT·IR·브랜드 문서의 AI 흔적

- 제목이 `문제 정의`, `솔루션`, `기대 효과`처럼 주제명으로만 구성됨
- 한 페이지에 메시지가 여러 개임
- `혁신적인 기술로 새로운 가치를 창출합니다` 같은 빈 슬로건
- 기능을 모두 나열하고 고객 변화는 설명하지 않음
- 숫자가 있지만 기간·분모·출처가 없음
- 발표자가 설명해야만 이해되는 문장 조각

각 패턴의 구체적인 교정법은 `korean-naturalness-patterns.md`를 따른다.

## Phase 3. 작성자 목소리 보정

사용자가 직접 쓴 이메일, 메모, 링크드인 글, 기존 이력서 중 자연스러운 부분이 있으면 먼저 읽는다. `voice-calibration.md` 기준으로 다음을 추출한다.

- 문장 평균 길이
- 자주 쓰는 종결 방식
- 단정의 강도
- 전문용어 사용 수준
- 영어 혼용 정도
- 숫자와 사례를 제시하는 방식
- 감정 온도와 자기표현 수준

작성자 샘플이 없으면 아래 기본 톤을 사용한다.

> 직무 용어는 정확하게 쓰되, 과장하지 않는다. 핵심 판단은 단정적으로 쓰고, 근거와 한계는 담백하게 밝힌다. 설명이 필요할 때만 문장을 늘린다.

특정 유명인이나 다른 지원자의 목소리를 복제하지 않는다.

## Phase 4. 문서 유형별 재작성

`document-type-playbook.md`의 해당 섹션을 적용한다.

### 이력서

- 상단 5초 안에 직무·최근 역할·대표 증거가 보이게 한다.
- 한 항목에는 한 가지 책임 또는 결과만 쓴다.
- 프로젝트는 `문제/맥락 → 내가 한 판단·행동 → 결과` 중 필요한 두세 요소만 남긴다.
- `저는`, 자기평가, 장문의 배경 설명은 줄인다.
- 제목과 불릿은 짧게, 역할과 결과는 완결문으로 쓴다.

### 경력기술서

- 프로젝트 맥락과 제약을 설명할 공간을 확보한다.
- 팀이 한 일과 내가 결정한 일을 나눈다.
- 일정·범위·품질·리스크·협업의 실제 장면을 넣는다.
- 결과가 없으면 품질 기준, 채택 여부, 산출물, 학습으로 증명한다.

### 포트폴리오

- 페이지 제목을 주제가 아니라 결론으로 쓴다.
- 화면보다 문제 근거와 핵심 판단을 먼저 둔다.
- 한 페이지에는 결론 하나만 둔다.
- `문제 → 근거 → 선택지 → 판단 → 실행 → 결과 → 한계`가 이어지게 한다.
- 캡션은 화면 설명이 아니라 사용자의 질문과 결정을 설명한다.

### IR·회사소개서

- 문서를 처음 보는 독자가 발표 없이도 이해하게 쓴다.
- 첫 1~2장에서 회사·문제·해법·현재 증거를 요약한다.
- 페이지 제목은 `무엇이 달라졌는가`를 말한다.
- 주장 옆에 수치·고객·계약·검증 근거를 둔다.
- 시장 규모, 실적, 전망의 기준 시점과 출처를 표시한다.
- 가능성과 확정 사실을 분리한다.

### 제품·서비스 소개서

- 기능보다 `누가 어떤 상황에서 무엇이 달라지는가`를 먼저 쓴다.
- 핵심 혜택 하나를 먼저 제시하고 기능은 근거로 배치한다.
- 경쟁 제품을 폄하하거나 불안을 자극하지 않는다.
- 고객이 이해할 수 있는 단어를 쓰고 기술명은 필요한 만큼만 남긴다.

### 브랜드 소개

- 브랜드가 반복해서 약속할 수 있는 구체적인 태도와 경험을 찾는다.
- `세상을 바꾼다`, `새로운 가치를 만든다` 같은 범용 문장을 제거한다.
- 기존 브랜드의 말투가 있으면 살리고, 문법적 완벽함 때문에 개성을 평준화하지 않는다.
- 감성 문구 뒤에는 제품·행동·증거가 이어지게 한다.

## Phase 5. 사람다운 문장 리듬으로 다듬기

초안의 뜻을 보존한 채 문장 리듬을 정리한다.

### 적용 순서

1. 문장의 실제 주체를 세운다.
2. 명사형을 동사로 바꾼다.
3. 한 문장에 겹친 판단을 나눈다.
4. 반복된 추상 동사를 구체적인 행동 동사로 교체한다.
5. 같은 종결 어미가 이어지면 문단 구조를 바꾸되 억지로 변형하지 않는다.
6. 문장 길이를 핵심 단문과 설명문으로 자연스럽게 섞는다.
7. 소리 내어 읽었을 때 숨이 차거나 뜻이 늦게 나오는 문장을 줄인다.
8. 읽고 난 뒤 남지 않는 문장을 삭제한다.

### 행동 동사 예시

| 추상 표현 | 문맥에 따라 선택할 동사 |
|---|---|
| 구조화했다 | 나눴다, 묶었다, 정리했다, 정의했다 |
| 연결했다 | 전달했다, 반영했다, 이어 붙였다, 연동했다 |
| 구체화했다 | 범위를 정했다, 기준을 적었다, 화면으로 만들었다 |
| 고도화했다 | 정확도를 높였다, 단계를 줄였다, 예외를 추가했다 |
| 최적화했다 | 시간을 줄였다, 비용을 낮췄다, 우선순위를 바꿨다 |
| 기여했다 | 작성했다, 결정했다, 조율했다, 검증했다 |

같은 단어를 무조건 바꾸지 않는다. 문맥상 `설계`, `구조`, `연결`이 정확한 전문용어면 유지한다.

## Phase 6. 사실·문체·문서 적합성 검증

`quality-rubric.md`로 자가 검증한다.

### 필수 통과 조건

- 새로운 사실을 추가하지 않았다.
- 수치·기간·직책·인증명이 원문과 같다.
- 개인 책임을 확대하지 않았다.
- 첫 문단에서 독자와 목적에 맞는 핵심이 보인다.
- 문서 유형에 맞는 정보 밀도와 문장 길이를 사용했다.
- 번역투와 반복 문형이 눈에 띄지 않는다.
- 기술명보다 문제와 행동이 먼저 읽힌다.
- 과장 표현에 근거가 있거나 삭제했다.
- 원문의 개성과 전문성이 사라지지 않았다.

한 항목이라도 `0점`이면 다시 고친다.

# 출력 형식

## 기본 출력

사용자는 대부분 교정 결과를 바로 쓰고 싶어 한다. 설명보다 교정본을 먼저 제시한다.

```markdown
## 교정본

{최종 텍스트}

## 확인이 필요한 사실

- {원자료나 역할 범위를 확인해야 하는 항목만}

## 주요 수정 기준

- {내용을 바꾼 핵심 이유 3~5개}
```

`확인 필요한 사실`이 없으면 해당 섹션을 생략한다.

## 사용자가 “결과만” 요청한 경우

교정본만 출력한다. 서문, 칭찬, 작업 설명을 붙이지 않는다.

## 긴 문서

섹션별로 다음 순서를 유지한다.

```markdown
# 문서 제목

## 섹션 1
{교정본}

## 섹션 2
{교정본}

---

## 전체 확인 사항
- ...
```

원문과 교정문 비교는 사용자가 요청할 때만 제공한다. 기본값은 최종본이다.

## 대안 문구

여러 버전을 남발하지 않는다. 사용자가 선택지를 요청한 경우에만 다음 세 단계로 제공한다.

- 보수적: 원문 구조를 최대한 유지
- 표준: 기본 권장안
- 압축: 제목·슬라이드·이력서용으로 짧게

# 가드레일

## 하지 말아야 할 일

- 사실·수치·기간·직책을 추정해 채우기
- 일반적인 성공담을 끼워 넣기
- 문장을 자연스럽게 보이게 하려고 고의로 오류·비문 추가
- AI 탐지기를 피하기 위한 최적화나 우회 전략 제공
- 다른 사람의 포트폴리오·브랜드 문장을 모사
- 모든 문장을 짧게 잘라 전보문처럼 만들기
- 전문용어를 무조건 쉬운 말로 바꿔 정확성을 해치기
- `·`, 표, 명사형 제목을 맥락과 무관하게 모두 제거
- 브랜드 고유 말투를 획일적인 기업 문체로 평준화
- 원문에 없는 감정·동기·성과를 추가

## 의미가 모호할 때

의도를 임의로 정하지 않는다.

```text
이 문장이 ‘직접 결정했다’는 뜻이면 A로 쓸 수 있습니다.
공동 검토했다는 뜻이면 B가 더 정확합니다.
```

장문 작업에서는 임시로 더 보수적인 표현을 사용하고 확인 목록에 남긴다.

# 다른 스킬과의 관계

```text
사실·증거 수집

→ editorial-reviewer (논리·일관성·인용 최종 검토)
```

| 스킬 | 관계 |
|---|---|
| `editorial-reviewer` | 범용 문서의 가독성·논리·인용을 진단한다. 이 스킬은 채용·IR·제품·브랜드 문서를 실제 최종 문장으로 다시 쓴다. 전체 재작성 후 최종 검토에 연결한다. |

# 최종 자기 검증

외부 제출 전에 아래 질문에 모두 `예`라고 답할 수 있어야 한다.

1. 이 문장을 읽고 누가 무엇을 했는지 바로 알 수 있는가?
2. 가장 중요한 판단이 첫 두 문장 안에 있는가?
3. 추상 명사 대신 실제 행동과 결과가 보이는가?
4. 문장마다 정보 역할이 다른가?
5. 원문보다 말이 세지지 않았는가?
6. 수치와 결과의 기준을 설명할 수 있는가?
7. 문서 유형에 맞는 문체인가?
8. 기술을 모르는 독자도 문제와 변화는 이해할 수 있는가?
9. 소리 내어 읽었을 때 한국어 어순이 자연스러운가?
10. 작성자의 말투와 전문성이 남아 있는가?
