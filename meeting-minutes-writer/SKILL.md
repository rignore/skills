# Meeting Minutes Writer

STT(Speech-to-Text) 변환 텍스트를 전문 회의록으로 변환하는 스킬.

**핵심 가치:** 음성 녹취의 노이즈(오변환·잡담·발화 중복)를 제거하고, 의사결정과 액션 아이템이 명확히 추적 가능한 문서를 만든다.

---

## Phase 0 — 시작 전 확인

스킬 실행 전 아래 항목을 확인한다. 누락 시 가정 기반으로 진행하되 `⚠️ 가정` 형식으로 명시한다.

### 필수 입력

| 항목 | 수집 방법 | 부재 시 처리 |
|------|----------|------------|
| STT 텍스트 원문 | 파일 업로드 또는 텍스트 붙여넣기 | **없으면 진행 불가** — 파일 요청 |
| 회의 일시 | 사용자 제공 또는 파일명·메타데이터 추정 | `⚠️ 가정: 일시 불명확` 처리 |
| 참석자 목록 | 사용자 제공 또는 STT 화자 레이블 추출 | 텍스트 내 발화자명으로 추정 |
| 산출물 형식 | 사용자 지정 | 기본값: Notion 페이지 |

### 선택 입력 (제공 시 품질 향상)

- 회의 주제·목적 (사전 안건)
- 화자 레이블 매핑 (`화자1 = 김철수` 형태)
- 특수 용어·약어 사전 (제품명, 내부 코드명 등)

## Phase 1 — STT 원문 분석 & 전처리

### 1-1. 파일 읽기

- 업로드된 파일이 있으면 `/mnt/skills/public/file-reading/SKILL.md`를 참조하여 올바른 방식으로 읽는다.
- 텍스트가 붙여넣기된 경우 그대로 사용한다.

### 1-2. STT 오류 자동 보정

STT 변환 과정에서 발생하는 오류 패턴을 맥락 기반으로 보정한다.

| 오류 유형 | 예시 | 보정 기준 |
|----------|------|----------|
| 고유명사 오변환 | "세이프코어" → "SafeCore" | 전후 맥락 + 업계 용어 기반 |
| 동음이의어 | "회사" vs "환자" | 문서 주제·화자 맥락 |
| 끊긴 문장 | "그러니까... 음... 결국에는" | 의미 단위로 재조합 |
| 발화 중복 | 같은 말을 반복한 부분 | 의미 중복 제거, 1회만 유지 |
| 숫자·단위 오변환 | "삼십 프로" → "30%" | 숫자 표현 통일 |

**보정 원칙:**
- 원문 사실은 변경하지 않는다. 발화 내용의 *의미*는 보존, *표현*만 교정.
- 불확실한 보정은 `[추정: ~]` 태그로 표시하고 회의록 말미 주석에 모은다.
- 명확히 알아들을 수 없는 부분은 `[청취 불가]`로 표시한다.

### 1-3. 구조 파악

STT 원문을 읽고 아래 항목을 내부적으로 파악한다 (사용자에게 서술하지 않음):

- 주요 안건 수 및 전환 시점
- 발화자 수 및 식별 가능 여부
- 결정된 사항과 미결 사항 구분
- 액션 아이템 후보 (담당자·기한 포함 여부)
- 시각화가 유효한 데이터 (비교·숫자·일정 등)

## Phase 2 — 회의록 작성

### 2-1. 회의록 구조

아래 섹션 순서를 기본 템플릿으로 사용한다. 해당 내용이 없는 섹션은 생략한다.

```
1. 회의 개요
2. 회의 목적 및 배경
3. 안건별 주요 논의
4. 결정 사항
5. 미결 사항 / 보류
6. 후속 조치 (Action Items)
7. 다음 회의 예정 (해당 시)
8. 부록 (보정 주석, 참고 자료)
```

---

### 2-2. 섹션별 작성 가이드

#### § 1. 회의 개요

```
일시: YYYY-MM-DD HH:MM ~ HH:MM (총 N시간 M분)
장소 / 형태: [오프라인 장소명 또는 화상회의 플랫폼]
참석자: [이름 (직책/역할)] — 화자 레이블 매핑이 있으면 적용
작성자: [회의록 작성 도구 또는 담당자]
```

#### § 2. 회의 목적 및 배경

- 이 회의가 왜 열렸는지 1~3문장으로 서술.
- 사전 안건이 제공된 경우 목록으로 표시.

#### § 3. 안건별 주요 논의

안건마다 아래 형식을 반복한다:

```markdown
### 안건 N: [안건명]

**핵심 논점**
- [논점 1]: [주요 내용]
- [논점 2]: [주요 내용]

**참석자 주요 의견**
| 발화자 | 주요 입장 / 발언 요약 |
|--------|---------------------|
| 홍길동 | ~ |
| 김철수 | ~ |

**논의 결과** (결정됐으면 § 4로, 미결이면 § 5로 이관)
```

**작성 규칙:**
- 발화를 그대로 옮기지 않는다. **핵심 주장·근거·수치**만 압축.
- 감탄사·필러("음", "어", "그러니까") 제거.
- 구어체를 문어체로 전환. ("해야 할 것 같아요" → "검토 필요")
- **중요한 수치·일정·이름은 볼드체**로 강조.
- 비교·요약에 유효한 데이터가 있으면 Markdown 표로 정리.

#### § 4. 결정 사항

```markdown
| # | 결정 내용 | 결정 근거 | 관련 안건 |
|---|----------|----------|---------|
| 1 | ~로 확정 | ~ | 안건 N |
```

- 결정된 사항만 포함. 논의 중인 것은 § 5로.
- 명확한 **행동 지침**이 있으면 결정 내용에 포함.

#### § 5. 미결 사항 / 보류

```markdown
| # | 사안 | 미결 이유 | 다음 단계 |
|---|------|---------|---------|
| 1 | ~    | 데이터 부족 / 이해관계자 협의 필요 / 추가 검토 | ~ |
```

#### § 6. 후속 조치 (Action Items)

```markdown
| # | 내용 | 담당자 | 마감일 | 우선순위 |
|---|------|--------|--------|---------|
| 1 | ~    | 홍길동  | 2026-06-10 | High |
```

- 담당자·마감일이 STT에서 언급된 경우 반드시 추출.
- "다음 주까지" 등 상대 날짜는 회의 일시 기준으로 절대 날짜 변환.
- 언급이 없으면 `미지정`으로 표시 (임의 날짜 생성 금지).
- 우선순위는 회의에서 강조 빈도·긴급성 표현 기준으로 High / Mid / Low 부여.

#### § 7. 다음 회의 예정

- 언급된 경우만 작성. 일시·장소·주요 안건 예고.

#### § 8. 부록

- **STT 보정 주석**: `[추정: ~]` 태그로 표시된 항목 목록.
- **청취 불가 구간**: `[청취 불가]` 발생 위치와 전후 문맥 요약.
- 2개 이하면 부록 섹션 생략 가능.

### 2-3. 시각화 판단 기준

아래 조건 중 하나라도 해당하면 Markdown 표 또는 간단한 구조 다이어그램으로 시각화한다:

| 조건 | 시각화 형태 |
|------|-----------|
| 3개 이상 옵션 비교 | 비교 표 |
| 일정·마일스톤 논의 | 간트 형태 표 (Mermaid gantt 또는 표) |
| 수치·지표 변화 언급 | 수치 비교 표 |
| 프로세스·플로우 설명 | Mermaid flowchart LR |
| 역할·책임 분담 | 역할 표 |

## Phase 2.5 — 가독성 검토 (Editorial Review Gate)

Notion 업로드 전 `editorial-reviewer` 스킬 기준으로 초안을 검토한다. **이 단계를 통과한 내용만 Notion에 올라간다.**

### 검토 범위 (회의록 특화)

회의록은 일반 문서 대비 아래 항목에 집중 검토한다:

| 우선순위 | 검토 항목 | 회의록 특화 이유 |
|---------|---------|--------------|
| 🔴 차단 | 수치·날짜·담당자 불일치 | Action Item 오기재 시 실제 업무 오류 발생 |
| 🔴 차단 | 결정 사항 vs 미결 사항 혼재 | 잘못 분류된 결정은 후속 혼선을 낳음 |
| 🟡 보완 | AI 투 문장 (이중 피동·번역투·명사화) | STT 보정 + AI 생성 특성상 높은 빈도로 발생 |
| 🟡 보완 | 구어체 잔존 ("그러니까", "아무튼" 등) | 전처리 단계에서 놓친 필러 최종 점검 |
| 🟡 보완 | 용어 일관성 | 동일 인물·기능·안건을 다르게 지칭하는 경우 |
| 🟡 보완 | 상대 날짜 잔존 ("다음 주", "어제") | 절대 날짜 변환 누락 최종 확인 |
| *(생략)* | 자기완결성·구조 정합성 | 회의록은 내부 참석자 대상이므로 강도 완화 |

### 검토 출력 형식

검토 결과는 사용자에게 별도로 표시하지 않는다. **내부 처리 후 수정된 최종본을 바로 Notion에 업로드**한다.
업로드 완료 후 아래 요약만 1블록으로 보고한다:

```
✅ 가독성 검토 완료 — Notion 업로드 진행
- 🔴 수정: N건 / 🟡 자동 반영: N건
- 수정 내용: [항목별 1줄 요약, 없으면 생략]
```

### 게이트 처리 규칙

```
🔴 차단 이슈 있음  → 즉시 자동 수정 후 재검토 1회.
                     재검토 통과 시 바로 업로드 진행.
                     재검토 후에도 🔴 잔존 시에만 사용자에게 확인 요청.

🔴 없음 + 🟡 있음  → 🟡 항목 전부 자동 반영 후 바로 업로드 진행.
                     사용자 확인 요청 없음.

🔴 없음 + 🟡 없음  → 바로 업로드 진행.
```

**원칙: 사용자를 호출하는 경우는 🔴 재검토 후에도 잔존하는 경우뿐이다.**

### 회의록 검토 제외 항목

아래는 `editorial-reviewer`의 일반 체크리스트에 포함되나 회의록에는 적용하지 않는다:

- 자기완결성 — 참석자 대상 문서이므로 내부 전제 설명 불필요
- 외부 출처 인용 검증 — 회의 발언 자체가 1차 소스
- 목차-본문 일치 — 회의록 구조는 스킬 템플릿으로 이미 보장

## Phase 3 — 출력

### 3-1. 출력 형식 선택

| 요청 형식 | 처리 방법 |
|----------|---------|
| **Notion** (기본값) | Notion MCP로 새 페이지 생성. 제목: `[회의록] YYYY-MM-DD 회의명` |
| **Markdown** | 대화창 내 코드 블록 또는 `.md` 파일 생성 |
| **Word (.docx)** | `/mnt/skills/public/docx/SKILL.md` 참조하여 생성 |
| **지정 없음** | Notion 기본 → 사용자가 없으면 Markdown 대화 출력 |

### 3-2. Notion 출력 시 추가 규칙

- 페이지 최상단에 **Callout 블록**으로 TL;DR 요약 (3줄 이내):
  - 주요 결정 N건
  - Action Item N건 / 담당자 목록
  - 미결 사항 N건
- Action Items는 **Inline Database** (체크박스 + 담당자 + 마감일 속성)로 생성.
- 참석자가 Notion 계정을 가진 경우, 담당자 필드에 @멘션 가능 여부 확인 후 적용.

### 3-3. Notion MCP 사용 시 주의

- 페이지 생성 전 `notion-search`로 동일 회의록 중복 여부 먼저 확인.
- 부모 페이지(회의록 보관 위치)를 사용자에게 확인하거나 이전 회의록 페이지와 동일 위치에 생성.
- 내용이 많으면 **heading 블록을 먼저 생성 후 각 섹션 내용 append** 방식으로 안정성 확보.

## Phase 4 — 검토 & 인계

작성 완료 후 사용자에게 아래 항목을 간결하게 보고한다:

```
✅ 회의록 작성 완료
- 안건: N건
- 결정 사항: N건
- Action Items: N건 (담당자 미지정: N건)
- 미결 사항: N건
- STT 보정 주석: N건 (확인 필요)
```

- STT 보정 주석이 있으면 확인 요청: "아래 항목은 맥락 추정으로 보정했습니다. 확인 후 수정해 주세요."
- `[청취 불가]` 구간이 있으면 별도 안내.

## 작성 가드레일 (전 섹션 공통)

- **사실 외 추가 금지**: STT에 없는 내용을 회의록에 창작하지 않는다.
- **화자 의견 중립 서술**: 특정 발언이 "옳다/좋다" 등의 평가 없이 사실 그대로 요약.
- **구어체·감탄사 제거**: "아무튼", "사실은", "솔직히 말하면" 등 필러 제거.
- **상대 날짜 금지**: "다음 주", "어제" 등을 절대 날짜로 변환. 불가능하면 `[날짜 확인 필요]`.
- **볼드 남용 금지**: 수치·이름·결정 사항·마감일 등 행동 추적에 필요한 정보만 볼드.
- **이모지 금지**: 섹션 제목·불릿에 이모지 미사용. Notion Callout 블록 아이콘은 기본값 유지.
- **면책 문구 금지**: "참고로", "STT 특성상 오류가 있을 수 있으니" 등 방어적 단서 본문 삽입 금지. 오류는 § 8 부록으로만 처리.
