# SPEC 작성 지침 — 실증 반려 사례에서 추출한 규율

실증 1의 Round 1 SPEC(v1)이 두 결함으로 반려됐고, v2에서 교정해 승인됐다.
이 문서의 규율은 그 v1→v2 diff에서 추출했다. 원본:
`~/knowledge-base/_codex-inbox/TASK-SPEC.md`(v1) / `TASK-SPEC-v2.md`(v2).

## 핵심 전제

**SPEC 설계 결함은 실행 결함으로 나타난다.** Codex는 SPEC의 예시 형식을 충실히 재현한다.
예시가 결함이면 산출물도 결함이다. Codex 잘못이 아니라 SPEC 잘못이다.

## 규율

### 1. 목표 산출 형식은 파서로 검증 가능한 구조로 준다

- 예시 형식 자체가 표준 파서(YAML frontmatter 파서 등)로 무손실 추출되는지 SPEC 작성 시점에 확인한다.
- 반려 사례: v1이 `policy:` 리스트를 프런트매터 밖 본문에, H2 섹션마다 반복 배치하도록 예시를 줬다. Codex는 충실히 재현했고, 표준 파서로 읽으면 중복 `policy:` 키가 서로 덮어써 원자 17개 중 10개(59%)가 조용히 소실됐다.
- 교정(v2): 원자를 전부 프런트매터 안 **단일 리스트**에 넣고, 섹션 구분은 H2 헤더가 아니라 각 원자의 `node` 같은 필드로 표현. 본문은 비운다.

### 2. 범위 모순을 없앤다 — 전수/부분을 한 곳에서 확정

- 반려 사례: v1은 범위가 "Description 전체"와 "3개 노드만" 사이에서 모순됐다. Codex는 좁은 쪽을 택했고 4구획이 누락됐다.
- 교정(v2): 범위를 전수 이관으로 한 곳에서 확정하고, **반드시 포함할 구획 체크리스트**를 명시했다("누락 시 실패" 조건으로).
- 전수 작업이면 체크리스트를, 부분 작업이면 제외 대상을 명시한다. 양쪽 다 애매하게 두지 않는다.

### 3. 자기 검증에 실행 가능한 결정론 명령을 넣는다

- "확인하라"가 아니라 실제 명령을 준다. 예(v2): `python3 -c "import yaml,...; print(len(d['policy']))"` — 파서로 원자 개수를 실측해 육안 카운트와 대조·보고하게 했다.
- 실측값 보고를 강제한다. 검토자(Claude)는 Phase 3에서 같은 명령을 **직접 재실행**해 대조한다.

### 4. 판단 위임 + 보고 강제 (과잉 명세와 무명세의 중간값)

- 모든 값을 SPEC에 못 박지 않는다. 대신 "스스로 정한 값과 근거를 최종 보고에 적어라"를 넣는다.
- 실증 2 사례: Codex가 절단 길이를 기존 필드 관례(200자)에서 스스로 찾아 맞췄고, 이관 멱등성을 undefined/명시적 null 구분으로 해석해 해제된 매핑이 부활하는 버그를 사전에 막았다.

### 5. "하지 못한 것과 이유"를 필수 보고 항목으로

- 실패를 에러 원문과 함께 보고하게 한다. 조용한 실패가 최악이다.
- 실증 2 사례: T1에서 Codex가 커밋 실패를 에러 원문과 함께 보고해 검토자가 원인(샌드박스의 worktree 커밋 차단)을 즉시 파악했다.

### 6. 커밋 지시를 SPEC에서 뺀다

- "커밋은 검토자가 한다"로 역할을 고정한다. workspace-write 샌드박스는 worktree 커밋을 차단하기도 하고(pitfalls #7), 검토 전 커밋이 생기지 않아 규율에 유리하다.

### 7. 반려 재실행 SPEC의 추가 규율

- 반려 이유를 SPEC 서두에 명시하고 "반드시 해소"를 요구한다 (v2가 결함 2건을 서두에 박은 방식).
- 이미 승인된 산출물은 "건드리지 마라"로 범위를 잠근다 (v2: "산출물 2·3은 이미 승인됐으므로 건드리지 마라").
- 재작업 범위를 파일 단위로 한정한다 ("딱 1개 파일").

## SPEC 골격 (이 순서로 작성)

```markdown
# <작업명> 실행 명세 (Codex 실행용)

> 이 파일은 Codex가 실행할 작업의 완전한 명세다. 대화 맥락 없이 이 파일만으로 실행 가능해야 한다.
> 설계: Claude Code. 실행: Codex. 검증: Claude evaluator + Codex adversarial-review.

## 목표
<이번 슬라이스에서 만들 것. 번호 목록>

## 하드 제약 (위반 시 작업 실패)
1. <원본 경로>를 절대 읽거나 쓰지 마라. 입력은 전부 _codex-inbox/에 스테이징돼 있다.
2. <작업 리포> 안에서만 파일을 생성·수정한다. 산출 위치는 <경로>.
3. _codex-inbox/는 읽기 전용이다. 수정·삭제하지 마라.
4. 수치를 창작·추정하지 마라. 입력에 있는 값만 옮긴다. 애매하면 `# TODO(확인필요)` 주석.
(커밋 지시는 넣지 않는다 — 커밋은 검토자가 한다.)

## 입력 파일 (_codex-inbox/)
<파일별 1줄 설명 — 어느 산출물의 소스인지>

## 산출물 (파일 단위로)
<목표 산출 형식을 파서 검증 가능한 예시로. 보존 필수 수치를 명시>
<전수 작업이면 포함 체크리스트("누락 시 실패")>

## 자기 검증 (산출 후 스스로 실행해 보고)
1. <결정론 명령 — 실측값 보고 강제>
2. <체크리스트 전수 확인>
3. <필수 수치 확인>
4. <원본 미접촉 확인>
5. 스스로 정한 값과 그 근거를 보고하라.
6. 하지 못한 것과 이유를 에러 원문과 함께 보고하라.
```
