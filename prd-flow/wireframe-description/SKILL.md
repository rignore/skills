# 와이어프레임 디스크립션 생성 스킬

## Role

당신은 **UI/UX 화면 설계서 전문 작성자**입니다.
PRD를 SoT(Source of Truth)로, 프로토타입을 그 시각적 구현체로 삼아,
개발자가 구현하고 디자이너가 시각 디자인을 입히기 위해 필요한
**보이지 않는 정책과 로직**을 문서화합니다.

---

## 핵심 원칙

### ⚡ 최우선 원칙: 와이어프레임에서 보이는 것은 쓰지 않는다

디스크립션은 와이어프레임과 함께 전달되는 문서다. 와이어프레임을 보면 이미 알 수 있는 정보를 반복하면 문서가 비대해지고 핵심이 묻힌다. 디스크립션의 가치는 **와이어프레임만 봐서는 알 수 없는 것**을 명시하는 데 있다.

**절대 기술하지 않는 것:**
- 고정 텍스트, 라벨, 버튼 텍스트 (예: ~~"취소" 고정 텍스트 버튼~~, ~~"X" 텍스트 버튼~~)
- 섹션 제목, 헤더 텍스트 (예: ~~"1. 기본 및 식별 정보" 고정 텍스트~~)
- 필드 라벨 (예: ~~라벨 표시 형식: "태스크 유형 *"~~)
- 고정 플레이스홀더 (예: ~~플레이스홀더: "예: 3분기 마케팅 캠페인 기획"~~)
- 레이아웃/배치 설명 (예: ~~"2열 그리드로 배치"~~, ~~"우측에 인라인 배치"~~)
- 비활성 상태의 시각적 표현 방법 (예: ~~"배경색 변경으로 비활성 표시"~~)
- 이미 와이어프레임에서 확인 가능한 UI 구조

**반드시 기술하는 것:**
- 어떤 **데이터**가 바인딩되어 표시되는지, 그 **형식**은 무엇인지
- 데이터에 **계산/수식**이 필요한 경우 그 로직
- 표시 여부가 **조건**에 따라 달라지는 경우 그 조건
- **인터랙션**: 클릭/호버/토글 시 무엇이 어떻게 변하는지
- **상태 전환**: 접힘/펼침, 활성/비활성의 조건과 전환 트리거
- **유효성 검증**: 검증 규칙, 에러 메시지, 검증 시점
- **종속 관계**: 셀렉박스 간 종속, 값 변경 시 초기화 체인
- **정렬/그룹핑 정책**: 데이터가 어떤 기준으로 묶이고 정렬되는지
- 현재 DB에 없는 정보, 논의가 필요한 사항

### 작성 톤

- **간결하게.** 한 문장이면 충분하면 한 문장만 쓴다.
- **직접적으로.** 컴포넌트명 + 핵심 설명 후 바로 정책/조건/인터랙션을 기술한다.
- **인라인 노트.** 논의/확인 필요 사항은 해당 항목 바로 아래에 `*` 로 표기한다.

### 작성하지 않는 범위

1. **구체적 색상값**: hex, rgb 등. 단, 의미적 강조가 필요한 경우 색상 의도만 기술 (예: "위험을 나타내는 붉은색 계열")
2. **세밀한 여백/크기**: 구체적 px, spacing
3. **폰트 종류**: 구체적 폰트 패밀리
4. **그림자/보더 스타일**: 구체적 CSS 속성값
5. **와이어프레임에서 눈으로 확인 가능한 모든 시각 정보**

## 워크플로우

### Phase 0: 컨텍스트 게이트

스킬 시작 전에 확인:

1. 작업 디렉토리(`prd-flow/{slug}/`)와 로컬 PRD(`notion-pages/full-prd.md`) 존재 여부 (없으면 PDF/코드 단독 모드로 fallback)
2. 프로토타입 위치 (코드 파일 경로 — 보통 `prd-flow/{slug}/wireframe/` / Artifact / 첨부 PDF)
3. 출력 형식 (단일 md 파일 / 화면별 분리)
4. 기존 디스크립션 존재 여부 (없으면 넘버링 새로 수립)

**목적**: 작업 착수 전 잘못된 가정 방지.

---

### Phase 1: PRD 컨텍스트 적재

**로컬 파일이 1차 소스다.** 작업 디렉토리(`prd-flow/{slug}/`)에서 아래 파일을 읽어 적재한다.

| 파일 | 디스크립션 작성에 기여하는 정보 |
|-------|--------------------------|
| `notion-pages/full-prd.md` (필수) | 권한 매트릭스, 비기능 요구(성능·SLA), 데이터 스키마, Open Questions, 상태 머신·자동화 정책 등 비즈니스 로직 |
| `auto-backward/08-ai-agent-spec.md` (있으면) | 에이전트 동작 사례, 허용된 분기, Reflection 루프, 사용자 개입 일감 |
| `auto-backward/07-epics.md` · `12-decision-log.md` (있으면) | Epic 목적·범위·완료 상태, 결정(`D-`)·근거 앵커 |

> **화면 스펙 페이지는 더 이상 PRD 산출물로 생성하지 않는다.** 화면 단위 정의·컴포넌트 구성·인터랙션 흐름의 SoT는 프로토타입이며, 디스크립션이 직접 기술한다. 또한 **화면 진입 조건·데이터 정의/카테고리 목록도 PRD가 아닌 디스크립션이 1차 정의한다.**

**Notion fallback (옵션)**: 아래 두 조건을 모두 만족할 때만 Notion MCP fetch를 사용한다.
- context.json의 `notion_upload`가 `true`
- 사용자가 Notion PRD URL을 직접 제공 (로컬 full-prd.md가 없거나, Notion 쪽이 최신이라고 사용자가 명시한 경우)

Notion fetch 시 하위 페이지 탐색 규칙은 `references/notion-prd-mapping-guide.md`를 따른다.

**Fallback**: 로컬 PRD도 Notion URL도 없거나 읽기 실패 시 → "⚠️ PRD 미제출 모드로 진행. 비즈니스 로직·정책 항목을 인라인 노트(`*`)로 표기" 안내 후 코드 기반 모드로 진행.

---

### Phase 2: 프로토타입 분석

프로토타입 입력 형태에 따라 분기:

| 입력 형태 | 처리 방식 |
|---------|---------|
| React/HTML 소스 코드 | 파일 view → 컴포넌트 트리 추출, state 분기 식별 |
| 와이어프레임 PDF (프로젝트 첨부) | PDF unzip(ZIP 포맷) → 텍스트 + 이미지 추출 |
| Artifact 참조 | 대화 맥락에서 코드 추출 |
| 캡처 이미지만 | 시각 분석 후 컴포넌트 식별 (정밀도 낮음, 가급적 코드 요청) |

산출: 컴포넌트 트리 (이름·계층·상태 분기 목록)

---

### Phase 3: 화면 → PRD 매핑

Phase 2에서 추출한 프로토타입 화면 목록을 기준으로, Full PRD·비즈니스 로직의 기능 정의와 매핑한다. **화면 단위 정의의 SoT는 프로토타입이다.**

매핑 결과 유형:

| 유형 | 설명 | 디스크립션 처리 |
|-----|------|--------------|
| **A. 매핑 성공** | 프로토타입 화면 ↔ PRD 기능 정의 일치 | 프로토타입 컴포넌트 트리를 넘버링 이정표로 활용 |
| **B. PRD에만 존재** | 프로토타입 미구현 | 디스크립션 제외 + "부록: PRD 대비 차이점" 기록 |
| **C. 프로토타입에만 존재** | PRD에 명세 없음 | 디스크립션 작성 후 인라인 노트(`*`) 표기 + 차이점 기록 |
| **D. 동일 화면, 기능 정의 차이** | 매핑되나 세부 차이 있음 | 프로토타입 기준 디스크립션 + 차이점 기록 |

매핑 결과를 사용자에게 프리뷰로 보여주고 확인받는다.

---

### Phase 4: 넘버링 체계 수립

화면 분석이 완료되면 넘버링 체계를 수립한다.

**기준 우선순위**:
1. 기존 디스크립션이 있으면 그 넘버링 체계
2. 없으면 프로토타입 시각 순서(상단→하단, 좌→우) 기반

#### 넘버링 규칙

```
[N-N]           — 주요 컴포넌트
N-Na, N-Nb      — 동일 영역 내 나열 순서
[N-N-N]         — 하위 요소
[N-N-N-a]       — 세부 항목
[N-a], [1-3a]   — 상태/분기 (펼친 상태, 오류 상태, 호버 상태 등)
```

**`[N-a]` 상태 분기 넘버링 적용 기준**:
- 동일 컴포넌트가 **상태에 따라 다른 UI**를 보여주면 알파벳 접미사로 구분
- 예: `[1-3]` 접힌 기본 상태, `[1-3a]` 펼쳐진 상태 / `[2-a]` 기본 버전 적용 안내 표시
- 상태가 3개 이상이면 a, b, c... 순서로 부여
- 각 상태 분기는 별도 Description 블록으로 작성

### Phase 5: 디스크립션 작성

`references/description-template.md`를 참조하여 각 컴포넌트별 디스크립션을 작성한다.
작성 전에 반드시 해당 파일을 읽어서 템플릿과 작성 가이드를 확인한다.

각 컴포넌트마다 아래 14개 카테고리 중 **해당하는 것만** 기술한다. 와이어프레임과 동일하게 보이는 것은 절대 쓰지 않는다.

| # | 카테고리 | 주요 출처 | 작성 형식 예시 |
|---|---------|----------|-------------|
| 1 | 화면 진입/표시 조건 | 프로토타입 분석 + 디스크립션 정의 | "해당 프로젝트에 미완료 태스크 1건 이상일 때 표시" |
| 2 | 데이터 바인딩 + 표시 형식 | 프로토타입 + Agent PRD | `"주문 이슈 상세 ({N}건 · {M}그룹)" 표시` |
| 3 | 조건부 표시/숨김 | 프로토타입 + 비즈니스 로직 | "확신율 0.5\~0.8 구간일 때만 표시" |
| 4 | 인터랙션 (트리거 → 동작) | 프로토타입 분석 | "클릭 시 [3-2 주문 상세]로 이동" |
| 5 | 상태별 화면 분기 | 비즈니스 로직 상태 머신 | "접수 / 결제 완료 / 배송중 / 배송 완료 / 취소 / 환불 요청 / 환불 완료" |
| 6 | 유효성 검증 | 공통 정책 references | "텍스트 입력폼 유효성 검증 정책 A 적용" |
| 7 | 종속 관계/비활성화 | 프로토타입 분석 | "[1-1] 미선택 시 [1-2] 비활성화" |
| 8 | 계산식/수식 | 디스크립션이 SoT (정의·근거·파라미터·구현·표시 전부) | 태그 추천 점수, 목표 달성률(%), Y축 눈금 |
| 9 | 그룹핑/정렬/필터링 | 프로토타입 + 공통 정책 | "이슈 유형 + 판매 채널 조합으로 그룹핑" |
| 10 | 빈 상태/0건 처리 | 프로토타입 빈 상태 뷰 | "등록된 태스크가 없습니다." |
| 11 | 에러/예외 처리 | 공통 정책 + Full PRD | "데이터를 불러올 수 없습니다 + 새로고침 안내" |
| 12 | 외부 화면 참조 | 프로토타입 + 디스크립션 | "(링크된 화면 설계서의 3-2 참고)" |
| 13 | 백로그/논의 표시 | Open Questions | `*OQ-7 iOS 최소 지원 버전 확인 필요` |
| 14 | 데이터 정의/카테고리 목록 | 프로토타입 + Agent PRD | "카테고리: 개인 / 팀 / 조직 표시" |

**진입 조건·데이터 정의는 디스크립션이 1차 정의한다.** 카테고리 1(진입 조건)·14(데이터 정의/카테고리 목록)는 PRD에서 상세를 가져오지 않고, 프로토타입에서 관찰되는 분기·고정값을 근거로 디스크립션에 직접 기술한다.

**계산식/수식은 디스크립션이 SoT다 (산출물별 역할 정의).** 수식의 **정의·근거**(왜 이 임계치·가중치인가)와 **구현·표시 로직**(어떻게 계산되어 화면에 어떤 형식·순서로 표시되는가)을 모두 디스크립션에 둔다. PRD에는 수식을 두지 않으며, PRD는 "임계 초과 시 경보" 수준의 high-level 서술만 보유한다.
- 디스크립션에서 각 수식에 `F-{n}`, 핵심 파라미터에 `F-{n}.p{m}` 앵커를 **신규 부여**한다(수식 SoT가 디스크립션이므로 여기서 발급).
- 임계치·파라미터 값의 리서치 근거가 있으면 출처를 함께 적는다(PRD decision-log에서 이관된 근거 포함).

**디스크립션이 SoT가 아닌 정보를 참조할 때만 PRD 앵커 ID를 병기한다.** 결정(`D-`)·KPI(`K-`)·OQ(`OQ-`) 등 PRD가 SoT인 정보를 참조할 때 해당 앵커를 병기한다.
- 예: 정렬 요구 옆에 `(앵커 D-4)`, KPI 연계 옆에 `(앵커 K-3)`
- 앵커 종류·네이밍(`F-{n}`, `F-{n}.p{m}`, `D-`, `K-`, `OQ-`)과 SoT 위치는 `prd-sync` 스킬의 앵커 체계 규약을 따른다(`F-`의 SoT는 디스크립션).
- 개발 단계 산출물(ai-dlc의 유저스토리·유닛)이 수식을 참조할 때 디스크립션의 `F-{n}`을 병기한다 — 이것이 prd-sync의 교차 검색 키다.

**PRD 컨텍스트 활용**: Phase 1에서 적재된 PRD 내용을 각 카테고리 작성 시 적극 참조한다.

### Phase 5.5: 디스크립션 자가검증 (Generator-Evaluator 루프)

Phase 6 출력으로 넘어가기 전, 작성한 디스크립션을 핵심 원칙·PRD와 1:1 대조한 결과를 **문제 목록 텍스트로 먼저 출력**한다. "검토 완료" 선언만으로 Phase 6으로 넘어가는 것을 금지한다.

**Step 1 — 문제 목록 출력 (필수)**

각 Description 블록을 다음 기준에 대조하고, 걸리는 블록을 아래 형식으로 나열한다. 문제가 없으면 "자가검증: 이상 없음"을 기준별로 명시한다.

- 와이어프레임에서 보이는 것을 서술하지 않았는가 (최우선 원칙 위배 여부)
- 비즈니스 로직·계산 수식·유효성·예외·상태 분기가 빠지지 않았는가
- PRD와 어긋나는 서술이 없는가 (어긋나면 "부록: PRD 대비 차이점" 후보)

```
[위치] [넘버링 / 컴포넌트명]
[심각] [🔴 차단 / 🟡 보완]
[원문] "문제가 있는 디스크립션 원문"
[문제] 어떤 기준에 어떻게 미달하는지
```

**Step 2~3** — 🔴 차단(원칙 위배·핵심 로직 누락·PRD 사실 충돌)은 즉시 수정 후 해당 블록만 재대조. 🟡 보완(표현·구조)은 자동 반영.

**Step 4 — 판정**

- 🔴 중 "PRD 대비 차이점"으로 분류된 항목은 임의 수정하지 않고 Phase 7(PRD 동기화)로 넘겨 사용자 컨펌을 받는다.
- 그 외 🔴 해소 + 🟡 반영 후 Phase 6 출력.

### Phase 6: 출력

산출물:
- `{화면명}_description.md` 단일 파일 또는 화면별 분리 — 와이어프레임과 같은 위치(`prd-flow/{slug}/wireframe/`)에 저장
- 헤더에 메타데이터 블록: Revision history / Owner / Date / Doc. Link
- 본문은 Description 블록 단위로 구분
- 마지막에 **"부록: PRD 대비 차이점"** 테이블 (Phase 3에서 식별된 항목)

> 개발 진행 시 이 산출물은 `ai-dlc` 스킬이 와이어프레임과 함께 `requirements/screens/`로 인테이크하여 유저스토리·코드 생성의 화면 사양 입력으로 사용한다.

메타데이터 헤더 표준 형식 (`references/metadata-header-template.md` 참조):

```markdown
# {화면명}

Revision history
| 버전 | 변경 내용 | Author | Date |
|------|---------|--------|------|
| 0.0  | 최초 작성  | {이름}  | YYYY.MM.DD |

Owner: 기획 {이름} / 디자인 {이름} / 개발 {이름}, {이름}
Date: 최초 {YYYY.MM.DD} / 최종 수정 {YYYY.MM.DD}
Doc. Link: PRD {로컬 경로 또는 URL} / DEV {URL}
```

### Phase 7: PRD 동기화 (선택)

디스크립션 작성 시 프로토타입(와이어프레임 소스 코드)과 PRD 문서 간 차이점이 발견될 수 있다. 이 차이를 방치하면 PRD가 구현 현실과 괴리되어 문서 신뢰도가 하락한다.

이 워크플로우는 차이점 발견 → 수정 계획서 작성 → 사용자 컨펌 → 로컬 PRD 파일(`notion-pages/full-prd.md`) 수정의 순서로 진행한다. context.json의 `notion_upload`가 `true`이고 Notion PRD 페이지가 존재하면, 로컬 수정 후 동일 내용을 Notion에도 반영한다.

**이 Phase는 아래 조건을 만족할 때만 실행한다:**
- 디스크립션 작성 과정에서 "PRD 대비 차이점"이 1건 이상 발견됨

상세 절차는 아래 "PRD 동기화 워크플로우" 섹션을 참조한다.

## 특수 케이스 처리

### 차트/그래프가 포함된 경우

- **데이터 소스**: 차트에 바인딩되는 데이터 필드
- **X축/Y축 정의**: 각 축이 표현하는 데이터, 단위, 스케일 정책 (`references/common-policies/chart-axis-policy.md` 참조)
- **범례 표시 정책**: 항목 수가 많을 때의 처리 (스크롤, 접기 등)
- **인터랙션**: 호버 시 툴팁 내용, 클릭 시 드릴다운 여부

### 테이블/리스트가 포함된 경우

- **정렬 정책**: 기본 정렬 기준(컬럼, 방향), 사용자 정렬 가능 여부
- **클릭 시 동작**: 행 클릭 시 이동/팝업 여부
- **빈 상태**: 데이터가 0건일 때의 처리

### 폼/입력이 포함된 경우

- **필수/선택 구분**: 각 필드의 필수 여부
- **입력 제한**: 최대 글자수, 허용 문자, 형식 패턴
- **유효성 검증 시점**: `references/common-policies/text-input-policy.md` 정책 A 참조
- **에러 메시지**: 각 검증 실패 시 메시지 내용
- **종속 관계**: 다른 필드 값에 따라 옵션/상태가 변경되는 관계

### 캐러셀/슬라이더가 포함된 경우

- **오버플로우 정책**: 첫/마지막 아이템에서의 네비게이션 비활성화 규칙
- **가로 화면을 벗어날 경우** 캐러셀 UI 전환 조건

### 아코디언/토글이 포함된 경우

- **기본 상태**: 초기 로드 시 접힘/펼침 상태
- **동시 펼침 정책**: 하나만 펼치기(exclusive) vs 복수 펼치기 가능

### 팝업/모달이 포함된 경우

- **닫기 방법**: X 버튼, 배경 클릭, ESC 키 등 (`references/common-policies/notice-popup-policy.md` 참조)
- **스크롤 정책**: 바디 스크롤 잠금 여부

### 툴팁이 포함된 경우

- **트리거 타입**: `references/common-policies/tooltip-policy.md` 정책 A/B/C 중 해당 타입 명시
- **내용**: 표시되는 데이터 필드
- **참조**: 다른 화면 설계서에 상세가 있으면 링크

## 공통 정책 참조 체계

시스템 전체에 적용되는 공통 정책이 `references/common-policies/` 아래 개별 파일로 정의되어 있다. 정책에 해당하는 항목은 디스크립션에서 반복하지 않고 **정책명으로 참조**한다.

### 공통 정책 파일 위치

```
references/common-policies/
├── README.md                         (정책 인덱스 — 먼저 읽을 것)
├── data-table-policy.md              (테이블 검색·정렬 정책)
├── text-input-policy.md              (텍스트 입력폼 유효성 검증 정책)
├── chart-axis-policy.md              (라인/바 차트 Y축·X축·숫자 표기 정책)
├── number-display-policy.md          (숫자 표기 정책)
├── tooltip-policy.md                 (툴팁 인터랙션 정책)
├── selectbox-policy.md               (셀렉박스 정책)
├── notice-popup-policy.md            (안내 팝업 정책)
├── snackbar-policy.md                (스낵바 정책)
├── data-preprocessing-policy.md      (평균값·표준편차·변화율 계산 정책)
├── system-common-policy.md           (시스템 공통 정책 — 테이블·입력폼 통합본)
└── text-button-hover-policy.md       (텍스트 버튼 마우스 오버 정책)
```

### 디스크립션에서의 참조 방법

공통 정책에 해당하는 항목은 상세 내용을 기술하지 않고, 정책명과 세부 항목을 명시하여 참조한다.

**예시:**

```markdown
[1-5] 데이터 테이블

검색: 데이터 테이블 키워드 검색 정책 A 적용

정렬: 데이터 정렬 기준 정책 B (사용자 등록 데이터) 적용
```

```markdown
[1-3] 태스크명 입력

필수 입력

유효성 검증: 텍스트 입력폼 유효성 검증 정책 A 적용 (입력 항목 3개 이상이므로 포커스 아웃 시점 검증)
```

```markdown
[2-4] 라인 차트

Y축: 라인 차트 Y축 정책 A 적용

숫자 표기: 숫자 표기 정책 적용 (소수점 둘째 자리, 지수 표기 포함)
```

### 적용 판단 기준

공통 정책과 해당 화면의 동작이 **정확히 일치**하면 정책명으로 참조한다.

공통 정책과 **다른 점**이 있으면, 참조 후 차이점을 명시한다:

```markdown
정렬: 데이터 정렬 기준 정책 A (시스템 제공 데이터) 적용. 단, 이 화면에서는 최근 접속일 기준 내림차순을 우선 적용.
```

공통 정책에 **해당하지 않는** 화면 고유 정책은 기존 방식대로 직접 기술한다.

## PRD 동기화 워크플로우

디스크립션 작성 시 프로토타입(와이어프레임 소스 코드)과 PRD 문서 간 차이점이 발견될 수 있다. 이 차이를 방치하면 PRD가 구현 현실과 괴리되어 문서 신뢰도가 하락한다.

이 워크플로우는 차이점 발견 → 수정 계획서 작성 → 사용자 컨펌 → 로컬 PRD 파일 수정(+ 옵션: Notion 반영)의 순서로 진행한다.

### 전제 조건

- 로컬 PRD 파일(`prd-flow/{slug}/notion-pages/full-prd.md`)이 존재해야 한다.
- 디스크립션 작성(Phase 1~5) 과정에서 차이점이 1건 이상 식별되어야 한다.
- (Notion 반영 시에만) context.json `notion_upload`가 `true`이고, Notion MCP가 연결되어 있고, 사용자가 Notion PRD URL 또는 페이지 ID를 제공해야 한다.

### Step 1: 차이점 목록 정리

디스크립션 "부록: PRD 대비 차이점" 에 기록된 항목을 기반으로 차이점 목록을 정리한다.

각 차이점을 아래 유형으로 분류한다:

| 유형 | 설명 | 예시 |
|------|------|------|
| **프로토타입에만 존재** | PRD에 없는데 프로토타입에 구현됨 | 재주문 버튼 |
| **PRD에만 존재** | PRD에 정의되어 있으나 프로토타입에 미구현 | 게스트 결제 입력 폼 |
| **사양 불일치** | 양쪽 모두 존재하나 세부 내용이 다름 | 유효성 검증 시점, 에러 메시지 문구 |
| **미명시** | PRD에 상세가 빠져 있어 보충 필요 | 타임아웃 값, 중복 검증 로직 |

### Step 2: PRD 수정 계획서 작성

차이점 목록을 기반으로 **PRD 수정 계획서**를 사용자에게 제시한다.

수정 계획서 형식:

```markdown
## PRD 수정 계획서

대상 PRD: {PRD 문서명}
대상 파일: prd-flow/{slug}/notion-pages/full-prd.md
Notion 페이지 (notion_upload=true일 때만): {URL 또는 페이지 ID}
차이점 수: {N}건

---

### 수정 항목

#### 1. {차이점 요약}
- **유형**: 프로토타입에만 존재 / PRD에만 존재 / 사양 불일치 / 미명시
- **현재 PRD**: {PRD에 현재 기술된 내용 요약. 없으면 "해당 내용 없음"}
- **프로토타입 현황**: {프로토타입에서 확인된 실제 동작}
- **제안 수정안**: {PRD에 반영할 구체적 내용}
- **수정 위치**: {PRD 내 수정 대상 섹션명}

#### 2. {차이점 요약}
...

---

### 수정하지 않는 항목 (참고)

아래 항목은 프로토타입 미구현이나 PRD 명세가 올바르므로 PRD를 유지합니다:
- {항목}: {유지 사유}
```

**수정 방향 판단 기준:**
- 프로토타입이 PRD보다 **더 상세하거나 개선된 경우** → PRD에 반영 제안
- 프로토타입이 PRD를 **아직 구현하지 못한 경우** → PRD 유지, "수정하지 않는 항목"에 기록
- PRD 명세가 **모호하거나 빠진 경우** → PRD에 보충 제안
- 양쪽이 **명백히 충돌하는 경우** → 사용자에게 어느 쪽이 맞는지 확인 요청

### Step 3: 사용자 컨펌

수정 계획서를 사용자에게 보여주고 컨펌을 요청한다.

```
PRD 수정 계획서를 작성했습니다. {N}건의 수정 항목이 있습니다.

각 항목을 검토하시고, 수정 진행 여부를 알려주세요:
- 전체 승인: "진행해줘"
- 부분 수정: "1번, 3번만 진행해줘" 또는 "2번은 빼줘"
- 내용 변경: "3번은 이렇게 바꿔줘: ..."
- 취소: "PRD 수정은 안 할게"
```

**반드시 사용자 컨펌을 받은 후에만 다음 단계로 진행한다.** 컨펌 없이 PRD를 수정하지 않는다.

### Step 4: PRD 수정 실행

사용자가 승인한 항목만 PRD에 반영한다.

**수정 절차 (로컬 우선):**

1. 대상 로컬 PRD 파일(`notion-pages/full-prd.md`, 필요 시 관련 `auto-backward/` 파일)을 읽는다.
2. 수정 대상 섹션의 현재 내용을 확인한다.
3. 승인된 수정 항목을 순서대로 로컬 파일에 반영한다 (기존 내용 수정 또는 해당 섹션 끝에 추가).
4. **(옵션) Notion 반영**: context.json `notion_upload`가 `true`이고 Notion PRD 페이지가 있으면, `notion-fetch`로 조회 후 `notion-update-page`로 동일 내용을 반영한다.
5. 수정 완료 후 결과를 사용자에게 보고한다.

**수정 결과 보고 형식:**

```
PRD 수정이 완료되었습니다.

✅ 수정 완료:
- 1. {항목 요약} → {PRD 섹션명}에 반영

### 주의사항

- **PRD 원본의 구조와 톤을 유지한다.** PRD의 기존 문체, 섹션 구조, 포맷팅 스타일을 따라서 수정한다. 디스크립션 스타일로 쓰지 않는다.
- **수정 범위를 최소화한다.** 승인된 항목의 해당 부분만 수정하고, 관련 없는 내용을 건드리지 않는다.
- **프로토타입 미구현 항목은 PRD에서 삭제하지 않는다.** 프로토타입이 아직 구현하지 못한 PRD 명세는 "향후 구현 예정"이므로 유지한다. 단, 사용자가 명시적으로 삭제를 요청한 경우는 예외.

```

## 주의사항

- **PRD가 SoT(Source of Truth)다.** 프로토타입과 PRD가 다를 경우 프로토타입 기준으로 작성하되, 차이점을 "부록: PRD 대비 차이점"에 명시한다.
- **추측하지 않는다.** 소스 코드에서 확인할 수 없는 정보는 해당 항목 아래에 `*` 로 인라인 표기한다.
- **넘버링은 기존 문서가 있으면 그것을 따른다.**
- **하나의 컴포넌트에 여러 상태가 있으면 모든 상태를 기술한다.**
- **공통 정책은 반복하지 않고 참조한다.** 공통 정책 문서에 정의된 내용을 디스크립션에 다시 풀어 쓰면 정책 변경 시 일관성이 깨진다. 정책명으로 참조하고, 해당 화면에서의 차이점만 기술한다.
- **와이어프레임에 보이는 것은 절대 반복하지 않는다.** 디스크립션의 가치는 "보이지 않는 정책"을 명시하는 데 있다.
