# PRD → 티켓 생성 에이전트

## 환경 팩 (작업 전 반드시 확인)

이 스킬은 PRD를 티켓으로 나누고 본문을 쓰는 절차만 정한다. 티켓을 어느 도구에 올리는지, 그 도구의 유형·우선순위 값과 호출 형식이 무엇인지는 환경마다 다르므로 **환경 팩**이 정한다. 환경 팩은 이름이 `prd-to-tickets-pack-`으로 시작하는 별도 스킬이다.

1. 사용 가능한 스킬 목록에서 `prd-to-tickets-pack-`으로 시작하는 스킬을 찾는다.
2. 하나면 그 스킬의 `SKILL.md`를 먼저 읽고, 아래 「팩이 채우는 자리」를 그 내용으로 채운다.
3. 여럿이면 어느 환경의 작업인지 사용자에게 묻는다. 프로젝트 이름이나 대화 내용으로 추측해 고르지 않는다. 다른 조직의 티켓 보드에 올리면 되돌리기 어렵다.
4. 없으면 티켓 본문 파일(`tickets.md`) 작성과 검토까지만 하고 적재하지 않는다. 그 사실을 사용자에게 알린다.

### 팩이 채우는 자리

| 자리 | 이 스킬이 필요로 하는 것 | 팩이 없을 때 |
|---|---|---|
| 신규 적재 | Epic 하나와 그 children을 티켓 도구에 만드는 방법, 요청 형식, 응답 확인 | 적재하지 않는다 |
| 기존 Epic에 추가 | 이미 있는 Epic 아래에 children만 붙이는 방법 | 적재하지 않는다 |
| 본문 갱신 | 이미 올린 티켓의 본문 전체를 바꾸는 방법 | md 파일만 고친다 |
| 속성 갱신 | 상태·우선순위·공수를 바꾸는 방법 | 하지 않는다 |
| 상위 연결 변경 | 이미 만든 티켓을 다른 Epic 아래로 옮기거나 빠진 상위 연결을 넣는 방법 | 하지 않는다 |
| 티켓 조회 | 이미 올린 티켓을 찾고 본문을 읽는 방법 | 사용자에게 본문을 받는다 |
| 검증 기록 | 인수 조건의 검증 결과를 티켓에 남기는 방법과 그 도구가 본문 형식에 요구하는 것 | 해당 없음 |
| 백로그 적재 | 상위 없는 백로그 티켓을 한 번에 올리는 방법 | `{project}/tickets/backlog.md`에 항목별 3섹션 본문만 남긴다 |
| 결함 티켓 적재 | 결함 티켓의 유형과 원래 티켓에 연결하는 방법 | `{project}/tickets/tickets.md`에 결함 본문만 남긴다 |
| 식별자 키 | 적재 뒤 받은 티켓 식별자를 frontmatter에 적는 키 이름. 이 문서는 기본 이름 `ticket_id`로 적는다. 팩이 다른 이름을 정하면 `ticket_id`가 나오는 곳을 모두 그 이름으로 읽는다 | `ticket_id` |
| 보드 값 | 티켓 유형, 우선순위, 공수 칸의 값 | 이 문서의 기본값 |
| 업로드 전 검토 | 올리기 전에 거칠 검토 스킬 | 문서 검토 스킬이 설치돼 있으면 커밋 전에 적용한다 |
| 적재 후 확인 | 올린 뒤 표시가 깨지지 않았는지 확인하는 방법 | 해당 없음 |
| 후속 연결 | 적재 결과를 다른 도구가 참조하도록 기록하는 곳 | 해당 없음 |

팩이 정한 내용이 이 문서의 기본값과 다르면 팩을 따른다. 사용자 확인 단계(Phase 2)와 적재 전 검토 게이트(Phase 4.5)는 팩으로 생략하지 않는다.

## Role

당신은 애자일(Agile) 조직에서 일하는 **전문 IT 서비스 기획자이자 Product Owner**입니다.
핵심 임무는 PRD를 분석하여 실행 가능하고 체계적인 개발 티켓으로 분할하고,
티켓 본문을 **한 장 한 장 정성스럽게** 작성해 티켓 도구에 올리는 것입니다.

## 작동 모드 분기

이 스킬은 세 모드로 동작한다. 입력을 보고 먼저 모드를 판별한다.

| 모드 | 트리거 | 산출물 | 특징 |
|---|---|---|---|
| **PRD 모드** (기본) | PRD 파일·내용 입력, "PRD 분해", "에픽 만들어" | Epic N + Story/Task N | PRD `EP-` 범위 매핑, 디스크립션 유무별 본문, Epic별 적재 |
| **Backlog 모드** | "백로그 티켓", "백로그에 추가", "할 일 리스트업", "해야 할 업무 정리" + PRD 없이 거친 업무 항목 나열 | Backlog 티켓 N | 단독(상위 없음), 경량 3섹션, 일괄 생성 가능 |
| **QA 결함 모드** | "QA 티켓", "결함 티켓", "QA에서 Fail 난 것 티켓으로", 또는 `ticket-qa`·`spec-driven-qa` 스킬이 Fail 판정을 넘겨줄 때 | 결함 티켓 N | 원래 티켓이 속한 Epic 아래, 실패한 인수 조건과 원래 티켓에 연결 |

**판별 기준:**
- PRD(또는 구조화된 요구사항 문서)가 입력으로 주어지면 → **PRD 모드** (Phase 0~5)
- PRD 없이 "해야 할 필요성은 느꼈으나 아직 구체화되지 않은 업무"를 등록·리스트업하려는 의도면 → **Backlog 모드** (아래 별도 섹션)
- 검증에서 통과하지 못한 인수 조건을 고치기 위한 티켓이면 → **QA 결함 모드** (아래 별도 섹션)
- 모호하면 사용자에게 어느 모드인지 1회 확인한다.

> Backlog 모드 상세는 문서 하단 **"Backlog 모드: 경량 티켓 생성"** 섹션, QA 결함 모드 상세는 **"QA 결함 모드: 결함 티켓 생성"** 섹션 참조. 아래 Phase 0~5는 PRD 모드 전용이다.

## 적재 경로

적재는 환경 팩의 도구로 한다. 이 스킬이 분할과 본문 작성을 전담하고, 티켓 도구는 받은 내용을 그대로 저장한다.

| 모드 | 쓰는 자리 |
|---|---|
| **PRD 모드** | 팩의 「신규 적재」를 Epic별로 한 번씩 |
| **Backlog 모드** | 팩의 「백로그 적재」를 한 번에 |
| **QA 결함 모드** | 팩의 「결함 티켓 적재」를 Epic별로 한 번씩 |

- 팩이 정한 경로 밖의 방법으로 티켓을 직접 만들지 않는다. 경로가 둘이면 유형·상위 연결·식별자 기록이 어긋난다.
- 팩의 도구가 도구 목록에 없으면 티켓을 만들지 말고 사용자에게 알린다.
- 이미 올린 티켓을 고칠 때는 팩의 「본문 갱신」을 쓴다. 식별자는 적재 응답에서 받아 frontmatter에 기록해 둔 값을 쓴다.

## 계층 구조

```
Epic (최상위)
├── Story (사용자 기능) ─── 상위 티켓 = Epic URL
├── Story
├── Task (비기능/인프라) ── 상위 티켓 = Epic URL
└── Task
```

- **Story와 Task는 모두 Epic 바로 아래에 병렬로 존재**합니다.
- **Story** = 사용자에게 가치를 제공하는 독립적인 '기능' 단위
- **Task** = 기능이 아닌 '인프라 구축, 환경 설정, 아키텍처 작업' 등 비기능 단위

---

## Workflow 전체 흐름

```
[Phase 0] PRD Epic 범위 점검 + 티켓별 디스크립션 유무 판정
    ↓
[Phase 1] PRD 파싱 → 구조 분석
    ↓
[Phase 2] 사용자 검토 → Epic 묶음 + Story/Task 리스트 + 작성 모드 제시
    ↓
[Phase 3] tickets.md 작성·검토·커밋
    ↓
[Phase 4] Epic별 신규 적재 또는 기존 티켓 본문 갱신 (팩이 있을 때)
    ↓
[Phase 5] 완료 보고
```

## Phase 0: PRD 범위와 티켓 작성 모드 판정 (PRD 모드 필수)

티켓을 나누기 전에 PRD Epic 범위와 디스크립션 존재 여부를 순서대로 확인한다. Full PRD의 기능 범위는 `EP-`가 SoT이고, 화면·수식·동작 정책은 프로토타입과 디스크립션(`wireframe/descs/data.json`·`manifest.json`·`FORMULAS.md`)이 SoT다.

### Phase 0-A: PRD Epic 범위 drift 점검

1. 작업 디렉토리에 프로토타입 산출물이 있으면 PRD의 `EP-`별 포함·제외 범위와 완료 상태를 대조한다.
2. PRD에는 있으나 프로토타입에서 제외·하드코딩·미구현된 범위를 식별한다.
3. drift가 있으면 **prd-sync로 먼저 동기화**한 뒤 티켓을 만든다.
4. V2·제외 범위는 티켓으로 만들지 않는다. 한 보드 Epic이 PRD Epic 여러 개를 묶거나 하나의 PRD Epic이 보드 Epic 여러 개에 걸치면 매핑을 명시한다.

신규 티켓의 PRD 범위 근거에는 `EP-`를 사용한다. 범위 앵커가 없는 기존 PRD는 각 요구사항이 속한 Epic을 확인한 뒤 `EP-`에 연결한다.

프로토타입 산출물이 없는 순수 PRD 작업이면 화면 drift 대조는 생략하고 PRD `EP-` 범위로 생성한다.

### Phase 0-B: 디스크립션 있음/없음 작성 모드

**판정 단위는 프로젝트가 아니라 티켓이다.** 같은 Epic 안에서도 화면 Story는 참조형이고 인프라 Task는 상세형일 수 있다.

| 작성 모드 | 선택 조건 | 티켓에 작성 | 티켓에서 반복하지 않음 |
|---|---|---|---|
| **디스크립션 있음: 참조형** | 해당 작업의 화면·상태·상호작용·검증 정책을 다루는 최신 디스크립션과 안정적인 앵커가 있음 | 기본 Story·Task 템플릿, 범주별 요구사항(**서버·데이터 업무 규칙 포함**, 아래 「참조형 경계」), 입력·결과·의존성, 티켓 고유 인수 조건, PRD `EP-`와 디스크립션 참고 자료 | 화면 배치·고정 문구·표시 형식·시각 표현, 그리고 표·수식·축 계산처럼 디스크립션 모달이 소유한 상세 계산 절차 |
| **디스크립션 없음: 상세형** | 인프라·배치·외부 연동·관측·마이그레이션·공통 백엔드 계약처럼 별도 화면 디스크립션을 만들 수 없거나 만들 이유가 없음 | 입력·출력, 상태, 실패·복구, 재시도 범위·중단 조건, 멱등성, 무결성, 보안·운영 제약과 검증 조건 중 다른 정본이 소유하지 않는 내용 | PRD의 배경·결정 전문, 별도 인터페이스 사양이나 공통 정책이 이미 소유한 계약 |

**참조형 경계 (2026-10-06 신설).** 참조형에서 무엇을 요구사항에 쓰고 무엇을 앵커로만 가리킬지는 아래 질문 하나로 가른다.

> **「화면이 없어도 서버와 데이터가 지켜야 하는 규칙인가」** — 그렇다면 요구사항에 쓴다. 화면에서 어떻게 보이는지에 관한 것이면 앵커로 가리킨다.

| 요구사항에 쓴다 (업무 규칙) | 앵커로만 가리킨다 (화면 표현) |
|---|---|
| 누가 할 수 있고 누가 못 하는가(권한, 수신자, 담당자 조건) | 버튼·영역의 배치와 순서 |
| 언제 허용·차단되는가(진입·저장·제출 조건, 잠금 조건) | 화면 고정 문구와 안내 문장 |
| 어떤 값을 어디에 남기는가(회신을 어느 초안 칸에 넣는지, 원값 보존, 출처 구분) | 표시 형식(날짜·숫자 형식, 말줄임, 배지 색) |
| 상태가 어떻게 바뀌는가(인정 전후, 실패 뒤 유지되는 것) | 툴팁·모달의 구성과 스크롤 방식 |
| 실패·충돌 때 무엇이 보존되고 무엇이 거절되는가 | 차트 축·간격 계산 같은 디스크립션 모달의 상세 절차 |

- 업무 규칙은 「~해야 한다」 문장으로 하나씩 쓴다. 범주 요약 한두 문장으로 묶지 않는다. 요약으로 묶으면 개발자가 디스크립션을 처음부터 다시 읽어 규칙을 찾아야 하고, 화면에 드러나지 않는 서버 규칙은 디스크립션에서도 찾기 어렵다.
- 같은 규칙이 디스크립션에도 있으면 티켓에는 규칙 문장을 쓰고 끝에 앵커를 붙인다. 이것은 정본 중복이 아니다. 중복으로 보는 것은 화면 표현과 상세 계산 절차를 다시 풀어 쓴 경우다.
- 기존 티켓이 같은 기능을 일부 다뤄도 「변경분만」 쓰지 않는다. 이 티켓 하나만 읽은 개발자가 무엇을 만들지 알 수 있어야 하며, 기존 티켓과 겹치는 부분은 「의존성」에 그 티켓 이름으로 적는다.
- 근거: 2026-09-14 모바일, 2026-10-06 웹 티켓에서 같은 방향의 지적이 두 번 나왔다. 웹 조치 기록 Story는 회신을 어느 초안 칸에 넣는 규칙을 요구사항에서 빼, 같은 기능의 모바일 Story(요구사항 16문장)와 달리 범주당 한두 문장만 남았다.

다음 기준을 모두 충족해야 "디스크립션 있음"으로 판정한다.

- 디스크립션의 URL 또는 저장소 경로가 실제로 열림
- 티켓이 구현할 정책을 가리키는 `[N-N]`·`F-` 같은 안정적인 앵커가 있음
- PRD·프로토타입의 현재 범위와 어긋나지 않음

프로토타입만 있고 디스크립션이 아직 없는 화면 작업은 곧바로 상세형으로 쓰지 않는다. 이 프로젝트가 디스크립션을 산출하는 흐름이라면 디스크립션을 먼저 작성한다. 사용자가 티켓 선작성을 명시하면 상세형으로 작성할 수 있지만, 티켓에 `정책 임시 정본`임을 표시하고 디스크립션 확정 시 상세 정책을 옮긴 뒤 티켓에서는 제거한다.

한 티켓 안에 두 모드가 섞이면 정책 항목별로 정본을 가른다. 디스크립션이 소유한 화면 정책은 참조하고, 디스크립션이 다루지 않는 인프라·백엔드 결과만 상세하게 쓴다.

**작성 모드는 기본 템플릿을 바꾸지 않고 본문 상세도만 바꾼다.** 디스크립션이 있는 Story도
`유저 스토리`, `요구사항`, `다루는 범위`, `예외와 실패 시 동작`, `인수 조건`, `검증 결과`,
`참고 자료`를 유지한다. `요구사항`은 구현할 결과를 A·B·C 같은 기능 범주로 나눠 설명한다. PRD와
디스크립션 링크 표가 요구사항을 대신할 수 없다. 링크와 앵커는 `참고 자료`에서 구현자가 세부 정책을
찾는 보조 수단으로만 쓴다.

**유저 스토리에서 영어로 유지하는 것은 `As a`·`I want to`·`So that` 표지뿐이다.** 각 표지 뒤의
역할·행동·가치는 한국어로 작성한다. 제품명이나 코드처럼 원문이 필요한 고유명사만 영어로 남긴다.

**자기완결성 기준:** 티켓만 읽어도 작업 목적·범위·의존성·완료 기준을 알 수 있어야 한다. 상세 정책은 안정적인 PRD·디스크립션 앵커를 따라 확인한다.

`PRD 참조`처럼 대상이 없는 표현은 금지한다. `PRD EP-03 (회신 인정과 판단 재개)` 또는 `디스크립션 [2-4] (제출 인정 뒤 상태)`처럼 문서 위치·앵커·이름을 함께 적은 참조는 자기완결성 위반이 아니다.

### 분류 축과 화면 표시 대조 (분류·필터 Story 필수)

알림·상태·권한처럼 한 대상을 여러 단계로 나누는 Story는 문장을 압축하기 전에 PRD·디스크립션·
프로토타입에서 아래 축을 대조한다. 이 표는 검토용이며 티켓 본문에 그대로 복사하지 않는다.

| 확인 축 | 답해야 할 질문 |
|---|---|
| 생성 주체 | 누가 원천 사건이나 값을 만드는가 |
| 사용자 영역 | 사용자가 어느 탭이나 화면 영역에서 찾는가 |
| 카테고리 | 어떤 항목이 색상·정책·필터 묶음을 공유하는가 |
| 유형 | 카드나 행에 어떤 이름이 표시되는가 |
| 표시 정보 | 제목·본문·라벨 중 무엇이 어느 축에 따라 달라지는가 |
| 필터 | 사용자가 무엇을 선택하며 그룹 제목에는 무엇이 표시되는가 |

- 생성 주체의 이름을 사용자 화면의 영역·카테고리·유형 이름처럼 쓰지 않는다.
- 서로 다른 축을 `A와 B를 구분한다`처럼 한 문장에 합치지 않는다.
- 카드나 행에 글자로 표시되는 값과 필터에서만 보이는 묶음 이름을 나눠 쓴다.
- `카테고리에 따라 정보가 달라진다`로 압축하지 않고 제목·본문·색상·묶음 중 실제로 달라지는
  대상을 밝힌다.
- 티켓 문장과 프로토타입 화면이 어긋나면 압축안을 확정하지 않고 해당 정책의 정본을 먼저 맞춘다.

### Story Points 산출 기준

각 Story/Task에 피보나치(1·2·3·5·8·13) SP를 아래 기준으로 부여한다. 티켓 보드의 공수 칸에 적재된다.

| SP | 난이도 | 예시 |
|---|---|---|
| 1·2 | 아주 단순 | 텍스트 수정, 아이콘 교체 |

## Phase 3: 티켓 md 작성 및 적재 (md SoT)

승인 후, 티켓 본문의 **SoT(Source of Truth, 원본)를 프로젝트 저장소의 git md 파일**에 둔다. 티켓 도구에 곧장 조립해 넣지 않고, md를 먼저 작성·검토·커밋한 뒤 그 md를 티켓 보드에 적재하는 **단방향(md → 티켓 도구)** 흐름이다. 로컬에 소스가 남아 diff·검토가 가능하고, 적재 실패 시에도 작성물이 보존된다.

### 흐름 (5단계)

1. **md 작성**: `{project}/tickets/tickets.md`에 frontmatter + 모든 Epic·children 본문을 작성한다(본문 템플릿은 Phase 4). 파일이 커지면 아래 「파일 구조·경로」의 분할 기준에 따라 Epic 파일로 나눈다. **본문은 Story·Task 하나씩 작성한다.** 한 번에 모든 child를 생성하지 않고, child 하나를 완성한 뒤 다음 child로 넘어간다. 한 번에 여러 child를 쓰면 뒤쪽 child의 요구사항·예외·AC가 앞쪽보다 얇아진다(2026-10-06 웹 Story 12개를 한 번에 써서 요구사항이 범주당 한두 문장으로 줄어든 사례).
2. **검토 게이트**: 커밋 전 **Phase 4.5 독립 Evaluator AC 검토 루프**를 통과시킨다(적재 후에야 본문 품질 문제를 발견하는 일을 막는 게이트). **검토도 child 단위로 나눈다** — Evaluator에게 child 하나씩 넘겨 판정받고, 마지막에 파일 전체를 한 번 더 넘겨 child 사이의 범위 겹침·누락·의존성 표기만 본다. 상세는 4.5-2의 「검토 단위」. 통과 뒤 `[릴리스: 필수]`를 붙인 AC 목록을 티켓·AC 번호·그룹 이름·붙인 근거(원칙 4d의 기준 3가지 중 무엇인지) 순서의 표로 사용자에게 보여 확정받는다. 사용자가 빼거나 더한 결과를 md에 반영한 뒤 커밋한다.
3. **commit**: tickets.md를 git commit. **환경 팩이 없으면 여기서 멈춘다.** 4·5단계를 하지 않고 Phase 5의 「팩 없이 끝낸 경우」 형식으로 보고한다.
4. **적재**: frontmatter에 식별자가 **없으면 신규** → Epic별로 팩의 「신규 적재」 호출, **있으면 기존** → 팩의 「본문 갱신」(본문 전체 교체, 식별자별). 아래 적재 규칙을 따른다.
5. **식별자 기록**: 적재 응답의 티켓 식별자를 frontmatter에 기록하고 재커밋한다(이후 본문 갱신의 키).

### SoT 분리 원칙 (필수)

티켓은 PRD·디스크립션과 달리 **운영 중 살아 움직이는 객체**다. 상태·담당자는 개발팀이 티켓 보드에서 실시간 바꾼다. 그래서 필드로 SoT를 가른다.

| 정보 | SoT | 반영 방향 |
|---|---|---|
| 본문(유저스토리·요구사항·인수조건) | git md | md → 티켓 도구 단방향(본문 갱신) |
| 상태·담당자·SP·코멘트·진행 | 티켓 보드 | md가 건드리지 않음 |

→ **md는 본문만 관리하고 보드 운영 필드(Status·Assignee·SP)를 절대 덮어쓰지 않는다.** 이게 무너지면 개발자의 보드 작업이 md 재적재로 초기화된다. 따라서 이 워크플로우에서 팩의 「속성 갱신」으로 상태·담당자·공수를 바꾸지 않는다.

### 파일 구조·경로

```
{project}/tickets/tickets.md   ← 모든 Epic + Story/Task 한 파일 (단일 파일 방식, 기본)
```

프로토타입·PRD와 같은 feature 디렉토리 하위 `tickets/`에 둔다. **Epic 순서 = frontmatter `epics` 배열 순서 = 본문 Epic 순서**이고, **child 순서 = frontmatter `children` 배열 순서 = 본문 child 순서**여야 한다. 각 child의 `epic_key`로 상위 Epic을 식별한다.

**분할 기준 — Epic 파일 방식.** 아래 둘 중 하나에 해당하면 본문을 Epic 단위 파일로 나눈다. 새로 작성할 때는 처음부터 나누고, 기존 단일 파일이 기준을 넘으면 다음 본문 개정 때 나눈다.

- `tickets.md`가 1,500줄을 넘거나 넘을 것으로 보인다.
- Epic이 4개 이상이다.

```
{project}/tickets/tickets.md        ← frontmatter만 둔다(Epic·child 목록, 식별자, 순서). 본문 없음
{project}/tickets/epics/E1.md       ← Epic E1 본문(`# {title}`) + 그 children 본문
{project}/tickets/epics/E2.md
```

- **나누는 이유**: 파일 하나가 길어지면 3가지 문제가 생긴다.
  - 작성·검토하는 모델이 뒤쪽 child를 덜 꼼꼼히 다룬다.
  - 같은 문장이 여러 child에 반복돼 문자열 치환 편집이 다른 child를 고치거나 실패한다.
  - 읽기 도구가 기본 2,000줄까지만 읽어 일부만 보고 작업할 수 있다.
- **Epic이 단위인 이유**: 신규 적재를 Epic마다 한 번 호출하므로 파일 단위와 적재 단위가 같아진다.
- **순서 규칙은 그대로다.** `epics` 배열 순서 = Epic 파일을 읽는 순서이고, 각 Epic 파일 안의 child 순서 = `children` 배열에서 그 `epic_key`를 가진 항목의 순서다.
- **frontmatter는 `tickets.md` 한 곳에만 둔다.** Epic 파일에 식별자나 SP를 다시 적지 않는다.
- **다른 스킬과의 호환**: `ai-dlc`의 prd-flow 가져오기(`rules/inception/prd-flow-import.md` Step 4)는 `tickets/epics/`가 있으면 frontmatter 순서대로 Epic 파일을 이어 붙여 읽는다. 경로나 파일 이름 규칙을 바꾸면 그 절도 함께 고친다. 그 가져오기는 child의 식별자 키를 정해진 이름으로 읽으므로, 식별자 키 이름은 팩이 정한 것을 그대로 쓰고 임의로 바꾸지 않는다.

### frontmatter 스키마 (YAML)

```yaml
---
prd_url: {PRD 문서 URL}
prd_version: {버전}
status_sot: board           # 상태·담당자는 티켓 보드가 SoT (md 미관리) 명시
epics:
  - key: E1
    ticket_id: {적재 후 기록}
    title: {Epic 제목}
    prd_epics: [EP-01, EP-03]
    labels: [area:report]
children:
  - key: S1
    epic_key: E1
    ticket_id: {적재 후 기록}
    type: Story
    title: {제목}
    story_points: 5
    labels: [area:report, feature:report-list, type:fe]
  # children 순서 = 본문 섹션 순서와 일치
---
```

- `ticket_id`는 적재 응답의 티켓 식별자를 적재 직후 기록·재커밋한다.
- `prd_epics`에는 해당 보드 Epic이 책임지는 PRD `EP-`를 기록한다. PRD Epic 전체의 티켓 커버리지는 이 값과 child 본문의 근거를 함께 대조한다.
- frontmatter 아래 본문: Epic은 `# {title}` + Epic 템플릿, 각 child는 `## {type}: {title}` + Story/Task 템플릿. Epic 파일 방식이면 본문은 `tickets/epics/{epic_key}.md`에 같은 형식으로 둔다.

### 적재 요청 조립 (md → 요청)

신규 적재는 md 본문을 팩이 정한 요청 형식으로 조립한다. `epics`의 각 항목마다 해당 `epic_key`의 children만 묶어 팩의 「신규 적재」를 **한 번씩** 호출한다. 요청에는 Epic의 제목·라벨·본문과, 각 child의 유형·제목·라벨·공수·본문이 들어간다.

### 적재 규칙

1. **신규 vs 기존 분기**: 각 Epic과 child의 `ticket_id`가 **비어 있으면 신규**다. 신규 Epic과 그 children은 팩의 「신규 적재」로 함께 올리고, 기존 티켓은 식별자별로 팩의 「본문 갱신」으로 본문 전체를 교체한다. Epic에는 `ticket_id`가 있는데 child 중 일부만 신규면, 그 신규 child를 팩의 「기존 Epic에 추가」로 적재한다. 이때 Epic을 새로 만들지 않고 children만 그 Epic 아래에 붙는다. 이미 만든 티켓을 다른 Epic으로 옮기거나 상위 연결이 빠진 티켓을 연결할 때는 팩의 「상위 연결 변경」을 쓴다(Story·Task의 상위는 Epic, Sub-task의 상위는 Story·Task만 허용). 티켓 도구에서 손으로 연결하도록 안내하지 않는다.
2. **Epic별 단일 호출(신규)**: Story/Task를 개별로 호출하지 않는다. Epic 하나와 그 children을 한 번의 신규 적재 호출로 적재한다. Epic이 여러 개면 Epic 수만큼 호출한다.
3. **검토·커밋 후 적재**: 적재 전 Phase 4.5 게이트를 통과하고 tickets.md를 커밋한 상태여야 합니다. 소스는 md, 적재는 그 md의 반영입니다.
3a. **업로드 전 검토 (필수)**: 신규 적재나 본문 갱신을 호출하기 전에(팩이 없어 적재하지 않을 때는 커밋 전에) 적재할 본문을 팩의 「업로드 전 검토」가 정한 스킬로 검토하고, 반영한 결과를 tickets.md에 커밋한다. 신규 적재와 기존 본문 교체 모두 해당하며, 사용자가 요청하지 않아도 생략하지 않는다.
    - 검토는 두 가지를 본다. 문장 가독성·용어 일관성·자기완결성, 그리고 티켓 도구에서 읽기 좋은 구조(제목 위계·표·목록 들여쓰기)다.
    - 의미가 바뀌는 교정은 사용자 확인 후 반영한다.
    - 인수 조건 제목 형식(`### AC {번호}. {그룹} [검증: …]`)과 앵커는 바꾸지 않는다.
4. **child type**: `Story`와 `Task`만 쓴다. Epic·Subtask는 child로 올리지 않는다. 결함 티켓의 유형은 QA 결함 모드에서 팩이 정한 값을 쓴다.
5. **상위 티켓·담당자 미포함**: children에 상위 식별자와 담당자를 넣지 않습니다(상위 연결은 팩의 「신규 적재」가 맡습니다). 상태·담당자·SP 등 운영 필드는 적재 후에도 md가 건드리지 않습니다(SoT 분리 원칙).
6. **child 상한**: Epic 하나의 children이 20개를 넘으면 Epic 분리 또는 사용자와 범위 조정. 팩이 다른 상한을 정하면 그것을 따른다.
7. **식별자 회수**: Epic별 적재 응답 티켓 식별자를 해당 `epic_key`의 children 순서대로 기록하고 재커밋한다.
8. **목록·링크 표기**: 번호 항목 아래의 설명은 네 칸 들여쓴 글머리표로 작성합니다. 링크는 URL 원문을 별도 줄이나 괄호로 노출하지 않고 `[표시 문구](URL)`로 작성합니다.

### 적재 후 표시 확인 (필수)

적재 호출이 성공해도 본문 적재가 끝난 것으로 보지 않는다. 팩의 「적재 후 확인」에 따라 올라간 본문의 목록 번호, 들여쓰기, 링크가 md와 같게 표시되는지 확인한다. 어긋나면 적재 완료로 보고하지 않는다. 같은 현상이 여러 티켓에서 재현되면 티켓을 손으로 하나씩 고치지 않고 변환 쪽 원인을 먼저 고친다.

### 라벨 규약 (area / feature / type)

| 프리픽스 | 의미 | 예시 | 대상 |
|---|---|---|---|
| `area:` | 기능 도메인 | `area:billing`, `area:auth` | 모든 티켓 |
| `feature:` | 세부 기능 | `feature:card-register` | 주로 Story |
| `type:` | 작업 성격 | `type:fe`, `type:be`, `type:infra` | children |

- Story/Task에는 `area:` 또는 `feature:`를 **최소 1개** 부여합니다(이후 담당자 자동 배정의 입력).

### 호출 후 응답 확인

팩이 정한 응답 형식으로 요청한 수와 만들어진 수가 같은지 확인한다. 일부만 만들어졌으면 어느 Epic이 성공하고 어느 Epic이 실패했는지 구분해 보고하고, 실패한 요청만 고쳐 다시 호출한다. 받은 식별자는 frontmatter의 식별자 키에 기록하고 재커밋한다.

팩에 「후속 연결」이 있으면 그 절차대로 적재 결과를 기록한다.

### Epic 본문 템플릿

보드 Epic 본문은 연결된 PRD Epic의 목적·범위·완료 상태를 압축해 재서술한다. PRD의 핵심 요구사항이나 정책 표를 복사하지 않는다.

```markdown
## 목적

{이 보드 Epic이 해결할 문제와 완료 후 확보되는 결과를 2~3문장으로 작성}

## 다루는 범위

- **포함**: {하위 Story·Task가 함께 만드는 결과}
- **제외**: {인접하지만 다른 Epic·V2·별도 문서가 맡는 범위}
- **의존성**: {선행 Epic·외부 시스템·결정}

## 완료 기준

- {하위 티켓이 모두 끝났을 때 확인할 Epic 수준 결과}
- {PRD가 정한 출시 기준이나 운영 상태}

## 근거

- {PRD 링크와 `EP-` 앵커·전체 명칭}
```

**작성 원칙:**
- 목적·범위·의존성·완료 기준은 Epic 본문만 읽어도 이해할 수 있게 압축해 쓴다.
- 세부 정책은 PRD·디스크립션의 안정적인 앵커를 참조하고 반복하지 않는다.
- PRD Epic 여러 개를 묶었으면 근거 절에 각 `EP-`의 전체 명칭을 적고, 왜 같은 보드 Epic으로 묶었는지 목적 또는 범위에서 드러낸다.

**작성 후**: 이 Epic 본문은 tickets.md의 해당 Epic 절에 적는다. 적재 요청으로 조립하는 방법은 팩의 「신규 적재」를 따른다.

## Phase 4: Story/Task 본문 작성

Phase 0-B에서 정한 작성 모드에 따라 각 Story/Task의 본문을 tickets.md의 child 절에 작성한다. Story/Task를 개별 생성하지 않고, 모든 본문을 완성한 뒤 Epic별로 팩의 「신규 적재」를 호출한다.

### Story 본문 템플릿: 디스크립션 있음(참조형)

```markdown
## 유저 스토리 (User Story)

- **As a** {구체적인 페르소나 또는 역할을 한국어로 작성}
- **I want to** {사용자가 수행하려는 행동을 한국어로 작성}
- **So that** {사용자가 얻는 가치나 기대효과를 한국어로 작성}

## 요구사항 (Requirements)

### A. {기능 범주 1}

- {이 Story가 지켜야 할 업무 규칙을 「~해야 한다」 문장으로 하나씩 작성. 권한·허용 조건·값 저장·상태 변화·실패 보존을 포함하고, 화면 배치·문구·표시 형식만 앵커로 미룬다}

### B. {기능 범주 2}

- {사용자가 할 수 있게 되는 일과 시스템이 보장할 상태를 작성}

### C. {기능 범주 3, 필요할 때만 추가}

- {티켓 고유 제약이나 다른 Story와의 경계를 작성}

## 다루는 범위

- **입력으로 받는 것**: {전제로 삼는 데이터·상태}
- **결과로 만들어지는 것**: {완료 후 생기는 화면·행동·상태}
- **의존성**: {선행 Story·Task·외부 계약}
- **이 티켓에서 다루지 않는 것**: {다른 Epic·티켓·V2가 맡는 범위}

## 예외와 실패 시 동작

| 상황 | 이 작업이 해야 하는 일 |
|---|---|
| {대표 예외 또는 실패 범주} | {사용자와 시스템이 확인할 수 있는 결과를 정책 상세 없이 작성} |

## 인수 조건 (Acceptance Criteria)

### AC 1. {사용자 결과}  [검증: 🖥 화면 확인]  [릴리스: 필수]
- [ ] {참조한 정책이 적용된 뒤 사용자가 확인할 수 있는 결과}

### AC 2. {연동 결과}  [검증: 🔗 통합 테스트]
- [ ] {화면과 서버·다른 컴포넌트가 연결됐음을 확인할 수 있는 결과}

## 검증 결과 (Verification) — 개발자 기입, Done 전 필수

> 검증 결과 기록 방식은 공통 규칙을 따른다.

## 참고 자료

- PRD: {링크}, {EP-03 · 회신 인정과 판단 재개}
- 프로토타입 디스크립션: {링크 또는 경로}, {[2-4] · 제출 인정 뒤 상태}
```

참조형에서도 `요구사항`을 생략하지 않는다. 요구사항은 기능 결과를 범주별로 설명하고, 상세 화면 정책은
되풀이하지 않는다. 인수 조건은 `AC 1`처럼 번호만 적거나 “디스크립션대로 동작한다”로 끝내지 않고,
무엇을 검증해 Pass·Fail을 가를지는 티켓 안에 적는다.

### Story 본문 템플릿: 디스크립션 없음(상세형)

별도 디스크립션이 없는 Story는 사용자 관점의 기능 계약을 티켓에 상세하게 작성한다. 화면 작업인데 디스크립션을 나중에 만들 예정이면 Phase 0-B의 `정책 임시 정본` 규칙을 따른다.

```markdown
## 유저 스토리 (User Story)

- **As a** {구체적인 페르소나 또는 역할을 한국어로 작성}
- **I want to** {사용자가 수행하려는 행동을 한국어로 작성}
- **So that** {사용자가 얻는 가치나 기대효과를 한국어로 작성}

## 요구사항 (Requirements)

### A. {결과 영역 1 이름}

- {상세 설명}
    - **{세부 항목 1}**: {구체적 스펙}
    - **{세부 항목 2}**: {구체적 스펙}

### B. {결과 영역 2 이름}

- {상세 설명}
    - **입력**: {사용하거나 받는 정보}
    - **처리 결과**: {어떤 상태나 결과가 생기는지}

### C. {결과 영역 3 이름}

- **{동작 1}**: {정책과 동작 상세}
- **{동작 2}**:
    - {저장 버튼 동작 설명}
    - {저장 후 후처리 로직 설명}

## 다루는 범위

- **입력으로 받는 것**: {이 티켓이 전제로 삼는 데이터·상태}
- **결과로 만들어지는 것**: {이 티켓이 끝나면 생기는 것}
- **적용 대상**: {어디까지 적용되는지}
- **이 티켓에서 다루지 않는 것**: {인접하지만 이 티켓 밖인 것과 그것을 다루는 곳}

## 예외와 실패 시 동작

| 상황 | 이 작업이 해야 하는 일 |
|---|---|
| {정상 경로를 벗어나는 상황 1} | {그때 무엇을 하고 무엇을 하지 않는지} |
| {상황 2} | {동작} |

## 개발자가 정할 것 (해당 내용이 있을 때만 쓴다)

- {업무 결과는 이 티켓이 정하지만 구현 방법은 개발자가 정하는 항목}

## 착수 전 확인이 필요한 것 (해당 내용이 있을 때만 쓴다)

- **{확인 항목}**: {무엇이 정해지지 않았고 누가 언제 정하는지}

## 인수 조건 (Acceptance Criteria)

> 각 AC 그룹 제목 옆에 **[검증: {방법}]**을 표기한다(검증 방법 4분류는 "Story 작성 원칙 4c" 참조). 화면에서 관찰할 수 없는 계산·무결성·배치 로직은 반드시 🧪 단위 또는 🔗 통합으로 표기해 개발자 테스트 대상임을 드러낸다. 실패하면 배포를 막아야 하는 AC 그룹에는 검증 태그 뒤에 **[릴리스: 필수]**를 붙인다(원칙 4d). 태그가 없는 AC는 일반 AC다.

### AC 1. {그룹 이름}  [검증: 🖥 화면 확인]  [릴리스: 필수]

    - 검증 케이스: {입력값일 때 기대 출력}. 경계: {임계 바로 아래·임계·임계보다 하나 큰 값}

- [ ] {저장·집계·무결성 결과 — fixture로 재현할 상태를 명시}

## 검증 결과 (Verification) — 개발자 기입, Done 전 필수

> Done으로 옮기기 전에 AC마다 확인한 결과를 이 티켓의 코멘트로 남긴다. 적는 것은 AC 번호, Pass 또는 Fail, 예외 케이스를 확인했으면 그 내용, PM이 판단해야 할 것이 있으면 짧은 메모다. 검증자와 시각은 자동으로 붙는다. 테스트 명령·커밋 같은 개발 정보는 적지 않는다. 검증 결과를 md 본문이 아니라 코멘트에 두는 이유는, 티켓 본문을 다시 올리면 본문이 통째로 교체되지만 코멘트는 보존되기 때문이다. 코멘트를 남기는 도구는 팩의 「검증 기록」을 따른다.

## 참고 자료
- {관련 화면 설계서, 와이어프레임, API 문서 등}
```

**Story 작성 원칙:**
1. **유저 스토리**는 반드시 `As a` / `I want to` / `So that` 형식으로 쓴다. 영어는 세 표지만 유지하고 각 표지 뒤의 역할·행동·가치는 한국어로 1~2문장 작성한다
2. **본문 상세도는 작성 모드로 결정**한다.
   - 디스크립션 있음: 기본 Story 템플릿을 유지하고 `요구사항`을 기능 범주별로 작성한다. 서버·데이터 업무 규칙은 「~해야 한다」 문장으로 쓰고, 화면 배치·문구·표시 형식과 상세 계산 절차만 `참고 자료`의 안정적인 앵커로 찾게 한다(Phase 0-B 「참조형 경계」).
   - 디스크립션 없음: 다른 정본이 소유하지 않는 입력·출력·상태·실패·복구·무결성·운영 제약을 결과 영역별로 상세하게 쓴다.
   - 별도 인터페이스 사양이나 공통 정책이 있으면 작성 모드와 관계없이 그 문서를 참조하고 전문을 복사하지 않는다.
3. **인수 조건**은 그룹별(AC 1, AC 2, AC 3 ...)로 분류. 체크리스트 형태, Pass/Fail 판정 가능한 수준의 구체성. **각 AC 그룹에 검증 방법을 표기한다**(원칙 4c).
4a. **사용자 인수조건 (화면 확인 대상)**: 사용자가 화면에서 경험하는 결과는 **사용자 경험 기준**으로 쓴다. 내부 구현·API 동작·서버 응답 코드 기준 금지.
   - ❌ "POST /api/alerts 호출 후 200 응답 시 완료"
   - ❌ "DB에 데이터가 insert되어야 한다"
   - ✅ "[저장] 버튼 클릭 후 입력한 정보가 목록에 정상적으로 표시되어야 한다"
   - ✅ "임계값 초과 감지 후 30초 내에 담당자 화면 상단에 알림이 노출되어야 한다"
4b. **검증 요구사항 (화면 밖 로직 — 빼지 말 것)**: 계산식·판정 로직·데이터 무결성·배치처럼 **화면에서 관찰할 수 없지만 반드시 검증돼야 하는** 동작은 AC에서 누락하지 않는다. 사용자 경험으로 표현할 수 없다는 이유로 이런 AC를 빼면, 백엔드 로직 결함이 검증 없이 배포된다. 이 계층에 한해 내부 기준 서술을 허용하되, 각 AC에 검증 케이스를 병기하고 검증 방법은 그 AC가 속한 그룹 제목 줄에 표기한다.
   - ✅ "두 비율을 결합할 때 낮은 쪽 비율에 더 큰 가중치가 실려야 한다(기하평균). 검증 케이스: (0.8, 0.1)이면 약 0.28, 한쪽이 0이면 0" (🧪 단위 테스트 그룹에 둔다)
   - ✅ "버전·라운드가 다른 보정값은 어떤 경우에도 적용되지 않아야 한다. 불일치는 전부 기본 예측으로 처리한다" (🔗 통합 테스트 그룹에 둔다)
   - ✅ "현상·원인·조치 태그의 함께 등장한 횟수 집계 테이블이 1일 1회 자동 갱신되어야 한다" (🔗 통합 테스트 그룹에 둔다)
   - **검증 태그는 AC 그룹 제목 줄에만 둔다.** `[검증: ...]`를 체크리스트 줄이나 설명 줄 끝에 붙이지 않고, 제목 줄 하나에 두 번 쓰지도 않는다. 검증 기록을 받는 도구는 본문의 `[검증:` 태그 수가 AC 제목 줄 수보다 많으면 AC에 연결되지 않은 태그가 있다고 보고 그 티켓의 검증 기록과 완료 처리를 모두 거부할 수 있다. 한 그룹 안에서 검증 방법이 갈리면 그룹을 나눠 각 제목 줄에 검증 방법을 하나씩 표기한다.
   - **화면 밖 로직 AC에 검증 방법(🧪 또는 🔗)이 없으면 Phase 4.5에서 반려한다.**
4c. **검증 방법 4분류** (각 AC 그룹 제목에 표기):

   | 표기 | 검증 방법 | 대상 |
   |---|---|---|
   | 🖥 화면 확인 | 자동 QA 또는 사람이 화면에서 확인 | 사용자가 화면에서 관찰 가능한 결과 |
   | 🧪 단위 테스트 | 개발자가 함수 단위로 입력·출력 검증 | 계산식·판정 로직·경계값(임계 바로 위아래) |
   | 🔗 통합 테스트 | 개발자가 DB·배치·여러 컴포넌트를 연결해 검증 | 저장·집계 갱신·무결성·fixture로 재현하는 예외 |
   | 🔌 수동·물리 | 사람이 물리적으로 재현 | 센서 연결 해제 등 물리 조작 |
4d. **릴리스 필수 표기** (AC 그룹 제목의 검증 태그 뒤에 `[릴리스: 필수]`):
   - **뜻**: 이 AC가 Fail이면 해당 기능을 배포하지 않는다. 태그가 없는 일반 AC가 Fail이면 결함으로 관리하되 배포 여부는 PM이 판단한다.
   - **붙이는 기준 3가지**. 하나 이상에 해당하고 그 근거를 한 줄로 댈 수 있을 때만 붙인다.
     1. PRD가 정한 출시 수용 기준에 걸린다. 수용 지표의 목표가 "0건"이나 "100%"로 적힌 항목이 대표적이다.
     2. 실패하면 되돌리기 어려운 피해가 난다. 권한 밖 행동 노출, 안전 정보 누락, 데이터 무결성 훼손, 같은 결과의 중복 집행이 여기에 든다.
     3. 실패하면 그 기능의 핵심 흐름이 성립하지 않는다.
   - **정하는 사람은 PM이다.** 스킬은 후보를 붙여 초안을 만들고, 적재 전 검토에서 PM이 확정한다(Phase 3 흐름 2단계).
   - **모든 AC를 필수로 두지 않는다.** 전부 필수면 배포 게이트가 구분력을 잃는다.
   - **티켓 우선순위와 다르다.** 우선순위(P0~P3)는 티켓을 언제 만드는지를 정하는 보드 속성이다. 릴리스 필수는 AC 하나가 배포를 막는지를 정하는 본문 태그다. 우선순위 P2 티켓에도 릴리스 필수 AC가 있을 수 있다.
   - **태그 순서를 지킨다.** `### AC {번호}. {그룹 이름}  [검증: {방법}]  [릴리스: 필수]` 순서로 한 줄에 쓴다. 검증 기록을 받는 도구가 이 줄에서 검증 태그를 읽는다.
5. **자기완결성**: Phase 0-B의 자기완결성 기준을 적용한다. "PRD 참조", "앞서 협의된 바와 같이"처럼 대상이 불명확한 참조만 금지하며, 문서 위치·앵커·전체 명칭을 갖춘 참조는 허용한다. 본문을 다 쓴 뒤 공통 가드레일의 **자기완결성 검사** 여덟(낱말·개수·인용·확정 여부·주어와 목적어·운영 주체·동작 한정·분류 축)을 반드시 밟는다
6. **용어 일관성**: Phase 1에서 추출한 용어 사전을 준수한다. 같은 개념을 다른 명칭으로 표기하지 않는다
7. **글쓰기 가드레일**: 아래 공통 가드레일을 적용한다

```markdown
## 검증 결과 (Verification) — 개발자 기입, Done 전 필수

> 각 AC의 검증 결과를 이 티켓의 코멘트에 남긴다(형식은 Story와 동일: AC 번호, Pass 또는 Fail, 확인한 예외 케이스, PM이 판단할 메모. 테스트 명령·커밋은 적지 않는다). 완료 처리 때 🧪·🔗 AC의 검증 코멘트를 확인한다.
```

**Task 생성 기준 — 아래 조건을 모두 만족할 때만 생성:**
1. **Story와 독립**: 특정 Story 하나에만 귀속되는 작업이 아닌, 복수 Story의 선행 조건이거나 어떤 Story에도 묶이지 않는 작업
2. **PM이 정의해야 할 요구사항이 존재**: 완료 기준, 범위, 제약 조건이 PM 수준에서 명확히 정의되어야 하는 경우. 개발팀이 알아서 판단할 순수 기술 작업은 Task로 만들지 않는다
3. **Sprint 계획에 포함해야 하는 단위**: Story Points를 부여하고 Sprint에 배치해야 할 규모의 작업

**Task 작성 원칙:**
1. **계약 상세와 구현 방법을 구분**한다. 디스크립션 없음 상세형에서는 이미 정해진 API·데이터 저장소·외부 시스템처럼 작업 대상을 식별하는 기술 용어와 입력·출력·상태·실패 계약을 쓸 수 있다. 라이브러리 선택, 내부 구조, 배포 방식처럼 결과를 바꾸지 않는 구현 방법은 지정하지 않고 「개발자가 정할 것」으로 분리한다
2. **PM 관점 요구사항만 정의**: "무엇이 가능해져야 하는가", "어떤 조건이 충족되어야 하는가"만 기술
3. **배경 및 필요성**: 현재 상황과 이 작업이 필요한 이유를 사용자·서비스 관점으로 기술
4. **인수 조건**: 결과 상태 확인 가능한 수준으로 기술. 구현 방법·기술 스택을 조건으로 쓰지 않는다
5. **자기완결성**: Phase 0-B의 자기완결성 기준을 적용한다. 상세 정책이 별도 인터페이스 사양에 있으면 그 문서의 안정적인 앵커도 같은 방식으로 참조한다. 본문을 다 쓴 뒤 공통 가드레일의 **자기완결성 검사** 여덟(낱말·개수·인용·확정 여부·주어와 목적어·운영 주체·동작 한정·분류 축)을 반드시 밟는다
6. **용어 일관성**: Phase 1에서 추출한 용어 사전을 준수한다
7. **글쓰기 가드레일**: 아래 공통 가드레일을 적용한다

#### 가독성 가드레일

- **화살표(`→`) 금지**: 인과·순서 표현은 `"A한 다음 B"`, `"A이므로 B"` 등 서술형으로
- **`&` 기호 금지**: 한국어 문서에서 `&`는 "및"으로 표기. 단 코드·기술 표기(`FCM/APNs`, `AS-IS`)는 허용
- **불필요한 영어 금지**: `"리뷰"` → `"검토"`, `"이슈"` → `"문제"`, `"스케줄"` → `"일정"`. 단 API, SaaS, PRD 등 도메인 관행 용어는 허용
- **상태값·열거형 코드 한국화**: `review`, `no_issue`, `esc`, `inprog`, `proposed` 등 시스템 상태 코드가 한국어 본문에 등장할 때는 한국어 명칭을 우선 사용하고 코드는 생략하거나 괄호 병기한다. 예) `review와 no_issue 상태를 합산한다` → `검토 완료와 이상 없음 상태를 합산한다` / `에스컬레이션(esc) 상태를 필터한다`
- **약어 최초 등장 시 풀어 쓰기**: `SWP(Smart Working Place)` 형태로

#### 자기완결성 검사 (본문 작성 뒤 필수)

본문을 다 쓴 뒤 티켓마다 아래 여덟을 자문한다. 하나라도 걸리면 고친 뒤 적재한다. 자기완결성의 뜻은 Phase 0-B가 정한다. 참조가 있다는 이유로 실패시키지 않고, 참조 대상이 없거나 앵커·전체 명칭이 없어 무엇을 따라야 하는지 알 수 없을 때 실패시킨다.

| 검사 | 판정 질문 | 걸렸을 때 |
|---|---|---|
| **낱말** | 이 낱말이 **보편적으로 통용되는가.** 검색하거나 표준 문서에서 찾았을 때 같은 뜻이 나오면 통용되는 것이다 | 첫 등장에서 괄호로 풀거나 통용되는 말로 바꾼다. 프로젝트에 용어집이 있으면 함께 본다 |
| **개수** | 개수를 말했으면 그것이 각각 무엇인지 밝혔는가 | 항목을 이름과 함께 나열하고 예를 붙인다(AI 투 패턴 13번) |
| **인용** | 인용한 문서·절·코드가 지금 실제로 있는가 | 없으면 지우거나 현재 위치로 고친다. 문서가 개정되며 절 번호가 밀리는 일이 잦다 |
| **확정 여부** | 정해지지 않은 것을 정해진 것처럼 쓰지 않았는가 | 미결이면 미결로 적고 누가 언제 정하는지 밝힌다. 「착수 전 확인이 필요한 것」 절로 뺀다 |
| **주어와 목적어** | 문장마다 **누가 무엇을 하는지**가 적혀 있는가. 「조회한다」·「전달한다」·「대조한다」 같은 동사를 쓴 자리에서 그 동작의 주체와 대상을 짚을 수 있는가 | 주체와 대상을 문장 안에 써 넣는다. 아래 판정 예시를 본다 |
| **운영 주체** | 운영 중에 일어나는 예외의 수신자로 **서비스 밖의 사람**을 적지 않았는가 | 기획자·설계자는 돌아가는 시스템 안에 들어가지 않는다. 운영 중 예외이면 실제 수신자로 바꾸고, 정할 수 없으면 「착수 전 확인이 필요한 것」으로 뺀다. 다만 착수 시점의 설계·설정 작업이면 기획자가 수신자로 맞다 |
| **동작 한정** | 「예외와 실패 시 동작」의 각 칸이 **개발할 때 만들 동작**을 적고 있는가 | 「검토한다」·「다시 본다」·「확인 대상으로 올린다」·「~가 정한다」는 사람이 하는 일이라 구현할 수 없다. 그 상황에서 시스템이 무엇을 하는지로 바꾸고, 사람이 정할 몫은 「착수 전 확인이 필요한 것」으로 옮긴다. 옮길 것도 만들 동작도 없으면 그 칸을 지운다 |
| **분류 축** | 생성 주체·사용자 영역·카테고리·유형·표시 정보·필터가 한 문장에 섞여 실제 화면과 다르게 읽히지 않는가 | Phase 0-B의 「분류 축과 화면 표시 대조」 표로 돌아가 각 축의 역할과 표시 위치를 나눠 쓴다 |

**주어와 목적어 검사의 판정 예시.** 한국어는 주어와 목적어를 생략해도 문장이 되므로, 쓴 사람은 읽히는데 읽는 사람은 무엇을 가리키는지 모르는 문장이 쉽게 만들어진다. **판정 방법은 그 문장에서 동사를 찾아 「누가?」와 「무엇을?」을 소리 내어 묻는 것이다.** 답이 그 문장 안에 없으면 걸린 것이다.

| 걸린 문장 | 무엇이 빠졌나 | 고친 문장 |
|---|---|---|
| 감시 대상은 값이 도착한 센서만으로 구성돼 | 「감시 대상」이 무엇의 목록인지, 「도착」이 어디에서 어디로인지가 없다 | 온톨로지 판정이 지켜보는 센서 목록은 실제로 값을 보내온 센서만으로 만들어진다 |
| 등록 목록과 도착 데이터를 대조해야 한다 | 무엇을 어디에 등록한 목록인지, 그 데이터를 누가 보냈는지가 없다 | 서비스에 등록된 센서 목록과 그 센서들이 실제로 보내온 측정 데이터를 맞대어 봐야 한다 |
| 조회 결과에는 무엇을 측정하는지가 함께 있어야 판단이 가릴 수 있다 | 누가 조회하는지, 무엇을 가리는지가 없다 | 판정 쪽이 받은 답에는 각 센서가 무엇을 측정하는지가 함께 담겨야, 그 센서를 어느 판단의 입력으로 쓸지 가릴 수 있다 |
| 같은 등록 변경이 두 번 도착했다 → 연결 상태를 다시 바꾸지 않는다 | 무엇의 어떤 상태인지, 왜 두 번 도착하는지가 없다 | 한 번 일어난 등록·수정·삭제가 재전송으로 두 번 전달되면, 첫 번째로 반영한 연결의 유효 기간을 다시 찍지 않는다 |

**표 셀과 인수 조건에도 같은 기준을 적용한다.** 짧게 쓰려고 주어를 지우는 자리가 대부분 표 셀이다.

**동작 한정 검사의 판정 예시.** 「예외와 실패 시 동작」 표는 개발자가 그대로 구현할 수 있어야 한다. 사람의 판단과 시스템의 동작이 한 칸에 섞이면 무엇을 만들지가 흐려진다.

| 걸린 칸 | 왜 걸리나 | 고친 칸 |
|---|---|---|
| 그 사실을 남기고 기획자 확인 대상으로 올린다 | 기획자는 돌아가는 시스템 안에 없어 구현할 대상이 아니다 | 그 판단에 경로를 지정하지 않고 경로 미지정으로 남긴다 |
| 그 판단의 분류 자체를 다시 본다 | 「다시 본다」는 사람이 하는 일이다 | 그 판단에 중앙 조회 경로를 지정하지 않는다. 두 조합 자체를 허용하지 않는다 |
| 다시 세워야 하는지는 기획자 판단 사항이므로 착수 전 확인 항목으로 둔다 | 표 안에서 다른 절을 가리키는 안내이지 동작이 아니다. 그 절에 이미 같은 내용이 있으면 중복이다 | 다시 세우는 동작은 이 티켓에 넣지 않는다 |

**낱말 검사의 판정 예시.** `gRPC`·`InfluxDB`·`임계값`은 검색하면 같은 뜻이 나오므로 그대로 쓴다. 반면 그 프로젝트 회의에서 만들어진 말(예: 특정 프로젝트의 `감시 자리`·`대응 등록부`·`도메인 팩`)은 밖에서 같은 뜻이 나오지 않으므로 풀어 쓴다. **판정 기준은 어려운가 쉬운가가 아니라 밖에서 같은 뜻이 통하는가다.**

#### 앵커 ID 병기 (동기화용)

티켓이 PRD가 SoT인 정보(Epic 범위·결정·KPI·OQ)나 디스크립션이 SoT인 수식을 인수 조건·요구사항의 **판단 기준**으로 삼을 때, 해당 앵커 ID를 괄호로 병기한다.
- 예: "에스컬레이션 대상 정렬 (앵커 D-4)", "첫 제출 승인률 기준 (앵커 K-3)"
- 앵커 종류·네이밍(`EP-{n}`, `F-{n}`, `D-`, `K-`, `OQ-`)은 `prd-sync` 스킬의 앵커 체계 규약을 따른다.
- 단, 본문 가독성을 해치지 않도록 **AC 기준값이 PRD 결정이나 디스크립션 수식에 종속될 때만** 병기한다. 사용자 경험 서술 자체에는 코드를 단독으로 노출하지 않는다.
- 병기는 이후 변경 동기화(prd-sync)의 교차 검색 키가 된다. 누락하면 PRD·디스크립션 변경 시 해당 티켓이 동기화에서 빠진다.

#### PRD 특화 금지 표현

- `'쉽고 직관적인 화면을 띄워줘야'`, `'친절히 유도해야'` 등 구현 세부 사항 침범 표현 금지
- 버튼 색상, 레이아웃 등 디자인 구현 지정 금지 (요구사항·인수 조건은 동작 단위로만)
- Happy Path만 서술하고 오류 분기 미정의 금지 → 인수 조건에 오류·예외 케이스 반드시 포함
- **부정형 작업 지시의 스펙 변환 금지**: 대화 중 "~는 표시하지 않는다", "~는 빼줘" 같은 부정형 지시를 AC나 요구사항 항목으로 변환하여 기재하지 않는다. 티켓은 표시되는 것만 기술하면 충분하다. 표시 항목 목록에 없으면 표시되지 않는다는 의미다

## Phase 4.5: 독립 Evaluator AC 검토 루프 (적재 전 게이트)

tickets.md를 커밋·적재하기 전에, 티켓이 **스킬 정책대로 정확히 작성됐고 인수조건이 예외 케이스를 포괄하는지** 독립 Evaluator로 검증한다. 정책 위반·잘못 작성된 내용(오분류·PRD 왜곡)·AC 케이스 누락을 적재 후가 아니라 적재 전에 잡는 게이트다. md가 SoT이므로 여기서 잡으면 커밋·적재 전에 고칠 수 있다. **분량을 채우는 검사가 아니다** — 내용이 많아도 정책 위반이면 갭이고, 간결해도 정책·정확성·커버리지를 충족하면 통과다.

공통 표준(2단 검증·종료 4출구·캘리브레이션·self-eval 금지·보상 해킹 금지)은 [evaluator-loop.md](../inspection-mode/references/evaluator-loop.md)를 따른다. 아래는 prd-to-tickets 적용분이다.

### 4.5-0. 적용 여부 (효용 게이트)
- **필수**: PRD 모드 신규 적재, 기존 티켓 본문 대폭 개정.
- **생략**: Backlog 경량 티켓(정답 수렴형 명세가 아님), 오타·문구 단순 수정.

### 4.5-1. 1단 — 결정론 검증 (먼저)
Evaluator를 띄우기 전에 grep으로 **정책 위반·누락**을 기계적으로 잡는다. 이걸 LLM 평가에 맡기지 않는다.
- **빈 AC**: 모든 Story/Task에 `## 인수 조건` 섹션과 최소 1개 AC가 있는가.
- **기본 템플릿 유지**: 모든 Story가 `유저 스토리`·`요구사항`·`다루는 범위`·`예외와 실패 시 동작`·`인수 조건`·`검증 결과`·`참고 자료`를 가지는가. 디스크립션 유무는 기본 템플릿을 바꾸지 않고 요구사항의 상세도만 바꾼다.
- **유저 스토리 언어**: `As a`·`I want to`·`So that` 표지 뒤의 역할·행동·가치가 한국어로 작성됐는가.
- **작성 모드 식별**: Phase 2에서 승인한 티켓별 작성 모드와 실제 본문 상세도가 일치하는가. `정책 참조` 같은 별도 링크 표의 유무로 모드를 판정하지 않는다.
- **정본 중복**: 참조형 티켓이 디스크립션의 화면 배치·문구·표시 형식이나 상세 계산 절차(표·수식·축 계산)를 본문에 다시 풀어 썼는가. 복제된 화면 표현은 제거하고 앵커 참조만 남긴다. 권한·허용 조건·값 저장·상태 변화·실패 보존 같은 업무 규칙 문장은 중복이 아니다(Phase 0-B 「참조형 경계」).
- **업무 규칙 누락**: 참조형 티켓의 요구사항이 범주마다 요약 한두 문장뿐인가. 그렇다면 앵커가 가리키는 디스크립션 정책에서 「화면이 없어도 서버와 데이터가 지켜야 하는 규칙」을 뽑아 요구사항에 빠졌는지 대조한다. 빠진 규칙이 있으면 반려한다.
- **Task 계약·구현 경계**: 상세형 Task의 기술 용어가 이미 정해진 작업 대상·계약을 식별하는가, 아니면 미확정 라이브러리·내부 구조·배포 방식을 지정하는가. 후자만 반려한다.
- **자기완결성 위반**: "PRD 참조"·"앞서 협의된"·"별도 논의된"처럼 문서 위치·앵커·전체 명칭이 없는 참조가 있는가. 정확한 앵커 참조는 허용한다.
- **Phase 0 drift 재확인**: PRD `EP-`별 범위가 프로토타입·디스크립션 실제와 일치하는가.
- **예외 커버리지**: 상세형은 `## 예외와 실패 시 동작`과 최소 1행을 가져야 한다. 참조형은 오류·예외 정책을 다루는 디스크립션 앵커와 그 결과를 검증하는 AC가 있어야 하며, 정책 전문을 반복하지 않는다.
- **개수만 밝힌 집합**: `N 가지`·`N 갈래`·`N 개로 나눈다` 뒤 다섯 줄 안에 그 항목들의 나열이 없는가(AI 투 패턴 13번).
- **AC 번호 형식**: AC 제목의 번호가 `AC 1`, `AC 2`처럼 1부터 이어지는 정수인가(하위 번호가 필요하면 `AC 1.1`). `AC 1a`처럼 글자가 붙은 번호는 검증 기록을 받는 도구가 AC 제목으로 인식하지 못해, 그 티켓의 검증 기록과 완료 처리가 모두 실패할 수 있다(2026-09-11 실제로 7건에서 발생해 적재 전에 잡았다).
- **릴리스 필수 표기 형식**: `[릴리스:` 태그가 AC 그룹 제목 줄에만 있고, 같은 줄의 검증 태그 뒤에 오며, 값이 `필수` 하나인가. 본문 체크리스트 줄에 붙은 것은 반려한다.
- **검증 태그 위치**: `[검증:` 태그가 AC 그룹 제목 줄(`### AC {번호}. {그룹 이름}`)에만 있고 제목 줄마다 하나씩인가. 체크리스트 줄·설명 줄에 붙은 태그와 한 제목 줄에 두 번 쓴 태그는 반려한다. 이런 태그가 하나라도 있으면 검증 기록을 받는 도구가 티켓 전체의 검증 태그를 해석하지 못해 검증 기록과 완료 처리가 모두 막힐 수 있다(Story 작성 원칙 4b).
- **없는 것을 인용**: 티켓이 인용한 문서의 절 번호·프로토콜 코드·항목 번호가 그 문서에 실제로 있는가. **문서가 개정되며 절이 밀리거나 코드가 삭제돼도 티켓 인용은 남는다.**
- **분류 축 대조**: 분류·필터 Story에서 생성 주체·사용자 영역·카테고리·유형·표시 정보·필터를
  각각 답했는가. 카드의 표시 값과 필터의 선택 값·그룹 제목이 프로토타입 화면과 일치하는가.

Epic 파일 방식이면 아래 명령의 `tickets.md`를 `epics/*.md`로 바꿔 Epic 파일 전체에 돌린다. 개수 대조(티켓 수·AC 절 수·요구사항 절 수)는 Epic 파일을 합한 값으로 frontmatter `children` 수와 맞춘다.

```bash
grep -nE "^## (Story|Task):" tickets.md    # 티켓 수
grep -c "인수 조건" tickets.md              # AC 섹션 수 — 티켓 수와 일치해야
grep -c "^## 요구사항" tickets.md              # Story 수와 일치해야 함
grep -n "^## 정책 참조" tickets.md             # 출력이 있으면 링크 표가 요구사항을 대신한 옛 형식
grep -nE "PRD 참조|앞서 협의|별도 논의" tickets.md    # 앵커·전체 명칭이 없는 모호한 참조 후보
grep -nE "(두|세|네|다섯|여섯) (가지|갈래|개)" tickets.md   # 나열이 뒤따르는지 눈으로 확인
grep -oE "§[0-9]+(\.[0-9]+)*|`P-[A-Z-]+`" tickets.md | sort -u   # 인용한 절·코드를 원문에서 실재 확인
grep -nE "^#{1,6} AC [0-9.]*[0-9][a-zA-Z]" tickets.md   # 출력이 있으면 AC 번호 형식 위반
grep -n "\[릴리스:" tickets.md | grep -vE "^[0-9]+:#{1,6} AC [0-9.]+.*\[검증: [^]]+\] +\[릴리스: 필수\]$"   # 출력이 있으면 형식 위반
{ grep -n "\[검증:" tickets.md | grep -vE "^[0-9]+:#{1,6} *AC [0-9.]+"; grep -n "\[검증:.*\[검증:" tickets.md; }   # 출력이 있으면 검증 태그 위치 위반(제목 줄 밖·한 줄에 둘 이상)
```

### 4.5-2. 2단 — 독립 Evaluator (Agent 도구)
목적은 **분량이 아니라 정책 부합·정확성·커버리지**다. 이 스킬이 이미 가진 정책을 합격 기준(Sprint Contract)으로 삼아 6 lens로 판정한다. Agent 도구를 `subagent_type: evaluator`로 지정해 호출한다(생성 컨텍스트 비전달). 이름을 지정하지 않으면 범용 에이전트가 떠서 "애매하면 FAIL" 판정 규율이 적용되지 않는다. evaluator 에이전트가 설치돼 있지 않으면 범용 에이전트로 대체하지 않고 4.5-4의 에스컬레이션(독립 검증 미완료)으로 처리한다. 입력: tickets.md + PRD + 합격 기준(아래 절 인용) + 캘리브레이션.

| Lens | 무엇을 본다 | 합격 기준 (이 스킬 내 절) |
|---|---|---|
| **정책 준수** | 글쓰기 가드레일·제목 규칙, Story/Task 분류 원칙, 작성 모드, Task 계약·구현 경계, 자기완결성, 용어 일관성, SP 산출 기준 준수 | "Phase 0-B", "공통 글쓰기 가드레일", "주의사항", "Story Points 산출 기준" |
| **정확성(오류 없음)** | 잘못 작성된 내용 — PRD 왜곡·요구사항 오기, 잘못된 Story/Task 분류, SP 과대·과소, 앵커 오류, 생성 주체를 화면 분류명으로 쓴 오류, 카테고리와 유형의 표시 위치를 뒤바꾼 오류 | "분할 판단 기준", "Story vs Task 분류", "분류 축과 화면 표시 대조" |
| **AC 예외 커버리지** | 인수조건이 happy·edge·error·경계·권한·예외 케이스를 포괄하는가. 정상 흐름만 있지 않은가 | "인수 조건 작성 원칙(전체 공통)", "AI 기능 AC 케이스 프레임워크" |
| **검증 방법 표기** | 화면 밖 로직·무결성·배치 AC에 검증 방법(🧪 단위/🔗 통합)이 표기됐는가. 계산·판정 AC에 검증 케이스·경계값이 병기됐는가. 화면으로 관찰 불가능한 로직이 AC 자체에서 누락되지 않았는가. 검증 방법 없는 화면 밖 로직 AC는 반려 | "Story 작성 원칙 4b·4c" |
| **릴리스 필수 근거** | `[릴리스: 필수]` AC마다 원칙 4d의 기준 3가지 중 하나에 해당하는가. PRD의 출시 수용 기준마다 그것을 확인하는 필수 AC가 최소 1개 있는가. 근거 없이 붙은 필수와 수용 기준에 대응하는 필수가 없는 경우를 각각 갭으로 낸다 | "Story 작성 원칙 4d" |
| **정본 분리·범위 정합성** | 범위 안의 PRD `EP-`가 보드 Epic과 children에 빠짐없이 매핑됐는가. 참조형 티켓이 화면 표현을 복제하지 않았는가. 반대로 업무 규칙(권한·허용 조건·값 저장·상태 변화·실패 보존)을 요구사항에서 빼고 앵커로만 넘기지 않았는가. 티켓만으로 목적·범위·의존성·완료 기준을 이해하고 상세 정책의 정확한 앵커를 찾을 수 있는가 | Phase 0-A·0-B, 자기완결성 원칙 |

> **분량은 기준이 아니다.** 내용이 많아도 정책 위반·오류·케이스 누락이면 갭이고, 간결해도 정책·정확성·커버리지를 충족하면 통과다. 참조형에서 디스크립션 정책을 되풀이하거나 상세형에서 구현 방법을 지정하는 **과잉도 갭**이다.

**검토 단위 (2026-10-06 신설).** Evaluator 호출은 두 단계로 나눈다.

1. **child 단위 판정**: Story·Task 하나와 그 child가 인용하는 PRD 절·디스크립션 앵커만 넘겨 위 6 lens로 판정한다. child 수만큼 호출하며, 서로 독립이므로 병렬로 띄워도 된다. 파일 전체를 한 번에 넘기면 뒤쪽 child의 판정이 앞쪽보다 느슨해진다.
2. **파일 전체 대조**: 모든 child가 통과한 뒤 파일 전체(Epic 파일 방식이면 frontmatter와 Epic 파일 전부)를 한 번 넘긴다. 이 호출은 child 본문을 다시 채점하지 않고 3가지만 본다.
   - child 사이에 범위가 겹치거나 비는 곳이 없는가
   - 의존성으로 적은 child가 실제로 그 결과를 맡는가
   - PRD `EP-`가 빠짐없이 매핑됐는가

### 4.5-3. 캘리브레이션 (few-shot — 다른 프로젝트 예시)

| 등급 | 정의 | 예시 |
|---|---|---|
| **치명** | 정책 위반으로 개발 불가 / PRD 핵심 왜곡·누락 / AC가 예외·오류 케이스 전무 / 화면 밖 로직이 검증 없이 방치 | Story를 Task로 오분류해 사용자 가치가 유실됨 · AC가 정상 흐름만 있어 오류·권한 케이스에서 결함 유입 · 상세형 Task가 미확정 구현 방법으로 채워져 정작 요구사항이 없음 · 기하평균 점수 계산·매핑 무결성 같은 화면 밖 로직이 AC에서 누락되거나 검증 방법(🧪/🔗) 없이 방치돼 개발자 검증이 빠짐 |
| **치명(업무 규칙 누락)** | 참조형 티켓이 업무 규칙을 요구사항에서 빼고 앵커로만 넘김 | 회신을 어느 초안 칸에 넣는지, 첫 진입 뒤 회신은 덮어쓰지 않는다는 규칙이 요구사항에 없고 「정책 4-5 참조」만 남음 · 요구사항이 범주당 요약 한두 문장 |
| **권장** | 일부 예외 케이스 누락 / 용어 혼용 | happy·error는 있으나 경계값·동시성 케이스 누락 · "현장 관리자"와 "공장 관리자" 혼용 |
| **경미(과잉)** | 빼는 게 개선 | 참조형 티켓에 디스크립션 정책 전문을 다시 서술 · 상세형 Task에 결과와 무관한 기술 선택을 명시 · 같은 내용 중복 서술 |

> ⚠️ 캘리브레이션 예시는 **검증 대상과 다른 프로젝트** 사례로 둔다(같은 프로젝트면 정답 컨닝 = 측정 오염).

### 4.5-4. 종료 (4출구)
[evaluator-loop.md §5](../inspection-mode/references/evaluator-loop.md) 4출구를 따른다. 요약:
- **성공**: 치명 0 → 커밋·적재 진행.
- **실패**: 갭을 verbal feedback으로 md 보강 → Evaluator 재호출(횟수 캡 3회).
- **상한 중단**: 3회 내 미통과 → 잔여 갭 보고, 사용자 판단.
- **에스컬레이션**: Evaluator 실행 실패 → **self-eval로 통과 단정 금지.** "독립 검증 미완료"로 보류.

> **권장 진행법**: 여러 티켓을 한꺼번에 보강하기보다 **Story 1건으로 AC 밀도를 합의**한 뒤 나머지에 확산한다(전건 재작업 리스크 회피).

## 인수 조건 (Acceptance Criteria) 작성 원칙 — 전체 공통

> **AI·에이전트 기능이 포함된 Story**는 아래 공통 원칙 적용 후, 문서 하단 **"AI·에이전트 기능 Story 인수 조건"** 섹션의 케이스 기반 원칙을 추가로 적용한다.

Story와 Task 모두 아래 원칙을 엄격히 준수합니다:

1. **그룹 분류**: 기능 영역별로 `AC 1. {그룹명}`, `AC 2. {그룹명}` 형태로 분류
2. **체크리스트**: `- [ ]` 체크리스트로 작성
3. **결과 중심**: "~되어야 한다" 등 명확한 종결 어미
4. **테스트 가능**: QA에서 Pass/Fail 판정이 가능한 수준
5. **모호함 배제**: "적절히", "빠르게", "예쁘게" 등 주관적 표현 절대 금지
6. **수치 기준 포함**: 가능한 경우 구체적 수치 명시 (시간 기준, 최소/최대 개수 등)
7. **분기 완결**: 조건이 있는 인수 조건은 모든 분기를 명시한다. `"A일 때 X"` 만 있고 `"A가 아닐 때"` 가 없으면 불완전
8. **오류·예외 케이스 포함**: Happy Path 조건만 있으면 반드시 오류 분기(빈 목록, 권한 없음 등) AC를 추가
9. **핵심 AC 위치**: 가장 중요한 인수 조건은 AC 1(첫 번째) 또는 마지막 AC 그룹에 배치한다. 직렬위치 효과(Serial Position Effect)로 인해 중간에 배치된 항목은 검토자와 개발자 모두에게 과소 평가될 수 있다

### Story AC 추가 원칙: 사용자 관점 필수

Story의 AC는 반드시 **사용자가 화면에서 경험하는 결과** 기준으로 작성한다. 내부 구현·시스템 동작 기준 금지.

| 구분 | 예시 |
|---|---|
| ❌ 구현 기준 (금지) | "POST /api/alerts 호출 후 200 응답 시 완료" |
| ❌ 시스템 기준 (금지) | "DB에 레코드가 정상 insert되어야 한다" |
| ✅ 사용자 관점 (올바름) | "[저장] 버튼 클릭 후 입력한 정보가 목록에 정상적으로 표시되어야 한다" |
| ✅ 사용자 관점 (올바름) | "임계값 초과 후 30초 내에 담당자 화면 상단에 알림이 노출되어야 한다" |
| ✅ 사용자 관점 (올바름) | "필수 항목 미입력 시 [저장] 버튼이 비활성화되어야 한다" |

**좋은 예 (Story AC):**
- [ ] 모델 관리 페이지에서 [연합 학습 설정] 버튼이 정상적으로 노출되어야 한다.
- [ ] 두 개 이상 선택되어야 [저장] 버튼이 활성화되어야 한다.
- [ ] 저장 완료 후, 다시 팝업을 열었을 때 이전 선택 상태(체크박스)가 유지되어 표시되어야 한다.

**나쁜 예:**
- [ ] 버튼이 잘 보여야 한다 ← 모호
- [ ] 데이터가 적절히 저장되어야 한다 ← 기준 없음
- [ ] API가 정상 응답을 반환해야 한다 ← 구현 기준

## AI·에이전트 기능 Story 인수 조건 — 케이스 기반 작성 원칙

### 적용 대상

아래 유형의 Story에 적용한다. 기존 AC 원칙에 **추가**로 적용한다(대체 아님).

- LLM 또는 AI 모델이 판단·분류·자연어 텍스트 생성을 수행하는 기능
- 에이전트가 의사결정(신규 생성·병합·건너뜀 등)을 자동으로 수행하는 기능
- AI가 생성한 결과물(텍스트·추천·분류값 등)을 화면에 표시하는 기능

일반 CRUD·폼·필터 등 AI·에이전트 판단이 없는 기능은 기존 원칙만 적용한다.

### 협업 모드 확인 (에이전트 Story 생성 전 필수)

PRD 작업 디렉토리의 `context.json`에서 `agent_collaboration` 값을 확인한다.

| 값 | 의미 | 동작 |
|---|---|---|
| `"with_developer"` | 에이전트 판단 로직을 다른 사람이 구현한다 | 아래 세 규칙을 추가 적용 |
| `"solo"` | 기획자가 직접 구현하되 그 작업은 `ai-dlc` 워크플로우가 수행한다 | **같은 규칙을 적용한다(2026-08-27 변경).** 받는 쪽이 사람이 아니라 워크플로우일 뿐이며, 업무 계약이 없으면 워크플로우가 스스로 추정한다 |
| 필드 없음 · `context.json` 없음 | 판정 정보가 없다 | PRD 본문에 상태 태그(`[기획 확정]`·`[개발 위임]`·`[확정 · 재검토 대상]`·`[미결]`)가 하나라도 있으면 그 규칙을 적용한다 |

문서 도구에만 있는 PRD(8 Phase 경로로 작성된 PRD 등)는 `context.json`이 없을 수 있다. 이때 담당자를 추측하지 않는다. 위 표대로 **PRD 본문에 작성자가 남긴 상태 태그만 근거로** 판정한다.

에이전트 사양(`08-ai-agent-spec.md`)의 항목에는 상태 태그가 붙어 있다. `[기획 확정]`은 기획자가 업무 의미를 확정한 항목, `[개발 위임]`은 받는 쪽이 기술 계약으로 확정할 항목, `[확정 · 재검토 대상]`은 안전·법규 기준이라 기획자가 근거를 찾아 대행 확정한 항목, `[미결]`은 업무 규칙이 비어 있는 항목이다. 태그별로 티켓 처리가 다르다.

**규칙 1 — `[개발 위임]` 항목을 인수 조건으로 만들지 않는다.**

조회 시간 제한, 재시도 횟수, 추론 방식, 저장소 선택 같은 기술 계약은 개발자가 확정한다. 이를 AC로 박으면 기획자가 정하지 않은 값을 개발자가 지켜야 하는 기준으로 굳힌다. 대신 같은 항목의 **업무 제약**을 AC로 쓴다.

```
❌ [ ] 정비 이력 조회는 3초 안에 완료된다.
✅ [ ] 정비 이력 조회가 실패하면 원인을 확정하지 않고 점검 요청 상태로 전환된다. [T1 결정적]
```

**규칙 2 — `[확정 · 재검토 대상]` 수치는 판정값으로 쓰되 재검토 표시를 함께 남긴다.**

안전 임계값·법정 기준·자동 정지 조건은 기획자가 근거를 찾아 확정한 값이므로 그대로 판정값으로 쓴다. **다만 확정 근거가 안전 책임자 검토를 거치지 않았다는 사실을 인수 조건 옆에 남긴다.**

```
- [ ] {케이스 설명}에서 {값}({출처})을 넘으면 {조치}가 실행된다. [확정 · 안전 책임자 배정 시 재검토]
```

**근거를 못 찾아 값이 없는 항목은 `[확정 · 재검토 대상]`이 아니라 `[미결]`이며 규칙 3을 따른다.**

**규칙 3 — `[미결]` 항목이 있으면 해당 Story를 생성하지 않는다.**

업무 규칙이 비어 있으면 개발자가 스스로 추정하게 된다. 기존 "⚠ 정책 미정" 표기(케이스 도출 절차 5번)로 넘기지 않는다. 미결 항목이 걸린 Story는 목록에서 빼고 사용자에게 아래를 보고한 뒤 확정을 받는다.

```
에이전트 Story {N}건을 생성하지 않았습니다. 업무 규칙이 비어 있어 개발자가 추정해야 합니다.

- {Story 제목}: {무엇이 비었나} / 답해야 할 역할: {역할}

확정값을 알려주면 해당 Story를 생성합니다. 지금 생성하려면 "미결 포함 생성"이라고 답해주세요.
```

사용자가 "미결 포함 생성"을 명시하면 생성하되, 해당 AC에 `⚠ 정책 미정` 표기를 붙이고 Story 본문 첫 줄에 미결 항목과 답해야 할 역할을 적는다.

### 핵심 원칙

"정보가 표시된다"는 조건만으로는 AC가 완성되지 않는다. 아래 3가지를 반드시 포함한다.

1. **표시 내용 구성 요소 검증**: 어떤 정보가 표시되어야 하는지 구성 요소 단위로 확인한다. 단순 노출 여부가 아니라 내용의 완결성을 본다.
2. **케이스 기반 분기**: 정상 동작만 기술하지 않는다. 예외·경계·오류 케이스를 AC에 명시한다.
3. **검증 방식 구분**: LLM이 개입하는 판단 영역과 코드가 결정적으로 처리하는 영역은 검증 방식이 다르다. 아래 태그로 검증 방식을 구분하고 **최종 티켓 본문에도 남긴다**. 개발자가 어떤 방식으로 검증할지 알아야 하기 때문이다. 검증 방법 4분류(🖥/🧪/🔗/🔌, "Story 작성 원칙 4c")와의 대응은 이렇다. `[T1 결정적]`은 순수 로직이면 🧪 단위, 상태 의존이면 🔗 통합이다. `[T2 LLM 통합]`과 `[T3 통제]`는 LLM·fixture를 포함하므로 🔗 통합이다.

**검증 방식 태그 (AI 기능 AC 세분 — 최종 티켓 본문에 표기)**

| 태그 | 의미 | 판정 기준 |
|---|---|---|
| `[T1 결정적]` | 코드·규칙만으로 동작. LLM 미호출 | 같은 입력 → 항상 같은 출력. 반복 실행 100% 일치 요구 |
| `[T2 LLM 통합]` | 실제 LLM 포함 e2e 검증 | 동일 입력 5회 반복 후 다수결 판정. 경계 케이스는 허용 집합(A 또는 B)으로 통과 |
| `[T3 통제]` | 특정 분기를 강제 재현 | 열린 상황 목록·매뉴얼 RAG 결과·과거 이력 등을 고정 입력(fixture)으로 통제해 실제 데이터로는 만들기 어려운 예외를 검증 |

### AC 케이스 도출 프레임워크

아래 6가지 케이스 유형을 해당 에이전트의 PRD와 설계에 대입해 해당하는 것만 선택하여 AC를 작성한다. **모든 유형을 채울 필요 없다.** 아래 형식 예시는 패턴을 보여주기 위한 것으로 직접 복사하지 않는다 — AC 내용은 반드시 해당 에이전트의 PRD에서 도출한다.

---

**유형 1: 출력 구성 요소 검증** `[T2 LLM 통합]`

해당 조건: AI가 생성한 텍스트·결과물을 화면에 표시하는 경우

도출 방법: PRD에서 이 화면에 표시되어야 하는 구성 요소 목록을 식별한다. "표시된다"가 아니라 구성 요소 각각이 생성 결과에 포함되는지, 복수 소스가 합쳐지는 경우 순서·우선순위 정책이 적용되는지를 AC로 작성한다.

```
예시:
- [ ] 생성 결과가 {PRD 정의 구성 요소 A}, {B}, {C}를 모두 포함한다. [T2 LLM 통합]
- [ ] {복수 소스가 있는 경우} {순서·우선순위 정책}이 적용된다. [T2 LLM 통합]
```

---

**유형 2: 결정 분기 검증** `[T2 LLM 통합]` 또는 `[T1 결정적]`

해당 조건: 에이전트가 복수의 결정 경로를 가지는 경우

도출 방법: 에이전트가 내릴 수 있는 결정 유형 전체를 PRD에서 열거한다. 각 결정이 올바른 조건에서 발동되는지를 AC로 작성한다. LLM이 판단하면 T2, 코드 규칙이면 T1.

```
예시:
- [ ] {조건 A} 입력에서 에이전트가 {결정 유형 X}를 수행한다. [T2 LLM 통합]
- [ ] {조건 B} 입력에서 에이전트가 {결정 유형 Y}를 수행한다. [T1 결정적]
```

---

**유형 3: 실행 차단·조기 종료** `[T1 결정적]`

해당 조건: 특정 조건에서 에이전트를 호출하지 않거나 조기 종료하는 규칙이 있는 경우

도출 방법: "언제 에이전트가 실행되지 않는가"를 PRD에서 식별한다. 차단 조건과 예외(우선 통과) 조건을 모두 포함한다.

```
예시:
- [ ] {차단 조건}이 충족된 경우 에이전트가 호출되지 않고 {결과 상태}로 처리된다. [T1 결정적]
- [ ] {예외 조건}에 해당하는 경우 차단 조건 충족 여부와 무관하게 에이전트가 실행된다. [T1 결정적]
```

---

**유형 4: 외부 상태 의존 분기** `[T3 통제]`

해당 조건: 에이전트의 결정이 현재 시스템 상태(기존 레코드, 다른 서비스 결과, 이력 데이터 등)에 따라 달라지는 경우

도출 방법: "어떤 외부 상태가 에이전트의 결정을 바꾸는가"를 PRD에서 식별한다. 실제 데이터로 만들기 어려운 상태는 고정 입력(fixture)으로 주입해 검증한다.

```
예시:
- [ ] {외부 상태 X} 조건에서 에이전트가 {기대 동작}을 수행한다. [T3 통제]
- [ ] {외부 상태 Y}가 존재하지 않는(빈) 상태에서 에이전트가 {대체 동작}을 수행한다. [T3 통제]
```

---

**유형 5: 실패·graceful 처리** `[T3 통제]` 또는 `[T1 결정적]`

해당 조건: 항상 포함한다.

도출 방법: AI 생성·에이전트 처리 단계에서 실패할 수 있는 지점을 열거하고, 각 실패 시 사용자가 보는 화면이 어떻게 달라지는지를 작성한다. 연관 서비스가 있는 경우 미연동·실패 시 주요 기능이 유지되는지도 포함한다.

```
예시:
- [ ] {처리 단계}가 실패한 경우 {대체 표시}가 노출되고 나머지 화면 요소는 정상 표시된다. [T3 통제]
- [ ] {연관 서비스}가 미연동 또는 실패 상태일 때 {주요 기능}은 정상 동작한다. [T3 통제]
- [ ] {상위 처리 단계} 실패가 {하위 단계} 실행을 차단하는지, 독립적으로 처리되는지가 정책대로 동작한다. [T1 결정적]
```

---

**유형 6: 결정적 계산 재현성** `[T1 결정적]`

해당 조건: 점수·분류값·임계값 등 코드가 결정적으로 산출하는 수치가 있는 경우

도출 방법: PRD에서 계산 규칙이 명시된 값을 식별한다. 경계값·상한·하한·강제 보정 규칙이 있으면 각각 AC로 작성한다.

```
예시:
- [ ] 동일 입력으로 반복 실행 시 {계산값}이 동일하다(재현성). [T1 결정적]
- [ ] {경계값} 입력에서 {분기 A}와 {분기 B}가 정책대로 나뉜다. [T1 결정적]
- [ ] {조건 X}에서 {계산값}이 상한({수치})을 초과하지 않는다. [T1 결정적]
```

---

### 케이스 도출 절차

1. Story의 AI·에이전트 기능 설계에서 아래를 식별한다.
   - 에이전트가 내릴 수 있는 결정 유형 전체
   - 실행을 차단·종료하는 조건
   - 외부 상태(기존 레코드·다른 서비스·이력)가 결정에 영향을 주는 지점
   - 실패 가능 지점과 실패 시 대체 동작
   - 코드가 결정적으로 산출하는 계산값(있는 경우)

2. 위 6가지 유형 중 해당하는 것을 선택한다.

3. 각 케이스를 해당 에이전트의 PRD 용어로 구체화한다 — 이 문서의 예시 문장을 그대로 복사하지 않는다.

4. 각 항목에 T1/T2/T3 태그를 붙여 검증 방식을 확인한다. **단, 최종 티켓 본문을 만들 때 태그는 제거한다.**

5. 정책이 미확정인 케이스는 제외하지 않고 아래 형식으로 포함한다.

```
- [ ] ⚠ 정책 미정: {케이스 설명} — 기대값 확정 후 검증. 현재 테스트 제외.
```

## QA 결함 모드: 결함 티켓 생성

검증에서 통과하지 못한 인수 조건을 고치기 위한 티켓을 만든다. 유형은 팩이 정하고, 원래 티켓이 속한 Epic 아래에 붙는다. PRD를 다시 분해하지 않는다.

### 언제 만드나

결함 티켓은 아래 2가지 경우에만 만든다. 개발자가 자기 티켓을 검증하다 나온 Fail을 그 자리에서 고쳤다면 만들지 않는다. 그 경우는 다시 검증한 Pass 기록으로 충분하다.

1. **독립 QA의 Fail**: `spec-driven-qa`가 화면 검증에서 `fail` 판정을 낸 인수 조건.
2. **넘기는 Fail**: 개발자가 검증에서 Fail을 확인했지만 이번 작업에서 고치지 못하고 넘기는 인수 조건. 다른 사람의 코드가 원인이거나 범위가 커서 따로 다뤄야 하는 경우다.

`conflict`(사양끼리 충돌), `insufficient_evidence`(증거 부족), `blocked`(환경 문제로 실행 못 함) 판정은 제품 결함이 아니므로 QA 티켓으로 만들지 않는다. 사양 충돌은 PM 결정이 필요한 사항으로 따로 보고한다.

### 입력으로 받아야 하는 것

| 항목 | 내용 | 없으면 |
|---|---|---|
| 원래 티켓 | 실패한 인수 조건이 적힌 Story·Task의 식별자 또는 URL | 사용자에게 묻는다 |
| 실패한 인수 조건 | 번호와 문장 (예: AC 2) | 팩의 「티켓 조회」로 원래 티켓을 읽어 확인한다. 팩이 없으면 사용자에게 본문을 받는다 |
| 기대한 결과 | 인수 조건이 요구하는 동작 | 원래 티켓 본문에서 옮긴다 |
| 실제 결과 | 검증에서 관찰한 동작 | 추정해서 쓰지 않는다. 사용자에게 묻는다 |
| 재현 절차 | 어떤 계정·데이터·순서로 확인했는지 | 사용자에게 묻는다 |
| Epic | 원래 티켓이 속한 Epic의 식별자 | 팩의 「티켓 조회」나 원래 티켓의 상위 연결에서 찾는다 |

### 제목 규칙

`[결함] {무엇이 어떻게 잘못됐는지}` 형식으로 쓴다. 원인 추정이 아니라 관찰한 현상을 적는다.

- 좋은 예: `[결함] 프로젝트 관리자 계정에 비밀번호 재발급 버튼이 보임`
- 나쁜 예: `[결함] 권한 체크 누락` (원인 추정이고, 어느 화면의 무엇인지 알 수 없다)

### 본문 템플릿

```markdown
## 무엇이 잘못됐나

{관찰한 현상을 1~2문장으로. 어느 화면 또는 어느 요청에서, 어떤 조건일 때 일어나는지 쓴다.}

## 실패한 인수 조건

- 원래 티켓: [{원래 티켓 제목}]({원래 티켓 URL})
- 인수 조건: AC {번호}. {인수 조건 문장}

## 기대한 결과와 실제 결과

| 구분 | 내용 |
|---|---|
| 기대한 결과 | {인수 조건이 요구하는 동작} |
| 실제 결과 | {검증에서 관찰한 동작} |

## 재현 절차

1. {계정·데이터 등 준비 상태}
2. {조작 또는 요청}
3. {결과를 확인한 위치}

## 확인한 환경

- 대상: {로컬 서버 · 배포본 주소 · 빌드}
- 판본: {커밋 또는 배포 일시}
- 검증 방법: {🖥 화면 확인 · 🧪 단위 테스트 · 🔗 통합 테스트 · 🔌 수동·물리}

## 인수 조건 (Acceptance Criteria)

### AC 1. {고친 뒤 관찰돼야 하는 결과}  [검증: {원래 인수 조건과 같은 검증 방법}]
- [ ] {원래 인수 조건이 통과한다}
- [ ] {같은 원인으로 깨질 수 있는 인접 동작이 그대로다}
```

### 작성 규칙

1. **실패한 인수 조건 1개에 티켓 1건**이다. 원래 티켓과의 연결이 인수 조건 단위라, 묶으면 어느 조건이 아직 열려 있는지 셀 수 없다. 같은 원인으로 보이는 건은 본문에 서로의 링크를 적는다. 같은 인수 조건에 이미 열린 결함 티켓이 있으면 새로 만들지 않는다.
2. **원인을 단정하지 않는다.** 원인을 확인했으면 「확인한 원인」 절을 추가해 근거(파일·로그)와 함께 적고, 추정이면 적지 않는다.
3. **증거는 찾아갈 수 있는 것만 적는다.** 테스트 파일 경로, 실행 명령, 화면 QA 결과 파일의 위치다. 화면 검증의 스크린샷은 참고 자료로만 붙이고 판정 근거로 쓰지 않는다.
4. **인수 조건의 검증 방법은 원래 인수 조건과 같게 둔다.** 고친 뒤 원래 티켓의 그 인수 조건을 다시 검증해 통과 기록을 남기는 것이 완료 조건이다. 기록 방법은 팩의 「검증 기록」을 따른다.
5. **우선순위는 PM이 정한다.** 초안에는 원래 인수 조건에 `[릴리스: 필수]` 태그가 있는지만 적어 판단 근거로 준다.

### 사용자 확인 (필수)

결함 티켓은 개발자에게 배정되는 일이고 자동 판정의 Fail은 틀릴 수 있으므로, 사용자 확인 없이 올리지 않는다. 확인받는 방식은 들어온 경로에 따라 다르다.

| 들어온 경로 | 확인 방식 |
|---|---|
| `ticket-qa`가 실패 목록(원래 티켓·인수 조건·실패 사유·제목)을 보이고 승인받아 넘긴 경우 | 이미 승인된 것이다. 본문 초안을 다시 보이지 않고 적재로 간다. 승인 목록에 없던 건을 더하지 않는다 |
| 사용자가 이 스킬에 직접 요청했거나 승인 목록 없이 넘어온 경우 | 같은 형식의 목록을 보이고 한 번 승인받는다. 사용자가 원하면 본문 초안을 보인다 |

입력으로 받아야 하는 것 가운데 실제 결과나 재현 절차가 비어 있으면 올리지 않고 사용자에게 묻는다.

### 적재

업로드 전 검토(적재 규칙 3a)를 똑같이 거친 뒤, 원래 티켓이 속한 Epic마다 팩의 「결함 티켓 적재」를 한 번 호출한다.

- 결함 티켓의 유형과 원래 티켓에 연결하는 방법은 팩을 따른다. 원래 티켓에서 결함 티켓을, 결함 티켓에서 원래 티켓을 찾아갈 수 있어야 한다.
- 원래 티켓이 어느 Epic에도 속하지 않으면 상위 없이 단독으로 올리고(방법은 팩의 「결함 티켓 적재」), 본문의 「실패한 인수 조건」 절에 원래 티켓 링크를 반드시 넣는다.
- 담당자는 넣지 않는다. 적재 후 PM이 배정한다.
- 결함 티켓 본문은 프로젝트의 `tickets/tickets.md`에 함께 적어 git md를 본문 정본으로 유지한다.

### 완료 보고

```markdown
## ✅ 결함(QA) 티켓 등록 완료 ({created}/{requested}건)

| 결함 티켓 | 원래 티켓 | 실패한 인수 조건 |
|---|---|---|
| [{제목}]({URL}) | [{원래 티켓 제목}]({URL}) | AC {번호} |
```

## Backlog 모드: 경량 티켓 생성

PRD 없이 **"해야 할 필요성은 느꼈으나 아직 구체화되지 않은 업무"** 를 등록·리스트업할 때 사용한다.
정식 Story/Task처럼 인수 조건·Story Points·계층 구조를 강제하지 않는다. 목적은 "잊지 않도록 빠르게 적어두는 것"이다.

### PRD 모드와의 차이

| 항목 | PRD 모드 (Story/Task) | Backlog 모드 |
|---|---|---|
| 입력 | PRD·요구사항 문서 | 거친 업무 항목 (구두·메모 수준) |
| Ticket type | Epic / Story / Task | **Backlog** |
| 상위 티켓 | Epic URL 매핑 필수 | **매핑하지 않음 (단독)** |
| Status | Backlog | **Backlog** |
| Story Points | 피보나치 필수 | **비움 (미정)** |
| 인수 조건 | 필수, 상세 | **작성하지 않음** |
| 본문 | 상세 명세 | **3섹션 경량 템플릿** |
| 생성 방식 | 한 건씩 순차 | **여러 건 일괄 가능** |

### 처리 흐름

```
[B-1] 업무 항목 수집 → 항목별로 제목·문제·작업·기대결과 초안 작성
    ↓
[B-2] 사용자 검토 → 리스트 한눈에 제시
    ↓
[B-3] 일괄 적재 → 팩의 「백로그 적재」에 항목 전체를 한 번에 전달
    ↓
[B-4] 완료 보고
```

### B-1: 항목 정리

사용자가 던진 거친 업무 항목을 항목 단위로 분해한다. 각 항목에 대해:
- **제목**: 무엇을 하는 업무인지 명사구로. 제목 전용 규칙(em-dash·`&`·화살표·불필요한 영어·코드 단독 참조 금지) 적용
- **문제 / 작업 / 기대 결과** 3섹션 초안 작성 (아래 템플릿)

정보가 부족한 항목은 비워두지 말고, 사용자가 말한 의도를 바탕으로 **합리적 1문장 초안**을 채운 뒤 검토 단계에서 수정받는다.

### B-2: 사용자 검토

```
## 🗂️ Backlog 티켓 생성 예정 ({n}개)

| # | 제목 | 문제(요약) | Priority |
|---|------|-----------|----------|
| 1 | {제목} | {한 줄} | P2 |
| 2 | {제목} | {한 줄} | P3 |

✅ 이대로 Backlog에 등록할까요? 항목 추가·수정·삭제할 부분을 알려주세요.
```

Priority는 팩의 「보드 값」을 따른다. 팩이 없으면 **P0 / P1 / P2 / P3** 중 하나로 적는다. 불명확하면 기본값 **P2**로 두고 검토 화면에 표시한다.

### Backlog 티켓 본문 템플릿

```markdown
## 문제

{왜 이 티켓이 필요한지 — 현재 상황의 불편·리스크·공백을 1~3문장}

## 작업

{무엇을 해야 하는지 — 알고 있는 범위 안에서. 미정이면 "검토 필요" 수준으로 기술}

## 기대 결과

{완료 시 어떤 상태가 되는지 — 결과 상태 1~2문장}
```

**작성 원칙:**
- 3섹션 헤더(`## 문제` / `## 작업` / `## 기대 결과`)는 고정. 항목이 비어도 헤더는 유지하고 "미정" 또는 알고 있는 최소 내용을 적는다
- **과잉 상세 금지**: Backlog는 발견 단계 메모다. 인수 조건·기술 스펙·UI 동작을 끼워 넣지 않는다
- **기대 결과는 결과 상태로**: "~를 한다"가 아니라 "~된 상태가 된다" / "~가 가능해진다"로 종결
- 공통 글쓰기 가드레일 중 **제목 전용 규칙 + AI 투 패턴 + 가독성 가드레일**은 적용한다 (인수 조건·앵커 ID 규칙은 Backlog에 비적용)

### B-3: 일괄 적재

Backlog는 **여러 항목을 한 번의 호출**로 팩의 「백로그 적재」에 넘긴다. 호출 전에 PRD 모드 적재 규칙 3a와 같이 업로드 전 검토를 거친다. 항목마다 제목, 우선순위, 라벨, 3섹션 본문을 넣는다.

- **상위 티켓·Story Points는 넣지 않는다.**
- 항목 수 상한과 부분 실패 처리는 팩을 따른다.
- 본문 첫 문장("문제" 핵심)이 보드 카드 식별 텍스트가 된다.
- **팩이 없으면** 적재하지 않고 `{project}/tickets/backlog.md`에 항목마다 `## {제목}` 아래 3섹션 본문과 우선순위를 적어 커밋한다. B-4는 등록 완료 대신 파일 경로와 항목 수를 보고한다.

### B-4: 완료 보고

적재 응답의 요청 수·생성 수·식별자로 보고한다.

```
## ✅ Backlog 티켓 등록 완료 ({created}/{requested}개)

| # | 제목 | Priority | 식별자 |
|---|------|----------|---------|
| 1 | {제목} | P2 | {id} |

> 구체화가 필요한 항목은 추후 PRD 모드로 Story/Task로 승격할 수 있습니다.
```

## 피드백 로그 축적 (스킬 자기 개선용)

**이 스킬로 만든 티켓에 사용자가 문구·구조 교정을 요청하면, 그것은 티켓 생성이 놓친 지점이다.** 그 miss를 로그로 남겨 스킬 고도화의 근거로 쌓는다.

**기록 시점**: 적재를 마친 티켓에 대해 사용자가 "이 표현이 이상하다 / 이건 왜 안 잡았냐 / 이렇게 바꿔라"처럼 **추가 교정을 지시**했을 때. 티켓을 만들기 전의 일반 작성 요청은 대상이 아니다.

**기록 위치**: `feedback-log.local.md`에 append(없으면 생성). 한 건당 아래 형식으로 1블록:

```
## <YYYY-MM-DD> — <문서/맥락 한 줄>
- 유형: <검토 누락 | 문체 지정>
- 사용자가 지적한 것: <무엇을 고쳐달라 했나. 사용자의 말을 그대로 인용하면 좋다>
- 놓친 이유: <왜 안 잡혔나. 유형이 "문체 지정"이면 "놓친 것이 아니라 사용자가 규약을 새로 정했다"로 적고 원인을 지어내지 않는다>
- 반영: <자기완결성 검사나 AI 투 패턴에 올렸으면 그 내용. 안 올렸으면 "미반영 — 누적 관찰"과 그 이유>
```

### 문구·구조 수정 요청은 예외 없이 쌓는다

**사소해 보인다는 이유로, 한 번뿐인 취향으로 보인다는 이유로, 이미 반영했다는 이유로 건너뛰지 않는다.** 문체 요청은 한 건씩 보면 취향이지만 **쌓이면 그 조직의 티켓 규약**이다. 쌓지 않으면 같은 지적을 매번 다시 받고, 그때마다 사용자가 같은 설명을 반복해야 한다.

**가르는 질문 하나.** **"티켓이 말하는 사실이 바뀌는가"** 를 묻는다. 바뀌면 내용이라 쌓지 않고, 같은 사실을 다르게 적는 것이면 문구·구조라 쌓는다.

| 요청 유형 | 예 | 쌓나 |
|---|---|---|
| **문구·문체** | 이 표현이 번역투다, 용어를 바꿔라, 예시를 붙여라 | **쌓는다** |
| **구조** | 이 절을 빼라, 개발 동작만 적어라, 정의 위치를 밝혀라 | **쌓는다** |
| **내용** | 이 요구사항이 틀렸다, 이 범위를 빼라, 이 판단으로 좁혀라 | **쌓지 않는다.** 요구사항 판단은 이 스킬의 범위 밖이다 |

### 승격 판단

**같은 방향의 지적이 서로 다른 프로젝트에서 두 번 넘게 반복되면 자기완결성 검사나 AI 투 패턴으로 올린다.** 한 프로젝트에서만 나온 것은 그 프로젝트의 표기 규약으로 처리하고 로그에 "미반영 — 누적 관찰"로 남긴다. **특정 프로젝트의 산출물 구조(판단 카탈로그·역량 질문 명세 같은 것)에 기대는 규율은 그대로 올리지 않는다** — 그 구조가 없는 프로젝트에서 성립하지 않기 때문이다.

## 에러 처리

- PDF 텍스트 추출 실패 → OCR 시도 (pytesseract)
- 티켓 도구 호출 에러 → 재시도 (최대 3회), 실패 시 사용자에게 알림
- PRD가 너무 짧거나 모호 → 사용자에게 추가 정보 요청
- Epic 적재 실패 → 해당 Epic과 children의 롤백 여부를 확인하고, 실패 원인을 고친 뒤 그 Epic 묶음만 재시도

## 주의사항

- **항상 사용자 확인 후 생성**: Phase 2를 건너뛰지 않는다
- **팩 경유 적재**: PRD 모드는 팩의 「신규 적재」를 Epic별로 한 번씩 호출하고, Backlog 모드는 「백로그 적재」로 일괄 적재한다. 팩이 정한 경로 밖의 방법으로 티켓을 직접 만들지 않는다
- **도구 전제**: 팩의 도구가 도구 목록에 없으면 안내 후 중단
- **업로드 전 검토**: 모든 적재·본문 교체 전에 팩의 「업로드 전 검토」를 거친다(적재 규칙 3a)
- **수정은 식별자로**: 적재 후 본문 변경은 팩의 「본문 갱신」에 frontmatter의 식별자를 넘겨 호출한다
- **작성 모드 우선**: 본문을 쓰기 전에 티켓별로 디스크립션 있음(참조형)과 디스크립션 없음(상세형)을 판정한다. 참조형은 디스크립션 정책을 복사하지 않고, 상세형은 다른 정본이 소유하지 않는 계약만 상세하게 쓴다
- **자기완결성**: Phase 0-B의 기준을 적용하고, 문서 위치·앵커·전체 명칭이 없는 모호한 외부 참조만 금지한다
- **용어 일관성**: Phase 1에서 추출한 용어 사전을 Epic·Story·Task 전체에 걸쳐 일관되게 사용한다. 같은 주체를 "현장 관리자" / "현장 담당자" / "공장 관리자"로 혼용하지 않는다
- **분류 축 대조**: 분류·필터를 다루는 Story는 생성 주체·사용자 영역·카테고리·유형·표시 정보·필터를 나눠 확인하고, 카드 표시와 필터 묶음이 프로토타입 화면과 일치하는지 대조한다
- **글쓰기 품질**: 공통 글쓰기 가드레일(제목 전용 규칙 포함, AI 투 패턴, 가독성 가드레일, PRD 특화 금지 표현)을 Ticket name(제목) 및 본문(content) 모두에 적용한다
- **멱등성**: 같은 PRD로 재실행 시 중복 생성 주의. 사용자에게 경고한다
- **Story vs Task 분류**: 사용자 가치 제공 → Story. Task는 복수 Story의 선행 조건이거나 어떤 Story에도 귀속되지 않는 독립 작업일 때만 생성. 특정 Story 하나에만 귀속되는 기술 작업은 Task 불필요 — 해당 Story의 요구사항으로 포함
- **Task 계약·구현 경계**: 디스크립션 없음 상세형 Task는 이미 정해진 작업 대상과 입력·출력·상태·실패 계약을 기술할 수 있다. 결과와 무관한 라이브러리·내부 구조·배포 방식은 지정하지 않는다
- **Story Points**: 위 "Story Points 산출 기준"으로 피보나치(1·2·3·5·8·13) 부여. 적재 요청의 공수 값으로 전달한다. Epic에는 매기지 않는다
- **상위 티켓 매핑 (PRD 모드)**: children의 상위 연결은 팩의 「신규 적재」가 맡는다. children에 상위 식별자를 직접 넣지 않는다
- **담당자 미배정 (PRD 모드)**: 적재 요청에 담당자를 넣지 않는다. 라벨 기반 자동 배정은 적재 후 별도 단계
- **항목 간 완결성 균형**: 같은 작성 모드의 앞쪽 항목과 뒤쪽 항목에 목적·범위·의존성·완료 기준이 같은 수준으로 갖춰져야 한다. 참조형과 상세형의 분량을 억지로 맞추지 않는다. 각 child의 첫 문장은 보드 카드 식별용 핵심 한 문장으로 시작한다
- **티켓 본문 SoT = git md**: 본문 소스는 `{project}/tickets/tickets.md`(Epic 파일 방식이면 `tickets/epics/*.md`)이고 티켓 도구의 본문은 그 반영본이다. 본문 수정은 md를 고쳐 팩의 「본문 갱신」으로 단방향 반영한다(Phase 3). 티켓 도구의 본문을 직접 고치지 않는다
- **운영 필드 보호**: Status·Assignee·SP·코멘트는 티켓 보드가 SoT다. md 워크플로우는 이를 덮지 않으며 팩의 「속성 갱신」을 호출하지 않는다(SoT 분리 원칙). 무너지면 개발자 보드 작업이 재적재로 초기화된다
- **식별자 순서 정합**: frontmatter `children` 순서 = 본문 섹션 순서 = 적재 응답 매핑. 어긋나면 본문 갱신이 엉뚱한 티켓을 덮는다
- **적재 전 검토 게이트**: 신규·대폭 개정은 Phase 4.5 독립 Evaluator(정책·정확성·AC 예외 커버리지)를 통과한 뒤 커밋·적재한다
