# 검토자 지시문

검토자는 작성 맥락을 받지 않은 새 에이전트다. Claude Code에서는 `evaluator` 에이전트를, 없으면 새 하위 에이전트를 쓴다. 아래 틀의 `{}` 칸만 채워서 준다. 틀의 문장은 줄이지 않는다. 한 문장을 뺄 때마다 검토자가 그 문장이 막던 해석으로 되돌아간다.

## 1. 입력 원칙

**주는 것**

- 얼린 사본 경로와 "활성 사양과 내용이 같다"는 한 문장
- 원문 파일 전부(`sources`에 오른 것)
- 검토자용 추적표 경로(`reviewer_view.py`로 만든 것. 작성자의 판정 근거와 이전 판정이 빠져 있다)
- 판정 기준 기록(`criteria_rulings`) 전체와 그 해석 규칙
- 이번 회차에 바뀐 곳의 목록. 직전 사본과 이번 사본의 차이(diff)를 준다. **바꾼 이유는 주지 않는다**
- 행이 다른 문서로 옮겨 가기로 돼 있으면(`move_candidate`, `destination_pending`), 그 목적지 문서
- 대상 사양이 따라야 하는 작성 정책이 있으면 그 문서

**주지 않는 것**

- 대화 내용, 작성 경위, 작성자의 해명
- 결정 로그. 결정 가운데 판정에 필요한 것은 판정 기준 기록으로 옮겨서 준다
- "이번 회차에 무엇을 고치려 했다"는 설명. 차이 목록은 주지만 의도는 주지 않는다

**입력을 회차마다 줄이지 않는다.** 회차가 거듭되면 "지난번에 봤으니" 하고 목적지 문서나 이전 판본을 빼기 쉽다. 빼면 그 문서가 필요한 행은 대조되지 않은 채 통과한다. 실제로 목적지 확인 대기 행 8개가 4회차부터 끝까지 목적지 문서와 대조되지 않았다.

**검토자 계열을 도중에 바꾸지 않는다.** 계열(Claude, Codex 등)을 바꾸면 남은 실패가 수정 부족 때문인지 판정 기준 차이 때문인지 가릴 수 없다. 2회차까지 동등으로 확인된 행 다수가 계열을 바꾼 3회차에 실패로 뒤집힌 적이 있다.

## 2. 범위 분담 (검토자 2명일 때)

- 요구사항 행을 번호 순으로 반씩 나눈다. 원문이 여럿이면 원문 문서 단위로 나눠도 된다.
- 제외 행은 한 명이 모두 본다.
- 추적표 밖 요구를 찾는 원문 줄 범위도 나눈다. 행 범위와 같은 쪽으로 맞춘다.
- 모순과 규칙 위반은 **두 명 모두 대상 전체**를 본다. 모순은 범위를 가로질러 생기기 때문이다.
- 각자에게 "다른 검토자가 맡은 행의 판정은 내지 않는다"를 적는다. 겹쳐 판정하면 `record_round.py`가 기록을 거부한다. 다른 검토자 범위의 행이 목록에 섞여 있으면 `OUT_OF_SCOPE`로 낸다.

## 3. 지시문 틀

```text
당신은 사양 완전성 검토자다. 작성자와 분리돼 있고 파일을 고치지 않는다. 판정 결과 JSON 한 개를 {출력 경로}에 쓰고, 최종 응답에는 실패 행 id 목록과 각 항목의 건수만 짧게 돌려준다.

## 무엇을 판정하나
원문이 요구한 것이 대상 사양에 빠지지 않고 뜻이 바뀌지 않은 채 들어 있는지를 판정한다. 문장이 좋은지, 내용이 옳은지는 판정하지 않는다.

## 입력
- 대상 사양(얼린 사본): {사본 경로}. 활성 사양 {활성 경로}와 내용이 같다.
- 원문: {원문 경로 목록과 각각 무엇의 정본인지}
- 추적표: {검토자용 추적표 경로}. 원본 추적표 {원본 추적표 경로}는 아래 기계 검사에만 쓰고 열어 읽지 않는다. 원본에는 작성자가 적은 판정 근거가 들어 있다
- 이번 회차에 바뀐 곳: {diff 파일 경로 또는 "첫 회차라 없음"}
- 목적지 문서: {경로 목록 또는 "없음"}
- 작성 정책: {경로 또는 "없음"}

## 먼저 할 것
1. 기계 검사를 실행하고 결과를 machine_checks에 적는다: python3 {스킬}/scripts/check_trace.py {원본 추적표 경로} --root {작업 폴더}
   기계 검사 통과는 뜻이 보존됐다는 뜻이 아니다.
2. 대상 사본과 활성 사양이 같은지 diff로 확인해 적는다.

## 맡을 범위
- 요구사항 행: {예: PRD-001~PRD-060}. 다른 행의 판정은 내지 않는다.
- 제외 행: {전부 또는 "없음"}
- 추적표 밖 요구를 찾을 원문 범위: {예: prd.md L1~L240}
- 모순과 규칙 위반: 대상 사양 전체

## 판정 기준
1. 행 판정: 원문 줄이 담은 업무 의미 6요소, 곧 발동 조건·주체·의무·예외·실패 처리·권한 경계 가운데 하나라도 빠지거나 약해지면 FAIL이다. 애매하면 FAIL 쪽으로 기운다.
2. 뜻이 target_locations가 아닌 다른 절에 있으면 PASS로 판정하고 reason에 실제 위치를 적는다.
3. 금지가 허용 조건으로 바뀌었으면 FAIL이다. 예: "반려되면 실행하지 않는다"가 "승인 회신을 받은 뒤 실행한다"로만 남아 반려·보류·무응답일 때의 행동이 비었다.
4. 권한이 넓어졌으면 FAIL이다. 원문에 없는 호출 권한, 자동 실행, 승인 생략이 생겼다.
5. 제외 판정: 제외 행이 에이전트의 동작·권한·실패·기록·평가 요구를 담고 있으면 FAIL이다. 권한성 요구를 제외로 빼는 것이 가장 위험한 오분류다.
6. 추적표 밖 요구: 맡은 원문 범위에서 요구 문장인데 어떤 요구사항 행이나 제외 행에도 들지 않은 것을 찾는다.
7. 모순: 구체적인 입력 상황 하나를 들어 두 규정이 그 상황에서 서로 다른 행동을 요구함을 보일 때만 인정한다. 각 모순에 scenario(입력 상황), rule_1(위치와 요구 행동), rule_2(위치와 요구 행동)를 적는다. 표현 차이, 판정 기준이나 사양의 우선 조항으로 풀리는 경우, 한쪽이 다른 쪽을 가리키기만 하는 경우는 모순이 아니다.
8. 규칙 위반: 작성 정책이 주어졌으면 그 정책을 어긴 곳. 없으면 빈 배열.
9. 행에 verification_status가 있으면 사람이 정한 상태다. approved_removal 행은 판정 기준 기록의 결정대로 사양에 없으면 PASS이고, 사양에 남아 결정과 어긋나면 FAIL이다. destination_pending 행은 destination이 있으면 그 목적지 문서에 뜻 그대로 있는지, 없으면 대상 사양의 target_locations에 임시 경계로 남아 권한을 새로 만들지 않는지 판정한다. source_conflict_pending 행은 판정하되 reason에 두 원문 가운데 사양이 어느 쪽을 따랐는지 적는다.
10. 고친 범위만 다시 보는 회차에서는, 바뀐 문장이 당신이 맡지 않은 행(직전 판정을 이어받을 행)의 금지·예외·권한 경계를 무력화하는지도 본다. 예: 7절에 "반려되어도 긴급 시 재가동할 수 있다"가 들어가면 5.1절의 "반려되면 재가동하지 않는다"를 뒤집는다. 이런 경우는 모순으로 적는다.

## 판정 기준 기록
추적표 metadata.criteria_rulings는 확정된 판정 기준이다. 원문과 어긋나면 이것을 따른다. 같은 주제의 기준이 여럿이면 나중 항목이 앞 항목을 대체한다고 적힌 경우 그것을 따른다. 기준 자체가 틀렸다고 보면 판정은 기준대로 내고 criteria_objections에 이의를 적는다.

## 출력 형식
{
  "reviewer": "{A}",
  "machine_checks": {"check_trace": "PASS|FAIL와 출력 요지", "target_identity": "..."},
  "requirements": [{"id": "...", "verdict": "PASS|FAIL|OUT_OF_SCOPE", "reason": "원문 줄 번호와 대상 줄 번호를 넣은 한국어 완결 문장"}],
  "exclusions": [{"id": "EX-01", "verdict": "PASS|FAIL", "reason": "..."}],
  "outside_trace_findings": [{"source": "원문 id", "location": "L줄", "excerpt": "원문 인용", "why_requirement": "..."}],
  "contradictions": [{"id": "C-{A}-1", "scenario": "...", "rule_1": "위치와 요구 행동", "rule_2": "위치와 요구 행동"}],
  "rule_violations": [{"location": "...", "description": "..."}],
  "criteria_objections": [{"target": "기준 또는 행 id", "objection": "...", "suggestion": "..."}],
  "result": "PASS|FAIL"
}
PASS 행에도 한 줄 사유를 남긴다. result는 맡은 범위의 FAIL, 추적표 밖 요구, 증명된 모순, 규칙 위반이 모두 0일 때만 PASS다. 기준 이의는 result에 영향을 주지 않는다.
```

## 4. 회차 목적 문단

재확인 회차에는 틀 맨 앞에 "이번 회차가 확인할 것"을 한두 문장 더해도 된다. 예: "간결성 검토를 반영해 문장을 줄였다. 줄인 문장이 금지나 예외를 약하게 만들지 않았는지 본다." **무엇을 확인할지는 적고, 왜 그렇게 고쳤는지는 적지 않는다.** 이유를 적으면 검토자가 작성자의 의도대로 읽는다.

## 5. 검토자 출력 보관

검토자 출력은 세션 임시 폴더가 아니라 작업 폴더의 `records/`에 바로 쓰게 한다. 임시 폴더는 비워질 수 있다. 지시문도 회차마다 `records/round-N-prompt-A.txt`처럼 남긴다. 나중에 판정이 흔들렸을 때 지시문이 달랐는지 확인할 수 있어야 한다.
