# 함정 기록

2026-09-14~09-25에 에이전트 시스템 공통 사양 하나를 23회차까지 검토하며 실제로 겪은 것이다. 원문은 839줄이었고 추적표는 요구사항 192개와 제외 20개였다. 요구사항 실패가 처음 0이 된 것은 8회차, 두 검토자가 처음 함께 통과한 것은 15회차였다.

## 1. 작성자가 만든 회귀

회차가 늘어난 가장 큰 원인은 검토자가 아니라 작성자였다. 9회차부터 14회차까지의 실패는 대부분 직전 회차에 작성자가 넣은 문장에서 나왔다.

| 유형 | 무슨 일이 있었나 |
|---|---|
| 축약으로 요구사항 소실 | 839줄을 341줄로 줄인 초안에서 원자 요구사항 141개 가운데 12개가 약해지고 31개가 빠졌다 |
| 요구를 제외로 잘못 분류 | 도구별 호출 권한을 "작성·개발 추적 정보"로 제외했다. 나중에 28행으로 분해해 되살렸다 |
| 추적표 요약 오기 | 요약이 원문에 없는 권한을 요구하게 쓰였다. 추적표가 채점 기준이라 틀린 요약은 틀린 채점을 만든다 |
| 같은 원문 줄을 요구와 제외에 동시에 둠 | 뜻이 빠져도 제외를 근거로 통과할 수 있다. `check_trace.py`가 경고로 알린다 |
| 표현을 고치다 금지를 새로 만듦 | "통신이 끊긴 엣지에서는 어느 값도 최신으로 가정하지 않는다"가 센서 관측까지 막아, 단절 중 판단과 인터록 지시가 멈추는 규정이 됐다 |
| 확정된 기준을 거스름 | 앞 회차에 확정한 경로 순서를 다음 회차에 뒤집었다 |
| 발동 조건을 바꿈 | 민감도 상향 조건을 다른 사건으로 바꿔, 즉시 조치 경로에서 발동하지 않게 됐다 |
| 조건을 좁히다 다른 경로를 막음 | "이상 없음이면 현장에서 종결한다"가 열린 상황의 복구 요청 경로를 막았다 |
| 조건에 필수 요소를 덧붙임 | 복구 요청에 결론을 필수로 붙여 "조치가 끝남"만으로 가던 경로가 사라졌다 |
| 새 의무를 권한 표에 전파하지 않음 | 한 주체에 새 행동을 요구하고 그 주체의 업무 시작 조건과 도구 범위에는 넣지 않았다 |
| "하나뿐" 전제를 깨는 권고 | 작성자 권고가 같은 판단에 상황 둘을 만들었다. 기획자가 "권고대로" 승인해 그대로 사양에 들어갔다 |
| 한 도착 순서만 막는 패치 | 고친 문장이 다른 도착 순서에서 같은 결함을 다시 냈다 |
| 원칙이 안전 입력을 버림 | "늦게 도착한 결과로는 상황을 열지 않는다"는 원칙이 단발성 사건의 이상 있음 결과까지 버렸다 |
| 금지 문장을 허용 문장으로 바꿈 | "회신이 없거나 반려·보류이면 실행하지 않는다"를 "회신을 받은 뒤 실행한다"로 바꿔 반려 뒤 실행이 허용되는 것처럼 읽혔다. **같은 실수를 두 번 반복했다** |
| 조사 없이 공백으로 등재 | "확인을 요청할 수단이 없다"를 공백으로 올렸는데, 실제로는 근거와 함께 도구를 주지 않기로 정한 배정이었다 |
| 예외 단서를 열거 없이 씀 | "진입 전 확인처럼 ~하는 확인"이 어느 확인을 가리키는지 사양 안에 기준이 없어, 다른 점검까지 면제로 읽힐 수 있었다 |
| 판정 기준을 고쳐 씀 | 기존 기준 문구를 고쳤다가 지적받았다. 기준은 추가만 한다 |

### 고친 직후 작성자 자기 점검 4가지

검토자를 부르기 전에 고친 문장마다 확인한다. 이 점검을 하지 않아 생긴 회차가 가장 비쌌다.

1. 고친 문장이 "하나뿐" 전제(열린 상황 하나, 경로 하나, 주체 하나)를 깨는가.
2. 새로 행동을 요구받은 주체의 권한 표와 도구 표와 업무 시작 조건에 그 행동이 있는가.
3. 같은 대상을 다루는 다른 절(경로 순서, 상태 표, 권한 표, 도구 표)에 구체적인 입력 하나를 넣었을 때 결과가 하나로 나오는가.
4. 금지나 부정 문장을 고쳤다면, 반려·무응답·실패 입력을 넣었을 때 여전히 "하지 않음"이 나오는가.

### 사람에게 권고를 올릴 때

기획자는 "권고대로"라고 승인하는 경우가 많다. 그러면 권고의 결함이 다음 회차의 모순으로 돌아온다. 권고를 올리기 전에 권고안에도 위 점검 4가지를 적용한다.

## 2. 수렴하지 않을 때

4회차부터 10회차까지 실패가 줄지 않았다. 원인은 4가지였다.

1. **같은 사실을 여러 절이 나눠 적었다.** 상황의 생성, 후속 경로, 해제, 업무 시작 조건을 5개 절이 따로 적어, 한 절을 고치면 다른 절과 어긋났다. 흩어진 규정을 한 절의 표로 모으고 다른 절은 그 표를 가리키게 다시 쓴 뒤 요구사항 실패가 처음 0이 됐다. **첫 작성이라면 상태·경로·해제처럼 여러 절이 참조하는 규칙을 처음부터 한 절에 둔다.**
2. **모순 인정 기준이 없었다.** 표현 해석만으로 모순 후보가 쏟아졌다. 증명 형식(입력 상황, 규정 1, 규정 2)을 도입하자 남은 모순이 모두 문장으로 풀리는 것이 됐다.
3. **작성자가 확정된 기준을 놓쳤다.** 한 번에 여러 절을 고치다 생긴다. 실패한 행만 고친다.
4. **검토자 판정 폭이 흔들렸다.** 같은 계열의 검토자라도 회차마다 새로 띄우므로, 문구가 같은 행이 다른 회차에 실패로 나오기도 했다. 지시문의 판정 기준을 구체적으로 적고, 흔들림이 확인되면 판정 기준 기록에 그 경우를 적는다.

그 뒤에 얻은 교훈 4가지가 더 있다.

- **경합 모순이 두 번 연속 나오면 사례 패치를 멈추고 원칙 하나로 부류를 닫는다.** 도착 순서 하나를 막는 문장은 다른 도착 순서에서 같은 결함을 낸다.
- **원칙을 세우면 그 원칙이 버리는 입력을 함께 점검한다.**
- **통과한 회차에도 기준 이의를 반드시 읽는다.** 통과 판정 안에 안전 공백이 들어 있었다.
- **두 검토자가 따로 짚은 같은 기준 이의는 안전 공백 후보로 사람에게 올린다.**

## 3. 운영

| 함정 | 대처 |
|---|---|
| 세션 임시 폴더가 비워져 검토자 지시문, 검토 결과, 스킬 초안, 장기 계획을 잃었다 | 추적표, 사본, 지시문, 검토자 출력을 모두 작업 폴더에 둔다. 장기 계획은 저장소의 상태판에 둔다 |
| 검토자 둘이 도는 동안 종료 검사(결함 주입 자기검사)가 시간 초과로 실패했다. 실제 결함은 없었다 | 검토자가 도는 동안 무거운 검사를 돌리지 않는다. 시간 초과를 결함으로 단정하지 않고, 검사를 지우거나 느슨하게 하지 않는다. 끝난 뒤 다시 돌린다 |
| 다른 세션이 원문(도구 카탈로그)을 고쳐 지문이 어긋났다 | 행 위치를 다시 지정하고 지문을 갱신한다. 지문 고정은 변경을 알려 줄 뿐이다. 바뀐 내용이 사양에도 반영돼야 하는지는 검토자에게 따로 보게 한다. 이렇게 해서 확정값 2개가 사양에만 빠진 것을 찾았다 |
| **다른 세션이 대상 사양을 직접 고쳤다.** 통과 판정을 받은 사양이 검토 없이 바뀌었다 | `check_trace.py`의 대상 지문 불일치가 이것을 알린다. 통과는 그 지문의 판본에만 유효하다. 다시 얼리고 바뀐 범위를 재검토한다 |
| 검사기에 회차 이름을 박아 두어 회차마다 검사기 코드를 고쳤다 | 이 스킬의 스크립트는 회차를 숫자로 다뤄 코드를 고치지 않는다 |
| 사양을 고친 뒤 추적표 지문을 갱신하지 않아 검사가 실패했다 | 순서를 "사양 수정, 사본 얼리기(지문 자동 갱신), 추적표 위치 갱신, 기계 검사"로 고정한다 |
| 한 칸만 고친 회차의 재검토를 작성자 판단으로 생략했다 | 생략하지 않는다. 대신 고친 범위를 맡는 검토자 1명만 돌리고, 그 사실을 회차 기록에 적는다. 작성자가 스스로 "약해질 수 없다"고 판정하는 구조가 같은 실수를 두 번 부른 구조다 |
| 통과한 뒤에도 행 상태가 "검토 대기"로 남았다 | `record_round.py`가 판정대로 행 상태를 바꾼다 |
| 한 회차에 토큰 40만~55만 개가 들었고, 사용량 한도에 걸려 작업을 나흘 미뤘다 | 회차 수를 줄이는 것이 비용을 줄이는 것이다. 자기 점검 4가지와 구조 먼저 원칙이 가장 큰 절감이다 |
