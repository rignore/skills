# prd-flow 공통 Evaluator 검증 루프 표준

산출물(desc·PRD·디자인 등)이 합격 기준을 1회 실행으로 못 채워 사용자가 매번 수동 수정을 반복하는 문제를 줄이기 위한, prd-flow 전 스킬 공통의 독립 검증 루프 표준이다.

> **위치·소유**: 현재 inspection-mode가 이 문서를 소유하며, **desc 품질 표준으로서 단독으로 완결**된다. 타 스킬·워크플로우(예: ai-dlc 기반 개발 단계의 검증 루프)는 `inspection-mode/references/evaluator-loop.md` 경로로 참조한다. 확대가 검증되면 공통 위치(`shared/references/`)로 승격한다.

> **근거**: Reflexion(Shinn et al., 2023, arXiv:2303.11366) Actor/Evaluator/Self-Reflection 분리 / Anthropic "Harness design for long-running application development"(생성≠평가 분리, Sprint Contract, few-shot 캘리브레이션) / tosea.ai "Loop Engineering AI Agents"(결정론 검증 우선, 종료 4출구, 진전 없음 감지, 보상 해킹 방지).

> **검증 근거**: 이 표준의 효과는 [evaluator-loop-validation-log.md](evaluator-loop-validation-log.md)에 회귀검증 기록으로 누적한다(케이스 A·B·C 3건, 2026-06-30 일반화 입증).

---

## 1. 핵심 원칙

1. **생성 ≠ 평가 분리**(필수). 산출물을 만든 메인 에이전트가 자기 평가하지 않는다. 평가는 Agent 도구로 띄운 독립 서브에이전트가 한다.
2. **결정론 검증 우선, LLM 평가는 보조**. grep·빌드·스키마·앵커 정합 등 기계 검증을 먼저 통과시키고, 주관 판단(정책 부합·표현 품질)만 LLM Evaluator에 맡긴다.
3. **합격 기준 정량화 + few-shot 캘리브레이션**. 체크리스트를 치명/권장/경미 등급으로 나누고, "이건 치명 / 이건 경미" 예시 몇 개로 평가자를 보정한다. Evaluator에 SKILL.md만 던지지 않는다.
4. **Sprint Contract = Gate**. 생성 착수 시점에 "이 산출물의 합격 기준"을 명문화하고, Evaluator는 그 계약으로 판정한다.
5. **종료 4출구 + 횟수 캡**. 무한 루프·비용 폭발을 막는다(§5).
6. **최소 복잡도·효용 게이트**. 모든 phase에 루프를 걸지 않는다(§2).

---

## 2. 언제 적용하나 (효용 게이트)

| 적용 | 생략 |
|---|---|
| 주관 판단이 필요하고(정책 부합·명세 충분성·표현 품질) 1회 실행으로 자주 누락되는 **복잡 phase** | 결정론 검증(grep·빌드·스키마)만으로 충분히 잡히는 단순 phase |
| 개발자가 desc만으로 구현해야 하는 명세, PRD↔산출물 정합 | 화면에서 보이는 것·라벨·배치 등 기계적으로 확인되는 항목 |

> 모델 성능이 올라가면 이 게이트를 다시 판단한다. 효용이 비용을 넘지 않으면 적용하지 않는다.

---

## 3. 2단 검증 구조

```
1단 결정론 검증 (먼저, 기계적)
   grep·빌드·스키마·앵커 정합으로 누락·위반을 0건으로 만든다
   → 통과해야 2단으로
2단 독립 LLM Evaluator (Agent 도구)
   1단이 못 잡는 주관 판단만 — 정책 부합·명세 충분성·과잉/누락
```

1단에서 잡히는 갭(예: 인터랙션 컴포넌트 무넘버링, 반복 행 무바인딩)을 2단 LLM 평가에 맡기지 않는다. 비싸고 비결정적이다.

## 4. Evaluator 서브에이전트 프롬프트 템플릿

Agent 도구(독립 서브에이전트)로 호출한다. 메인 에이전트의 생성 컨텍스트를 넘기지 않는다.

```
너는 독립 평가자(Evaluator)다. 이 산출물을 만든 주체가 아니며, 생성 의도를 추측해 봐주지 않는다.

[입력]
- 산출물: <검증 대상 — desc data.json / PRD 본문 / 화면 코드 등>
- Sprint Contract(합격 기준): <착수 시점에 합의한 합격 기준 목록>
- 캘리브레이션 예시: <치명/권장/경미 라벨 예시 — 스킬 로컬에서 주입>
- (재호출 시) 이전 라운드 갭: <누적 verbal feedback>

[판정 규칙]
- 불확실하면 "통과"가 아니라 "갭"으로 분류한다.
- 합격 기준에 없는 잣대를 새로 만들지 않는다(보상 해킹 역방향 방지).
- 과잉 작성("없음" 명시·범위 외 설명 등)도 갭이다(빼는 것이 개선).
- 계산식·로직(L-n)은 입력·수식·단위를 전수 확인한다. **PRD에 수식이 없어도 desc 자체로 개발 가능한지 본다** — PRD 정합만으로 추상적 PRD를 통과시키지 않는다.
- PRD 앵커(EP-·F-·D-)는 PRD 원문과 **1:1 대조**한다 — 사람이 기록으로 안 남긴 충돌·통짜 누락이 여기서 잡힌다.
- desc의 정책 인덱스 UI 토큰(`{L-n}`·`{tpl:...}`·`{run:...}`)은 **설명 모드(정책 인덱스 패널) 전용** 장치다. 실제 화면 컴포넌트(JSX)의 클릭·모달 이벤트가 아니다. 산출물(desc·티켓 AC·요구사항)이 이 토큰을 "화면 클릭 시 동작하는 실제 인터랙션"으로 서술하면, 실제 컴포넌트 코드(`screens/`·`components/`의 onClick·모달 트리거)에 그 인터랙션이 있는지 확인하고 없으면 갭이다. desc의 UI 표현을 곧 실제 화면 인터랙션으로 가정하지 않는다. (실제 사례: 요약 카드에 클릭 이벤트가 없는데 desc `{tpl:L-3:채널별 정산 내역}` 토큰을 근거로 "요약 카드 클릭 시 채널별 정산 모달 확인" AC가 작성됨 — 정책 인덱스 버튼을 실제 카드 인터랙션으로 오해)

[출력 — JSON]
{
  "gaps": [
    {"grade": "치명|권장|경미", "location": "<앵커/넘버>", "what": "무엇이 빠졌나/과잉인가", "why": "왜 문제인가", "evidence": "<PRD/정책 앵커>"}
  ],
  "verdict": "pass | fail",
  "reason": "<판정 근거 1줄>"
}
판정: 치명 0건이면 pass, 1건이라도 있으면 fail.
```

## 5. 종료 4출구

| 출구 | 조건 | 처리 |
|---|---|---|
| **성공(pass)** | 치명 0 + 권장은 처리 또는 기각 근거 명시 | 루프 종료, 통과 보고 |
| **실패(fail)** | 자격 미달이고 메인이 자동 보강 가능 | 갭을 verbal feedback으로 메인에 주입 → 보강 → Evaluator 재호출 |
| **상한 중단(cap)** | 횟수 캡(기본 3회) 도달, pass 못 함 | 현 상태 + 잔여 갭 목록 보고, 사용자 판단 요청 |
| **에스컬레이션** | Evaluator 실행 실패(API 오류 등) 또는 메인이 자동 보강 불가한 결정 | **self-eval로 통과 판정 금지.** 재시도 후에도 실패면 "독립 검증 미완료"로 명시하고 보류 보고 |

---

## 6. 진전 없음 감지

- 라운드 N과 N-1의 갭 수·내용이 실질적으로 동일하면 보강이 수렴하지 않는 것 → 상한 중단(출구 cap)으로 전환하고 사용자에게 보고한다.

---

## 7. 금지 (이번 세션 교훈 = 반례)

- **self-eval 통과 금지**: 독립 Evaluator가 실패(예: API 529 Overloaded)하면 self-evaluation으로 "통과"를 단정하지 않는다. 생성=평가 편향이 차단막을 무너뜨린다(2026-06-29 Round 2 실패 사례).
- **SKILL.md만 주지 말 것**: few-shot 캘리브레이션 예시 없이 평가하면 등급 판정이 흔들린다.
- **보상 해킹 금지**: 통과를 위해 합격 기준 자체를 느슨하게 바꾸지 않는다.
- **모든 phase 무거운 루프 금지**: §2 효용 게이트를 먼저 통과한 phase에만 적용한다.

---

## 8. 호출 방법 (Agent 도구 기준)

1. 메인 에이전트가 1단 결정론 검증을 먼저 통과시킨다.
2. Agent 도구로 Evaluator 서브에이전트 1회 호출(§4 템플릿 + 스킬 로컬 캘리브레이션 주입).
3. 판정이 fail이면 갭을 verbal feedback으로 정리해 보강한 뒤 Agent를 재호출한다(이전 갭 누적 주입 = Reflexion memory).
4. §5 4출구 중 하나에 도달할 때까지 반복한다. 횟수 캡은 기본 3회.
5. 다회 병렬 평가(여러 페르소나 동시 → 합성)가 필요하면 Workflow를 검토한다. 단 **사용자 opt-in 필수**.
