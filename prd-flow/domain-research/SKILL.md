# Domain Research

프로젝트별 도메인 지식베이스를 **웹 리서치로 구축**하는 스킬. 특정 회사·제품의 고정 지식베이스 대신, PRD 주제에서 도출한 토픽을 인터넷에서 검색해 로컬 캐시 파일로 저장하고 재사용한다.

## 이 스킬의 위치

| 시점 | 호출 주체 | 동작 |
|---|---|---|
| Gate 0 (프로젝트 시작) | `prd-builder-discovery` | 제품 카테고리·핵심 기능 키워드로 초기 캐시 1~4개 생성 |
| Auto Phase 진행 중 | `prd-builder-auto` | 새 도메인 키워드 등장 시 보강 캐시 생성 |
| 페르소나 리뷰 직전 | `prd-builder-auto` | 리뷰 영역의 캐시가 누락된 경우 보강 |
| 사용자 직접 요청 | 사용자 | "○○ 도메인 조사해줘" |

## 산출물

```
prd-flow/{feature-slug}/research/
├── domain-{topic-slug}.md      # 토픽별 리서치 캐시 (템플릿: references/research-cache-template.md)
└── ...
```

캐시 파일은 프로젝트의 **도메인 근거 자료(SoT 보조)**다. 이후 PRD 작성·페르소나 리뷰·정합성 검토(`prd-builder-auto` H1)가 Read로 적재해 참조한다.

## 워크플로우

### Step 1 — 리서치 토픽 도출

PRD 주제에서 조사할 토픽을 1~3개로 압축한다. 초기 적재 시 사용자에게 확인:

```
이 프로젝트의 도메인 리서치 토픽을 확인해주세요. (예: "반려동물 헬스케어", "산책 기록 앱", "위치 기반 서비스")
제안: {주제에서 도출한 토픽 1~3개}
이 토픽들로 웹 리서치를 진행해 프로젝트 지식베이스를 구축합니다.
```

토픽 유형 가이드 (하나의 토픽이 여러 유형을 겸할 수 있음):

| 유형 | 조사 내용 | 예시 토픽 |
|---|---|---|
| 제품 카테고리 | 대표 제품·기능 구성·UX 관행 | "habit tracker apps", "B2B 재고 관리 SaaS" |
| 도메인/산업 | 용어·규제·정책·데이터 특성 | "반려동물 헬스케어", "핀테크 송금" |
| 핵심 기능 | 구현 패턴·임계치·벤치마크 | "푸시 알림 리텐션", "구독 결제 플로우" |
| 사용자층 | 행동 특성·접근성 요구 | "시니어 사용자 모바일 UX" |

### Step 2 — 기존 캐시 확인

`prd-flow/{slug}/research/`에 같은 토픽 캐시가 있으면 **재사용**한다 (재검색하지 않음). 캐시 상단의 조사 일시가 오래됐거나(6개월+) 사용자가 갱신을 요청하면 재조사를 제안한다.

### Step 3 — 웹 검색

토픽당 **1~2회** WebSearch. 쿼리는 핵심 1~2개로 압축한다 (폭주 방지 상한 — 프로젝트 초기 적재 전체 기준 최대 4토픽 × 2회).

쿼리 패턴:
- `"{제품 카테고리} best practices {연도}"` / `"{카테고리} feature comparison"`
- `"{도메인} 용어" / "{domain} terminology glossary"`
- `"{기능} benchmark metrics"` / `"{기능} industry standard"`
- `"{도메인} regulations {지역}"` (규제가 관련될 때만)

결과 활용 규칙:
1. **패턴·수치·용어·관행만 추출**한다. 검색 원문 전체를 캐시에 붙여넣지 않는다.
2. 모든 수치·주장에 `[출처: 도메인]`을 병기한다.
3. 출처가 하나뿐인 수치는 "단일 출처" 표시를 남긴다.

### Step 4 — 캐시 파일 작성

`references/research-cache-template.md` 구조로 `research/domain-{topic-slug}.md`를 생성한다. 파일 상단 메타데이터(조사 일시·사용 쿼리·출처 수)는 필수.

### Step 5 — 적재 안내

생성/재사용된 캐시를 현재 대화에 Read로 적재하고 사용자에게 안내:

```
도메인 리서치 캐시 적재 완료:
- domain-pet-healthcare.md (도메인 용어·규제)
- domain-walk-tracking.md (유사 제품 패턴·벤치마크)

이후 PRD 작성과 페르소나 리뷰에서 위 자료와의 정합성을 함께 검토합니다.
```

**동시 적재 상한: 4개 토픽.** 컨텍스트 비대화 방지를 위해 현재 Phase와 관련된 캐시만 적재한다.

## 보강 적재 (Phase 진행 중)

다음 상황에서 추가 토픽을 조사한다:

- 사용자 답변에 처음 등장한 새 도메인 키워드 (예: Gate 0에서 "산책 기록"만 조사했는데 Backward에서 "수의사 연동" 등장)
- 페르소나 리뷰 직전, 그 페르소나가 검토할 영역의 캐시가 없는 경우
- 사용자가 명시적으로 "○○도 조사해줘" 요청

보강 시 안내 후 진행:

```
이 시점에 추가 리서치가 필요해 보입니다:
- {토픽}: {왜 필요한지 한 줄}
지금 조사해서 검토에 반영할까요? (예/아니오)
```

## 신뢰도 규칙 (필수)

웹 리서치는 확정 사양이 아니라 **참고 근거**다.

1. **단정 금지**: 리서치 값으로 채운 결정은 "리서치 기반 결정"으로 분류하고 출처를 decision-log에 기록한다. Silent Default 카운트에서는 제외하되 근거 없는 확정처럼 쓰지 않는다.
2. **사실검증 직렬 연결**: 캐시의 핵심 수치·주장은 `shared/reviewers/editorial-reviewer.md`의 사실 검증 관점으로 한 번 더 거른다. 의심 항목은 캐시에 `⚠️ 검증 필요` 표시.
3. **사용자 지식 우선**: 사용자가 직접 제공한 도메인 지식이 리서치와 충돌하면 사용자 지식을 따르고, 충돌 사실을 캐시와 decision-log에 1줄 남긴다.

## 페르소나 리뷰 연계

페르소나 리뷰 호출 시, 적재된 캐시가 있으면 페르소나 프롬프트에 명시한다:

```
[Staff Engineer 호출]
적재된 도메인 리서치 캐시:
- domain-pet-healthcare.md
- domain-walk-tracking.md

위 리서치 근거와 PRD 간 충돌·누락·정합성을 함께 검토해 주세요.
```

## 한계 및 주의

- **컨텍스트 비대화**: 토픽 수·적재 수 상한(4개)을 지킨다. 캐시 파일 하나는 200줄 이내로 압축한다.
- **시점 스냅샷**: 캐시는 조사 시점 기준이다. 빠르게 변하는 도메인(요금, 규제)은 갱신 일시를 확인한다.
- **리서치 불가 도메인**: 사내 시스템·비공개 사양 등 웹에 없는 지식은 사용자가 직접 자료를 제공해야 한다. 제공받은 자료는 같은 템플릿으로 `research/domain-{topic}-user-provided.md`에 정리한다.
