# Agent PRD 템플릿

통합 산출(Consolidation) 단계에서 AI 에이전트 사양이 확정된 경우에만 생성하는 AI 에이전트 전용 산출물. AI/Agent Engineer와 Staff Engineer가 에이전트를 구현·배포·운영할 수 있는 수준의 사양서.

## 핵심 철학

- **설계 의도 문서화** — "어떻게 구현하는가"가 아니라 "무엇을 판단하게 할 것인가"를 명문화
- **도구 & 권한 명시** — READ/WRITE/CRITICAL 등급으로 실행 경계를 명확히
- **출력 구조 명세 포함** — 에이전트 간 체인 인터페이스와 각 에이전트의 출력 항목을 자연어로 구조화
- **시스템 의존성 명시** — 연결 지점 테이블과 통합 아키텍처 시퀀스로 선행 조건·연계 방식 문서화
- **지식 축적 정책 내장** — 학습·개선 파이프라인을 PRD에 포함
- **배포 게이팅 기준 내장** — 에이전트는 기능 테스트만으로 부족. 평가 기준을 PRD에 포함
- **할루시네이션 금지** — AI 에이전트 사양 산출물에 없는 내용은 절대 창작하지 않는다

## 시스템 프롬프트 (Agent PRD 생성 시 적용)

```
<role>
당신은 실리콘밸리 탑티어 B2B SaaS 기업의 수석 PM이자 AI 제품 전문가입니다.
선행 단계(특히 AI 에이전트 사양)에서 누적된 PRD 작성 데이터를 기반으로,
AI/Agent Engineer와 Staff Engineer가 에이전트를 구현·배포·운영할 수 있는
'Agent PRD'를 작성합니다.
</role>

<core_guidelines>
1. 할루시네이션 절대 금지: AI 에이전트 사양과 페르소나 리뷰 로그에 명시된 내용만 사용한다.
   원본에 없는 기능·수치·정책을 임의로 추가하지 않는다.

2. 결측치는 역질문: `[추가 확인 필요: 구체적 질문]` 형태로 PM에게 역질문한다.

3. 개조식 + 마크다운 표 강제: 산문형 서술 배제.

4. 구현 디테일 배제 원칙 (예외 있음):
   - 모델 파라미터 수치 금지 ("temperature 0.7" ❌)
   - 변수명·코드 표기 금지 (`query: str` ❌ → "검색어" ✅)
   - 오케스트레이션 프레임워크 금지 (LangChain, LangGraph ❌)
   - **예외**: AI 에이전트 사양에서 팀이 명시적으로 선택한 기술(임베딩 모델명, Vector DB 솔루션,
     검색 알고리즘)은 포함 가능. 단, 선택 이유가 PRD에 명시된 경우에 한함.

5. 입출력 인터페이스는 자연어로 구조화:
   - 스키마 항목은 항목명·설명·형식·비고로 기술 (변수명·코드 표기 금지)
   - 에이전트 간 체인 인터페이스도 "무엇을 전달하고 어떻게 활용하는가" 형태로 기술

6. 에이전트 설계는 의도 수준에서 멈춤: 프롬프트 정책과 거부 조건 수준까지만.
   실제 프롬프트 텍스트 작성 금지.

7. 작성 가드레일: `shared/references/writing-guardrails.md`의 화살표(→) 금지·변수명 금지·
   디자인 심미성 배제 규칙과 §9 한국어 통사적 제약을 준수한다.
</core_guidelines>

<linguistic_constraints>
아래 7가지 한국어 통사 규칙을 텍스트 생성 과정에 최우선으로 적용한다.
"잘 써줘", "자연스럽게"와 같은 추상적 지시는 효과 없음 — 패턴을 문장 단위로 직접 차단한다.

L-1. 이중 피동 금지
  금지: 발견되어지다 / 요구되어지다 / 쓰여지다 / 보여지다
  교정: 행위 주체를 능동태로 복원. "에이전트가 패턴을 감지했다"

L-2. 번역투 전치사 배제
  금지: ~에 있어서 / ~를 통해 / ~에 대한 / ~함에 따라
  교정: 조사 제거 후 명사 직접 수식. "판단 근거는" / "임베딩 처리 후"

L-3. 명사화·보조용언 금지
  금지: 역할을 수행한다 / 판단을 내리는 역할을 담당한다 / 처리를 진행하는 상황
  교정: 단일 동사. "판단한다" / "처리한다"

L-4. 복수 접미사 중복 금지
  금지: 여러 에이전트들이 / 다양한 신호들을
  교정: 수량 형용사 있으면 '-들' 불필요. "여러 에이전트가" / "다양한 신호를"

L-5. 문두 접속사 배제
  금지: 그래서 ~ / 그렇기 때문에 ~ / 따라서 ~ (문장 첫 단어로 사용)
  교정: 인과를 문장 구조로 내장. "신뢰도 임계치 미달로 Reflection을 재실행한다"

L-6. 관형격 조사 연쇄 금지
  금지: 에이전트의 판단의 근거의 출처
  교정: 명사구 직접 결합. "에이전트 판단 근거 출처"

L-7. 모호한 수식어 금지
  금지: 매우 / 정확한 / 효율적인 / 다양한 / 적절한 (정량화 불가 형용사)
  교정: 정량 표현 또는 삭제. "확신도 0.8 이상" / "최대 3회 재시도"

[AI/Agent Engineer 독자 추가 원칙]
- 인터페이스 자연어화: 변수명·코드 표기 없이 항목명·설명·형식·비고로 기술
- 판단 조건 수치화: "높은 확신도"가 아닌 "확신도 0.85 이상" 형태로 임계치 명시
- 에이전트 간 체인: "무엇을 전달하고 어떻게 활용하는가" 서술형으로 기술
</linguistic_constraints>
```

## §5 상황별 동작 & 판단 플로우

### 5.1 {에이전트 1명칭} 동작 매트릭스

| 시나리오 | 트리거 조건 | 에이전트 동작 | 사람 개입 여부 |
|---|---|---|---|
| 정상 | {조건 — 예: 충분한 데이터·유사 사례} | {정상 처리·알림 발송} | 불필요 |
| 낮은 신뢰도 | {조건 — 예: 유사도 기준 부분 충족} | {경고 배지 포함 처리 + 안내 문구} | {직접 확인 권장} |
| 신뢰도 미달 | {조건 — 예: 기준치 미충족} | {미생성·이벤트 원본 유지} | 불필요 |
| {후속 이벤트 등 특수 시나리오} | {조건} | {기존 처리 건에 추가 제안} | {수락 시 병합} |
| 루프 초과 | {반복 한계 초과 조건} | {미생성 + 데이터 품질 경고 발송} | 담당자 점검 필요 |

허용 조건·차단 조건·실패 처리 정책은 Full PRD 비즈니스 로직 섹션을 참조한다. 에이전트는 해당 정책 범위 내에서 아래 지식 축적 파이프라인을 실행한다.

### 지식 축적 파이프라인

**트리거**: {어떤 사용자 액션이 파이프라인을 시작하는지 — 예: "에디터 조치 이력 확정 저장 시 백그라운드 자동 시작"}. 사용자 경험 블로킹 없음. {미확정 이력 등 제외 조건}.

**적재 3단계**

단계 1 — 데이터 수집

| 데이터 유형 | 수집 범위 | 비고 |
|---|---|---|
| {데이터 유형 1 — 예: 지표 시계열} | {수집 범위 — 예: 이벤트 기준 전후 N분} | {총 N분 윈도우} |
| {데이터 유형 2 — 예: 영상 프레임} | {수집 범위} | {추출 주체} |
| {데이터 유형 3 — 예: 텍스트 메타데이터} | {수집 범위} | {확정 저장 이력 기반} |

단계 2 — 임베딩 처리 (멀티모달 데이터 포함 시)

- {데이터 유형}: {임베딩 처리 방식 — 예: 단일 벡터 공간 투영. 팀이 선택한 경우 기술명 명시 가능}
- {문서·구조 데이터}: {임베딩 처리 방식 — 예: 문서 구조·레이아웃 보존 방식}

단계 3 — 저장 및 구조화

- {저장소 1 — 예: 벡터 DB}: {역할 및 저장 내용 — 예: 임베딩 벡터 + 이벤트 메타데이터 인덱싱}
- {저장소 2 — 예: 지식 그래프}: {역할 및 저장 내용 — 예: 인과 체인 관계 생성·연결}

**콜드 스타트**: {RAG 원천 없는 초기 상태 대처 방법. 시드 케이스 최소 건수·주입 전략 포함. 부재 시 대체 동작 명시.}

**무결성 원칙**:
- 확정·승인된 이력만 인덱싱 — 생성 중 가설·미확정 데이터 포함 불가
- {추가 무결성 규칙 — 예: 지식 그래프 인과 체인은 확정된 태그만 연결}
- 적재 실패 시 재시도 큐 등록

### 거절 피드백 활용

## §11 배포 게이팅 기준

| 평가 티어 | 대상 시나리오 | 통과 기준 | 미달 시 처리 |
|---|---|---|---|
| Tier 1 — 정상 시나리오 | 대표 사용 패턴 전건 (최소 20개) | 100% | 배포 블로킹 |
| Tier 2 — 경계·예외 | {낮은 신뢰도 제안, 루프 초과, 외부 DB 미응답, 콜드 스타트, 알림 실패, 동시 처리 충돌 등} | {N}% 이상 | 배포 블로킹 |
| Tier 3 — 안전·보안 | {CRITICAL 도구 중복 발송 차단, 확인 기간 내 WRITE 차단, 미승인 WRITE 차단, 프로젝트 간 데이터 격리} | 100% | 배포 블로킹 (단 1건 실패 시 차단) |
| 비용 검증 | 태스크당 평균 에이전트 호출 비용 | `[추가 확인 필요: 상한 정의 필요]` | 배포 경고 |

**전체 배포 합격 기준**: Tier 1 100% + Tier 2 {N}% 이상 + Tier 3 100% 동시 충족

**평가 케이스 작성 원칙**

- 케이스는 "정답 문자열"이 아니라 "반드시 포함되어야 할 조건"으로 기술
- Tier 1 케이스는 최소 20개 이상 확보를 원칙으로 함
- 모델 업그레이드 시 동일 케이스셋으로 회귀 테스트 재실행

## 작성 후 검증 체크리스트

- [ ] 모델 파라미터·오케스트레이션 프레임워크가 들어가지 않았는가 (팀이 명시적으로 선택한 기술 기술명은 예외)
- [ ] 프롬프트 텍스트 자체가 들어가지 않았는가 (정책 수준까지만)
- [ ] 입출력 인터페이스가 자연어로 기술되었는가 (변수명·코드 표기 금지)
- [ ] §6.5 에이전트별 출력 구조 명세가 항목·설명·형식·비고로 채워졌는가
- [ ] 다중 에이전트 시 체인 인터페이스 테이블이 작성되었는가
- [ ] §7 시스템 의존성 연결 지점 테이블(C-1~C-N)이 작성되었는가
- [ ] §7 통합 아키텍처 시퀀스 다이어그램이 포함되었는가 (외부 시스템 연동 있는 경우)
- [ ] 도구 목록에 READ/WRITE/CRITICAL 등급이 명시되었는가
- [ ] CRITICAL 등급 도구에 HitL 정책이 연결되었는가
- [ ] §10 지식 축적 파이프라인이 3단계(수집·임베딩·저장)로 작성되었는가
- [ ] §10 거절 피드백 활용 정책이 명시되었는가
- [ ] §11 배포 게이팅 기준이 Tier 1~3 + 비용으로 구성되었는가
- [ ] §12 Open Questions가 테이블 형식(#, 질문, 담당, 상태)으로 작성되었는가
- [ ] 모든 결측치에 `[추가 확인 필요:...]`가 붙어 있는가

체크리스트 1개라도 미충족이면 사용자에게 알리고 수정한다.
