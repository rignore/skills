# 디자인 원칙

이 스킬 세트의 공통 디자인 원칙. 모든 PRD 산출물이 이 6개 원칙과 충돌하지 않는지 페르소나 리뷰 시 확인한다.

## 핵심 원칙: Clarify Everything — 모든 것을 명확하게

제품 디자인은 언제나 '명확함(Clarity)'을 기준으로 움직인다. 모든 시각적·상호작용적 결정은 **"이것이 사용자의 이해를 더 명확하게 만드는가?"** 라는 질문에 답해야 한다.

### 왜 명확성인가

1. 대부분의 제품은 여러 종류의 데이터와 기능을 통합 처리한다. 사용자가 화면을 보고 현재 상황을 직관적으로 이해하지 못하면, 제품이 약속한 핵심 가치가 훼손된다.
2. 모든 컴포넌트, 색상, 문구, 인터랙션 규칙이 명확하게 정의되어 있을 때 PM·디자이너·개발자가 같은 언어로 소통할 수 있고, 새로운 기능과 데이터가 추가되어도 일관된 경험을 유지할 수 있다.
3. 제품의 핵심 가치는 사용자가 시스템을 신뢰할 때만 실현된다. 정보를 명확히 보여주면 사용자는 즉시 판단하고 적절히 대응할 수 있다.

---

## 파생 원칙

### 1. 시스템 언어를 통일하여 예측 가능하게 (Unify the System for Predictability)

여러 데이터와 기능을 다루는 제품일수록, 어떤 화면이나 기기에서든 동일한 시각 언어와 인터랙션 규칙을 사용해 사용자 행동을 예측 가능하게 해야 한다.

**실천 방안**
- 디자인 토큰과 재사용 컴포넌트를 활용해 반복 작업을 최소화하고 시각적 일관성을 확보
- 색상·아이콘·용어·레이아웃 정의를 명확히 하여 표준 가이드로 관리
- 핵심 엔티티의 등록·삭제·설정 변경 등 핵심 UX 플로우는 제품 전반에서 동일한 단계와 규칙으로 통일
- 웹·모바일 앱에 동일한 디자인 시스템 언어와 UX 규칙 적용

**PRD 적용 지점**: 기능 정의 시 "기존 시스템에서 동일 기능이 어떻게 동작하는지" 먼저 확인하고 일관성 유지

---

### 2. 쉽게 인지하고 조작하여 오류를 방지 (Make It Intuitive to Prevent Errors)

사용자는 다양한 배경, 숙련도, 기기 환경에서 제품을 사용한다. 낯선 인터페이스나 불명확한 절차는 혼란·오류·실수로 이어져 제품 신뢰를 저해한다. 사용자의 인지 부하를 최소화하고 핵심 목표 달성에 집중하게 해야 한다.

**실천 방안**
- 친숙한 UI/UX 요소(흔히 사용되는 아이콘, 표준 레이아웃)를 사용해 인지 부하 최소화
- 자주 사용하는 핵심 정보(중요 알림, 현재 상태)는 가장 잘 보이는 위치에 배치
- 초보자/숙련자 수준에 맞춰 기능 노출 조절, 맥락에 맞는 안내(툴팁, 온보딩) 제공
- 작업 직후 '되돌리기' 또는 '취소' 옵션 제공
- 오류 발생 시 코드 대신 사용자가 바로 취할 수 있는 해결책 제시

**PRD 적용 지점**: 사용자 시나리오, 화면별 기능 정의, UI 텍스트 작성

---

### 3. 맥락과 이유를 연결하여 신뢰를 확보 (Connect the Context for Trust)

데이터를 분석해 상태 변화나 이상 징후를 알리는 제품에서는, 사용자가 단순히 알림이나 상태 변화만 보아서는 무슨 일이 일어났고 왜 발생했는지 이해할 수 없다. 맥락과 원인을 제공하지 않으면 판단 지연, 잘못된 대응, 시스템 신뢰 저하로 이어진다.

**실천 방안**
- 알림이나 상태 변화 발생 시 관련 원인 데이터·발생 시점·예상 영향·권장 조치를 하나의 UI에 통합
- 중요 알림은 경고 내용과 함께 권장 조치 행동을 명확히 제시
- 알림·로그·이벤트 히스토리는 데이터의 흐름과 시간 순서를 명확히 보여주어 전후 관계 파악 가능하게 설계
- 이상 징후 발생 시 발생 원인에 따라 명확히 구분된 색상과 아이콘으로 시각화

**PRD 적용 지점**: 알림 기능 정의, 에이전트 출력 정의, 모든 UI 텍스트

---

### 4. 유연하게 확장하여 사용성을 유지 (Grow with Structure to Maintain Usability)

사용 조직·환경마다 요구가 달라 새로운 기능이나 맞춤형 확장이 필수적이다. 기존 구조가 흔들리면 사용자 혼선을 초래하므로, 확장 시에도 일관된 사용성을 유지하여 사용자의 숙련도를 보호해야 한다.

**실천 방안**
- 모든 컴포넌트와 UI는 재사용과 확장을 염두에 두고 설계, 명확한 규격을 가짐
- 새로운 기능 추가 시 기존 시스템의 구조·컴포넌트 규칙·상호작용 패턴을 80% 이상 준수
- 신규 기능이 기존 패턴을 80% 이상 유지할 수 없는 명확한 사유(새로운 데이터 구조, 법적 요구, 산업 규격 변화 등)가 있는 경우에만 예외 허용. 이 경우 사용자에게 필요한 추가 학습을 최소화하는 방향으로 설계
- 예외 발생 시 해당 규칙 변경은 시스템 가이드라인에 업데이트되어 향후 다른 기능에도 일관되게 적용되도록 한다

**PRD 적용 지점**: 기능 정의, 우선순위(스코프 확장 판단)

---

### 5. 실시간성을 신뢰성으로 (Real-time as Reliability)

실시간 데이터를 다루는 제품의 본질은 데이터의 신뢰가 곧 제품 가치로 이어진다는 점이다. 데이터 수집·전송 과정의 문제가 사용자에게 투명하게 전달되지 않으면, 사용자는 잘못된 정보로 의사결정을 내리거나 시스템 신뢰를 잃는다.

**실천 방안**
- 데이터 연결 상태(정상·지연·끊김·재연결 중)가 사용자에게 가시적으로 표시되어야 함
- 연결 끊김 발생 시 영향받는 기능·화면이 명시적으로 안내되어야 함
- 일시적 지연과 영구적 끊김을 구분하여 사용자가 다른 판단을 할 수 있게 해야 함

**PRD 적용 지점**: 실시간 데이터 표시 기능, 알림 설계, 에러 처리

---

### 6. 안전 기본값 (Safe Defaults First)

잘못된 기본값 하나가 데이터 유실·오발송·과금 사고처럼 되돌리기 어려운 결과로 이어질 수 있다. 모호한 상황에서는 항상 더 안전한 쪽으로 기본값을 설정한다.

**실천 방안**
- 위험한 동작은 명시적 확인을 거치고, 가능한 경우 되돌릴 시간 제공 (알림 끄기, 자동 백업 해제, 권한 변경 등)
- 모호한 상황에서는 안전한 쪽이 기본값 (알림은 켜짐 상태, 권한은 좁게 부여)
- 파괴적 동작(영구 삭제, 일괄 변경)은 기본 비활성화. 명시적 활성화 후에만 가능
- 안전장치 성격의 기능(알림·백업·권한 제한)은 기본적으로 활성화, 비활성화하려면 추가 컨펌 필요

**PRD 적용 지점**: 권한·설정 기능 정의, 통합 리뷰의 Paranoid Reviewer 최종 체크

---

## 디자인 원칙 평가 체크리스트 (페르소나 리뷰 시 사용)

각 PRD 산출물에 대해 다음 질문에 답할 수 있어야 한다.

1. 이 기능/화면은 사용자에게 더 **명확함**을 제공하는가?
2. 기존 시스템과 **일관된 시각 언어**를 유지하는가? (원칙 1)
3. 사용자의 **인지 부하**를 늘리지 않는가? 친숙한 패턴을 사용하는가? (원칙 2)
4. 사용자가 **왜** 이 일이 일어났는지, **무엇을 해야 하는지** 즉시 알 수 있는가? (원칙 3)
5. 이 기능을 추가할 때 기존 패턴을 **80% 이상 준수**하는가? 예외라면 명확한 사유와 가이드라인 업데이트가 있는가? (원칙 4)
6. **데이터 연결 상태**가 사용자에게 가시적으로 전달되는가? (원칙 5)
7. 위험한 동작에 **안전 장치**가 있는가? 모호한 상황에서 안전한 쪽이 기본값인가? (원칙 6)
