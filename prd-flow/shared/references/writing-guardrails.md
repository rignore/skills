# PRD 본문 작성 가드레일

PRD 페이지의 모든 서술문에 적용되는 작성 규칙. UI 텍스트 작성은 별도(`ux-writing-guardrails.md`).

## 1. 화살표(→) 사용 규칙

### 금지

화살표로 인과·순서·결과를 표현하지 않는다. 완성된 문장으로 풀어쓴다.

❌ **나쁜 예**
- 결제 수단 만료 → 구독 결제 실패 다수 발생
- 임계치 초과 → 알림 발송 → 담당자 확인
- 신규 가입 → 온보딩 진입 → 첫 프로젝트 생성

✅ **좋은 예**
- 결제 수단 만료로 인한 구독 결제 실패 다수 발생
- 임계치를 초과하면 알림이 발송되며, 담당자가 확인하는 흐름
- 신규 가입자가 온보딩에 진입한 뒤 첫 프로젝트를 생성하는 경로

### 예외 — 시각적 조건 표현

**조건 결합·규칙 정의** 등 시각적으로 짧게 표현하는 것이 더 명확한 경우에만 부분적으로 사용 허용.

✅ **허용**
- 카테고리 동일 + 알림 유형 동일 + 60초 내 3건 이상 발생
- 신뢰도 ≥ 90% AND 데이터 건수 ≥ 100건
- 평일 09:00–18:00 KST

✅ **허용** (Mermaid 다이어그램 내부의 화살표는 당연히 OK)

## 2. 변수명·코드 표기 금지

기획 문서이지 코드 명세가 아니다. 모든 항목은 단어 또는 서술형으로.

❌ **나쁜 예**
- `user_id`, `is_active`, `event_type`
- `getStatus()`, `POST /api/orders`
- `status: "PENDING"`

✅ **좋은 예**
- 사용자 식별 정보, 활성 상태 여부, 이벤트 유형
- 상태 조회 기능, 상품 등록 요청
- 상태 값이 "대기 중"인 경우

### 단, 다음은 허용

- 산업·도메인 표준 약어 (SKU, VAT, OCR 등)
- 이미 제품·UI에서 사용 중인 한국어 용어
- 외부 시스템·표준 식별자 (예: SSN, OAuth)

## 3. 디자인 심미성 배제

PRD는 PM 관점 문서. 디자이너 영역은 작성하지 않는다.

❌ **PRD에 작성하지 않음**
- 색상 팔레트, 폰트 종류·크기
- 여백·패딩 수치, 둥근 모서리 반경
- 그림자, 트랜지션, 애니메이션 효과
- 아이콘 디자인 디테일

✅ **PRD에 작성함** (UX 흐름·정보 우선순위는 기획 영역)
- 화면 진입 시 가장 먼저 강조해야 할 정보가 무엇인지
- 핵심 알림이 항상 보이는 위치에 있어야 한다는 요구
- 사용자가 위험 상황일 때 명확히 구분되는 시각적 단서가 필요하다는 요구
- 색상으로 위험도를 구분해야 한다는 정책 (구체적 색상 코드는 ❌, "위험도별 색상 구분 필요" ✅)

## 4. 개발 구현 디테일 배제

마찬가지로 개발자 영역은 작성하지 않는다.

❌ **PRD에 작성하지 않음**
- 사용 라이브러리·프레임워크 선택
- 데이터베이스 스키마, 테이블 구조
- API 엔드포인트, HTTP 메서드
- 캐싱 전략, 쿼리 최적화 방법
- 인프라 구성 (서버 사양, 컨테이너 등)

✅ **PRD에 작성함**
- **비즈니스 로직**: "결제 완료 시 포인트가 적립되며, 환불 시 동일 금액의 포인트가 차감된다"
- **백엔드 시퀀스 (개략)**: Mermaid 시퀀스 다이어그램으로 시스템 간 흐름만 표현. 내부 구현은 블랙박스
- **데이터 정합성 요구**: "포인트 적립과 결제 기록은 항상 일치해야 함"
- **성능·응답 요구**: "알림은 발생 후 5초 이내 사용자 화면에 도달"

## 5. 개조식 우선

줄글 문장보다 번호 계층 + 짧은 서술형이 기본.

❌ **나쁜 예 (줄글)**
> 이 기능은 사용자가 상품을 등록할 때 사용되며, 등록 과정에서 사용자는 상품 카테고리를 선택하고 판매 가격을 입력해야 하고, 입력이 완료되면 시스템이 검증을 수행하여 중복 여부를 확인한 뒤 저장합니다.

✅ **좋은 예 (개조식)**
1. 상품 등록 화면 진입
   1-a. 상품 카테고리 선택
   1-b. 판매 가격 입력
2. 입력 완료 후 시스템 검증
   2-a. 동일 이름·동일 카테고리 상품 중복 여부 확인
   2-b. 중복 시 안내, 미중복 시 저장 진행

### 줄글이 더 적합한 경우

- 문제 정의의 배경 서술
- 페르소나 일대기·맥락 서술
- 디자인 원칙 같은 철학적 내용

## 6. 표 사용 권장

복수 항목을 비교·열거할 때는 표가 가장 효과적.

✅ **표가 적합한 경우**
- 사용자 역할별 권한 매트릭스
- 상태 전환 매트릭스 (현재 상태 × 가능한 다음 상태)
- MoSCoW 우선순위 분류
- KPI 지표별 측정 방법
- 화면별 기능 매트릭스

## 7. Mermaid 다이어그램 활용

Notion이 네이티브 지원. 비즈니스 로직과 백엔드 시퀀스에 적극 활용. 자세한 패턴은 `mermaid-patterns.md`.

**주요 사용처**:
- 비즈니스 로직 분기 (flowchart)
- 시스템 간 호출 흐름 (sequenceDiagram)
- 상태 머신 (stateDiagram)
- AI 에이전트 구성 (graph)

## 8. 약어·전문 용어 처리

- 처음 등장 시 풀어쓰고 괄호로 약어 표기. "월간 활성 사용자(MAU)"
- 이후로는 약어 사용 가능
- 산업·도메인 특화 용어는 PRD 페이지 하단에 용어집 토글 추가 권장

## 9. 한국어 통사적 제약 (AI 번역투 제거)

AI가 생성한 텍스트 특유의 기계 번역투·이중 피동·명사화 패턴을 배제하여 전문 테크니컬 라이터 수준의 문서를 작성한다. "잘 써줘"와 같은 추상적 지시는 효과가 없다. 아래 7가지 패턴을 문장 단위로 직접 차단한다.

| # | 문제 유형 | 금지 표현 예시 | 교정 방향 |
|---|---|---|---|
| L-1 | **이중 피동** | 발견되어지다, 쓰여지다, 보여지다, 요구되어지다 | 능동태로 복원. "시스템이 오류를 발견했다" |
| L-2 | **번역투 전치사** | ~에 있어서, ~를 통해, ~에 대한, ~함에 따라 | 조사 제거 후 명사 간 직접 수식. "도입 핵심은" |
| L-3 | **명사화·보조용언** | 역할을 수행하다, 지원을 하다, 진행을 하는 상황 | 단일 동사로. "지원한다", "진행한다" |
| L-4 | **복수 접미사 중복** | 많은 개발자들이, 여러 오류들을 | 수량 형용사 있으면 '-들' 불필요. "많은 개발자가" |
| L-5 | **문두 접속사** | 그래서 ~, 그렇기 때문에 ~, 따라서 ~ (문두 사용) | 인과를 문장 구조로 내장. "트래픽 급증으로 서버 증설이 필요하다" |
| L-6 | **관형격 연쇄** | 사용자의 데이터베이스의 백업본의 손상 | 명사구 직접 결합. "사용자 데이터베이스 백업본 손상" |
| L-7 | **모호한 수식어** | 매우, 직관적인, 훌륭한, 다양한, 효율적인 | 정량 표현으로 대체하거나 삭제. "3단계로 압축", "500ms 이내" |
| L-8 | **사물·시스템 주어 + 피동형** | "데이터가 시스템에 의해 처리되었습니다", 무생물이 행위 주체인 피동 문장 | 실제 행위자(담당자, 서비스)를 주어로 세우고 능동태 전환. 소프트웨어 자체가 주어일 때만 피동 허용 |
| L-9 | **문장 길이 획일화** | 연속 5문장 이상이 모두 30~50자 내외로 균일한 경우 | 핵심 주장은 15자 이내 단문으로, 부연 설명은 장문으로 교차 배치하여 리듬 변화 유도 |
| L-10 | **em-dash 압축 명사구** | "알림 꺼둔 상태에서 결제 실패 발생 — 구독 해지 직결 사례", "유사 과거 사례 최대 3건 제시 — 담당자가 수락/거절 판단" | em-dash를 연결 어미(~하며, ~이며)로 대체하고 뒤 명사구를 서술어로 완결. 표 셀·도식 레이블 등 문장 완결이 관례적으로 불필요한 맥락은 예외 |
| L-11 | **다항목 단문 압축** | 2개 이상 항목·케이스를 `~하고, ~하며, ~한다` 형태로 한 문장에 나열 | 도입 완성문 + 항목별 개조식 목록으로 분리. 각 항목도 서술어로 완결 |

**L-11 다항목 단문 압축 — 적용 기준과 교정 예시**

항목이 2개 이상이거나, 케이스(심각도별·확신도별·역할별 등)가 2개 이상인 경우에 적용한다. 항목 수를 도입 문장에 명시하면 독자가 목록의 끝을 예측할 수 있어 가독성이 높아진다.

❌ **나쁜 예 — 다항목 단문 압축**
- "확신도가 0.5~0.8인 구간에는 낮은 확신도 경고 배지를 표시하고, 담당자가 구성 이벤트를 직접 확인할 수 있도록 안내한다."
- "심각도별 처리 시간(높음 2시간 / 중간 4시간 / 낮음 8시간)을 초과하면 에스컬레이션 대상으로 지정하고 검토 필요 배지로 명시한다."

✅ **좋은 예 — 도입 완성문 + 개조식 목록**

확신도가 0.5~0.8인 구간에는 아래 두 항목으로 담당자가 상황을 직접 확인할 수 있도록 안내한다.
- 낮은 확신도가 표시된 경고 배지로 주의를 준다.
- 구성 이벤트를 직접 확인할 수 있도록 안내한다.

에스컬레이션 발동 기준은 심각도별로 다음과 같다.
- 높음: 2시간 초과 시 발동한다.
- 중간: 4시간 초과 시 발동한다.
- 낮음: 8시간 초과 시 발동한다.

### 독자별 추가 원칙

| 독자 | 원칙 |
|---|---|
| 임원·의사결정자 (1-Pager) | **결론 선배치(Answer First)**: 핵심 결론·요구 조치·임팩트를 첫 문장에 배치. 배경 서술을 앞에 쓰는 미괄식 금지 |
| 엔지니어·QA (Full PRD) | **조건 수치화**: "빠르게", "적절히" 대신 응답 시간·임계값·건수로 표현 |
| AI/Agent Engineer (Agent PRD) | **인터페이스 자연어화**: 변수명·코드 표기 없이 항목명·설명·형식·비고로 기술 |

## 10. 정보 배치와 직렬위치 효과

독자(사람과 LLM 모두)는 문서의 첫 항목과 마지막 항목을 중간보다 더 잘 기억하고 더 크게 반영한다. 이를 직렬위치 효과(Serial Position Effect)라 한다. 중간에 배치된 항목은 상대적으로 흐려진다(Lost in the Middle). 이 구조적 편향을 알고 있으면 문서의 정보 배치를 의도적으로 설계할 수 있다.

### 핵심 항목의 배치 원칙

핵심 요구사항, 최우선 인수 조건, 반드시 지켜야 할 제약은 목록의 **첫 번째 또는 마지막**에 배치한다.

❌ **나쁜 예 — 핵심이 중간에 묻힌 경우**

```
AC 1. 목록 표시 조건
AC 2. 정렬 기준
AC 3. 전송 실패 시 오류 메시지를 반드시 표시해야 한다  ← 핵심 AC
AC 4. 빈 목록 처리
AC 5. 로딩 상태 표시
```

✅ **좋은 예 — 핵심을 첫 번째 또는 마지막으로**

```
AC 1. 전송 실패 시 오류 메시지를 반드시 표시해야 한다  ← 핵심 AC
AC 2. 목록 표시 조건
AC 3. 정렬 기준
AC 4. 빈 목록 처리
AC 5. 로딩 상태 표시
```

### 섹션 마지막 문장 설계

각 섹션의 마지막 문장이 독자의 해당 섹션 인상을 결정한다. 섹션은 핵심 제약 또는 결정 사항으로 끝낸다. 부가 설명이나 예외 처리로 섹션을 끝내지 않는다.

### AI 생성 초안의 최신 편향 검토

LLM이 생성한 PRD 초안에는 생성 직전 대화에서 논의된 내용이 실제 중요도보다 과대 반영되는 경향이 있다. 최신 편향(Recency Bias)이다. 생성된 초안을 검토할 때 다음 세 가지를 확인한다.

1. 가장 최근에 논의된 요구사항이 실제 중요도에 비해 지나치게 상세하게 기술되어 있지 않은가
2. 대화 초반에 언급된 핵심 요구사항이 상대적으로 빈약하게 기술되어 있지 않은가
3. 작업 지시나 맥락 설명("이 부분은 삭제하기로 했어" 등)이 결과물 본문에 섞여 들어가지 않았는가
4. 대화 중 주어진 부정형 작업 지시("~는 표시하지 않는다", "~는 빼줘", "~는 삭제해줘")가 스펙 항목으로 변환되어 기재되지 않았는가

### 부정형 작업 지시의 스펙 변환 금지

문서는 화면에 **표시되는 것**만 기술한다. 표시하지 않기로 결정한 항목을 역으로 명시할 필요는 없다. 표시 항목 목록에 없으면 그것으로 충분하다.

❌ **나쁜 예 — 작업 지시가 스펙으로 새어 들어간 경우**
- "이메일 주소·가입 일자는 표시하지 않는다"
- "담당자 이름은 노출하지 않는다"
- "삭제된 B 문단은 포함하지 않는다"

✅ **좋은 예 — 표시되는 것만 기술**
- "멤버 목록 행에는 이름과 권한 등급을 표시한다"
- (이메일 주소·가입 일자에 대한 언급 없음)

**예외**: 보안·프라이버시 요구사항처럼 "표시하지 않는다"는 사실 자체가 비즈니스 정책으로서 명시적으로 문서화되어야 하는 경우는 허용한다. 예: "주민등록번호 전체를 화면에 노출하지 않는다 (마스킹 필수)"
