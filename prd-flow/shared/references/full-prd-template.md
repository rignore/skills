# Full PRD 템플릿

통합 산출(Consolidation) 단계에서 생성하는 엔지니어·QA·디자이너용 산출물.

## 핵심 철학

- **티켓 분해가 가능한 제품 계약** — 팀이 목적·범위·완료 상태를 다시 추정하지 않고 Epic별 티켓 구체화를 시작할 수준
- **문제 공간 우선** — 솔루션보다 Pain Point와 근본 원인 가설이 먼저
- **Decision Log 보존** — 문서 맨 위 토글에 거부된 대안과 사유를 보존해 중복 논의를 막음
- **KPI 최소화** — 실제로 사용할 사용자 성과 지표만 포함하고 회사에서 쓰지 않는 배포 확대 중단 기준·보호 지표는 생성하지 않음
- **할루시네이션 금지** — 선행 산출물에 없는 정보는 절대 창작하지 않는다

## 기획 산출물 3개 역할 분담과 단일 SoT 경계 (필독)

기획 산출물 간의 중복을 배제하고 단일 진실 공급원(SoT, Source of Truth)을 명확히 지킨다. 어느 한 산출물에 이미 정의된 내용을 다른 산출물에 불필요하게 복제하지 않는다.

| 산출물 | SoT 영역 (담아야 하는 것) | 배제 영역 (담지 않는 것) |
|---|---|---|
| **1. PRD (Full PRD)** | • 비즈니스 문제 정의, 가치, 페르소나 (High-level Why & What)<br>• 3~5개 Epic 범위(`EP-`) 및 완료 후 상태<br>• 제품·운영 핵심 요구사항 (3~7개, 상위 계약)<br>• 의사결정 로그(`D-`), 미결 과제(`OQ-`), 핵심 KPI(`K-`) | • 개별 UI 필드·컴포넌트·버튼 배치<br>• 화면 진입 조건, 뷰포트/레이아웃/스타일 세부<br>• 계산 수식(`F-`) 및 파라미터<br>• 개발 작업 단위 및 세부 인수 조건(`AC`) |
| **2. 프로토타입 + 디스크립션** | • 화면 구성 및 컴포넌트 동작 정책 (`[N-N]`)<br>• 화면 진입 조건, 데이터 표시 및 카테고리 목록<br>• 계산 수식 정의 및 파라미터 (`F-`)<br>• 사용자 인터랙션, 에러 상태 UI, 툴팁 | • 상위 비즈니스 배경 및 KPI 정당화<br>• 개발 작업 티켓 분해 및 백로그 관리 |
| **3. 개발 티켓** | • Story 및 Task 작업 단위 분해<br>• 테스트 가능한 구체적 인수 조건 (`AC`)<br>• API 호출 규격, 서버 에러 핸들링 상세<br>• PRD 앵커(`EP-`, `D-`) 및 디스크립션 앵커(`F-`) 참조 | • 비즈니스 배경 전문 재작성 (앵커 참조로 대체)<br>• 화면 컴포넌트 정책 재정의 (디스크립션 참조로 대체) |

## PRD와 티켓·프로토타입의 경계

Full PRD의 기능 요구사항은 Epic 단위로만 작성한다. 아래 Story·Task 위계는 후속 티켓 생성 단계에서 적용하며 PRD 본문에 미리 작성하지 않는다. 화면 단위 컴포넌트 정책과 수식은 디스크립션에서 정의한다. Epic 분리·이름·작성 수준은 `../../prd-builder-discovery/references/full-prd-epic-guidelines.md`를 따른다.

```
Epic (제품 영역 또는 큰 사용자 가치 묶음)
├─ Story (사용자 관점에서 가치를 느낄 수 있는 기능 단위 — Vertical Slice of User Value)
└─ Task (에픽 직속 인프라·기술 구축 작업 — 사용자 가치와 직접 무관)
```

| 구분 | 정의 | 예시 |
|---|---|---|
| **Story** | 사용자 관점 가치 단위. End-to-end 동작 가능. INVEST 원칙 적용 | "매니저가 상황 목록을 확인하고 수락/거절할 수 있다" |
| **Task** | 에픽 달성에 필요하지만 사용자에게 직접 가치를 주지 않는 인프라·기술 작업 | "Vector DB 환경 구축 및 프로젝트 간 격리 구성" |

> Story·Task·Sub-task와 세부 인수 조건은 티켓 생성 단계에서 정의하므로 PRD에 포함하지 않는다. 화면 필드·컴포넌트 동작·수식은 디스크립션에서 정의한다.

Epic 규모·분리 기준은 `../../prd-builder-discovery/references/full-prd-epic-guidelines.md` §1을 따른다.

## 시스템 프롬프트 (Full PRD 생성 시 적용)

```
<role>
당신은 실리콘밸리 탑티어 B2B SaaS 기업의 수석 PM이자 시스템 아키텍처에 대한 깊은 이해를
보유한 테크니컬 PM입니다. 선행 단계에서 누적된 PRD 작성 데이터를 기반으로,
엔지니어·QA·디자이너가 제품 범위와 완료 상태를 같은 뜻으로 이해하고, 후속 티켓을 구체화할 수 있는 'Full PRD'를 작성합니다.
</role>

<core_guidelines>
1. 할루시네이션 절대 금지: 선행 산출물과 페르소나 리뷰 로그에 명시된 내용 또는 직접 추론
   가능한 내용만 사용한다. 비즈니스 로직·제약 수치를 임의로 창작하지 않는다.

2. 결측치는 전문가 수준 역질문: 제품 범위·운영 정책·완료 판단에 필요하지만 원본에 누락된
   부분은 `[추가 확인 필요: 구체적 제품·운영 질문]` 형태로 표시한다. 구현 방법은 묻지 않는다.

3. 개조식 + 마크다운 표 강제: 산문형 텍스트 배제. 불릿 안의 완결문은 허용하며 핵심 요구사항 소제목은 Epic 작성 기준 §4를 따른다.

4. 단일 SoT 및 산출물 경계 준수: PRD는 High-level Why & What과 Epic 핵심 요구사항(3~7개, 상위 제품·운영 계약)만 작성한다. 화면 컴포넌트·배치·스타일·진입 조건·수식은 프로토타입/디스크립션으로, Story·Task·세부 인수 조건은 티켓 단계로 위임한다. PRD 본문에 세부 UI 제약을 나열하지 않는다.

5. B2B SaaS 필수 요소 강제 채움:
   - 비기능 요구사항: 성능·보안·관측성
   - 시스템 의존성: 연결 지점·선행 조건
   - 주요 엣지 케이스 및 데이터·관측 요구

6. Decision Log 배치: 본문 제목을 작성하지 않고 단일 메타 콜아웃 바로 아래 토글에 거부된 대안과 사유를 표로 정리한다. 별도 번호 섹션을 만들지 않는다.

7. KPI & 성공 지표 섹션 포함: 검증할 사용자 성과 KPI만 작성한다. 배포 확대 중단 기준·보호 지표·Kill Switch·Guardrail은 작성하지 않는다.

8. 페르소나 수 고정: §2에는 이번 문제를 직접 수행하는 페르소나를 정확히 2명만 작성한다. 이해관계자·권한 역할·내부 운영자는 별도 페르소나로 추가하지 않는다.

9. 작성 가드레일: `shared/references/writing-guardrails.md`의 화살표 금지·변수명 금지·디자인
   심미성 배제 규칙과 §9 한국어 통사적 제약을 준수한다.

10. 점진적 협업 작성 (`collaborative-writing` 기반): PRD를 한 번에 전체 일괄 생성하지 않는다.
    전체 구조와 Epic 목록 합의 → Epic/섹션별 단위 작성 → 기획자 피드백 반영 및 확정("고정하고 다음으로")의
    점진적 인터랙션 방식으로 완성한다.
</core_guidelines>

<linguistic_constraints>
아래 7가지 한국어 통사 규칙을 텍스트 생성 과정에 최우선으로 적용한다.

  교정: 행위 주체를 능동태로 복원. "시스템이 오류를 감지했다"

L-2. 번역투 전치사 배제
  금지: ~에 있어서 / ~를 통해 / ~에 대한 / ~함에 따라
  교정: 조사 제거 후 명사 직접 수식. "도입 핵심은" / "시스템 연동 후"

L-3. 명사화·보조용언 금지
  금지: 역할을 수행한다 / 지원을 한다 / 처리를 진행하는 상황
  교정: 단일 동사. "지원한다" / "처리한다"

L-4. 복수 접미사 중복 금지
  금지: 많은 개발자들이 / 여러 오류들을
  교정: 수량 형용사 있으면 '-들' 불필요. "많은 개발자가" / "여러 오류를"

L-5. 문두 접속사 배제
  금지: 그래서 ~ / 그렇기 때문에 ~ / 따라서 ~ (문장 첫 단어로 사용)
  교정: 인과를 문장 구조로 내장. "트래픽 급증으로 서버 증설이 필요하다"

L-6. 관형격 조사 연쇄 금지
  금지: 사용자의 데이터베이스의 백업본의 손상
  교정: 명사구 직접 결합. "사용자 데이터베이스 백업본 손상"

L-7. 모호한 수식어 금지
  금지: 매우 / 직관적인 / 훌륭한 / 다양한 / 효율적인 (정량화 불가 형용사)
  교정: 정량 표현 또는 삭제. "3단계로 압축" / "응답 시간 500ms 이내"
```

## 독립적으로 읽히는 문서

- 앞선 대화나 다른 문서를 읽지 않아도 현재 제품의 목적·범위·정책을 이해할 수 있게 쓴다.
- 현재 요구사항을 이해하거나 판단하는 데 필요한 배경·제약은 본문에 남긴다. 작성 과정, 판본 간 비교, 현재 범위와 무관한 과거 맥락은 본문에 섞지 않고 필요한 경우 변경 기록이나 근거 문서에 둔다.
- 내부 코드만으로 역할·요구사항·미결 내용을 대신하지 않는다. 의미를 풀어 쓰고 추적용 식별자는 필요한 경우 병기한다. 식별자 자체나 연결 관계를 임의로 삭제하지 않는다.

## KPI 선정 예시

아래는 지표를 정의하는 방법의 예시이며, 다른 프로젝트의 KPI로 복사하지 않는다. 프로젝트의 사용자 성과와 확보 가능한 자료를 기준으로 선정한다.

| 기능·추상적 가치 표현 | 측정 가능한 지표 예시 | 정의·측정 방법 예시 |
|---|---|---|
| 필요한 시점의 안내 | 알림 확인 후 검토 완료율 | 평가 기간에 알림을 확인한 대상 건 중 검토를 완료한 건의 비율. 알림 확인·검토 완료 기록을 연결하고 관찰 기간·중복·제외 기준을 사전에 정한다. 이 지표만으로 알림 시점의 적절성까지 입증하지 않는다. |
| 이해하기 쉬운 설명 | 설명 내용 이해 정확도 | 설명을 읽은 참여자의 확인 질문 응답 중 사전 정답에 맞는 응답의 비율. 질문·정답과 채점 기준을 테스트 전에 정한다. |
| 편리한 과업 수행 | 핵심 과업 독립 완료율 | 평가 과업 중 시험 진행자의 조작 도움 없이 완료한 과업의 비율. 과업별 완료 조건·도움의 범위를 정하고 수행을 관찰한다. |

- 선행 산출물 수정 후 통합 산출 단계 재실행 시 Full PRD 본문을 **덮어쓰기**

- 발행 전 `editorial-reviewer`로 문장·용어를 검토하고 `notion-organizer`로 블록 구조를 정리한다. `prd-flow-copilot`을 사용해도 두 단계를 생략하지 않는다.
- Notion 적재용 불릿과 체크리스트의 각 항목은 한 물리적 줄에 완결한다. 문장만 다음 줄로 넘겨 일반 문단이 생기게 하지 않는다.

## 작성 후 검증 체크리스트

- [ ] 문제 정의가 개조식 4열 표이며 근거와 검증할 가설이 분리되었는가? 근거의 출처·한계·미확인 상태가 드러나는가
- [ ] 현재 제품의 목적·범위·정책이 독립적으로 이해되고, 내부 코드만으로 의미를 대신하지 않았는가
- [ ] Non-Goals가 명시되었는가 (최소 3개)
- [ ] 본문 H1 제목이 없고 상단 메타가 상태·담당·최종 수정 한 줄로만 작성되었는가
- [ ] Decision Log가 상단 메타 바로 아래 토글에 있고 "거부된 대안과 사유"가 명시되었는가
- [ ] §2 페르소나가 정확히 2명인가
- [ ] 핵심 KPI가 기본 3개이며 `KPI / 정의 / 측정 방법`으로 작성되었는가? 기능명·추상적 가치가 아니라 측정 가능한 성과이고, 미확정 지표나 자료가 표시되었는가
- [ ] 배포 확대 중단 기준·보호 지표·Kill Switch·Guardrail이 포함되지 않았는가
- [ ] 시스템 의존성 연결 지점 테이블이 작성되었는가
- [ ] 기능 요구사항이 `EP-` 단위이며 Story·Task·세부 인수 조건이 포함되지 않았는가
- [ ] Epic 이름이 구현 구성요소가 아니라 완료 후 확보되는 결과·역량을 나타내는가
- [ ] 각 Epic의 목적·완료 후 상태가 2열 2행 표이고 완료 판단이 체크리스트인가
- [ ] 각 Epic에 포함 범위·핵심 요구사항·범위 밖이 있는가
- [ ] 각 Epic의 핵심 요구사항이 Epic 작성 기준 §4의 의미 중심 소제목 검토를 충족하며, 세부 항목과 역할이 구분되는가
- [ ] 성능 요구사항에 P95 기준 수치가 포함되었는가
- [ ] 운영 검증 기록이 KPI 또는 Epic 완료 판단에 연결되었는가
- [ ] 모바일 PRD라면 §9가 채워졌는가 (비-모바일이라면 §9가 생략되었는가)
- [ ] Open Questions가 하단 토글 안의 테이블 형식(#, 질문, 담당, 상태)으로 작성되었는가
- [ ] 불릿 문장이 물리적 줄바꿈으로 분리돼 일반 문단이 되지 않았는가
- [ ] 화살표(→)·변수명·디자인 심미성 표현이 사용되지 않았는가

체크리스트 1개라도 미충족이면 사용자에게 알리고 수정한다.
