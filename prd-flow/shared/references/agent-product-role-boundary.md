# 기획자와 에이전트 개발자 역할 경계

여러 에이전트가 협력하는 제품을 설계할 때 기획 요구와 기술 구현을 혼동하지 않기 위한 공통 정책이다.

## 적용 목적

에이전트의 추론 흐름·조회 순서·판단 경계를 논의하다 보면 기획자가 구현 방법을 지시하거나, 개발자가 업무 의미를 임의로 바꾸는 문제가 생길 수 있다. 이 문서는 두 역할이 각각 무엇을 결정하고 어디서 공동 검토해야 하는지 정한다.

## 기본 원칙

1. **기획자는 업무 계약을 책임진다.**
   - 에이전트가 왜 필요한지
   - 무엇을 판단해야 하는지
   - 어떤 입력과 근거가 필요한지
   - 앞선 판단 결과에 따라 어떤 추가 정보를 확인해야 하는지
   - 어떤 조건에서 종료·추가 판단·사람 확인으로 넘어가는지
   - 사용자가 받아야 할 결과와 성공·실패 조건이 무엇인지

2. **에이전트 개발자는 기술 계약과 구현을 책임진다.**
   - 업무 계약을 어떤 모델·도구·저장소·호출 구조로 구현할지
   - 데이터 구조와 API
   - 상태 저장·재시도·중복 방지
   - 모델 호출·검색·도구 실행 방식
   - 성능·장애·관측·배포 방식

3. **도메인·운영 책임자는 안전과 현장 판단 기준을 승인한다.**
   - 안전 기준값
   - 법정 기준
   - 설비 운전 범위
   - 자동 정지·자동 제어 권한
   - 오판 시 허용 가능한 대응 범위

## 경계 판정 규칙

- 코드가 없어도 설명할 수 있어야 하는 업무 행동은 기획 책임이다.
- 업무 의미를 바꾸지 않고 교체할 수 있는 구현 방식은 개발 책임이다.
- 안전·법규·현장 운전의 옳고 그름은 도메인 책임자가 승인한다.

## 단계적 판단이 필요한 경우

기획자는 특정 프레임워크나 구현 패턴을 강제하지 않는다. 대신 업무 흐름상 앞선 판단이 뒤의 입력·조회·행동을 바꾸는지를 명시한다.

예:

- 이상 원인 후보를 먼저 판단한다.
- 원인 후보에 따라 추가로 확인해야 할 센서·정비 이력·문서가 달라진다.
- 추가 확인 결과에 따라 새 이상 상황을 만들지 기존 상황에 합칠지 판단한다.
- 최종 상황과 원인에 맞는 대응 절차를 조회해 가이드를 만든다.

위와 같이 **앞선 판단 결과가 다음 단계의 필요한 맥락을 바꾸는 것**은 기획 요구다. 이를 반복 호출, 상태 그래프, 단일 실행 안의 내부 단계 등 어떤 기술 구조로 구현할지는 개발 책임이다.

개발자가 단순화를 제안할 수는 있지만 다음 중 하나가 발생하면 업무 계약 변경으로 본다.

- 필요한 중간 판단이 사라진다.
- 앞선 판단 결과에 따른 조회 분기가 사라진다.
- 이전 단계에서 생성된 근거를 다음 단계가 사용할 수 없다.
- 새 상황 생성과 기존 상황 병합처럼 서로 다른 업무 결과를 구분할 수 없다.
- 최종 출력이 요구한 판단 근거를 재현할 수 없다.

이 경우 기획자와 개발자는 구현 전에 업무 계약을 다시 합의한다.

## 의견 충돌 시 처리

1. 기획자는 기술 구조가 아니라 **깨지는 사용자·업무 시나리오**를 제시한다.
2. 개발자는 구현 제약과 대안을 제시하고, 각 대안이 업무 계약을 충족하는지 설명한다.
3. 기획자는 업무 시나리오와 수용 기준으로 결과를 검증한다.
4. 기술 구현 방식은 개발 책임자가 최종 결정한다. 단, 구현 선택으로 업무 의미나 수용 기준이 바뀌면 기획 책임자의 재승인이 필요하다.
5. 안전 기준과 자동 실행 권한이 관련되면 도메인·운영 책임자 승인을 받는다.

## 에이전트 PRD 필수 항목

에이전트 기능이 포함된 PRD에는 최소한 아래 내용을 기록한다.

- 에이전트가 답해야 할 업무 질문
- 입력 정보와 출처
- 추가 확인이 필요한 조건과 확인할 정보의 종류
- 판단 단계 사이에 반드시 전달돼야 할 업무 맥락
- 종료·추가 분석·다른 에이전트 전달·사람 확인 조건
- 출력 결과와 판단 근거
- 자동 실행·승인 후 실행·권고만 가능한 조치 구분
- 정상·누락·충돌·실패 시나리오의 수용 기준

## 완료 기준

다음 조건을 모두 만족해야 역할 경계가 정리된 것으로 본다.

- 개발자는 새로운 업무 규칙을 추정하지 않고 구현할 수 있다.
- 기획자는 코드나 프롬프트 내부를 읽지 않고도 요구사항 충족 여부를 검증할 수 있다.
- 구현 방식을 바꿔도 에이전트가 답해야 할 업무 질문과 판단 결과가 유지된다.
- 앞선 판단에서 만들어진 필수 맥락이 뒤의 판단에 전달되는지 시험할 수 있다.
- 도메인 책임자는 판단 기준과 실행 권한의 근거를 추적할 수 있다.

## PRD 검토 체크

에이전트 PRD를 확정하기 전에 다음 질문을 확인한다.

- 이 요구는 업무 행동인가, 구현 방식인가?
- 앞선 판단에 따라 다음에 필요한 정보가 달라지는가?
- 구현 단순화로 중간 판단이나 필수 맥락이 사라지지 않는가?
- 기획자가 기술 방식을 불필요하게 고정하고 있지 않은가?
- 개발자가 업무 의미를 임의로 단순화하고 있지 않은가?
- 의견 충돌을 코드 수준 논쟁이 아니라 업무 시나리오와 수용 기준으로 판정할 수 있는가?
