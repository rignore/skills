# 티켓 QA — 인수 조건 검증과 기록

티켓에 적힌 인수 조건(AC)이 완료 처리 전에 빠짐없이 검증되고, 그 결과가 티켓에 남아 티켓만 열어도 무엇을 확인했는지 알 수 있게 한다.

이 스킬은 검증 절차만 정한다. 티켓을 어느 도구에서 읽고 결과를 어디에 남기는지는 환경마다 다르므로 **환경 팩**이 정한다.

## 환경 팩 (작업 전 반드시 확인)

환경 팩은 이 스킬의 절차를 특정 조직의 도구에 연결하는 별도 스킬이다. 이름이 `ticket-qa-pack-`으로 시작한다.

1. 사용 가능한 스킬 목록에서 `ticket-qa-pack-`으로 시작하는 스킬을 찾는다.
2. 하나면 그 스킬의 `SKILL.md`를 먼저 읽고, 아래 「팩이 채우는 자리」를 그 내용으로 채운다.
3. 여럿이면 어느 환경의 작업인지 사용자에게 묻는다. 저장소 이름이나 대화 내용으로 추측해 고르지 않는다. 다른 조직의 도구에 기록을 남기면 되돌리기 어렵다.
4. 없으면 「팩이 없을 때」의 파일 방식으로 진행한다고 사용자에게 알리고 진행한다.

### 팩이 채우는 자리

| 자리 | 이 스킬이 필요로 하는 것 | 팩이 없을 때 |
|---|---|---|
| 티켓 찾기 | 담당자·상태로 내 티켓을 찾는 방법 | 사용자가 티켓 본문이나 파일 경로를 준다 |
| 본문 읽기 | 티켓의 인수 조건을 읽는 방법 | 사용자가 준 본문을 쓴다 |
| 검증 방법 표기 | 인수 조건에 검증 방법을 적는 표기 | 아래 「검증 방법 4분류」의 기본 표기 |
| 결과 기록 | 인수 조건별 결과를 티켓에 남기는 방법과 형식 | 저장소의 `qa/verification-log.md`에 덧붙인다 |
| 검증 장부 | 상위 묶음(Epic) 아래 모든 인수 조건과 기록을 대조하는 방법 | `qa/verification-log.md`와 티켓 본문을 스크립트로 대조한다 |
| 내 티켓 가리기 | 상위 묶음(Epic) 아래에서 담당자가 본인인 티켓만 골라내는 방법 | 사용자가 자기 티켓 목록을 준다 |
| 열린 결함 확인 | 인수 조건마다 이미 열려 있는 결함 티켓이 있는지 아는 방법 | `qa/defects/`의 파일 이름과 본문으로 확인한다 |
| 화면 실행 | 화면 확인 항목을 브라우저 자동화로 실행하고 판정하는 방법, 접속 주소·로그인 상태·설정 파일을 두는 자리 | `spec-driven-qa` 스킬을 직접 쓴다. 로그인 상태 파일은 저장소 밖에 둔다 |
| 결함 티켓 등록 | 결함 티켓의 유형, 붙일 위치, 올리는 절차 | `qa/defects/` 아래 md 파일로 남긴다 |
| 상태 변경 | 티켓 상태를 바꾸는 방법 | 하지 않는다 |
| 의미 판정자 | 실행 맥락을 받지 않고 증거만 보고 판정하는 별도 판정자 | 새 맥락의 서브에이전트에 증거 묶음만 넘긴다 |
| 기획 확인 항목 기록 | 검증 결과와 함께 기획 확인 항목을 남기는 방법 | 저장소의 `qa/planner-checks.md`에 덧붙인다 |
| 기획 확인 기록 | 기획자의 항목별 확정·변경 요청을 남기고, 현재 항목과 상태를 읽는 방법 | `qa/planner-checks.md`의 항목 줄 아래에 결정 줄을 덧붙인다 |

팩이 기획 확인 두 자리를 정하지 않으면 그 환경에는 기획 확인 항목을 남길 곳이 없다. 이때는 2가지를 지킨다.

- 개발자 모드에서는 후보를 확정받지 않고 6단계 보고에 참고로만 보인다. 기록하지 않았다고 알린다.
- 기획자 확인 모드는 진행하지 않고, 이 환경에는 기획 확인 기록 자리가 없다고 알린다.

다른 자리(코멘트, 메모, 파일)에 대신 적지 않는다.

팩이 정한 내용이 이 문서의 기본값과 다르면 팩을 따른다. 다만 「하지 않는 것」의 원칙은 팩으로 완화하지 않는다.

## 3층 구조와 이 스킬의 범위

QA는 세 층으로 나뉜다. 층마다 하는 주체가 다르다.

| 층 | 무엇을 하나 | 누가 | 수단 |
|---|---|---|---|
| 1. 티켓 검증 | 담당 티켓의 인수 조건을 검증하고 기록한다 | 담당 개발자 | 이 스킬의 「개발자 모드」 |
| 2. 빠짐 점검 | 상위 묶음 아래 모든 인수 조건에 기록이 있는지 센다 | 기획자·PM | 이 스킬의 「PM 모드」와 검증 장부 |
| 3. 독립 판정 | 구현 맥락을 모르는 판정자가 증거만 보고 판정한다 | 기획자·PM | `spec-driven-qa` 스킬 (이 스킬이 넘긴다) |

**한 세션이 Epic 전체를 기억으로 세지 않는다.** 티켓이 많으면 대화가 길어져 뒤쪽 인수 조건이 얕게 처리되거나 빠진다. 빠짐없이 했는지는 항상 검증 장부의 결과로 판단한다.

## 검증 방법 4분류

인수 조건마다 검증 방법이 하나씩 붙는다. 기본 표기는 인수 조건 제목 끝의 `[검증: …]` 태그다.

| 태그 | 뜻 | 누가 검증하나 |
|---|---|---|
| 🧪 단위 테스트 | 계산식·판정·경계값을 코드 단위로 확인한다 | 담당 개발자 |
| 🔗 통합 테스트 | DB·배치·외부 연동·정합성을 실제 구성으로 확인한다 | 담당 개발자 |
| 🖥 화면 확인 | 화면을 조작해 확인한다 | 담당 개발자가 브라우저 자동화로 검증한다. 릴리스 필수 항목은 독립 판정(3층)도 받는다 |
| 🔌 수동·물리 | 센서·장비·현장 조작이 필요하다 | 사람 |

## 기획 확인 항목

인수 조건은 기획자가 정한 업무 결과만 적는다. 그 결과를 사용자가 화면에서 어떻게 보고 입력하는지는 디자이너·FE가 정하고, 기획자는 QA 때 확인한다. 기획 확인 항목은 이번 구현에서 디자이너·FE가 정한 화면 규칙 가운데 기획자가 확인할 것을 한 문장씩 적은 목록이다.

- **예:** 「신호 없음 작업자의 위치는 「마지막 확인 위치」 문구와 함께 장소명·구역명으로 표시한다」
- **넣는 것:** 사용자에게 보이는 문구, 상태별 화면 표시(빈 값·오류·로딩·권한 없음), 표시 형식(단위·정렬·자릿수), 입력 제약(글자 수·필수 여부)을 이번 구현에서 정한 경우다.
- **빼는 것:** 인수 조건에 이미 적힌 것, 빈 값·연결 끊김처럼 공통 정책을 그대로 따른 것, 사용자에게 보이지 않는 구현 방식(갱신 주기, 재시도, 데이터 묶는 방법)이다.
- **형식:** 한 항목에 규칙 하나를 한 문장으로 쓴다. 200자를 넘지 않고, 한 티켓에 10개까지다. 관련 인수 조건이 있으면 그 번호를 붙인다.
- **판정과의 관계:** 기획 확인 항목은 통과·실패를 매기지 않는다. 인수 조건의 검증 결과와 따로 남고, 검증 완료 판정을 막지 않는다.

## 모드 판별

| 상황 | 모드 |
|---|---|
| 개발자가 자기 티켓을 검증하려 한다 ("내 티켓 QA 돌려줘", 특정 티켓 링크) | 개발자 모드 |
| 개발자가 Epic 링크를 주며 검증을 돌리려 한다 ("이 Epic QA 돌려줘") | 개발자 모드의 「Epic 단위로 한 번에」. 본인 티켓만 돌린다 |
| Epic·PRD·스프린트 단위로 검증 상태를 보려 한다 ("검증 장부", "빠진 거 없나") | PM 모드. 검증을 실행하지 않고 기록만 읽는다 |
| 기획자가 화면 규칙을 확인하려 한다 ("기획 확인 돌려줘", "기획 확인 항목 보여줘") | 기획자 확인 모드 |
| 구분되지 않는다 | 검증을 돌리려는 것인지 기록을 보려는 것인지 한 번 묻는다 |

## 개발자 모드 — 내 티켓의 인수 조건 검증

개발자가 직접 하는 일은 3단계에서 케이스 목록을 보고 고치는 것과, 세션이 할 수 없는 확인에 답하는 것뿐이다.

### 1단계. 대상 티켓 찾기

- 사용자가 링크나 제목을 주면 그 티켓을 쓴다.
- 주지 않으면 팩의 「티켓 찾기」로 담당자가 본인이고 진행 중인 티켓을 찾아 목록을 보이고 고르게 한다. 임의로 고르지 않는다.

### 2단계. 인수 조건 읽기

본문을 읽고 인수 조건을 검증 방법별로 나눈다.

| 검증 방법 | 이 모드에서 하는 일 |
|---|---|
| 단위 테스트 | 검증한다 |
| 통합 테스트 | 검증한다 |
| 화면 확인 | 검증한다. 브라우저 자동화로 실행하고 판정 스크립트가 판정한다 (아래 「화면 확인 항목」) |
| 수동·물리 | 검증하지 않는다. 사람이 확인해야 한다고 알린다 |
| 표기 없음 | 방법을 추정해 개발자에게 확인받는다 |

본인 코드가 건드리지 않은 인수 조건은 검증 대상에서 뺀다. 담당자가 여럿인 티켓은 각자 자기 몫만 기록한다.

**담당자가 본인이 아닌 티켓은 검증하지 않는다.** 사용자가 링크로 준 티켓이라도 담당자가 다른 사람이면 멈추고 그 사실을 알린다. 검증 기록은 작업한 사람이 자기 변경을 확인했다는 기록이라, 다른 사람이 대신 남기면 누가 무엇을 확인했는지 알 수 없게 된다.

### 3단계. 케이스 목록 확인 (사용자 확인 필수)

인수 조건은 요구사항 문장이지 테스트가 아니다. 인수 조건마다 "무엇을 어떤 입력으로 돌려 볼지"로 바꿔 목록으로 보여 준다.

- 정상 경로 1건 이상과, 인수 조건이 말하는 예외·경계 케이스를 모두 넣는다.
- 인수 조건에 예외·경계가 적혀 있지 않으면 빠진 것으로 보고 개발자에게 묻는다.
- 개발자가 케이스를 더하거나 뺀 뒤 확정한다. 확정 전에는 실행하지 않는다.

케이스 목록과 함께 **기획 확인 항목 후보**를 보여 준다(위 「기획 확인 항목」).

- **기존 항목 먼저:** 이 티켓에 이미 기획 확인 항목이 있으면 팩의 「기획 확인 기록」으로 현재 항목과 상태를 먼저 읽는다. 확정·미확인 항목은 문장을 글자 그대로 가져온다. 한 글자라도 바꾸면 기획자의 확정이 미확인으로 돌아가기 때문이다. 변경 요청 항목은 기획자의 요청 문장을 보이고, 고친 문장으로 바꾼다.
- **새 후보:** 이번 티켓의 코드 변경분에서 새 후보만 더한다. 변경분은 기준 브랜치와 현재 HEAD의 차이다. 기준 브랜치를 모르면 개발자에게 묻는다. 새로 추가하거나 바꾼 화면 문구, 빈 값·오류·로딩 분기, 표시 형식을 본다. 개발자가 와이어프레임이나 디자인 시안을 주면 함께 본다.
- **담당자가 여럿인 티켓:** 기획 확인 항목은 티켓에 목록 하나다. 다른 담당자가 남긴 항목도 글자 그대로 목록에 넣는다. 빼면 그 항목과 기획자의 결정이 현재 목록에서 사라진다.
- 후보마다 「인수 조건에 없음」을 확인한다. 인수 조건 문장에 이미 있는 규칙은 후보에서 뺀다.
- 개발자가 후보를 고치거나 더하거나 뺀 뒤 확정한다. 화면 변경이 없는 티켓은 「기획 확인 항목 없음」으로 확정한다.
- 세션이 코드에서 읽은 문구를 기획 의도로 단정하지 않는다. 확정은 개발자가 한다.

### 4단계. 실행

**통합 테스트는 로컬 서버를 실제로 띄워 확인한다.** 권한 검사 순서, DB 저장, 설정값 같은 문제는 단위 테스트로 드러나지 않는다.

1. 저장소의 실행 방법을 먼저 찾는다. README, 패키지 스크립트, 기존 테스트 설정 순으로 본다. 찾지 못하면 개발자에게 묻는다. 추측한 명령으로 서버를 띄우지 않는다.
2. 서버와 테스트용 DB는 로컬에서 띄운다. 여러 사람이 함께 쓰는 테스트 서버나 운영 서버를 대상으로 하지 않는다. 공유 환경에서는 다른 사람의 데이터 때문에 결과가 틀리게 나온다.
3. 필요한 계정·데이터는 테스트가 직접 만든다. 이미 있는 데이터에 기대지 않는다.
4. **확인한 요청은 저장소의 테스트 코드로 남긴다.** 그 자리에서 요청만 보내 눈으로 확인하고 끝내지 않는다. 테스트 파일이 남아야 다른 사람이 다시 확인할 수 있고, 다음 변경 때 다시 검증된다.
5. 해당 테스트가 이미 있으면 그것을 돌리고, 없으면 작성해 돌린다.
6. 실패하면 고치고 다시 돌린다. 이 반복은 티켓에 남기지 않는다.

테스트를 통과시키려고 테스트의 기대값을 인수 조건과 다르게 바꾸지 않는다. 인수 조건이 틀렸다고 판단되면 멈추고 개발자에게 알린다.

화면 확인 항목은 아래 「화면 확인 항목」의 순서로 실행한다. 단위·통합 테스트와 같은 로컬 서버를 쓴다.

### 5단계. 기록

검증을 마친 인수 조건을 팩의 「결과 기록」으로 남긴다. 한 티켓의 여러 인수 조건은 한 번에 묶어 기록한다. 어느 환경이든 기록에는 아래를 담는다.

| 항목 | 내용 |
|---|---|
| 인수 조건 번호와 결과 | 통과 또는 실패 |
| 검증 방법 | 티켓 본문에 적힌 방법과 같아야 한다 |
| 요약 | 무엇을 어떤 경우로 확인했는지 한 문장. 읽는 사람이 기획자·PM이라고 보고 쓴다. 파일 경로·명령·상태 코드 숫자만 나열하지 않는다 |
| 근거 | 테스트 파일 경로·테스트 이름·CI 주소처럼 찾아갈 수 있는 식별자. 다른 사람이 같은 테스트를 다시 돌릴 수 있게 테스트 파일 경로는 빠뜨리지 않는다 |
| 판본 | 검증한 커밋 |

실패도 기록한다. 실패를 숨기고 통과만 남기지 않는다.

3단계에서 확정한 기획 확인 항목은 팩의 「기획 확인 항목 기록」으로 같은 기록에 함께 남긴다. 항목만 따로 기록하지 않는다. 검증 결과의 요약이나 메모에 화면 규칙을 섞어 쓰지 않는다. 메모는 그 인수 조건을 검증하며 관찰한 전제만 적는다.

기획 확인 항목은 티켓에 목록 하나이고, 새로 올린 목록이 현재 목록을 통째로 바꾼다. 그래서 다시 검증할 때는 2가지를 지킨다.

- 목록이 바뀌지 않았으면 팩이 허용하는 경우 항목을 생략해 현재 목록을 그대로 둔다.
- 목록을 바꿀 때는 3단계에서 가져온 기존 항목과 다른 담당자의 항목까지 모두 다시 올린다. 바뀌지 않은 항목은 같은 문장을 그대로 쓴다. 문장이 한 글자라도 바뀌면 기획자가 다시 확인해야 하는 항목이 된다.

### 6단계. 마무리 보고와 다음 행동

기록 뒤 아래를 보고한다.

- 기록한 인수 조건과 결과
- 남긴 기획 확인 항목 수. 「기획자가 QA 때 확인할 항목 3건을 남겼다」처럼 쓴다
- 이번에 기록하지 않은 인수 조건과 그 이유(다른 담당자 몫, 수동 확인 필요, 서버나 로그인 문제로 실행하지 못함)
- 실패가 남았으면 어떤 인수 조건이 왜 실패했는지

상태 변경은 사용자가 요청할 때만 팩의 「상태 변경」으로 한다. 모든 대상 인수 조건이 통과이고 기록하지 않은 인수 조건이 없을 때만 다음 상태로 옮기자고 제안한다.

**고치지 않고 남긴 실패**가 있으면 아래 「결함 티켓 등록」의 목록으로 보이고 올릴지 한 번 묻는다. 그 자리에서 고쳐 다시 통과한 인수 조건은 목록에 넣지 않는다.

### Epic 단위로 한 번에

개발자가 Epic을 주면 그 Epic 아래 **본인이 담당한 티켓만** 차례로 검증한다. 다른 사람이 담당한 티켓은 읽지도 돌리지도 않는다.

1. 팩의 「내 티켓 가리기」로 Epic 아래에서 담당자가 본인인 티켓을 골라낸다. 고른 티켓과, 다른 사람 담당이라 뺀 티켓 수를 먼저 보인다. 본인 티켓이 없으면 멈춘다.
2. 지금 열린 저장소에서 검증할 수 없는 티켓(다른 저장소의 코드)은 대상에서 빼고 그 사실을 알린다. 그 티켓은 해당 저장소에서 따로 돌려야 한다.
3. 2단계와 3단계를 티켓마다 하되, 케이스 목록은 전체를 모아 한 번에 확인받는다.
4. 4단계와 5단계는 티켓마다 따로 한다. 기록도 티켓마다 따로 남긴다. 한 티켓의 실패가 다음 티켓의 검증을 막지 않는다.
5. 모든 티켓이 끝나면 6단계 보고를 티켓별로 묶어 한 번에 하고, 실패는 「결함 티켓 등록」의 목록으로 넘긴다.

티켓 수가 많아 대화가 길어지면 몇 개씩 나눠 진행하고, 어디까지 했는지는 기억이 아니라 팩의 「검증 장부」 결과로 확인한다.

### 화면 확인 항목

화면 확인 인수 조건은 `spec-driven-qa` 스킬을 실행 엔진으로 써서 검증한다. 그 스킬은 사양에서 시나리오를 만들고, 사람이 검토한 실행 대본을 브라우저 자동화(Playwright)로 그대로 재생하고, 기록된 증거만으로 판정한다. 접속 주소·로그인 상태·설정 파일을 어디에 두는지는 팩의 「화면 실행」이 정한다.

순서는 5가지다.

1. **사양 꾸러미.** 티켓의 화면 확인 인수 조건 문장을 그대로 사양 꾸러미로 옮긴다. 문장을 고쳐 쓰지 않고, 기대값을 정할 수 없으면 멈추고 묻는다.
2. **시나리오 = 케이스 목록.** 3단계에서 보인 케이스 목록이 곧 시나리오다. 사용자가 확정한 뒤에만 승인된 시나리오로 삼는다.
3. **대본 고정.** 확정된 시나리오와 설정 파일로 실행 대본을 만든다. 입력·클릭처럼 상태를 바꿀 수 있는 단계는 사용자 확정을 근거로 승인 기록을 만들어 대본에 묶는다.
4. **실행.** 로컬 서버를 띄운 상태에서 대본을 재생한다. 로그인이 필요한 화면은 팩이 정한 저장된 로그인 상태를 쓴다. 세션이 실행 중에 요소를 찾아 바꾸거나 다시 시도하지 않는다.
5. **판정.** 값으로 가릴 수 있는 판정(표시된 문자열, 개수, 주소)은 판정 스크립트가 한다. 의미를 읽어야 하는 판정은 팩의 「의미 판정자」에게 증거 묶음만 넘긴다.

규칙은 4가지다.

- 세션이 브라우저를 직접 조작해 눈으로 보고 통과를 선언하지 않는다. 기록하는 것은 대본 재생 결과를 판정 스크립트가 판정한 것뿐이다.
- "요소가 없다"를 확인할 때는 그 화면에 도착했다는 것(주소나 그 화면에만 있는 요소)을 함께 수집한다. 화면이 열리지 않은 상태에서도 "없다"는 참이 된다.
- 서버가 뜨지 않았거나 로그인이 만료돼 끝까지 가지 못한 실행(판정 `blocked`)과 증거를 못 모은 실행(`insufficient_evidence`)은 실패로 기록하지 않는다. 원인을 고치고 다시 돌린다.
- 기록할 때 검증 방법은 화면 확인이고, 요약 첫머리에 "화면 자동 검증:"을 적어 독립 판정과 구분한다. 릴리스 필수로 표시된 화면 확인 항목은 이 기록과 별개로 독립 판정 대상이다.

## PM 모드 — 상위 묶음 단위 빠짐 점검

### 1단계. 검증 장부 조회

팩의 「검증 장부」로 상위 묶음(Epic) 아래 모든 인수 조건과 최신 검증 기록을 대조한 결과를 얻는다. 결과를 보이고 아래 순서로 해석을 덧붙인다.

| 장부 항목 | 뜻 | 다음 행동 |
|---|---|---|
| 기록 없음 | 그 인수 조건을 검증했다는 기록이 없다 | 담당자에게 개발자 모드 검증을 요청한다. 릴리스 필수 항목은 3단계에서 독립 판정도 받는다 |
| 실패 | 최신 기록이 실패다 | 4단계에서 결함 티켓 등록 목록에 넣는다. 이미 열린 결함 티켓이 있으면 넣지 않는다 |
| 검증 방법 표기가 없어 셀 수 없는 티켓 | 본문에 검증 방법이 붙은 인수 조건이 없다 | 검증할 것이 없는 게 아니다. 티켓 본문에 검증 방법을 붙인다 |
| 읽지 못한 티켓 | 본문이나 기록 조회가 실패했다 | 원인을 확인한다. 통과로 세지 않는다 |
| 열린 결함 티켓 | 아직 닫히지 않은 결함 티켓이 있다 | 결함이 닫히고 원래 인수 조건이 다시 통과했는지 본다 |
| 기획 확인 항목 미확인·변경 요청 | 기획자가 아직 확인하지 않았거나, 변경을 요청했는데 개발자가 아직 반영하지 않았다 | 결함이 아니다. 기획자 확인 모드로 넘긴다 |

### 2단계. 장부가 세지 못하는 것 점검

장부는 "기록이 있는가"만 센다. 아래 3가지는 따로 본다.

1. **티켓에 배정되지 않은 요구**: 티켓이 전부 통과해도 PRD의 요구나 수용 지표가 어느 티켓에도 없으면 빈 곳이 남는다. PRD와 티켓의 대응을 따로 확인한다.
2. **티켓 사이에 걸친 동작**: 각 티켓은 통과하는데 이어 붙인 흐름이 깨질 수 있다. 대표 사용자 흐름 2~3개를 정해 3단계의 독립 판정 시나리오로 넣는다.
3. **기록의 내용**: 통과 기록 가운데 표본을 골라 요약이 인수 조건을 실제로 덮는지 읽는다. 자동 판정과 자기 보고는 1차 거름망이고 최종 확인은 사람이 한다.

### 3단계. 독립 판정으로 넘기기

릴리스 필수 항목과 PM이 직접 확인하려는 화면 확인 항목은 팩의 「화면 실행」으로 돌린다. 절차는 개발자 모드의 「화면 확인 항목」과 같고, 다른 점은 시나리오를 확정하는 사람이 개발자가 아니라 PM이라는 것과 기록을 팩의 「독립 판정 기록」으로 남긴다는 것이다.

- 이 스킬 안에서 화면을 조작해 통과를 선언하지 않는다. 실행한 쪽이 스스로 내린 통과 선언은 증거가 아니다.
- 값으로 가릴 수 있는 판정(개수, 응답 코드, 상태값)은 `spec-driven-qa`의 판정 스크립트가 한다.
- 의미를 읽어야 하는 판정이 나오면 팩의 「의미 판정자」에게 증거 묶음만 넘긴다. 시나리오 작성 대화, 실행 과정, 예상 판정은 넘기지 않는다. 같은 세션이 이어서 판정하지 않는다.

### 4단계. 결함 티켓 등록

장부에서 최신 기록이 실패인 인수 조건과 독립 판정이 실패로 판정한 인수 조건을 모아 「결함 티켓 등록」의 목록으로 보이고 올릴지 묻는다. PM 모드는 다른 사람의 티켓을 다시 검증하지 않는다. 남아 있는 기록만 읽는다.

사양끼리 충돌한다는 판정, 증거 부족, 환경 문제로 실행하지 못한 것은 결함이 아니다. 결함 티켓으로 만들지 않고 기획자·PM이 정할 일로 따로 보고한다.

### 5단계. 보고

상위 묶음 단위 보고는 장부의 숫자를 일상어로 풀어 쓴다. 예: "인수 조건 40개 중 31개는 통과 기록이 있고, 2개는 실패 상태이며, 7개는 아직 아무도 검증하지 않았다."

## 기획자 확인 모드 — 기획 확인 항목 확인

기획자가 개발자가 남긴 기획 확인 항목을 하나씩 확정하거나 변경을 요청한다. 세션은 목록을 모아 보이고 기획자의 결정을 그대로 기록한다. 세션이 화면 규칙이 맞는지 판단하거나 기획자 대신 결정하지 않는다.

### 1단계. 확인할 항목 모으기

- 기획자가 Epic을 주면 팩의 「기획 확인 기록」으로 그 Epic 아래 티켓의 기획 확인 항목과 상태를 읽는다. 티켓 하나를 주면 그 티켓만 고른다. 팩이 티켓 하나만 읽는 방법을 정하지 않았으면 팩의 지시를 따른다.
- 미확인 항목은 결정 목록으로 모은다.
- 변경 요청 항목은 개발자가 아직 고쳐 올리지 않은 것이다. 기획자에게 다시 묻지 않고 「개발자 반영 대기」 목록으로 따로 보인다.
- 확정된 항목은 수만 알린다.

### 2단계. 목록으로 보이고 결정받기

```markdown
## 기획 확인 항목 {N}건 — 확정할까요?

| 번호 | 티켓 | 항목 | 관련 인수 조건 | 문장 |
|---|---|---|---|---|
| 1 | {티켓 제목} | 2번 | AC 2 | {항목 문장 그대로} |

개발자 반영 대기 {N}건: {티켓 · 항목 번호 · 변경 요청 내용}
```

- 기획자는 번호별로 확정 또는 변경 요청을 고른다. 「전부 확정」이라고 하면 목록 전체를 확정한다.
- 변경 요청에는 무엇을 바꿀지 한 문장을 받는다. 그 문장 없이 변경 요청을 기록하지 않는다.
- 기획자가 정하지 않은 항목은 기록하지 않고 미확인으로 둔다.

### 3단계. 기록

팩의 「기획 확인 기록」으로 티켓마다 한 번에 남긴다. 항목 번호와 함께 1단계에서 읽은 문장을 글자 그대로 넘긴다.

기록이 거부되면 그 티켓의 결정은 하나도 기록되지 않는다. 이미 기록된 다른 티켓은 다시 묻지 않는다. 거부 이유에 따라 2가지로 처리한다.

- **문장이 바뀌어 거부된 경우:** 기획자가 목록을 본 뒤 개발자가 다시 검증해 그 번호의 문장이 바뀐 것이다. 그 티켓만 다시 읽는다. 문장이 그대로인 항목의 결정은 다시 묻지 않고 함께 보내고, 바뀐 항목만 기획자에게 다시 보인다.
- **그 밖의 이유로 거부된 경우:** 오류 문구를 그대로 보이고 멈춘다. 형식을 추측해 고쳐 다시 보내지 않는다.

### 4단계. 보고

티켓별로 확정 수와 변경 요청 수를 보고한다. 변경 요청은 담당 개발자가 고친 뒤 다시 검증하며 새 문장으로 올리면 다시 미확인이 된다고 알린다. 변경 요청은 결함 티켓으로 올리지 않는다.

## 결함 티켓 등록

결함 티켓은 통과하지 못한 인수 조건을 고치기 위한 티켓이다. 유형, 붙일 위치, 올리는 절차는 팩의 「결함 티켓 등록」을 따른다.

### 1. 대상 고르기

검증이 끝난 뒤 한 번에 한다. 실패가 나올 때마다 묻지 않는다.

| 인수 조건의 상태 | 처리 |
|---|---|
| 최신 판정이 실패다 | 등록 대상 |
| 실패였지만 그 자리에서 고쳐 다시 통과했다 | 대상 아님. 통과 기록으로 충분하다 |
| 실행하지 못했다(서버가 뜨지 않음, 환경 문제) | 대상 아님. 「다시 확인 필요」로 따로 보인다 |
| 증거가 부족하거나 사양끼리 충돌한다 | 대상 아님. 기획자·PM이 정할 일로 따로 보인다 |
| 같은 인수 조건에 이미 열린 결함 티켓이 있다 | 새로 만들지 않는다. 「이미 등록됨」으로 보인다 |

이미 열린 결함 티켓이 있는지는 팩의 「열린 결함 확인」으로 안다. 확인할 방법이 없으면 그 사실을 목록 위에 적고, 중복일 수 있다고 알린 뒤 묻는다. 확인하지 않은 채 없다고 단정하지 않는다.

### 2. 목록으로 보이고 한 번 승인받기

본문 초안은 보이지 않는다. 검증하면서 이미 확인한 내용이기 때문이다. 대신 목록 한 줄만 읽고도 무엇이 올라가는지 알 수 있어야 한다.

```markdown
## 실패한 인수 조건 {N}건 — QA 티켓으로 올릴까요?

| 번호 | 원래 티켓 | 인수 조건 | 왜 실패했나 | 올릴 QA 티켓 제목 |
|---|---|---|---|---|
| 1 | {티켓 제목} | AC 2 | {기대한 동작과 실제 관찰한 동작을 한 문장으로} | [결함] {관찰한 현상} |

이미 등록됨 {N}건: {원래 티켓 · AC 번호 · 열린 결함 티켓 제목}
다시 확인 필요 {N}건: {원래 티켓 · AC 번호 · 실행하지 못한 이유}
```

- 승인은 목록 전체에 한 번 받는다. 사용자가 번호로 뺄 것을 지정하면 그것만 빼고 올린다.
- 승인받기 전에는 올리지 않는다. 결함 티켓은 누군가에게 배정되는 일이고, 자동 판정의 실패는 틀릴 수 있다.
- 실패 사유를 한 문장으로 쓸 수 없으면 검증 기록이 부족한 것이다. 그 건은 「다시 확인 필요」로 옮긴다. 추정으로 채우지 않는다.

### 3. 올리기

승인된 건을 팩의 「결함 티켓 등록」으로 바로 올린다. 올린 뒤 결함 티켓 주소, 원래 티켓, 담당자를 표로 보고한다. 담당자는 개발자가 자기 티켓을 검증하다 올린 결함이면 그 개발자 본인이고, PM이 독립 판정에서 올린 결함이면 비워 두고 PM이 배정한다. 정하는 방법은 팩이 맡는다.

티켓 본문에는 아래를 담는다. 모두 검증 기록에서 옮긴다.

| 항목 | 내용 |
|---|---|
| 제목 | 관찰한 현상을 적는다. 원인 추정을 제목으로 쓰지 않는다 |
| 무엇이 잘못됐나 | 어느 화면 또는 어느 요청에서, 어떤 조건일 때 일어나는지 1~2문장 |
| 실패한 인수 조건 | 원래 티켓 링크와 인수 조건 번호·문장 |
| 기대한 결과와 실제 결과 | 인수 조건이 요구하는 동작과 검증에서 관찰한 동작 |
| 재현 절차 | 준비 상태, 조작 또는 요청, 결과를 확인한 위치. 테스트 파일 경로를 함께 적는다 |
| 확인한 환경 | 대상(로컬·배포본), 판본, 검증 방법 |
| 완료 조건 | 원래 인수 조건이 다시 통과하는 것. 검증 방법은 원래 인수 조건과 같게 둔다 |

규칙은 3가지다.

1. **실패한 인수 조건 1개에 티켓 1건이다.** 검증 장부가 인수 조건 단위로 열린 결함을 세므로, 묶으면 어느 조건이 아직 열려 있는지 알 수 없다. 같은 원인으로 보이는 건은 본문에 서로의 링크를 적는다.
2. 실제 결과와 재현 절차를 추정으로 채우지 않는다.
3. 원인은 확인한 경우에만 근거와 함께 적는다.

## 팩이 없을 때

- **결과 기록**: 저장소의 `qa/verification-log.md`에 날짜, 티켓 식별자, 인수 조건 번호, 검증 방법, 결과, 요약, 근거, 커밋을 한 줄씩 덧붙인다. 앞 기록을 고치지 않고 새 줄을 더한다. 같은 인수 조건은 마지막 줄이 최신이다.
- **검증 장부**: 티켓 본문의 인수 조건 목록과 `qa/verification-log.md`를 스크립트로 대조해 통과·실패·기록 없음을 센다. 눈으로 세지 않는다.
- **결함 티켓**: 목록 승인을 받은 뒤 `qa/defects/` 아래에 인수 조건 1개당 md 파일 하나로 남긴다. 파일 이름에 원래 티켓 식별자와 인수 조건 번호를 넣어, 다음 실행 때 이미 등록된 것인지 가릴 수 있게 한다. 외부 도구에 올리지 않는다.
- **화면 실행**: `spec-driven-qa` 스킬을 직접 쓴다. 설정 파일은 저장소의 `qa/spec-driven/`에, 로그인 상태 파일은 저장소 밖에 둔다.
- **상태 변경**: 하지 않는다.
- **기획 확인 항목**: `qa/planner-checks.md`에 티켓 식별자, 날짜, 커밋과 함께 항목 블록을 덧붙인다. 항목 줄은 `☐ 1. (AC 2) 문장`처럼 쓰고, 관련 인수 조건이 없으면 괄호를 뺀다. 앞 줄을 고치지 않는다.
  - **현재 목록:** 티켓별 마지막 항목 블록이다.
  - **기획자의 결정:** `→ 확정: 문장` 또는 `→ 변경 요청: 문장 — 요청 문장`과 확인자·날짜를 덧붙인다. 같은 문장의 마지막 결정 줄이 그 항목의 상태다.
  - **문장 대조:** 결정을 덧붙이기 전에 파일의 현재 문장과 1단계에서 읽은 문장을 대조한다. 다르면 기획자 확인 모드 3단계의 「문장이 바뀌어 거부된 경우」처럼 처리한다.

## 하지 않는 것

- 다른 사람이 담당한 티켓을 검증하거나 그 티켓에 검증 기록을 남기지 않는다.
- 승인받지 않은 결함 티켓을 올리지 않는다. 이미 열린 결함 티켓이 있는 인수 조건에 또 만들지 않는다.
- 장부를 보지 않고 "전부 검증됐다"고 말하지 않는다.
- 사용자가 요청하지 않은 상태 변경을 하지 않는다.
- 스크린샷을 통과의 근거로 쓰지 않는다. 참고 자료로만 붙인다.
- 세션이 화면을 직접 조작해 보고 통과를 선언하지 않는다. 화면 확인 기록은 고정한 대본의 재생 결과를 판정 스크립트가 판정한 것만 남긴다.
- 로그인 상태 파일의 경로나 내용, 계정과 비밀번호를 기록·코멘트·저장소에 쓰지 않는다.
- 공유 테스트 서버·운영 서버의 데이터를 바꾸는 검증을 하지 않는다.
- 실행한 세션이 의미 판정까지 이어서 하지 않는다.
- 환경 팩을 추측으로 고르지 않는다.
- 기획 확인 항목을 개발자 확정 없이 기록하지 않는다. 기획자의 결정 없이 확정이나 변경 요청을 기록하지 않는다.
- 기획 확인 항목을 통과·실패 판정이나 결함 티켓으로 바꾸지 않는다.
