# PRD Builder · Discovery (Macro Gate 모델)

PRD Discovery 단계의 인터랙티브 entry point. 거시 결정 3회(Macro Gate 1·1.5·2)만 사람이 개입하고, 그 사이 미시 결정은 `prd-builder-auto`가 자동 진행한다.

## Phase별 순차 컨펌 방식과의 차이

| 항목 | 전통적 Phase 순차 컨펌 | 본 스킬 (Macro Gate 모델) |
|---|---|---|
| 진행 방식 | 8 Phase 직렬 컨펌 | Macro Gate 3개 + Auto Phase 2개 |
| 인터랙션 횟수 | Phase당 1~2회 (총 11~16회) | 속도 우선: 게이트당 1~2회 (총 5~8회) / 탐구 우선: Gate 1 Sub-Gate 포함 (총 14~17회) |
| 사용자 부담 시점 | 매 Phase 컨펌 | 거시 결정 시점만 집중 |
| 자동화 영역 | 거의 없음 (모두 사용자 확인) | 미시 결정·솔루션 발산·상세화 |
| 산출물 위치 | 외부 도구에 점진 적재 | 로컬 파일이 SoT (Notion 업로드는 옵션) |
| 적합 시점 | 신중한 정통 PRD 작성 | 빠른 추진·시간 압박·반복 작업 |

## 핵심 원칙

1. **거시 결정만 사람**: 사람의 직관이 필요한 결정만 게이트로 분리. 모범 사례·정합성 검토는 자동 위임
2. **진행 방식 선택**: Phase 0에서 '속도 우선(묶음)' 또는 '탐구 우선(순차 문답)' 선택. 탐구 우선은 Gate 1의 3개 영역을 Sub-Gate 1a·1b·1c로 분리해 영역마다 2~3라운드 소크라테스식 문답 후 수렴
3. **공간 분리 (Double Diamond)**: Problem Space(Gate 1)와 Solution Space(Gate 1.5)를 명확히 분리. 솔루션이 문제·페르소나를 흔들지 않도록 순서 고정
4. **로컬 파일이 SoT, Notion은 옵션**: 모든 산출물의 진실의 원천은 `prd-flow/{feature-slug}/` 로컬 파일. Notion 업로드는 context.json `notion_upload`가 true일 때만, 게이트 통과 시점에만 수행. 중간 미확정 산출물은 Notion에 흩뿌리지 않음
5. **할루시네이션 금지**: 사용자가 명시하지 않은 결정은 prd-builder-auto의 decision-log에 Silent Default로 기록

## 외부 리서치 프로토콜 (Auto Phase 공통)

거시 결정과 자동 진행 과정에서 WebSearch로 외부 맥락(경쟁·시장·업계 관행·최신 기법)을 보강한다. 강도는 **필수** — 적용 지점에서 스킵하지 않는다.

**적용 지점** (묶음·순차 모드 공통)
- Gate 1: 문제 실재성·경쟁 검증
- Forward(솔루션 발산): 경쟁·대안 제품 패턴
- Backward(상세화): 임계치·KPI 벤치마크·AI 모델 최신성

**공통 규칙**
1. **검색량 상한**: 적용 지점당 1~2회. 쿼리는 핵심 1~2개로 압축한다. 폭주 방지를 위해 상한을 넘기지 않는다.
2. **결과 활용**: 패턴·수치·업계 관행만 추출. 검색 원문 전체를 컨텍스트에 적재하지 않는다.
3. **사용자 제공 지식 최우선**: 사용자가 직접 제공한 지식·사양이 최우선이다. 리서치 캐시(`research/domain-*.md`)는 확정 사양이 아니라 **참고 근거**다. 충돌 시 사용자 지식을 따르고, 충돌 사실만 decision-log에 1줄 남긴다.
4. **출처 병기**: 인용한 수치·주장은 `[출처: 도메인]` 형태로 산출물에 기록한다.
5. **회계 연계 (필수)**: 리서치로 채운 값은 Silent Default가 아니라 **'리서치 기반 결정'**으로 분류해 SD 카운트에서 제외한다. 단 출처를 `prd-builder-auto`의 decision-log에 반드시 기록한다. (상세: `prd-builder-auto`의 Silent Default 감지기 `research_backed_values`)
6. **가시화**: 수행한 리서치 건수·출처는 Macro Gate 2 리포트의 '외부 리서치' 섹션에 집계해 사용자가 일괄 검토하게 한다.
7. **리서치 값 단정 금지 (기본 규칙)**: 리서치 값을 확정 사실처럼 단정하지 않는다. `editorial-reviewer`의 사실 검증과 직렬로 연결해 출처 신뢰도를 한 번 더 거른다.
8. **캐시 환류**: 재사용 가치가 있는 리서치 결과(업계 표준 수치·경쟁 패턴·용어 정의 등)는 해당 토픽의 `research/domain-*.md` 캐시 파일에 출처와 함께 추가해 후속 스킬이 재활용하게 한다.

### context.json 스키마

작업 디렉토리 진입 시 즉시 작성. 후속 스킬(prd-builder-auto, prd-to-wireframe, notion-organizer 등)이 **산출물 경로·옵션 인지의 단일 출처**로 사용.

```json
{
  "feature_slug": "habit-tracker-reminders",
  "research_dir": "research/",
  "design_system": "design/design-system.md",
  "ux_writing_skill": "general-ux-writing",
  "notion_upload": false,
  "created_at": "2026-05-27T10:00:00Z"
}
```

| 필드 | 의미 |
|---|---|
| `feature_slug` | 작업 디렉토리 슬러그 |
| `research_dir` | domain-research가 생성한 도메인 리서치 캐시 디렉토리 |
| `design_system` | design-system-builder 생성물 경로 (prd-to-wireframe Phase 0에서 생성) |
| `ux_writing_skill` | UX writing 가이드 스킬 |
| `notion_upload` | Notion 업로드 사용 여부 (기본 `false` — 미사용 시 notion-pages/ 파일은 로컬 생성만) |
| `created_at` | 생성 시각 (ISO 8601) |

## 워크플로우

### 0. 진입 분류

사용자에게 4가지를 묻는다.

1. **제품/기능명**: 작업 디렉토리 슬러그
2. **제품 카테고리/도메인 키워드 (1~3개)**: 도메인 리서치 캐시 구축용 (예: "습관 트래커, 리마인더", "커머스, 환불 정책")
3. **탐구 깊이**: Gate 1(문제 정의·핵심 가치·페르소나)의 진행 방식
   - `속도 우선` (기본값): 3개 영역을 한 번에 묶어 제시. 1회 응답으로 확정
   - `탐구 우선`: Sub-Gate 1a → 1b → 1c 순차 진행. 영역마다 2~3라운드 소크라테스식 문답 후 수렴
4. **Notion 업로드 사용 여부** (기본값: 미사용): true 선택 시에만 추가로 **Notion 부모 페이지**(일괄 업로드 위치)를 묻는다. 미사용이면 notion-pages/ 파일은 로컬 생성만 하고 업로드 단계를 전부 생략한다.

#### context.json 작성

응답을 받으면 작업 디렉토리를 생성하고 context.json을 즉시 작성. 이후 모든 후속 스킬은 이 파일을 산출물 경로·옵션의 진실의 원천(SoT)으로 참조.

#### 도메인 리서치 캐시 구축 (Gate 1 진입 전 · 필수)

context.json 작성 직후, 2번 응답의 도메인 키워드로 `domain-research` 스킬을 호출한다.

```
domain-research 호출
  working_dir: ./prd-flow/{feature-slug}/
  topics: {도메인 키워드 1~3개 + 파생 토픽}
```

- 산출물: `research/domain-{topic}.md` 캐시 (**최대 4개 토픽**)
- 이 캐시는 이후 전 단계에서 재사용된다: Gate 1 사전 분석의 문제·페르소나 후보 도출, prd-builder-auto의 **페르소나 리뷰**("적재된 도메인 리서치 캐시: {목록}" 형태로 명시 전달)와 **정합성 검토**의 근거, Full PRD 페르소나 구체화의 추정 근거
- 캐시는 확정 사양이 아닌 참고 근거다. 사용자 제공 지식과 충돌하면 사용자 지식을 우선한다 (외부 리서치 프로토콜 규칙 3)

캐시 생성 완료 후 Macro Gate 1 진입.

### 1. Macro Gate 1 (Problem Space)

Phase 0에서 선택한 탐구 깊이에 따라 진행 방식이 분기된다.

---

#### 문제 후보 도출 원칙 (공통 · 필수)

문제 후보는 **표면적 증상**(도구·기능의 부재, "~하는 툴이 없다")이 아니라, 그 증상이 유발하는 **비즈니스·사용자 관점의 근본 문제**로 정의한다. 각 후보를 다음 3단으로 도출한다.

1. **표면 증상**: 사용자가 처음 말하는 불편(기능/도구 부재 형태)
2. **근본 원인 사슬**: 그 증상이 왜 생기고 무엇으로 이어지는지 원인→결과 사슬
3. **비즈니스/사용자 임팩트**: 전환율·이탈·활성화·신뢰·오안내·해결률 같은 **결과 지표**로 귀결

**규칙**
- "~하는 툴/기능이 없다"를 문제 후보 문장으로 쓰지 않는다. 그건 증상이지 문제가 아니다.
- 각 후보는 "누가, 어떤 맥락에서, 무엇 때문에, 어떤 결과(비즈니스·사용자 손실)를 겪는가"가 드러나야 한다.
- 결과 링크(예: 전환율↓·이탈)가 아직 근거 없이 추정이면 **가설로 표시**하고 Gate 1 실재성 리서치의 검증 대상으로 넘긴다. (할루시네이션 금지 원칙과 연계)

**예시**
- ❌ 표면 증상형: "흩어진 문서를 표준 포맷으로 자동 변환하는 툴이 없다"
- ✅ 근본 문제형: "지식 정제를 수작업에 의존해 신규 고객 온보딩 마찰이 크고, 정제 품질이 답변 성능을 좌우해 도입 전환·활성화가 저하된다 (전환율↓ 링크는 가설, 검증 대상)"

---

#### [속도 우선] 묶음 진행

문제 정의 + 핵심 가치 + 페르소나를 **한 번의 프롬프트에 묶어 제시**.

##### 사전 분석

게이트 진입 전, Claude가 다음을 준비한다.

- 문제 후보 3개 도출 (→ '문제 후보 도출 원칙' 준수) (사용자 입력·기존 CS 티켓·인터뷰 메모 기반. 자료가 없으면 일반론적 후보)
- 핵심 가치 가설 표현 형태 3개 (사용자 가치형 / 비즈니스 임팩트형 / 차별화 가설형)
- 페르소나 후보: 사용자 입력·도메인 리서치 캐시(`research/domain-*.md`)·작업 디렉토리 슬러그 기반 3~4개 도출

##### 프롬프트 템플릿

```markdown
Discovery 시작. 3개 영역을 한 번에 잡자.

[1] 문제 정의
후보 3개:
A) {문제 후보 A}
B) {문제 후보 B}
C) {문제 후보 C}
→ 메인 / 부차 / 범위 외 분류 + 분류 이유 1~2줄

[2] 핵심 가치 가설
표현 형태:
A) '{페르소나}가 {상황}에서 {Job-to-be-Done}을 할 수 있게 한다'
B) '{KPI}를 {정량 목표} 개선한다'
C) '{이해관계자}에게 {차별점}을 입증한다'
→ 1개 선택 또는 직접 작성

[3] 페르소나
후보:
A) {페르소나 A} ({권한·역할 요약})
B) {페르소나 B}
C) {페르소나 C}
D) {페르소나 D}
→ 메인/서브/범위 외 분류 + 각 페르소나별 핵심 Job-to-be-Done 1줄
```

##### 분리 트리거

응답이 다음 조건에 해당하면 묶음을 깨고 해당 영역만 재질문한다.

| 트리거 | 행동 |
|---|---|
| 영역 1~2개만 답변 | 누락 영역만 재질문 |
| 분류 이유가 모순 (예: "A 메인, 이유: A는 우선순위 낮음") | 해당 영역만 재질문 |
| 도메인 리서치 근거(`research/domain-*.md`)와 critical 충돌 | 해당 영역만 재질문 + 충돌 사유·출처 명시 (리서치는 참고 근거 — 사용자 지식이 우선) |
| 핵심 가치 가설이 메인 문제와 정렬 안 됨 | 두 영역 묶어 재질문 |

##### Gate 1 검증 (Generator-Evaluator 루프)

분리 트리거 표를 "통과/미통과"로 선언만 하고 넘어가는 것을 금지한다. 트리거 각 행을 사용자 응답과 1:1 대조한 결과를 **문제 목록 텍스트로 먼저 출력**한 뒤에만 통과 처리한다.

**Step 1 — 검증 결과 목록 출력 (필수)**

분리 트리거 4개 행 각각을 사용자 응답과 대조한다. 걸리는 항목이 없으면 "분리 트리거 대조: 4개 항목 모두 해당 없음"을 명시한다. 이 Step 없이 "Gate 1 통과"를 선언하지 않는다.

```
[항목] [분리 트리거 행 이름]
[심각] [🔴 재질문 / 🟡 보완]
[근거] 사용자 응답의 어느 부분이 트리거에 해당하는지
```

**Step 2~4** — 🔴 항목은 해당 영역만 재질문(사용자 호출). 🟡은 본문에 보완 반영. 🔴이 모두 해소되면 아래 산출물 생성으로 진행.

**Step 5 — 문제 실재성·경쟁 검증 (필수 리서치)** — 묶음·순차 모드 공통

Gate 1 확정 전 1회, 외부 리서치 프로토콜에 따라 메인 문제의 실재성과 경쟁·대안의 처리 방식을 검색해 대조한다. 결과는 문제 정의·핵심 가치 가설의 근거로 보강하고, 출처를 decision-log에 기록한다. 재사용 가치가 있는 결과는 `research/domain-*.md` 캐시에 환류한다. 검색 결과가 사용자 제공 지식과 충돌하면 사용자 지식을 우선한다.

#### [탐구 우선] Sub-Gate 순차 진행

Sub-Gate 1a → 1b → 1c 순서로 진행. 각 영역은 소크라테스식 문답 2~3라운드를 거쳐 사용자가 수렴 확정해야 다음 Sub-Gate로 넘어간다. **라운드 중에 이미 명확하다 판단되면 남은 라운드를 생략하고 수렴 제안을 먼저 던진다.**

##### Sub-Gate 1a: 문제 정의

**사전 준비**: 문제 후보 3개 도출 (→ '문제 후보 도출 원칙' 준수) (사용자 입력·CS 티켓·인터뷰 메모 기반. 자료 없으면 일반론적 후보)

**R1 — 증상 vs 원인 분리** (→ '문제 후보 도출 원칙' 준수)

문제 후보 3개를 제시하며 묻는다.

```
후보:
A) {문제 후보 A}
B) {문제 후보 B}
C) {문제 후보 C}

각 후보에 대해:
- 이것이 표면적 증상인가, 근본 원인인가?
- 이 현상이 발생하는 맥락은? (언제, 어디서, 어떤 조건에서)
- 빈도와 심각도를 수치 또는 비율로 표현할 수 있는가?
```

**R2 — 원인 심화**

R1 응답을 바탕으로 Claude가 근본 원인 가설 2~3개를 제시하며 묻는다.

```
R1 기반 근본 원인 가설:
1) {가설 1}
2) {가설 2}

- 왜 지금까지 이 문제가 해결되지 않았는가?
- 기존에 시도한 해결책이 있다면, 왜 불충분했는가?
```

**R3 — 수렴** (R2에서 이미 명확해지면 생략 가능)

```
문제 정의 확정안:
"{메인 문제 정의 1문장}"

동의하면 Sub-Gate 1b로 진행. 수정이 필요하면 변경 사항만 알려달라.
```

사용자 확정 시 `gate1/01-problem.md` 초안 기록 후 Sub-Gate 1b 진입.

##### Sub-Gate 1b: 핵심 가치 가설

**R1 — 수혜자 특정**

```
문제가 해결됐을 때 가장 직접적으로 달라지는 사람은 누구인가?
- 직접 수혜자: (역할·상황 중심으로 기술)
- 간접 수혜자: (조직·이해관계자)
- 이 사람의 현재 불편함을 한 문장으로?
```

**R2 — 성공 정의**

R1 응답을 바탕으로 3가지 표현 형태를 제시한다.

```
성공을 어떻게 정의할 것인가?
A) 사용자 경험형: '{수혜자}가 {상황}에서 {Job}을 할 수 있게 한다'
   예시: {R1 기반으로 채운 문장}
B) 비즈니스 임팩트형: '{KPI}를 {정량 목표} 개선한다'
   예시: {추정 가능한 문장}
C) 차별화 가설형: '{이해관계자}에게 {차별점}을 입증한다'
   예시: {문장}

1개 선택, 조합, 또는 직접 작성. 지금 수치 근거가 없어도 괜찮다. 방향성 확정이 목표.
```

**R3 — 수렴**

```
핵심 가치 가설 확정안:
"{가설 문장}"

동의하면 Sub-Gate 1c로 진행. 수정이 필요하면 변경 사항만 알려달라.
```

사용자 확정 시 `gate1/02-value-hypothesis.md` 초안 기록 후 Sub-Gate 1c 진입.

##### Sub-Gate 1c: 페르소나

**사전 준비**: 사용자 입력·도메인 리서치 캐시(`research/domain-*.md`)·작업 디렉토리 슬러그 기반 3~4개 후보 도출

**R1 — 현장 묘사**

페르소나 후보를 제시하며 묻는다.

```
후보:
A) {페르소나 A} ({권한·역할 요약})
B) {페르소나 B}
C) {페르소나 C}
D) {페르소나 D}

각 후보에 대해:
- 이 사람이 이 문제에 맞닥뜨리는 것은 언제, 어디서, 어떤 상황에서인가?
- 가장 불편한 순간(Pain Peak)은?
```

**R2 — 대안 행동 탐구**

R1 응답을 바탕으로 Claude가 현재 대안 행동을 추론 후 묻는다.

```
현재 이 사람들이 문제를 해결하는 방식 (추론):
A) {페르소나 A}: {추론된 대안 행동}
B) {페르소나 B}: ...

- 맞는가? 틀린 부분은 수정해달라.
- 이 대안이 왜 부족한가? (시간·정확도·접근성 등)
```

**R3 — 수렴**

```
페르소나 확정안:

| 페르소나 | 분류 | Job-to-be-Done |
|---|---|---|
| {A} | 메인 | {1줄} |
| {B} | 서브 | {1줄} |
| {C} | 범위 외 | — |

동의하면 교차 검증으로 진행. 수정이 필요하면 변경 사항만 알려달라.
```

사용자 확정 시 `gate1/03-personas.md` 초안 기록 후 교차 검증 진행.

##### [탐구 우선] 교차 검증

Sub-Gate 3개 확정 후 4개 항목을 대조한다. **결과 목록 출력 없이 "Gate 1 통과"를 선언하지 않는다.**

| 항목 | 점검 내용 | 불일치 시 |
|---|---|---|
| 문제-가치 정렬 | 핵심 가치 가설이 확정된 메인 문제와 정렬되는가 | Sub-Gate 1b만 재진입 |
| 문제-페르소나 정렬 | 메인 페르소나의 Job-to-be-Done이 메인 문제와 일치하는가 | Sub-Gate 1c만 재진입 |
| 가치-페르소나 정렬 | 핵심 가치 가설의 수혜자가 메인 페르소나와 일치하는가 | Sub-Gate 1b 또는 1c 재진입 |
| 도메인 정합성 | 도메인 리서치 근거(`research/domain-*.md`) 기준 critical 충돌 없는가 (리서치는 참고 근거 — 사용자 지식이 우선) | 해당 Sub-Gate 재진입 + 충돌 사유·출처 명시 |

4개 항목 모두 통과 시 Gate 1 통과 선언.

##### Sub-Gate 1.5a: 솔루션 방향

**R1 — 솔루션 이해 확인**

```
위 매트릭스를 바탕으로:
- 각 솔루션 후보가 메인 문제를 어떻게 해결하는지, 이해한 대로 설명해줄 수 있는가?
- 매트릭스에서 놓친 시각이 있다면 보완해달라.
```

**R2 — 선택 기준 탐구**

R1 응답을 바탕으로 Claude가 기준별 최적 조합을 추천한다.

```
어떤 기준으로 솔루션 방향을 결정할 것인가?
A) 문제 해결도 우선: 메인 문제를 가장 직접적으로 해결하는 것
B) 구현 가능성 우선: V1 내 실현 가능한 범위 내에서
C) 출시 속도 우선: 가장 빠르게 사용자에게 닿을 수 있는 것
D) 이해관계자 설득력 우선: 비즈니스 임팩트를 증명하기 쉬운 것

기준 1~2개 선택 또는 직접 서술.
```

선택한 기준에 따른 최적 솔루션 조합 추천과 그 이유를 제시한다.

**R3 — 수렴**

```
채택 솔루션 방향 확정안:
{S-번호 또는 조합} — {1~2줄 이유}

동의하면 V1 범위 결정으로 진행. 수정이 필요하면 변경 사항만 알려달라.
```

사용자 확정 시 Sub-Gate 1.5b 진입.

##### Sub-Gate 1.5b: V1 범위 경계

**R1 — 제약 조건 파악**

```
채택 솔루션을 기반으로:
- V1에서 반드시 포함해야 하는 것은? (없으면 가치 전달이 안 되는 최소 요소)
- 반드시 제외해야 하는 것은? (일정·리소스·의존성 이슈)
- 포함 여부가 모호한 항목이 있다면 무엇인가?
```

**R2 — Coverage Gap 분석**

R1 응답을 바탕으로 Claude가 Gap을 분석해 제시한다.

```
Coverage Gap 분석:

5. 기능 정의            기능 단위로 1개씩 (FN-01, FN-02 …). 우선순위 미표기
6. 우선순위             별도 섹션. P0/P1/P2에 FN- 매핑
7. KPI                  K- 앵커
8. 리스크               Devil's Advocate 처리 결과
9. 의사결정·확인 필요    D- / OQ-
```

**페르소나(§3) 작성 규칙 (구체화 필수)**
UX/UI 설계 시 직접 참조 가능한 수준으로 메인 페르소나를 구체화한다. 단순 역할·JTBD 1줄로 끝내지 않는다. 다음 항목을 표 + 서술로 포함한다.
- 기본 속성: 대표 인물(가상명)·연령대·권한·기술 숙련도·담당 규모
- 사용 맥락: 주/보조 사용 기기, 사용 환경(현장/사무실 등), 사용 시점
- 특성·심리: 책임·압박, 선호, 의사결정 성향
- 일상 워크플로우: 이 기능과 관련된 하루 동선을 번호 단계로
- Pain Point: 현재 불편을 구체 상황으로
- Job-to-be-Done: 한 문장
- 정보가 없으면 도메인 리서치 캐시(`research/domain-*.md`)·제품 사용 맥락 기반으로 합리적으로 추정해 채운다(페르소나는 가설 산출물). 서브·범위 외는 1줄로 간단히.

**기능 정의(§5) 작성 규칙 (불변)**
- **기능 단위로 그룹핑한다.** 각 기능을 `FN-{n}` ID로 1개씩 정의한다(컴포넌트·모달·로직 등 독립 기능 단위). **P0/P1/P2 우선순위로 묶지 않는다** — 우선순위는 §6에서 별도로 매핑한다.
- 각 기능 항목 형식: `### FN-{n}. {기능명}` 헤더 + (연관 수식이 있을 때만) 바로 아래 줄에 인라인 코드 메타 라인 `` `앵커: F-n` `` (여러 개면 `` `앵커: F-2, F-3` ``) + 정책(Policy)·흐름(Flow) high-level 서술.
- **§5에는 우선순위를 표기하지 않는다.** 우선순위는 §6에서만 다룬다.
- **앵커는 본문 문장에 섞지 않는다.** "수식 F-4 참조"처럼 서술에 녹이지 말고, 헤더 아래 별도 메타 라인 `` `앵커: F-n` ``으로만 표기한다(prd-sync 교차 검색용 메타). 연관 수식이 없는 기능은 앵커 라인을 생략한다.
- **수식·임계치·파라미터 본문은 PRD에 두지 않는다**(프로토타입/디스크립션 SoT). 기능 정의엔 "임계 초과 시 경보" 수준 서술만 둔다.
- 기능 식별자 `FN-{n}` 자체가 기능 앵커이며 PRD가 SoT다(`prd-sync` 규약). 디스크립션(화면 구현)·티켓(Story 분해)이 이 앵커를 참조한다.

**우선순위(§6) 작성 규칙**: P0/P1/P2 각 그룹에 §5에서 정의한 `FN-` ID를 매핑하고 분류 근거를 1줄로 적는다. 기능 본문을 반복 서술하지 않는다(중복 금지).

**제외**: 계산 수식 섹션, QA 케이스 목록은 Full PRD에 두지 않는다(각각 프로토타입·티켓 영역).

3. **notion-organizer 호출** (`mode: prd-consolidation`) — **context.json `notion_upload: true`일 때만**:

## 사용자 대면 커뮤니케이션 규칙 (게이트 프롬프트·선택지)

Macro Gate 1·1.5·2의 프롬프트, 솔루션 매트릭스 제시, 선택지, 그리고 **산출물(기능 정의 FN·우선순위·KPI·QA·솔루션 후보 등)을 대화 본문에 나열·요약해 제시할 때** 항상 적용한다. PRD 본문 가드레일과 **별개**이며, 기준은 "사용자가 로컬 md 파일을 열지 않고 그 자리에서 대략 무엇인지 판단할 수 있는가"다. 사용자가 개발 배경 없이 결정하는 경우가 많으므로, 내부 코드·짧은 이름·압축 라벨만으로 나열하거나 선택을 요구하면 안 된다.

- **산출물 코드 나열 시 한 줄 설명 병기**: 기능 정의(FN-1 …)·KPI(K-1 …)·테스트(TC-1 …)·솔루션 후보(S1 …)를 대화에 나열·요약할 때 코드와 짧은 이름만 쓰지 않고, 각 항목이 "실제로 무엇을 하는지"를 개발 배경 없는 사용자가 이해할 한 줄 평이 설명으로 반드시 붙인다. (예: "리마인더 등록(FN-1)" ❌ → "FN-1 리마인더 등록 — 반복 습관에 알림 시각을 지정하고 목록에서 켜고 끄도록 관리" ✅) "상세는 md에서 보라"는 전제로 코드만 나열하지 않는다. 이는 게이트 리포트 요약·산출물 목록 제시 전 구간에 적용된다.
- **내부 후보 코드 단독 금지**: 솔루션 후보 코드(S1·S2 …), 컴포넌트·노드명, 티켓/데이터셋 코드를 라벨·선택지에 단독으로 쓰지 않는다. 반드시 한 문장으로 "이 후보가 실제로 무엇을 하는지"를 평이하게 풀어 병기한다. (예: "S3 채택" ❌ → "여러 알림을 하나로 묶어 지정한 시각에 한 번만 보내 알림 피로를 줄이는 방식" ✅)
- **압축 명사구 라벨 금지**: "알림 피로 저감", "신뢰도 계층화" 같은 명사구만으로 선택을 요구하지 않는다. 사용자가 의미를 상상해서 해석해야 하는 라벨은 미완성으로 간주한다.
- **완결문 사용**: 선택지 설명은 주어·동작·결과가 드러나는 완결문으로 쓴다. 부분 미완성 문장이나 해석 여지가 있는 축약(예: "…까지만 V1", "…는 보조")을 그대로 남기지 않는다. 선택지 label이 짧게 축약될 때는 description에 완결문을 반드시 채운다.
- **기술 용어 풀이 병기**: 개발 용어(스키마·임계치·payload·endpoint 등)는 선택지에서 처음 등장할 때 역할을 풀어 설명한다.
- **화살표·기호 압축 금지**: 대화 프롬프트에서도 `A→B`·`↑↓`로 인과·조건을 뭉뚱그리지 않는다. 구체값과 완결문으로 쓴다.
- **선택 전 매트릭스 자족성**: 여러 후보 중 선택을 요구하기 직전에, 각 후보의 평이한 한 줄 설명을 같은 화면(직전 응답 본문)에 함께 제시한다. 사용자가 이전 응답으로 스크롤해 대조하게 만들지 않는다.

이 규칙 위반이 발견되면(사용자가 "무슨 뜻이냐", "풀어서 설명해달라"고 되물으면) 해당 게이트 프롬프트를 풀어 재작성한 뒤 다시 질문한다.

## 작성 가드레일

PRD 본문 작성 시 항상 다음 규칙을 적용한다.

- **화살표(→) 금지**: 인과·시퀀스는 서술형으로
- **예외**: 시각적 조건 표현 허용 ("동일 주문 + 결제 실패 + 60초 내 3회 이상 발생")
- **변수명·코드 표기 금지**
- **디자인 심미성 배제**: 색상·폰트·여백 등 디자이너 영역 작성 금지. UX 흐름·정보 우선순위는 허용
- **개발 구현 디테일 배제**: 라이브러리·DB 스키마 등 개발자 영역 금지. 비즈니스 로직·백엔드 시퀀스는 Mermaid 플로우차트로 작성
- **기능 정의 작성 고도(Altitude)**: high-level "왜(기능의 존재 이유)·무엇(어떤 기능)"과 정책(Policy)·흐름(Flow)까지만 작성. 아래 항목은 PRD에 담지 않고 프로토타입/디스크립션(wireframe-description) 단계에서 작성
  - 버튼·레이블의 정확한 표시 텍스트
  - 화면·모달 내 필드·항목 구성 목록
  - 마이크로 인터랙션 (클릭 후 동작, 모달 닫기 방식 등)
  - 상태별 UI 표현 방식 (프로그레스 바, 차트 유형 등)
  - 빈 상태·오류 상태의 구체적 문구
  - **계산 수식·임계치·파라미터 값·컴포넌트 동작 정책** (산출물별 역할 정의: PRD는 high-level만, 수식·동작 정책은 프로토타입 귀속)
- **개조식 우선**: 줄글보다 번호 계층 + 짧은 서술형
- **계산 수식은 PRD에 작성하지 않는다**: 임계치·점수·통계·차트 정책 등 모든 계산 수식은 **프로토타입(디스크립션)이 SoT**다. PRD에는 "임계 초과 시 경보" 수준의 high-level 서술만 두고, 구체 수식·값은 두지 않는다.
  - **수식 앵커는 디스크립션에서 부여·관리**: 각 수식에 `F-{n}`, 핵심 파라미터에 `F-{n}.p{m}` ID를 디스크립션에 부여한다. 네이밍은 `prd-sync` 스킬의 앵커 체계 규약을 따른다. 이 앵커는 티켓이 참조하고 prd-sync의 교차 검색 키가 된다. PRD는 수식 앵커를 보유하지 않는다(수식이 PRD에 없으므로).
- **UI 텍스트**: `general-ux-writing/references/ux-writing.md` 준수 (context.json `ux_writing_skill`이 가리키는 스킬)
- **디자인 제약**: 화면 단계에서는 `design-system-builder`가 생성한 `design/design-system.md`의 Hard Constraints를 적용 (prd-to-wireframe Phase 0에서 생성)

## 실행 시 첫 응답 패턴

요청을 받으면 바로 작성에 들어가지 않는다. 항상 다음 순서:

1. Macro Gate 모델 안내 (인터랙션 횟수·예상 소요 시간)
2. 0단계 4가지 확인 항목 질문 (제품/기능명, 도메인 키워드 1~3개, 탐구 깊이, Notion 업로드 여부 — 사용 시에만 Notion 부모 페이지 추가 질문)
3. 작업 디렉토리 생성 후 context.json 작성
4. `domain-research` 스킬 호출로 `research/domain-{topic}.md` 캐시 구축 (최대 4개)
5. Macro Gate 1 진입
