# Full PRD Epic 작성 기준

Full PRD의 기능 요구사항은 Epic 단위로만 작성한다. PRD는 제품 범위와 완료 상태를 합의하는 문서이고, Story·Task·세부 인수 조건은 티켓 단계에서 작성한다.

## 1. Epic 분리 기준

다음 조건 중 하나 이상이 성립하고, 별도 완료 상태를 판단할 수 있을 때 Epic을 분리한다.

- 다른 Epic과 독립적으로 우선순위를 조정하거나 출시할 수 있다.
- 완료 후 확보되는 사용자 가치 또는 운영 역량이 다르다.
- 주요 책임 팀, 외부 의존성, 위험 또는 검증 방식이 뚜렷하게 다르다.
- 한 Epic을 보류해도 나머지 Epic의 목적과 완료 판단이 유지된다.

아래 경우에는 나누지 않는다.

- 화면, API, 저장소, 에이전트처럼 구현 구성요소가 다르다는 이유만으로 분리한다.
- 하나의 사용자·운영 결과를 만들기 위한 순차 단계이며 각 단계만으로는 독립 가치가 없다.
- 같은 완료 상태를 표현하는 항목을 조직이나 기술 계층에 따라 중복 분리한다.

Epic 하나가 지나치게 크면 완료 상태가 둘 이상인지 먼저 확인한다. 반대로 Epic 하나에서 후속 Story를 둘 이상 도출하기 어렵다면 독립 Epic인지 재검토한다. 이는 분리 판단을 돕는 권장 기준이며 개수 강제 규칙은 아니다.

## 2. PRD와 티켓의 경계

| PRD의 Epic에 작성 | 티켓에서 작성 |
|---|---|
| 해결할 문제와 Epic 목적 | Story·Task 분해와 담당 티켓 |
| Epic 완료 후 달라지는 상태 | 사용자 흐름별 상세 동작 |
| 포함 범위와 제외 범위 | 화면 구성, UI 문구, 필드 목록 |
| 제품·운영 관점의 핵심 요구사항 | API, schema, payload, 저장·배포 방식 |
| 다른 Epic·시스템과의 주요 의존성 | 예외 분기, 재시도, 오류 처리의 세부 정책 |
| Epic 수준의 완료 판단 | 테스트 가능한 세부 인수 조건과 검증 케이스 |

안전·법규·권한처럼 Epic 범위와 출시 판단을 바꾸는 제약은 PRD에 남긴다. 구체 수치, 조건 조합, 기술 계약은 근거 문서·에이전트 사양·티켓 중 책임 문서에 둔다. 개별 에이전트의 행동·도구·판단 절차는 별도 에이전트 사양이 있으면 PRD에서 반복하지 않는다.

## 3. Epic 이름 작성 원칙

- 구현 구성요소가 아니라 완료 후 확보되는 결과나 역량을 이름으로 쓴다.
- `대상 + 달성 상태` 또는 `행동 + 결과` 형태의 짧은 명사구를 권장한다.
- `GraphDB 구축`, `어댑터 개발`, `관리 화면`처럼 기술·화면 명칭만으로 끝내지 않는다.
- 서로 다른 Epic 이름이 같은 완료 상태를 가리키지 않도록 구분한다.

예시:

- 권장: `등록 정보와 온톨로지 인스턴스의 일관된 연결`
- 비권장: `온톨로지 연결 어댑터`
- 권장: `중앙·엣지 판정의 연속 실행과 결과 동기화`
- 비권장: `엣지 서버 기능`

## 4. 권장 Epic 작성 수준

Epic 하나는 다음 구조를 기본으로 한다.

### 핵심 요구사항 소제목 작성 정책

이 정책은 Epic 안의 `핵심 요구사항` 상위 불릿에 적용한다. Epic 이름은 §3을 따른다. 소제목만 읽어도 적용 대상과 상황, 해결할 문제 또는 보장할 상태, 필요한 동작과 결과를 이해하게 하는 것이 목적이다.

- **의미 중심 작성**: 소제목은 의미가 완결되는 문장으로 쓴다. 문장 순서·특정 문형·글자 수는 강제하지 않는다. 의미가 드러나면 각 요소를 별도 구절로 반복하지 않고, 해당하지 않는 요소를 억지로 추가하지 않는다. `짧은 명칭: 설명`은 선택 사항이다. ‘허용된 근거 대조’, ‘근거를 지키는 설명’처럼 추상적인 원칙이나 명칭만으로 핵심을 대신하지 않는다.
- **주체에 맞는 표현**: 사용자·운영 요구사항은 해당 주체의 어려움과 가능해져야 할 판단·행동을 중심으로 쓴다. 시스템 요구사항과 시스템 간 연계 요구사항은 적용 조건, 시스템의 책임, 보장할 동작·상태를 중심으로 쓴다. 사용자 문형에 맞추려고 존재하지 않는 사용자 행동이나 문제를 만들지 않는다.
- **소제목과 하위 항목의 역할**: 상위 불릿의 완결문을 굵게 쓴다. 목적과 핵심 동작·결과를 하위 항목으로 모두 미루지 않는다. 세부 조건·예외·적용 범위·책임·미결 사항은 필요한 경우 한 단계 들여쓴 불릿에 적는다. 관련 비교표는 해당 요구사항 뒤에 둘 수 있다.
- **작성 수준**: 해결 방식은 제품·운영이 제공해야 할 동작 수준으로 쓴다. 시스템 요구사항이라는 이유로 API·스키마·저장 구조 등 구현 상세를 나열하지 않는다. §2의 PRD·프로토타입/디스크립션·티켓 책임 경계는 유지한다.
- **범위와 사실 보존**: 문장을 완성하기 위해 미확정 사용자·역할·기능·시점 보장·성능 보장을 추가하지 않는다. 축약하면서 원문의 조건과 제약을 누락하지 않는다. 요구사항 개수는 상위 불릿만 세며, 서식 변경 때문에 요구사항을 추가하거나 없애지 않는다.

#### 문체 예시

아래 예시는 문체 참고용이다. 금융 도메인의 사실·역할·기능·조건을 다른 프로젝트의 요구사항으로 전파하지 않는다.

- 사용자가 납부 요청의 내용이 본인 기록과 맞는지 확인할 때, 검증된 금융 내용과 조회에 동의한 기록을 비교해 일치 여부와 확인할 수 없는 부분을 알 수 있게 한다.
- 외부 기록 조회가 실패하면 대조를 완료한 것으로 처리하지 않고, 조회 실패와 대조 결과의 확인 불가를 구분해야 한다.
- 늦게 도착한 납부 기록이나 취소·정정이 기존 점검에 영향을 주면, 관련 결과를 갱신하고 변경 이유를 추적할 수 있어야 한다.

#### 검토 기준

- 무엇에 적용되는 요구사항인지 알 수 있는가?
- 필요한 상황이나 조건이 드러나는가? 해당하지 않는 조건을 억지로 추가하지 않았는가?
- 해결할 문제 또는 보장할 상태와 필요한 동작·결과를 이해할 수 있는가?
- 하위 항목을 읽어야만 요구사항의 목적을 알게 되지는 않는가?
- 추상적인 표현만 남거나, 원문에 없는 범위와 보장이 추가되지 않았는가?
- 특정 문형이나 글자 수가 아니라 의미의 충분성과 명확성으로 판단하는가?

### Epic 작성 양식

```markdown
### EP-01. {완료 결과 중심 Epic 이름}

| 목적 | 완료 후 상태 |
|---|---|
| {해결할 문제와 필요한 이유를 1~2문장으로 작성} | {Epic 완료 시 사용자·운영·플랫폼 관점에서 달라지는 상태를 1~2문장으로 작성} |

**포함 범위**
- {주요 기능 또는 업무 역량 3~7개}

**핵심 요구사항**
- **{적용 대상·상황과 필요한 동작·결과를 이해할 수 있는 완결문}.**
  - {그 요구사항의 적용 조건 또는 동작을 구체적으로 설명한다.}
  - {독자가 놓치기 쉬운 예외, 적용 범위, 담당 또는 미결 사항을 적는다. 해당 사항이 없으면 생략한다.}
- **{다음 요구사항의 핵심 목적과 동작·결과를 이해할 수 있는 완결문}.**
  - {해당 요구사항의 구체적인 내용을 한 단계 들여 쓴다.}

**범위 밖·주요 연계**
- {이번 Epic에서 다루지 않는 것 또는 다른 Epic·문서가 책임지는 것 1~3개}

**Epic 완료 판단**
- [ ] {Epic 결과가 확보됐는지 판단할 상위 수준 기준 1}
- [ ] {Epic 결과가 확보됐는지 판단할 상위 수준 기준 2}
```

목적과 완료 후 상태는 반드시 2열 2행 표로 작성한다. 첫 행은 `목적 | 완료 후 상태` 헤더이고 둘째 행은 내용이다. Epic 완료 판단은 반드시 `- [ ]` 체크리스트로 작성해 Notion에서 직접 완료 여부를 표시할 수 있게 한다.

Epic의 줄 수는 합격 기준이 아니다. 들여쓴 구체 내용 때문에 길어져도 독자가 목적·범위·완료 상태와 각 요구사항의 조건을 이해할 수 있으면 유지한다. 요구사항이 독립 결과 둘을 포함하면 분량을 늘리는 대신 Epic을 분리한다.

Epic 완료 판단은 세부 테스트 케이스가 아니다. `연결 성공률 99.9%`, `버튼 클릭 시 200 응답`처럼 구현·측정 세부를 넣지 않고, 어떤 결과가 확인되면 Epic을 완료로 볼지 적는다. 수치가 제품 출시 기준을 결정하는 확정 정책이면 KPI·비기능 요구사항·결정 로그에 두고 Epic에서는 해당 기준 충족을 참조한다.

## 5. 식별자와 이전 산출물 호환

- 신규 Full PRD는 `EP-{n}`을 Epic 앵커로 사용하고 `auto-backward/07-epics.md`를 정본으로 생성한다.
- 우선순위와 후속 티켓 Epic은 `EP-`를 참조한다.
- 기존 프로젝트의 `FN-{n}`과 `auto-backward/07-features.md`는 읽기·동기화 호환 대상으로만 지원한다. 새 PRD를 `FN-` 단위로 생성하지 않는다.
- Story·Task 식별자는 티켓 생성 단계에서 부여하며 Full PRD에 미리 만들지 않는다.
